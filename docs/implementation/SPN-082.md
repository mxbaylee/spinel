## Section lifetime and recovery handoff

**2026-10-23 — accepted.** Agent proposal and independent parent-agent concurrence
under the owner's current instruction to choose decisions when all personas agree.
This is an agent decision, not a new owner screenshot approval.

The approved section navigation replaces the stacked page. Mount only the selected
section, rather than hiding a live invitation panel containing a once-only secret.
Leaving Invites discards its address; revisiting fetches the list and eligible
recipients again, never reconstructing an address. Refreshing within the same
section retains a newly created address, including after a successful mutation
whose readback failed, preserving the existing manual-copy fallback.

An explicit People → Create recovery invite action selects the account and opens
Invites. Fresh eligible recipients validate that choice; a missing/ineligible
selection cannot silently become a new-account invite. Reactivating alone neither
creates nor sends an invitation. Pending access mutations disable section changes,
including hash/back navigation, so their result cannot be hidden mid-request.
Existing post-commit warnings continue to distinguish a saved change from a later
connection-cleanup or readback failure.

Each section owns its requests. Unmounting or superseding a read prevents old
responses from updating the replacement view or redirecting it on an old 401.
No server permission, endpoint payload or transfer decision changes. The optional
API callback runs before a response can redirect or publish decoded data; ordinary
callers retain their existing behavior.

- **Owner:** account recovery and handover retain their existing previews,
  credential invalidation and document/history preservation; no automatic invite.
- **Collaborator:** existing shares, retained credentials and truthful access
  changes remain protected by the same server behavior.
- **Link guest:** no account controls or document metadata become available;
  the established link invalidation/reactivation behavior remains unchanged.
- **Operator:** clearer section navigation, explicit recovery handoff and current
  recipient eligibility, protected passkeys/self-disable, and content-blind facts.
  Leaving an invitation requires deliberately creating another address if needed.

## Development transfer-preview observation repair

CI at `af695ea` failed the recovery browser scenario three times while the test
read the first transfer-preview response body. All three failure contexts show
the dialog already displaying retained-content counts and the recipient selector;
the corresponding production scenario passed. Source inspection explains the
development-specific race: StrictMode starts a preview, invalidates that effect,
and starts another. The current-generation guard intentionally rejects the first
response before consuming its body. Waiting only for response headers can select
that discarded request instead of the completed preview used by the dialog.

The test now observes a completed preview GET before inspecting its response and
also requires HTTP 200. It retains the exact response-field, recipient exclusion,
document-ID/name privacy, cancellation, transfer, retained-data and recovery
assertions. No production lifecycle guard, permission, timeout or retry policy
changes. This preserves Operator recovery coverage and Owner/Collaborator data
protection without exposing anything new to Link guests. The diagnosis is based
on source and CI failure contexts; the repair has not yet run in CI or locally.
Only `git diff --check` was run locally for this repair.
