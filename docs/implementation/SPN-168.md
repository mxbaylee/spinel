## 🔌 Reproduced cause and client repair

**2026-11-21, accepted agent decision; hosted verification pending.** Node
26.13.0 and Playwright 1.64.1 reproduce a concrete server-side idle close:

1. The API client completes one request, leaving an idle pooled socket.
2. The server event loop stalls for 6.2 seconds. Its unchanged idle deadline is
   5 seconds plus Node's 1-second buffer.
3. During the stall, the client sends its next request on that socket.
4. On resuming, the server handles the expired idle timer before reading the
   queued request. The original client reports `ECONNRESET`; the server process
   remains alive and the second request never reaches the handler.

This is captured in the maintained regression, using `server/http.ts` in a
separate process and the **actual pinned original Playwright bundle**. A control
that stalls only the client did not reproduce the reset: it observed the peer's
closure and opened a new connection. The server-stall reproduction, unlike a
timing sweep, synchronizes on the server's stall-start event and proves that the
client sent before the stall ended. No reset is injected in that reproduction.

The historical CI failure has the same client error and a stale process snapshot,
but no socket trace. **Its exact packet sequence and the reason for its scheduling
gap cannot be recovered.** The controlled reproduction establishes this failure
mechanism, not certainty that every old reset had this cause. Later resets must
still fail and be investigated; there is no error-string suppression.

The installed client's `_ensureAgent` creates HTTP and HTTPS agents with
`keepAlive: true`. Node's pinned `Agent.keepSocketAlive` starts its timeout at zero
when no agent timeout is configured; a positive server hint does not shorten zero.
More importantly, an already-dispatched request can still be waiting for a stalled
server to read it. Merely increasing a timeout would move the race and changing
the production server to tolerate it would alter the application under test.
[Upstream issue 42698](https://github.com/microsoft/playwright/issues/42698) reports
the related reuse failure; its comments include conflicting reproduction claims.
The local pinned-source experiment, not those claims, is the acceptance evidence.

**Chosen repair:** a version/hash-checked postinstall patch changes only the two
API request agents to `keepAlive: false`. Each test-control request obtains a fresh
connection. The same server stall then completes successfully, with exactly two
requests delivered once each. A deliberately reset POST still fails after one
request, and HTTP 503 remains visible. HTTPS proves the second agent branch.
There are no new dependencies or runtime monkey patches. Upgrades fail closed for
review; intentionally omitted development dependencies need no production patch.

**Alternatives and personas:** retries could duplicate mutations and are rejected.
Global `Connection: close` headers would change browser asset/navigation behavior
and are rejected. Wrapping every fixture request would spread policy across many
callers; the single guarded agent change covers standalone and browser-associated
API contexts. It adds connection setup to test-control HTTP(S) requests, a bounded
cost accepted for the Operator's trustworthy first-attempt gate. Owner,
Collaborator and Link guest retain native browser networking, application timeouts,
content/access assertions and save/sync behavior. No production emitter changes.

## 🧪 Repair verification checkpoint

The regression owner is `scripts/dependencies/patch-playwright.test.ts` in the
existing Node script suite. Its original bundle is the negative control; the
patched bundle is the positive control. Readiness is an IPC event from the real
listening server; cleanup disposes request contexts, closes sockets, joins the
owned child and removes temporary package copies and TLS credentials. IPC journal
barriers establish observation order rather than assuming HTTP and IPC delivery
order are the same. One bounded 6.2-second server stall per control is deliberate
fault injection, not a readiness delay or relaxed application assertion.

Local checks use the installed pinned Node 26.13.0, the shared serial runner and a
watchdog polling memory pressure and the owned process tree every 500 ms, with the
existing 2 GiB limit. The first exploratory run was resource-aborted at 314,368 KiB
when host pressure rose; it supplies no acceptance. After the owner closed unused
apps, the server-stall probe succeeded. The owner also authorized safe resource
management going forward (chat 2026-11-21).

The first four-test regression run passed (14.3 s, peak 461,792 KiB). Adding an IPC
barrier exposed a fixture bug in the next run: a batched `flushed` message could
arrive before the wait continuation and be missed, leading to its 15-second
deadline. The wait now checks the captured journal on every wake; no deadline was
increased. This is a test introduced here and repaired here, not an application
failure or a reason to retry the gate. Final checks, both exact-commit reviews and
hosted first-attempt smoke results will replace this pending checkpoint.
