## Accepted decision: one deployment-owned recovery supervisor

### Admission follows the work

Workspace, authentication and collaboration share the application's SQLite
runtime. Read-looking routes can still prepare documents, record OAuth state or
clean up placements. The application therefore admits normal HTTP, sync frames
and background jobs before they execute, rather than treating GET as proof of a
read-only operation. Public maintenance and the narrow Operator control lane
remain available separately.

An AsyncLocalStorage permit binds admitted work to the epoch in which it began.
Registered route wrappers retain returned promises through completion, including
after the HTTP client disconnects. Callback middleware retains a valid inherited
context until the request finishes; async OAuth/provider continuations retain
their own promise lifetime. Work that outlives a retired permit cannot borrow a
new epoch merely because the server has since resumed. Scheduled jobs skip
admission while paused and retain their due work for a later running cycle.

The database wrapper checks admission at actual execution of `run`, `get`, `all`,
iteration and `exec`, including writes with `RETURNING` and write-bearing CTEs.
The pinned libsql runtime does not implement the `Statement.readonly` property
advertised by its declarations. The denied-admission read lane therefore uses
SQLite `PRAGMA query_only=ON` around allowed read forms, then restores the prior
setting synchronously. It excludes connection-changing pragmas and `ATTACH`.
Read-only authorization transactions remain possible; an abandoned admitted
transaction cannot be committed by that lane and prevents a quiescent result.
This is defense in depth around the common runtime, not an SQL classification
claim based on method names.

The parent persists `draining` and a new epoch before notifying the child. The
child stops admission, waits for accepted HTTP/sync/job promises, checks for an
open database transaction and drains diagnostics before reporting its matching
epoch as drained. Only that report permits `paused`. A deadline or storage error
keeps the instance in maintenance with a visible failure.

### Linux supervisor and external journal

`server/supervisor.ts` controls the fixed `server/index.ts` child in its own Linux
process group. Its API accepts only fixed maintenance actions and validated IDs;
it has no command, executable, PID, database path or archive path parameter and
requires no Docker socket. Its journal and private Unix control socket live in
an existing canonical directory outside the database/diagnostics directory,
owned by the service UID, mode 0700. Deployment mounts it separately as
`/recovery`; it is excluded from workspace archives and disposable diagnostics.

The 0600 journal binds the instance, generation, configured database device/inode,
opaque epoch, phase, process ownership, notice and scoped operation authority.
Updates use exclusive temporary files, file `fsync`, atomic rename and directory
`fsync`. The directory stays pinned by an open descriptor and device/inode
checks. Kernel-owned abstract Unix sockets exclusively lease the recovery root,
canonical dataset path and existing dataset inode. Live-app ownership is separate from the
cold-operation lease, so a direct app can retain exclusive app ownership while
allowing legacy live setup commands. Both lease classes cover inode aliases.
First creation binds the new inode before SQLite opens. Standalone setup, backup
and transition commands retain cold ownership through process exit after any
database-open attempt; native `.close()` is not a complete descriptor-lifetime
boundary. Unref'd lease listeners do not keep failed processes alive.

The supervisor transfers copies of both path/inode lease pairs to the application
and maintenance verifier over private Node IPC, after journaling each process
identity. A fixed four-role address manifest, current file identity and complete
receipt acknowledgment gate the first SQLite open. The sender's callback alone
does not establish receipt. Receivers pin unref'd listeners until process exit;
native close, parent death and app shutdown cannot release ownership held by a
surviving process. Worker threads share the app's descriptor lifetime; the
synthetic WAL child inherits the same listeners to prove separate descendant
ownership. PDF workers receive serialized input and backup verifier processes
open only isolated staging databases, so they do not inherit live-workspace
ownership. No private Node descriptor API is used.

Every supervisor boot starts in `recovery-required`, including an ordinary clean
restart. Missing, corrupt, interrupted or unknown state does not open the app
database and never silently resumes editing. Explicit cold verification checks
the current file in a separate read-only worker, and start brings the same
generation up under maintenance. Readiness means the real listener and storage
owners initialized; jobs remain gated until explicit resume. A changed database
inode is refused. Replacing the live dataset remains SPN-112.
Boot acquires only exclusive recovery-root ownership, loads and persists closed
state, and then reconciles the journal's recorded orphan groups. Their inherited
listeners exclude app/CLI competitors during that cleanup. Only afterward can
the controller acquire both dataset leases, bind/recheck the inode and expose
private commands. An offline command that already owns a cold lease prevents
admission. This ordering lets recovery stop inherited owners without stealing
their leases, and prevents an early CLI from starting a child whose identity is
later erased by startup cleanup. Handoff and readiness share the bounded start
deadline; either ordering of the complete ownership ack and ready report is
retained until both barriers are satisfied. Failed or partial handoff stops the
recorded group without permitting an unowned SQLite open.

Focused crash tests exposed a short retirement interval: the recorded group and
strict database-handle scan had completed, yet a kernel listener bind briefly
returned `EADDRINUSE`; failure-only inventory found no remaining matching
listeners or owners by the subsequent cleanup boundary. This evidence does not
identify a particular native-thread or IPC cause. Startup therefore waits only
for typed, actual kernel `EADDRINUSE` after successful recorded-orphan
reconciliation, within the existing TERM plus forced-exit deadline. Every failed
partial acquire rolls back its own copies. A real exclusive bind of all four
listeners, fresh strict handle verification and unchanged known generation are
required before clearing recorded identities or exposing private commands.
Persistent cold-process exclusion has its own real-process regression. Direct
startup and standalone CLIs do not receive a retry or descriptor-scan bypass.

Stop first requires paused or recovery state. It sends TERM to the recorded owned
process group, escalates within a bound and inventories `/proc` before reporting
the group and its SQLite/WAL/shared-memory handles closed. Linux boot identity,
process start time and an inherited random ownership marker prevent an unrelated
reused PID from becoming a kill target. Unrelated handle owners are refused, not
killed. The verifier's identity is journaled too. IPC disconnect closes the
child's admission and initiates shutdown; restart reconciles recorded orphan
workers before another verification. Shutdown also rejects queued commands
before they can start a new worker.

Default bounds are 30 seconds for drain, 15 seconds for TERM plus 3 seconds for
forced exit, 30 seconds for application readiness and 15 seconds for verification.
The supervisor and verification worker each use a 64 MiB V8 heap ceiling; the app
retains its 256 MiB ceiling. They share the existing 1 GiB deployment container
limit. Control requests are at most 4 KiB, journals 32 KiB and replay receipts
128 entries; process/descriptor scans are bounded. These are refusal limits,
not a claim of measured target-host capacity.

### Current authority and cold recovery

Browser pause, notice publication and cancellation require the current active
Operator, matching account identity, exact configured origin/JSON request and
fresh passkey verification. Each action fixes an `intentExpiresAt` from the
server-issued verification deadline. Retrying after later re-verification cannot
extend that earlier intent's life. The parent validates authority no more than
five minutes into the future and retains durable operation-ID/intent-hash
receipts through that authorization window. Nonconsecutive retries cannot
republish a cancelled notice or reuse a consumed pause; mismatched intent is
refused. A full live receipt window refuses new actions instead of discarding
replay protection.

Pause returns a one-operation resume secret once, keeping only its hash outside
the workspace. It is bound to the operation, generation and expiry; successful
resume consumes it. A restored session alone cannot mint authority while paused.
An expired/lost response requires the OS-account-controlled cold CLI, which
exposes only status, pause, stop, verify, start and resume and requires the exact
current operation ID. Browser UI exposes pause/resume and notices; process stop,
start and verification remain cold-host actions. There is no automatic resume or
restore.

Public `/api/maintenance` exposes only availability, phase, opaque epoch and
notice. The loopback service is independent of the child/database. Caddy routes
that endpoint to it and has its own fixed 503 HTML/JSON fallback if either the app
or supervisor disappears, without exposing actors, operation IDs or job details.
The private mode-0600 control socket remains usable when ordinary app auth fails.
If authentication itself needs a database change, stop both app and supervisor,
run the cold setup/recovery CLI, then restart and verify/start/resume.

### Browser and offline retries

Mounted tabs capture an immutable maintenance epoch for mutations. Sync sockets,
HTTP transport and MCP edit requests carry their observed epoch; offline bundles,
queued native work and offline creation keep the epoch with which they were
prepared. Status polling cannot silently attach a later epoch to old work.
Missing epochs from older bundles fail closed when supervised mutation is
attempted. Accepted work can finish and receive its acknowledgment during drain;
later frames or delayed writes with the old epoch remain fenced after resume.

The banner leaves editors mounted and distinguishes maintenance from confirmed
saving. It tells people to retain pending work and reload only after accounting
for it; it does not claim browser-local edits reached the server. Existing
account, grant, guest revocation and offline-account fences still apply.

A clean editor can reopen after resume only after native input and the pending
queue have been checked again following the read-only/persistence barrier.
Downloaded copies first replace their clean saved base under the existing
writer lock and post-await checks. The subsequent full-page restart creates a
new HTTP epoch; an ordinary React remount would retain the old tab's epoch.
Pending queues, unfinished native input and missing recovery data prevent that
restart. Ordinary synchronization remount behavior is unchanged.

The exact guest metadata authorization GET remains readable during maintenance,
under the database's read-only boundary. Its current link scope, revocation and
expiry checks allow the existing guest poll to dispose a revoked view while
paused. Guest session exchange, collaboration preparation, PDF export and other
descendant routes remain gated. The public status poll contains only phase,
opaque epoch and notice; it adds no guest document or account metadata.

### Compatibility and operational cost

`npm start`, `npm run dev` and the image's default command keep their prior direct
developer/test startup and live setup behavior. Maintenance is explicitly
unavailable in that mode. On Linux a direct app keeps its live-application lease
until process exit and releases only the cold startup lease after listener
readiness. It does not scan unrelated desktop/browser processes: a supervised
child still draining after parent death retains inherited kernel ownership and
continues excluding direct startup and cold commands. Supervised operation uses
`start:supervised`/`dev:supervised`, and deployment Compose chooses that launcher
explicitly. First installation prepares the database cold before starting it.

The supported control profile is Linux with local filesystem semantics, one
application instance, one service UID and a shared network namespace for every
app/CLI accessing that dataset. Abstract socket ownership is network-namespace
scoped; official host-network Compose supplies that boundary across private PID
namespaces. Restart reconciliation keeps the same PID namespace, or follows the
complete termination of the previous namespace. The official supervisor is its
container's PID 1, so its death terminates that container's workers. Moving a
crashed host supervisor into a new PID namespace while host orphans still run is
unsupported; inherited leases still prevent a second app or cold command from
opening that dataset while any supervised owner survives. Arbitrary external SQLite writers in other namespaces are also
unsupported. Unreadable same-UID descriptor candidates fail closed. Operator work
increases: each controller restart requires
explicit verification, start and resume, and independent database-writing CLIs
require the supervisor to shut down and release its lease. In return, ordinary
application restarts, restored credentials and guessed process IDs cannot reopen
an uncertain generation. Caddy stays available when the app container exits;
the systemd oneshot unit does not imply container health or automatically restart
past encrypted-mount preflight. The updated [deployment](../deployment.md),
[maintenance](../maintenance.md), [development](../development.md) and
[backup](../backups.md) runbooks make those boundaries explicit.

## Accepted decision: announcements do not schedule destructive work

2026-10-27 — accepted by agent judgment, implementing the owner's 2026-10-27
[backup proposal](SPN-063-backup-options.md#pause-resume-and-scheduled-notices).

This delivery supports one-off in-app announcements with an absolute instant,
IANA zone and duration estimate. Missing local times are rejected and repeated
times require an explicit occurrence. A late announcement remains visible;
expiration never silently reports that maintenance succeeded. Cancellation is
explicit. Announcements do not pause the app or authorize recovery. Pause is a
separate current-Operator action with fresh passkey verification, and resume
also requires the expiring operation secret held outside the workspace.

The existing global banner, admin card and confirmation patterns cover these
states. Reaching the planned time marks a notice started; a controller restart
after the instant marks it missed. Neither state disappears at the estimated
end time. The shared announcement area retains its geometry as planned and
actual maintenance states change.
