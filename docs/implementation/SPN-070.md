# SPN-070 — Self-service passkey and session revocation

## Keep security changes tied to recent verification

Accepted 2026-10-27 by agent judgment under the standing persona delegation.

The ticket requires a server-verified passkey check from the previous five
minutes before removing a credential or ending other browser sessions. A separate
same-session WebAuthn ceremony preserves the current cookie, original sign-in
credential attribution and pending OAuth consent. Reusing ordinary sign-in would
rotate the session and could switch accounts or lose that consent association.
Existing sessions migrate without fresh proof. Client timestamps do not grant
authority; every protected operation reloads and checks its server-side proof.

Authenticated passkey addition has the same prerequisite. Otherwise an attacker
with an unlocked, stale browser session could register their own credential,
verify it and remove legitimate credentials. Initial setup, invitation acceptance
and recovery retain their separate, existing authorization and verified ceremony.
The last passkey cannot be self-removed, for any account role. Operator recovery
and administrator removal of a member's last credential remain available.

Owner and Collaborator gain equivalent protection and retain a way back in.
Operator keeps the existing recovery model and one shared credential-deletion
path. Link guests gain no account-management authority and their share links are
unaffected. The five-minute reuse window balances immediate security tasks with
repeated authenticator prompts; it is not protection against an attacker already
holding a session whose legitimate verification is still fresh.

## Keep credential removal distinct from browser-session sign-out

Accepted 2026-10-27 by agent judgment; follows the existing
[credential revocation rule](SPN-005.md#legacy-decision-58-credential-specific-revocation).

Removing a passkey deletes sessions attributed to it plus older unattributed
sessions. A synced credential may be present on several devices; confirmation
explains that scope. Removing the current session's credential also signs out this
browser. Signing out other devices preserves the exact current browser session
and all passkeys; someone with a surviving credential can sign in again. Neither
action disconnects assistant connections or revokes personal access tokens.

Reuse the administrator deletion primitive and live-access revalidation path.
Check ownership, session proof and last-key protection in the same transaction;
post-verification checks prevent an asynchronous ceremony from recreating revoked
authority. A committed operation whose notification or acknowledgement fails is
reported as uncertain rather than rolled back. The UI offers reload instead of
silently repeating it, because a repeated session revocation could affect a newly
signed-in browser.

Owner and Collaborator get precise scope and truthful results; Operator avoids a
second revocation implementation; Link guest access remains governed by its
existing link controls. No new persistent session inventory or device fingerprint
is introduced.

## Reuse the existing profile and confirmation patterns

Accepted 2026-10-27 by agent judgment. Placement follows
[the approved account design](../design/account.md) and its named passkey rows.

Passkeys remain inside Your profile with last-used metadata and a More → Remove
menu. A last-key attempt explains how to add another. Sign out other devices is
an explicit separate control. Existing modal, semantic title icon, theme tokens
and 44-pixel touch targets apply. Verification stays in the selected confirmation;
it never silently applies the pending action. Cancel ends the local ceremony;
responses after cancellation/unmount cannot execute the mutation. The same
profile sections, saved identity, local appearance and assistant consent flow
remain available.

All personas retain familiar account boundaries. Owners and Collaborators see
consequences before destructive actions, Operators use the same personal security
controls, and guests have no profile route. No new design pattern is needed.

## Verification and landing record

The verification surface includes service and HTTP tests for ownership, last-key
protection, five-minute proof expiry, migration, concurrent removal and verification,
legacy session revocation, same-session consent and cookie preservation, and failed
post-commit notifications. A real WebAuthn browser journey signs out another
browser, verifies with a retained passkey, removes the other credential and proves
that its native Sheet editor loses access while saved content remains intact.
Storybook covers cancellation, loading, failure, last-key and uncertain-result states.
