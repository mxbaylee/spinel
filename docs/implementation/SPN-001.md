## Legacy decision 1: React version

**Recorded:** 2026-10-17. **Status:** accepted.
**Authority:** Agent compatibility judgment.
**Source:** [original decision #1](https://github.com/mxbaylee/spinel/issues/1).

**Question:** Which React version should the scaffold use?

**Options considered in the original source:**

A — pin react and react-dom to 18.3.1, matching upstream's development baseline and existing types;
B — adopt React 19 now, gaining newer APIs but adding compatibility work before any editor exists.

**Outcome, rationale and current boundary:**

Pin React and React DOM 18.3.1 to match Univer's development baseline and existing types. React 19
was permitted by peers but no required feature justified the integration work. This records the
scaffold choice at the time, not an instruction to reject later reviewed upgrades.

**Persona tradeoffs recorded at the time:**

Operator favours a supported version with minimal integration work; Owner favours stable editors;
Collaborator favours predictable shared editor behaviour; Link guest favours reliable rendering on
their device. All four benefit from matching Univer's tested baseline.

## Legacy decision 2: One process and initial SQLite adapter

**Recorded:** 2026-10-17. **Status:** superseded in part.
**Authority:** Owner stack direction; agent scaffold implementation.
**Source:** [original decision #2](https://github.com/mxbaylee/spinel/issues/2).

**Question:** How should the scaffold serve the app and initialize SQLite?

**Options considered in the original source:**

A — Express with Vite middleware in development, built static assets in production and node:sqlite;
B — separate frontend/backend processes and a third-party SQLite addon, adding proxy and native
dependency setup.

**Outcome, rationale and current boundary:**

Use Express with Vite middleware in development and built assets in production, one loopback
listener, WAL and foreign keys, without replacing existing schema. The initial node:sqlite adapter
was accepted for the scaffold; decision
[#68](SPN-025.md#legacy-decision-68-single-sqlite-runtime-and-consistent-copies) subsequently
replaces that adapter. SQLite is a pre-production implementation, not an irrevocable storage
constraint. Authentication and document models were deliberately separate work.

**Persona tradeoffs recorded at the time:**

Operator favours one process, one loopback listener and no native database addon to compile; Owner
favours persistent local storage and a reliable dashboard; Collaborator favours a consistent app/API
origin for later sign-in and collaboration; Link guest favours a clear future access boundary with
no document data exposed by this placeholder.

## Legacy decision 3: Compiler-compatible linting

**Recorded:** 2026-10-17. **Status:** accepted.
**Authority:** Agent tooling judgment.
**Source:** [original decision #3](https://github.com/mxbaylee/spinel/issues/3).

**Question:** Which linter should SPN-001 use with the repository's TypeScript 7 compiler?

**Options considered in the original source:**

A — use Oxlint's TypeScript support, tsc for types, and Prettier for the new scaffold; B — downgrade
TypeScript to fit typescript-eslint; C — force incompatible peer dependencies.

**Outcome, rationale and current boundary:**

Use Oxlint, TypeScript typechecking and Prettier instead of downgrading TypeScript or forcing
incompatible typescript-eslint peer dependencies. Lint repository source; the original formatting
scope covered the new scaffold without gratuitously reformatting reference material. Clean
reproducible installation was the deciding evidence.

**Persona tradeoffs recorded at the time:**

Operator favours reproducible installs without forced peer dependencies; Owner favours defects being
caught before release; Collaborator favours reliable shared code; Link guest favours robust entry
points. All benefit from automated checks without a compiler downgrade unrelated to the ticket.
