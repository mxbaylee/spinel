# SPN-117 — development runtime fast API mitigation

## Accepted decision: exclude the failing compiler path in development

**2026-10-28 — accepted, agent judgment under the standing delegation.**
The pinned Node `26.12.1` process aborted while Vite served a large JavaScript
response in required development validation. The same fatal signature occurred
in the [original main job](https://github.com/mxbaylee/spinel/actions/runs/40576342950/job/122443889408)
and the [SPN-116 integration job](https://github.com/mxbaylee/spinel/actions/runs/40764745047/job/123085978994).
The latter executed merge `eb8d405c24b593d4a6b48ae4c3b12624e1624db0`, with the
same tree as PR head `7c3ccfd156e9f575b2405a10eecf7a2299bf5a35`, against main
`1a2f8aa2695400dd90ab8f10a99ea00c076359a6`.

The fresh first attempt reports `Lazy deopt after a fast API call with return
value is unsupported`, followed by `Buffer.byteLength`, HTTP
`maybePrepareFinalChunk` / `end`, and Vite's response middleware. Its string has
4,880,691 UTF-16 code units; the V8 diagnostic identifies a concatenated two-byte
string. Node then exits with an illegal instruction. The visible Sheet-save
assertion subsequently fails; both configured retries report connection refused.
The shard ends with 34 passed, one failed and 34 not run. Those consequences do
not establish a Sheet defect or a production availability incident.

The retained [failure archive](evidence/SPN-117-runtime-failure.zip) contains
both original fatal-log excerpts, the fresh complete JSON report and all three
affected attempts' context/diagnostics. The manifest names exact source lines,
member hashes and intentional omissions. Archive SHA-256:
`f961474c76743ced38c80e35dbae7392f37941ce23f893338c34db04a60073a0`.
The original [12,818,295-byte CI artifact](https://github.com/mxbaylee/spinel/actions/runs/40764745047/artifacts/12849848764)
has SHA-256
`03ff57c875441523eead8b2ee18f92e6db46758b374bde8297370fc4a33f4aa0`.
Neither original workflow was rerun to obtain this evidence.

### Source evidence and options

[Node issue 66870](https://github.com/nodejs/node/issues/66870) reports the same
HTTP/Vite/UTF-8-length crash family. Its explanation connects heap allocation
inside the fast callback with a V8 lazy-deoptimization limitation. Spinel's log
does not contain an event-level GC trace, so that particular triggering sequence
remains an upstream-supported explanation rather than a measured fact here.

The exact Node `26.12.1` source, commit
`bc2e01dcf6acd5cf7d169b5f26cf89abaaeb41f1`, supplies the narrower exclusion proof:

- The [compiler target selector](https://github.com/nodejs/node/blob/bc2e01dcf6acd5cf7d169b5f26cf89abaaeb41f1/deps/v8/src/compiler/fast-api-calls.cc#L376-L382)
  returns no fast target when `turbo_fast_api_calls` is false.
- The [call reducer](https://github.com/nodejs/node/blob/bc2e01dcf6acd5cf7d169b5f26cf89abaaeb41f1/deps/v8/src/compiler/js-call-reducer.cc#L4211-L4247)
  then uses the ordinary callback path. The unsupported non-void fast-call
  [abort continuation](https://github.com/nodejs/node/blob/bc2e01dcf6acd5cf7d169b5f26cf89abaaeb41f1/deps/v8/src/compiler/js-call-reducer.cc#L723-L740)
  belongs to the excluded path.
- Node [registers both slow and fast UTF-8 length callbacks](https://github.com/nodejs/node/blob/bc2e01dcf6acd5cf7d169b5f26cf89abaaeb41f1/src/node_buffer.cc#L2032-L2036).
  The pinned binary accepts `--no-turbo-fast-api-calls` directly on its CLI.

Use that flag only for development server processes: `npm run dev`, both
Playwright development web servers, conditional development children in
`e2e/app-process.ts`, and the existing development watch regression's child.
Put it before the TypeScript entry point. Keep the runtime pin, production and
container commands, browser compiler, heap limits and all test budgets intact.
Do not set a global `NODE_OPTIONS` or mutate V8 flags after startup. The pinned
[watch implementation forwards non-watch process arguments](https://github.com/nodejs/node/blob/bc2e01dcf6acd5cf7d169b5f26cf89abaaeb41f1/lib/internal/main/watch_mode.js#L61-L99)
to its child; the existing watch regression exercises that supported launch.

The alternative `res.end(Buffer.from(content))` avoids the reported HTTP
string-length call but is less complete on this pin: large-string
[`Buffer.from` itself uses the same UTF-8-length binding](https://github.com/nodejs/node/blob/bc2e01dcf6acd5cf7d169b5f26cf89abaaeb41f1/lib/buffer.js#L552-L580).
Patching Vite or adding a response adapter would add interception and response
semantics to maintain. A broad dependency upgrade lacks a verified upstream
repair. The direct process flag gives the smallest source-supported exclusion.

This disables all TurboFan fast API callbacks in those development Node
processes; potential development throughput overhead is the tradeoff. It does
not fix upstream V8. [V8 CLI flags lack Node's stability guarantee](https://nodejs.org/api/cli.html#v8-options),
so a runtime update must recheck support, source applicability and the affected
workload before retaining or removing this mitigation.

Operator gains trustworthy development validation without another dependency
or launcher abstraction. Owner retains exact content, offline recovery and
useful undo; Collaborator retains convergence and permissions; Link guest
retains scoped access, viewer denial and revocation. Their application behavior
is unchanged. Production remains subject to its ordinary tests and container
acceptance; current evidence does not justify changing its launch arguments.

## Bounded verification and remaining gate

One paired diagnostic was declared before execution on the pinned binary: default
fast calls, then disabled fast calls, serially under a 2 GiB process-tree
watchdog, 45 seconds per child and the existing 512/8 MiB heap limits. Use 64
fixed warm-up calls and one requested optimization, six small encoding cases,
four freshly concatenated strings of 4,880,691 code units, and eight fixed HTTP
GET/HEAD responses. Retain both first attempts, source, exact commands, compiler
graphs, response checks, exits and resource diagnostics. A missing optimized
fast call in the default arm makes the comparison inconclusive. This comparison
tests compiler-path exclusion and exact response semantics; it does not claim
to reproduce the rare crash or measure its incidence.

Both first attempts exited successfully: default 0.417 seconds, disabled 0.415
seconds; the watchdog observed 287.9 MiB peak for the serial pair. These elapsed
times are diagnostic observations, not a throughput benchmark. Both wrappers
completed TurboFan compilation and retained the pinned runtime's optimized and
TurboFanned status bits before and after all ten length cases. The default
graph's live `Unsigned32` fast-call node maps to `byteLengthUtf8(string)`, remains
reachable from `End` in the final TurboFan graph and has its C target in the
emitted machine code. The disabled graph has no fast API node. Thus the result
does not depend on an abandoned graph or a source-text search.

Both arms returned all ten expected lengths and eight exact HTTP responses;
cross-arm byte hashes and Content-Length behavior match, and both servers remained
listening after the eighth request. The default arm did not reproduce the rare
abort. The [complete paired evidence](evidence/SPN-117-fast-api-comparison.zip)
includes the original probe, commands, results, graph analysis, complete compiler
graphs/disassembly and watchdog log. Archive SHA-256:
`11f925dfd343db19aedd6d5a8e65335ce07a2950fef92ef64b1df25d1f96a181`.
No diagnostic optimization flags belong in normal application commands.
