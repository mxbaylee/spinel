## Native PDF recommendation and delivery boundaries

Date: 2026-10-23. Status: proposed, pending final independent review.
Decider: agent judgment under the owner's delegated all-persona review policy.
Evidence: bounded probes on main `5244d74`, plus independent source and visual
review by the `recovery_final_review` agent. This selects a delivery approach,
not a declaration that SPN-075's full export acceptance already passes.

Recommend the public Univer model/layout/render APIs with the installed
`@napi-rs/canvas` PDF backend, in a separately bounded server process. Keep pure
rendering in `lib/print`; authorization, snapshot preparation and download remain
in Spinel. Node rendering avoids making phone browsers hold full layout/image
copies and can reuse existing server-confirmed content. Its native memory and
deployment dependencies require explicit production limits and Linux validation.
No production renderer, service or dependency has been added by this feasibility
work. Existing Pro print paths remain until final integration.

### Options and licensing

- **Native public layout + Canvas PDF (recommended):** installed Univer core and
  engine-render 1.1.0 are Apache-2.0; installed Canvas 1.0.11 is MIT. Its public
  `PDFDocument.beginPage/endPage/close` creates vector text and drawing output.
  The two fixtures demonstrate this route with existing native snapshots and
  preserve native text/table layout rather than adding a separate paragraph
  engine. Public references: [Univer repository/license](https://github.com/dream-num/univer),
  [Canvas PDF API declarations](https://github.com/Brooooooklyn/canvas/blob/main/index.d.ts)
  and [Canvas license](https://github.com/Brooooooklyn/canvas/blob/main/LICENSE).
  Production must declare engine-render directly in the standalone package,
  move/add Canvas as a runtime dependency, verify Linux native binaries and
  retain bundled native/font license notices. Installed manifests are the
  version/license evidence; current upstream declarations can evolve.
- **pdfmake (credible alternative, source review only):** its MIT-licensed
  document-definition API covers paragraphs, lists, tables with spans and
  automatic pagination, explicit breaks, images, page sizes and fonts. It would
  require a second Sheet geometry adapter and a full Doc-to-definition mapping;
  rich native fidelity is not established by those documented capabilities.
  [Official 0.3 documentation](https://pdfmake.github.io/docs/0.3/) and
  [repository/license](https://github.com/bpampuch/pdfmake). No package was
  installed and no performance or fidelity comparison is claimed.
- **PDFKit (lower-level fallback, source review only):** MIT-licensed PDF drawing,
  text flow and tables could implement custom pagination, but would leave more
  native layout responsibility to Spinel. [Text documentation](https://pdfkit.org/docs/text.html),
  [table documentation](https://pdfkit.org/docs/table.html) and
  [license](https://github.com/foliojs/pdfkit/blob/master/LICENSE). Native output
  already establishes a viable bounded path, so building a second renderer
  during this prerequisite would not resolve the remaining native-model risks.

Only open-source/public APIs were inspected. No Pro implementation, license
workaround, browser Print flow or copied upstream code is involved.

### Reproducible evidence and limits

The [probe instructions](../../scripts/pdf-feasibility/README.md) retain exact
commands, the session resource guard, font/environment requirements and failure
semantics. Sources are TypeScript; outputs under
[`output/pdf/spn-097`](../../output/pdf/spn-097/) contain both PDFs, all eight PNG
pages, native fixture snapshots, metrics, PDF metadata/page-size reports and
PDF.js content assertions. Each current PNG was visually inspected after the
final crop repair. Independent review also inspected all pages before that repair
and was asked to recheck the changed Sheet pages.

- **Doc:** five pages, 29,024 bytes; measured layout/render/write phase about
  195 ms and process maximum RSS about 193.3 MiB (197,840 KiB in the stored metrics).
  Twenty-two paragraphs occur once, followed by a prepared 30-row/two-column
  result table spanning 17 + 13 rows, then an explicit `\f` page break and final
  paragraph. PDF.js verifies every paragraph and table marker occurs once.
  Every page is 450 x 525 pt, independently confirmed by PDF.js and `pdfinfo`,
  matching stored 600 x 700 layout pixels at 96 DPI; 48 px stored margins remain
  visible. The purple heading, purple table borders and light paper are visible.
- **Sheet:** three A4 pages, 15,175 bytes; about 27 ms and maximum RSS about
  165.2 MiB (169,184 KiB). Two wide pages use scale 0.775223, then a narrow
  worksheet uses scale 1. Hidden worksheet, row 5 and column 3 are absent;
  visible cell markers occur once. The merged heading, fill, borders and image
  beyond the populated cells remain visible. Requested margins are 36 pt
  (12.7 mm). The backend rounds fractional A4 page geometry to 595 x 842 pt;
  exact fractional page dimensions and the corresponding sub-point margin
  difference remain a production geometry decision/test, not proven precision.
  Final slices clip to the declared fixture extent, including the image bottom;
  independent review caught and prompted correction of excess blank grid rows.
- **Metadata:** both outputs have no Author, custom metadata, metadata stream,
  forms or JavaScript according to `pdfinfo`; generic Creator/Skia producer
  information remains. Synthetic inputs establish no real-user privacy claim.
- **Negative cap:** both `--page-cap=1` runs exit 1 and leave no PDF in the
  separate rejected directory. Doc fails after calculating its five-page
  skeleton; Sheet fails after rendering one page internally. Failure metrics
  preserve this distinction. These checks establish no partial file publication
  for this failure, **not bounded layout memory or resource-kill cleanup**.

These are small-fixture observations, not benchmarks, concurrency admission
limits or proof that every currently accepted document fits the 2 GB server.
The guard polls every 300 ms and can miss short peaks; process maximum RSS is
also recorded. Preparation, server snapshot copies, Formula workers, image
decoding and HTTP buffering are not represented by these measurements.

The public compatibility surface needed a Node `OffscreenCanvas` measurement
shim backed by `createCanvas`; without it native layout had zero font metrics.
A `UniverPrintingContext` subclass normalizes a solid `[0]` dash to `[]` because
the PDF backend rejects zero-total dash arrays. A public Spreadsheet subclass
disables editor Scene telemetry hooks, and public Group/Transform instances
provide scale/viewport context. Sheet image composition feature-checks the
runtime `drawImage` API because the PDF context return type omits it. These are
ordinary public adapters, not changes to SDK internals; compatibility needs tests
when dependencies change.

Known fidelity gaps remain explicit. All text uses the one bundled **bold** font;
regular/italic, font fallback and Unicode are unproven. The Doc has no image,
list, header/footer or drawing fixture. The prepared Formula table is an ordinary
native table containing synthetic values, not a Formula-object adapter, evaluator
or authorization test. Native table sentinels and paragraph indices must be built
correctly by a real adapter. The fixture proves explicit `\f`; paragraph-style
page-break variants remain unproven. Sheet extent and image placement are
explicit fixture constants, with fixed-height row-aligned slicing: automatic
used-range calculation, sparse/empty cases, image anchors, variable heights,
spanning merges/images and background handling remain delivery work. Rendering
the whole Doc per PDF page also needs scaling evaluation on longer documents.

### Access and resource boundary

SPN-075 must reuse `resolveDocument` / `sourceDocumentContext` and current
credential validation, including exact Space child scope. `PortableFiles.export`
currently deliberately permits account/trusted callers only; native JSON guest
restrictions stay unchanged. PDF needs its own read-only export path through
the same authorization primitives, not a broadened JSON endpoint. Operators
gain no document access. Wait for pending edits and obtain the current confirmed
snapshot with restore-generation protection; do not export a stale browser copy.

Only authorized image bytes cross into the renderer, never URLs, cookies or
credentials. Resolve same-document image references under the caller's current
scope, revalidate before release and do not allow arbitrary network fetches.
Existing compressed-byte limits are insufficient: one allowed 16-million-pixel
image can occupy roughly 61 MiB as RGBA before copies and PDF encoding.

`DocFormulas.evaluate` already rechecks source access around evaluation, but PDF
layout happens afterward. **Recheck every Formula input after rendering and
before releasing bytes.** If any source is no longer accessible, discard the
entire previous PDF and the whole affected Formula value/table, then perform a
bounded rebuild with a neutral placeholder. Never reuse stale numbers, retain a
partial aggregate or merely paint a placeholder over old PDF content. Recheck
again after rebuild; repeated changes exhaust a bounded retry and fail clearly.
Loss of host-document/session/link access aborts the download. A revoked guest
sees the revoked-link page. Already downloaded copies cannot be recalled.

Production needs an aggregate budget for snapshot clones, decoded image pixels,
Formula evaluation, native layout, PDF buffers and response bytes, as well as
input/pages/time/output limits. A V8 heap limit does not constrain Skia/native RSS.
Use isolated cancellable work with serialized admission appropriate to the 2 GB
host; retain admission until the cancelled process is fully terminated. Account
for concurrent transfer/Formula work rather than treating each independent cap
as the whole server budget. No document contents, credentials or private source
names belong in logs/metrics. Publish bytes atomically only after successful
rendering and final authorization. Neither admission policy nor safe numeric
production limits are chosen from these two small samples.
