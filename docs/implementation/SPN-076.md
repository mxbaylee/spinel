# SPN-076 — Share a Doc with its formula sources

## Explicit recipient source review

**2026-10-27 · Accepted permission contract; original composition superseded.**
Agent judgment under the owner's [standing delegation](grooming-2026-10-26.md#agent-decisions-and-visual-review),
for the requested SPN-076 implementation and merge. The original prerequisite
[PR #199](https://github.com/mxbaylee/spinel/pull/199) merged as
[`80feb8c`](https://github.com/mxbaylee/spinel/commit/80feb8c84e6cd45710c0f6c0c61a79f29ba52d27).
Its source scope, explicit consent and privacy requirements remain in force;
the [simpler People and Link decision](#simpler-people-and-link-sharing) below
supersedes only composition and verbosity. The following outcome records the
original decision, not the current dialog layout.

**Question.** How can an Owner share a useful report without accidentally
sharing its source Sheets or expanding a child grant into an entire Space?

**Context.** Native Doc formulas retain stable source IDs, and each viewer's
current authorization governs results. Sharing already stages per-person host
roles and keeps public links separate. Spaces have one outer sharing boundary;
there is no independent child grant. Existing source access may come from a
folder, another Space or ownership rather than a direct grant.

**Options.** Implicit source sharing hides a disclosure and violates SPN-033.
A global checkbox loses recipient context. A separate wizard duplicates the
existing sharing task. A checkbox beside each recipient and an exact source
review extends the existing dialog while keeping confirmation local and explicit.

**Outcome.** Adopt the [source-sharing pattern](../design/sharing.md#formula-sources-spn-076-design-prerequisite)
in its own prerequisite PR before building the new dialog. Source sharing is
unchecked by default; the checked review lists exact authorized source targets
and proposed Can view access. Existing access is kept without redundant writes.
Source-only additions remain possible for an already-shared host. Public links
never publish external sources.

For Space roots, review direct dependencies of all live Docs in the shared Space,
not only the currently selected child. This matches the actual share scope and
gives the same answer from dashboard and editor. Same-Space sources inherit
access. External Space grants explicitly include every current and future page
and folder. Bound discovery and fail clearly rather than silently truncating.
Do not recursively share dependencies of source Sheets or disclose unrelated
page names. Read current committed native snapshots; stale legacy checkpoints
are not a trustworthy source inventory.

Recheck host and source authority at confirmation. A material source/name/Space
boundary change requires a fresh unchecked review. Only currently authorized
names appear; inaccessible dependencies remain generic. Partial outcomes must
distinguish the host from each source and retain successful grants. An uncertain
response requires a fresh read, not a claim that nothing changed or an automatic
retry. Formula results always remain governed by the viewer's actual access.

**Persona effects.** The Owner can deliberately share a useful report and see
whole-Space disclosure before committing. The Collaborator can tell confirmed
access from proposed access and understand when another Owner or File admin
must act. The Link guest retains the original host/Space capability with no
external source inventory or account identity. The Operator receives no content
or source names, and no notification service or background dependency system
is introduced.

**Evidence.** Proposal screenshots are fixture previews using actual Spinel
theme tokens, shared modal and controls, alongside current production Sharing
captures. They establish layout only. The implementation PR must add real
server/unit/browser evidence, production stories and current theme/phone
screenshots. Both PRs require independent review on their final commits; UI
approval is **agent review only**.

## Simpler People and Link sharing

**2026-10-27 · Accepted design; implementation acceptance in progress.** Owner, chat
2026-10-27, while reviewing the SPN-076 implementation:

> The share dialog is confusing with a ton of stuff. Can we simplify it? Less text and buttons more abstraction of the common paths

The owner sets the simplification direction. The concrete composition below is
agent judgment using that request, the existing
[review-by-subtraction principle](../design/README.md#review-by-subtraction), the
shared controls and all four personas. Independent visual approval and final
implementation validation remain separate gates, under the standing delegation;
this record does not assert they have passed.

**Question and context.** How can ordinary sharing be easy to scan while explicit
source grants still show their exact scope? The original composition from
PR #199 puts every recipient's role, source inventory, explanatory text and
action beside the entire guest-link workflow. Repeated confirmed/draft labels
and recovery buttons compete with the active task. Account sharing and public
capability sharing are distinct common paths, and there are about two everyday
accounts rather than an open invitation workflow.

**Options and tradeoff.** Shortening every paragraph alone leaves the same number
of simultaneously active controls. Hiding all source information would weaken
informed consent, especially for a whole external Space. Choose visible People
and Link views, compact confirmed rows and one inline recipient editor. This
adds one deliberate action to edit a person's access while removing unrelated
controls from that edit. A native disclosure can hide an unchecked inventory;
checking must expose every proposed grant and keep it visible. Only the active
recipient requests a source review, reducing repeated work and status chatter.

**Outcome.** Adopt the revised [sharing pattern](../design/sharing.md#adopted-pattern)
as a dedicated superseding design prerequisite before implementing the new
composition:

- Open on **People**, with visible text **People / Link** tabs; folders have
  People only. The header close control remains and redundant Done is removed.
- Compact rows show name and confirmed effective role. Opening a manageable row
  reveals the sole inline role/source editor. Owner, File admin and inheritance
  help is contextual. Ownership and the actor's own grant remain protected.
  For a host Space, show once in that editor before Share / Save changes:
  **Applies to every current and future page and folder in this Space.**
- Keep one active draft. Cancel, switching recipient/tab or changing host
  discards that unsaved edit and clears source consent. Collapsed rows always
  show confirmed access; there is no hidden draft map. A new editor gets a fresh
  identity/role-bound review, and role/material-review changes also clear consent.
- The default People footer has **Copy account link**. Hide Copy while editing,
  and place **Cancel** plus the primary action immediately at the end of the
  active recipient editor, before later person rows: **Share** for a recipient
  without effective host access, or **Save changes** for existing access. The
  action includes only this recipient's selected host role and explicit source grants.
- **Include formula sources** starts off; no extra Formula sources heading is
  required. An unchecked inventory may collapse. When missing access is known,
  show **Some formulas won’t work without source access.**
  Checking reveals each exact authorized target marked **Can view · Proposed**,
  keeping that list visible until consent clears. Confirmed viewer roles remain
  **View only**. Kept roles and included sources may
  use collapsed details or a brief summary. Source-only sharing remains possible.
- A proposed external Space grant visibly names the Space, every exact source
  Sheet, **Entire Space**, and its scope over every current and future page and
  folder before saving. Same-Space inheritance needs one sentence and no child
  grant. One short unresolved warning exposes no private name, identity or count;
  an unreviewable dependency does not imply the recipient lacks access.
- Complete success collapses to a confirmed row, announces one concise status
  and returns focus. Partial or uncertain results keep the editor open with the
  same primary action and source controls. Fresh review and another explicit
  opt-in precede another attempt; source-check retry appears only on failure.
  There are no duplicate permanent Retry access / Review remaining buttons.
  After an uncertain response, an unchanged confirmed direct role with sources
  unchecked leaves Save changes disabled until a real role change or a fresh
  opt-in to eligible reviewed source grants.
- Keep the Link controller mounted across tabs so its once-only URL survives.
  Hide the inactive panel properly and disable tab/recipient switching and
  dismissal during either kind of write. The Link tab has concise audience,
  scope and source-limit information. Repeated session-lifetime, social-preview
  and general administrative prose moves to details or maintained documentation.
- Guest-link roles are editable when off or replacing. An enabled link normally
  shows its confirmed role and a fresh Copy guest link or clear Replace link…
  action; Turn off is in More. Preserve existing replacement, Space-creation
  and Space-revocation confirmations, immediate revocation, distinct account/
  guest copy semantics and selectable-address fallback.

**Unchanged contract.** This supersedes presentation and verbosity only. Source
review still uses current committed snapshots and stable bindings, all live Docs
for a host Space, complete bounded discovery, current account credentials and
independent host/source authority. Saving rechecks the exact reviewed set. Grants
only add Viewer where recipient access is absent; existing roles, inheritance,
ownership and timestamps remain intact. Changed names, dependencies or boundaries
require a fresh unchecked review. Hidden metadata remains redacted. Public links
gain no external source capability, even when account source grants exist.
Known partial outcomes retain successful grants; unexpected write failures keep
the existing atomic rollback behavior. An uncertain response requires reading
actual permissions and cannot claim that nothing changed. No automatic retry,
notifications, source-value copying or recursive sharing is introduced.

**Persona effects.** The Owner scans current access quickly and edits one person
with one primary action while still seeing exact proposed disclosure. The
Collaborator sees confirmed roles and concise remaining-access explanations,
with inherited access preserved. The Link guest retains the existing scoped
capability, privacy and revocation rules; the separate Link view does not expose
account names or external source inventory. The Operator's content/access
boundary and backend operation are unchanged; no new permission model or service
is added.

**Evidence and acceptance.** PR #199 and its screenshots remain historical
evidence for the original composition. The refinement PR must show labelled
fixture proposals using the real theme, modal and controls, with light/dark/phone
coverage and independent **agent review only** visual approval. It makes no
backend, native-browser or final-CI pass claim. The implementation must update
production stories and browser checks for keyboard tabs, one active editor,
draft/consent resets, recipient-local actions, visible proposed grant labels,
whole-Space disclosure, partial/uncertain recovery, focus return and once-only
guest URL retention. Existing authorization and public-isolation evidence remains
required on the current implementation commit.

## Runtime protocol and bounds

`SourceSharing` in `src/server/workspace/source-sharing.ts` owns the account-only
review and confirmation. The shared response types live in
`src/shared/sourceSharing.ts`; existing grant storage and authorization remain in
`WorkspaceFiles`, `WorkspaceStore`, `SpaceStore` and the native document resolver.
There is no separate permission model, dependency cache or notification service.

1. `POST /api/items/:id/sharing/review` accepts `{userId, role}` and returns a
   review for that recipient and proposed direct host role. It is read-only.
   The result includes projected effective host access, exact authorized targets,
   existing roles, proposed Viewer additions and a version fingerprint. A null
   direct role may still leave inherited host access.
2. The existing `PUT /api/items/:id/sharing` remains host-only when `sourceReview`
   is omitted, including for ordinary Sheets and folders. An explicitly checked
   source option adds `sourceReview: review.version` to the same recipient/role
   request. Extra target IDs or alternative source-selection fields are refused.
3. The service recomputes the complete plan under the same SQLite writer
   transaction as the grants. The fingerprint includes actor, recipient, host,
   proposed and current direct host roles, dependency IDs, current authorized
   names, recipient access, source grant authority/boundaries and Doc generations.
   A changed plan returns 409 before changing the host or sources. This also keeps
   source-only sharing from overwriting a concurrent host-role promotion.
4. Missing source access receives Viewer only. Any effective source access means
   no source write, including inherited grants, File admin and recipient ownership.
   Their role, direct-grant absence and `shared_at` remain intact. Existing host
   access is also not rewritten when its selected direct role is unchanged.
5. The response separates host updated/unchanged, newly shared authorized targets,
   authorized targets still requiring another administrator, and a fresh review.
   `unavailable` means this actor could not review some dependencies; it makes no
   claim about the recipient's access to them. `complete` confirms reviewed source
   access, never guaranteed formula calculation or valid worksheet references.

The server derives each source's current Space membership and checks the original
account credential before returning its name. Unknown, missing, private and
wrong-kind bindings are generic. Their IDs can affect a freshness fingerprint,
but neither those IDs nor names/parents appear in review metadata. The request
cannot supply its own grant targets. Operator, guest and unauthenticated callers
cannot use this account-sharing surface.

`CollaborationStore.committedDocumentSnapshot` provides a bounded synchronous read
of the active durable native Doc generation. It checks current access and refuses
active restoration. Never-activated Docs may use their legacy saved snapshot;
missing prepared native storage fails closed instead of using an old checkpoint.
The snapshot byte count is checked before parsing. Space Docs are processed one
at a time, keeping only the bounded dependency set rather than all snapshots.

| Review budget                                 |  Limit |
| --------------------------------------------- | -----: |
| Live Docs in the shared Space                 |    128 |
| Unique directly referenced source Sheets      |    256 |
| Serialized committed Doc snapshots, total     | 32 MiB |
| Custom ranges per Doc                         |  1,024 |
| Accumulated host/source/target ancestry reads | 10,000 |

These are refusal budgets, not permission to truncate a list. A failed complete
review cannot enable source opt-in. The original host-only sharing request remains
available with an accurate source-check warning. Ordinary source evaluation keeps
its separate [Formula bounds](../formulas.md#bounds-and-layout).

## Atomic grants and truthful partial outcomes

**2026-10-27 · Accepted.** Agent implementation judgment, following the explicit
source-review design and all four personas.

**Question and options.** Account grants share one SQLite database. Applying
independent writes would create extra rollback and retry cases when a later write
failed. A single transaction can keep the reviewed host and eligible source
changes consistent without hiding already-known source restrictions.

**Outcome.** Commit the explicit host role and every eligible reviewed Viewer
addition atomically. An unexpected database/write failure rolls all those new
changes back. There is no `await` between the final authority/dependency check
and the writes. A changed plan also performs zero mutations.

Known sources requiring another Owner or File admin are excluded from the proposed
grant batch; hidden sources cannot be verified. The eligible batch can succeed
while these other sources remain unresolved. That is the reported partial result:
the host and confirmed source grants are kept, unresolved access is stated, and
the next attempt starts with a fresh review and another opt-in. No automatic
request or grant retry is sent.

A lost HTTP acknowledgement is different from either known partial completion or
an observed rolled-back transaction. The client cannot infer the server outcome
from a network failure, so it must refresh actual permissions before claiming
success/failure or asking for another explicit attempt. It never says nothing
changed solely because the response was lost.

**Persona effects.** The Owner avoids unintended wider disclosure and partly
written grant batches. The Collaborator receives accurate confirmed versus
remaining-access information. The Link guest gains no external source capability,
even if those sources have independent account grants or public links. The Operator
keeps the existing SQLite transaction model and no access to content metadata.

## Verification record

Local backend verification used Node 26.12.1, the shared serial runner and a
process-tree memory watchdog. The initial service run passed 21 tests; the two
subsequent Doc-count/aggregate-byte regressions passed separately; the actual HTTP
regression passed. A final focused run passed five additional cases for a successful
File admin confirmation, the combined ancestry budget and public-link isolation.
These are **29 distinct backend tests**, not a claim that final head CI or browser
acceptance has completed. After integrating SPN-086 and the refined design baseline,
a combined service/HTTP run again passed all 29 cases (1,312 MiB peak). Observed peak memory was 1,072 MiB
for the initial service run, 838 MiB for the two capacity cases, and 952 MiB for
the HTTP run. The five additional cases peaked at 780 MiB. No resource-aborted run
is counted as a pass.

The tests cover exact/deduplicated identity, existing direct/inherited/owned roles
and timestamps, source-only sharing, inherited null-direct host access, hidden
metadata, known source-owner refusal, changed dependencies/names/Space boundaries,
concurrent host promotion, revoked host/source/session authority, current native
snapshots instead of stale legacy ones, restore invalidation, all-Doc Space scope,
whole external Space grants, atomic rollback after an injected database failure,
source/range/Doc/byte/ancestry refusal budgets, and HTTP envelope/origin/account/operator
fences. They also preserve the ordinary host-only request shape. Existing host and
source public-link/session rows remain byte-for-byte unchanged after account source
sharing; real formula evaluation by an ordinary Doc guest or a Space guest with an
external Sheet/Space source still fails before source preparation or loading.
