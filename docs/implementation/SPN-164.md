## ⏱️ Measured boundary and chosen deadline

**Accepted, 2026-11-22, agent decision after local reproduction.** On the
instrumented baseline, toggle Chromium offline then online and reopen the app,
holding only the actual session response before headers or during its body.
Both requests took **15,002.1 ms** to settle as `TimeoutError`; the named sign-in
stage remained active until that settlement. The real app then took its existing
outage path. This identifies a reproducible slow boundary, not the original Pixel
cause. Neither a real device nor physical radio recovery was simulated by claim.

Choose **3,000 ms across session headers and body**. This is a usability budget,
not a statistical network estimate: it allows the tested 2.5-second successful
response, is more patient than the existing 2-second health probe, and prevents
the observed 15-second stalled wait. Native browser acceptance allows up to
4,000 ms measured request settlement (1,000 ms scheduling tolerance); the actual
configured deadline remains 3,000 ms. Foreground/event-loop time is measured;
this does not promise a bound while the OS suspends the browser, or include
service-worker navigation, account-lock waits or device admission. After a
verified session the label becomes **saved files**, accurately separating those
existing bounded device operations from sign-in. No new UI pattern is introduced.

Use the same deadline for session reads on ordinary starts: browser connectivity
does not provide a reliable recent-reconnect discriminator, and a new readiness
probe would add another race/request. Other authentication reads and item-transfer
deadlines remain 15 seconds; explicit caller cancellation retains its own signal.
Known-offline starts still skip the session request entirely. A slow server may
therefore yield the existing device-copy/unreachable view earlier, without
deleting content, clearing a cookie or granting online authority. A received
session 401 remains a real denial even when its error body times out or is
malformed; consume/settle that body and verify the current owner before acting.

**Personas:** Owner gets a bounded wait and retained notebook; Collaborator keeps
access revocation and late-account fencing, accepting conservative local mode on
a slow response; Operator keeps the existing health/auth architecture and gets no
extra production polling or telemetry; Link guest's route/authority is unchanged.
Keeping 15 seconds fails the reproduced usability contract; using browser-online
as authenticated readiness would weaken authority. Neither option is selected.
