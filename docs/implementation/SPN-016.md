## Legacy decision 72: Scoped anonymous link capabilities

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Explicit agent decision.
**Source:** [original decision #72](https://github.com/mxbaylee/spinel/issues/72).

**Question:** How should per-document share links authenticate guests and protect personal metadata?

**Options considered in the original source:**

A — separate document-scoped guest sessions, hashed capability tokens and grant epochs, with generic
collaboration labels while sharing is enabled; B — guest accounts or owner impersonation, which
enlarges the account/dashboard boundary; C — rewrite all historic protocol UUIDs, which adds legacy
ACK/routing risk without hiding any additional resolvable profile.

**Outcome, rationale and current boundary:**

Use random 256-bit fragment capabilities, hashed server-side, exchanged for bounded 24-hour scoped
sessions with generation/epoch fencing. Revoke or rotate invalidates live connections and all
subsequent content/image/protocol access. Guests have generic identities and only the linked
View/Edit capability: no account, dashboard, history or native-file-export authority. Enforce this
through every boundary and after awaited work, not merely a browser route. This is an agent
implementation choice under the existing link scope, not invented owner approval.

The maintained [guest-link rules](../sharing.md#guest-links) specify anonymous
presence, scoped cookie/token behavior and revocation across native and image paths.

**Persona tradeoffs recorded at the time:**

The Operator needs bounded credentials and no account-administration exposure. The Owner needs
view/edit links they can revoke without changing document ownership. The Collaborator needs current
permissions enforced and personal profile details hidden from visitors. The Link guest needs a
direct document-only page with a clear expired-link message.
