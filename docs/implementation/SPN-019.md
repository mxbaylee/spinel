## Legacy decision 62: Personal tag normalization

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Agent metadata judgment.
**Source:** [original decision #62](https://github.com/mxbaylee/spinel/issues/62).

**Question:** How should personal tags work on shared documents and after a tag is removed?

**Options considered in the original source:**

A — keep a per-user vocabulary plus per-document assignments, authorize assignment changes with
current read access, and preserve unused names for suggestions. This gives the Owner and
Collaborator stable reusable labels, with small separate tables for the Operator and no guest
endpoint. B — derive suggestions only from current assignments and require content-edit access for
tagging. This uses one table but loses previously used labels when the last assignment is removed
and prevents viewers from organizing their own references.

**Outcome, rationale and current boundary:**

Let each account privately tag readable documents, including Viewer shares, without modifying the
source document or its modified time. Normalize lower-case NFC, strip one leading # and enforce the
64 UTF-16-unit limit, rejecting empty/control-containing or still-hash-prefixed names. Keep unused
vocabulary for suggestions; vocabulary and associations remain personal. Use the existing small
SQLite/access model. No guest tagging, folder tagging or broader visibility follows from tags.

**Persona tradeoffs recorded at the time:**

Owner wants reusable labels without changing document contents. Collaborator wants independent
organization, including for view-only shares. Operator wants one small SQLite model and no new
access privilege. Link guest must not see account-specific tags or suggestions.
