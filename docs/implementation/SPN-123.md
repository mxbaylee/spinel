# Operation and sync diagnostic coverage

## Accepted coverage

**Date/status:** 2026-10-29, accepted. **Authority:** Owner approved the full
grooming proposal and delegated effort/impact and scope judgment in this chat.

The existing diagnostics infrastructure already samples memory, storage and
connections, records several jobs and Formula operations, observes native Doc
composition duration, and records server sync outcomes. The registry's
`document-open`, `document-save`, `search` and `snapshot-restore` operations and
client `sync.edit.resync`/`sync.resync.pending` have no production emitters on
audited main `6ed8ec2511707f7d9481692901b3f2f6c4480f4a`. The browser route admits
only `operation.*`; adding a client sync emitter requires a reviewed allowlist,
not removal of that boundary. `doc-compose` duration is already emitted.

Complete those specific seams and explain recent expensive/recovery paths:

| Boundary | Observation and limit |
| --- | --- |
| Document open | Start through usable editor readiness, with failure/cancellation and a precisely stated endpoint. |
| Save | Local durable persistence and server acknowledgment are separate outcomes; disconnected work cannot produce a false server success. |
| Search / snapshot restore | Existing operation duration and bounded outcome, without query, document or snapshot contents. |
| Sync/offline recovery | Fixed reconnect/resync reason, duration, pending count/oldest age, duplicate-receipt/publication and recovery outcomes. Count logical operations deliberately across retries. |
| Native Doc work | Existing capacity/quiet flush duration plus reason and group counts; observe failure without swallowing/replacing the exception. Checkpoint capture/skip and persistence measurements expose discarded work. |
| Maintenance | Phase changes, drain duration/admitted count, verification/refusal outcomes; instrumentation cannot become recovery authority. |
| System context | Bounded process CPU/event-loop sampling using existing runtime facilities; no raw profiler or new agent/service. |

Use explicit units and start/end definitions, bounded fixed codes, existing
opaque authorized IDs/context and server-derived account attribution. Preserve
the distinction between frontend claims and backend observations. Continue to
exclude guest browser collection and content, titles, formulas, raw URLs,
credentials, unbounded labels and arbitrary exception text. Preserve the
collector's session, visibility, offline and truncate-generation semantics.

**Options and choice:** keeping only the current metrics leaves named operations
unobserved; a general tracing platform introduces avoidable storage and runtime
cost. Extend the existing bounded collectors and downloads. SPN-098 consumes
whatever observations are retained and does not depend on this expansion;
SPN-110 expires observations independently. Neither ticket's completion is
claimed here.

**Verification:** enumerate promised emitters and actual callsites; inject known
durations, failure/cancellation and retry conditions; verify access and exact
field admission. Measure overhead and collection pressure. Disabled or failing
observers must leave native content, queues, history, access and saved/peer
convergence unchanged. A registry constant alone is not completed instrumentation.

## Implementation kickoff and ordering

**2026-10-29, agent decision under the owner's explicit SPN-123/SPN-098 sequencing
delegation.** Start SPN-123 from `81e369d3d2f7f67329924430e22edd9caa66d816`.
SPN-098 consumes existing retained observations and has no instrumentation
prerequisite. Completing the producers first makes its eventual feedback downloads
more useful without combining the separate durable-feedback/export/UI outcome.
SPN-110 continues to own retention. Keep this PR draft and unmerged as requested.

The complete outcome remains **L**. The existing account collector, exact event
registry, sync callbacks, offline checkpoint commit, history transactions,
maintenance supervisor hooks and minute health sampler provide the needed seams.
No new durable queue, tracing protocol, SDK patch or analytics service is planned.
The early risk is maintenance: the ordinary app sink deliberately stops during
draining, and verification runs while the app is down. Its observation path must
preserve store-generation fencing and recovery authority before this can pass.

Offline and hidden browser intervals remain uncollected; they cannot be recovered
by relabelling old observations into a new account/session/collection generation.
Actual local checkpoint commit and matching server acknowledgement must be named
separately. A resolved optional persistence hook is not proof of a durable write.

The Operator gains bounded investigation data; Owner and Collaborator retain
unchanged document/access/save guarantees; Link guests gain no browser collection.
Both independent whole-ticket reviews and current-head CI are pending at kickoff.

## Ongoing diagnostic upkeep

**2026-10-29, accepted owner direction:** because bots perform most code changes,
put metric maintenance in the PR template and backlog process. Keep one maintained
inventory in `docs/diagnostics.md`, linked from `AGENTS.md`. Each relevant change
reviews the actual emitter's timing, outcome, retries, attribution, privacy,
bounds and observer isolation together with its regression. A specific no-impact
explanation is valid; generic new metrics, duplicated checklists and another CI
waiver are unnecessary. Reviewers assess this within existing scope/correctness/
verification/maintenance rubric points. All seven required CI gates remain.

This gives the Operator dependable interpretation over time, protects Owner and
Collaborator save/access behavior, and preserves Link guest collection exclusion.
