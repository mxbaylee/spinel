## Keep an immutable sent request and a separate confirmed replica

**Date/status:** 2026-10-26, accepted by implementing-agent judgment under the
SPN-058 protocol and sender requirements.

**Question:** How can optimistic editing survive a disconnect after the server
commits but before the sender sees its acknowledgment?

Keeping only the current visible model loses the exact transform base. Resending
a rebased request with a fresh ID can apply an already committed edit again.
Reloading immediately when a later edit refuses can also discard the result of
a request the server is still deciding. The chosen queue keeps a confirmed native
replica, an immutable original wire envelope, its separately rebased optimistic
form and atomic unsent groups. A reconnect resumes from the confirmed revision
and retries the exact original envelope. The durable receipt identifies the
sender's broadcast revision. The client advances confirmed state without applying
the optimistic edit twice, and uses confirmed-plus-old-inflight cells for buffer
rebasing. A refusal waits for the sent request's answer before reloading.

The optional persistence callback records a checkpoint, including the original
envelope, before its first send and fences stale async completions. Actual disk
outbox persistence remains SPN-053. Pending-free hashing reads the visible native
model and fences stale async results; it does not verify only the client's
private confirmed replica. The browser and server share canonical native-value
normalization, while the server keeps its streaming hash and existing budgets.

**Alternatives:** A new retry ID risks duplicate durable edits. Reusing the ID
with changed contents violates the server receipt contract. Reusing today's
optimistic cells as the base changes conflict semantics. A second transport flag
would allow mismatched browser/server choices, so preparation alone advertises
`syncVersion: 1` behind the existing flag.

**Personas:** Owners and Collaborators keep truthful save status and durable
exactly-once retries. Link guests use the same queue within their exact capability
scope. Operators retain one application server and database, with no new service
or migration. Offline disk durability is not implied for any persona.

## Preserve native undo and exact mutation capture

**Date/status:** 2026-10-26, accepted by implementing-agent judgment implementing
the ticket's explicit native capture and sender rules.

The public `onMutationExecutedForCollab` event is the capture boundary. General
command completion is insufficient because commands can emit several mutations,
and filtering by supported IDs would hide an unsupported edit. The only exact
renderer exemptions are `sheet.operation.clear-drawing-transformer` and
`doc.operation.clear-drawing-transformer`; other mutation-shaped events receive
strict admission and explicit refusal. `onlyLocal`, `fromCollab` and
`fromChangeset` are excluded, while `syncOnly` is retained.

Before-command observation supplies context that disappears after application:
worksheet order, inserted paragraph IDs and insert/delete-with-shift geometry.
Capture copies params, resolves style IDs, preserves triggers and normalizes
native row/column metadata arrays to sparse index records. The transform owns
reserved claims and derived fields. Atomic output and absolute-write tails are
never split to make a wire batch fit; an oversized atomic edit refuses visibly.

Paragraph preparation visits actual JSON1 text-x components and their direct
insert actions. It does not interpret arbitrary objects inside inserted values
or custom-range properties, even when that opaque metadata resembles a TextX
operation. A review regression reproduced the former recursive walk changing
metadata IDs and marker values. The repaired tests compare the original metadata
with local, captured and persisted values, since agreement between replicas
alone would also accept identical corruption on every peer.

The OSS `createUniver` collaboration option disables core undo/auth/mention
services in expectation of Pro replacements. The new path therefore initializes
with `collaboration: false`, retains core undo services and installs its own
capture. The initial remote application used `onlyLocal` and `fromCollab`.
[SPN-059](SPN-059.md#formula-verification-and-headless-calculation) corrects the
live-editor path: `onlyLocal` suppresses formula registration and calculation for
received cell writes, while `fromCollab` alone prevents capture echo. The confirmed
revision replica retains its separate local-only application path.
The existing image insertion safeguards
remain. The still-used Pro print license service remains until its separate
removal; no new Pro dependency or license workaround is introduced.

**Personas:** Owners and Collaborators keep native editing and undo behavior.
Link guests receive the same edit semantics with existing viewer restrictions.
Operators get a reusable workspace package with public imports and no
application-specific transport dependency. No persona gains broader document
access through capture.

### Initialization and pre-application review repairs

The first hosted native-app run exposed a global legacy facade initializer that
requested omitted Pro services. Legacy preparation now imports that facade only
for the legacy path, before constructing its editor. A page that has already
installed the global initializer asks for a full page reload before changing to
the native backend; it does not patch the SDK or install dummy services.

The native editor's public permission providers project Spinel's exact unit grant
before unit creation. The OSS standalone default recognizes demo-role user IDs,
so real account and guest IDs otherwise lose edit/copy permission during its
asynchronous initialization. The projection preserves real identities and native
resource serialization, denies unsupported shared-permission writes, and keeps
nonroot protected objects conservative. A downgrade updates the local grant before
the editor's read-only presentation; later native refreshes cannot restore editing.

Captured pending work publishes immediately while initialization is pending, and
an initialization error retains the dirty state. Sheet edit-start/change/end
listeners attach before unit loading, protecting even unfinished cell input.
An attempted inert startup guard disrupted native input focus in hosted legacy
tests and was removed; early dirty tracking and initial grant projection protect
the initialization boundary while preserving the SDK's focus lifecycle.
Reload notices are cleared only by editing after the replacement is ready, so a
preexisting cell edit or image upload cannot erase the discard explanation.

The native before-command hook also bounds compact geometry before a local
handler can allocate its merge cache. It checks current aggregate merge area,
inserted sheet geometry/count and resulting native axis sizes using the server's
limits. The same admission runs before remote handlers: an individually valid
peer merge can exceed the visible budget when combined with optimistic local
merges. Handler-spy regressions exercise replay and rejection without allocating
oversized fixtures. These cross-check and independent-review repairs protect Owners,
Collaborators and editing Link guests from silent pending loss and stale native
state; Operators retain the existing memory and access boundaries.

## Invalidate stale native undo history when a remote change arrives

**Date/status:** 2026-10-26, accepted safety decision by implementing agents
after an integration cross-check of the public OSS `IUndoRedoService` contract.

The native local undo service stores raw inverse mutations and executes them
unchanged. It does not transform its history when the collaboration client
applies a remote row insertion or text edit. Reusing that history can clear the
old cell address after the local value has moved, or edit the wrong Doc offset.
Keeping native services enabled alone is therefore insufficient.

The visible adapter clears that unit's local undo/redo history through the public
`clearUndoRedo(unitId)` API for every accepted remote revision, including when
rebasing leaves no visible mutation. A peer edit in a locally deleted row still
changes the confirmed base; retaining its old inverse could restore stale data.
Native local undo/redo remains available until a remote change intervenes. Already
captured undo mutations remain ordinary pending edits and receive strict
transform/admission. Own acknowledgments do not invalidate history. Rewriting
the service's private stacks or guessing inverse bases would create another
unproven transform contract, so this slice does neither. Full collaborative undo
history is not claimed. Native Sheet and Doc regressions exercise remote changes
before an attempted undo and retain the normal local undo case. Actual native row
deletion, resume replay and lost-ack retry tests also prove that an invisible peer
edit invalidates history while an own acknowledgment preserves it.

**Personas:** Owners, Collaborators and editing Link guests lose older undo
availability when another editor changes the document, but cannot use a stale
inverse to corrupt a different cell or text range. Operators gain no persistence
or deployment requirement. SPN-056's integrated review must assess this explicit
conservative limitation before default activation.

## Retain conservative reference rewrite admission

**Date/status:** 2026-10-26, rejected optimization proposal; agent judgment for
this client slice, preserving SPN-056's existing conservative contract.

**Question:** Should capture drop a name rewrite whose record equals the current
record, or a formula rewrite whose formula text currently matches the cell?

The ticket asks this implementation to consider that optimization. Equality in
the already-mutated optimistic model does not prove that the rewrite was a no-op
at the command's common base. It can also erase the structural command's intent
when another editor rewrites references concurrently. Implementing this safely
would require additional before-command reference state and a convergence proof
for the exact provenance rules. The chosen client keeps the rewrite, its trigger
and the transform's existing refusal semantics. It does not silently weaken the
admission contract to reduce refusals. SPN-056's integrated review can evaluate
the observed cost and any separately proven optimization.

**Personas:** Owners, Collaborators and Link guests retain conservative,
explainable rejection rather than risking silent reference drift. Operators
avoid a second client-only conflict policy and additional reference caches.

## Render Doc presence without replacing local selection

**Date/status:** 2026-10-26, accepted by implementing-agent judgment using the
existing People, profile-label and editor-overlay design patterns. Visual
approval is a separate merge gate.

Remote Doc cursors and selections use independent public `TextRange` canvas
objects and `DocCanvasPopManagerService` labels. They do not reuse the local
selection manager. Labels use `requiresStableLayout: false`, `hideOnInvisible`,
canvas containment and the established overlay layer so presence cannot hold an
asynchronous document layout or cover application dialogs. Local profile styling
preserves native selection offsets, direction and focus, and skips pointer,
composition and pending-layout transitions. An explicit follow action sets the
body segment/page and uses the public facade to select and focus a supported
range. Unsupported encodings remain non-jumpable presence.

Every socket has a generated connection identity. Saved account profile data is
server-owned. When a root has an active guest link, all its rooms anonymize all
members for every recipient; clients submit only bounded selection strings.
Cursor coalescing, rate bounds, heartbeat/access cleanup and disposal keep this
state ephemeral. Space child changes retire the old channel before replacement.

**Personas:** Owners and Collaborators see consistent profile colors and icons
on both native editors without having remote activity steal their selection.
Link guests see generic names and empty avatars and cannot inject identity.
Operators gain no presence storage, additional service or diagnostic document
data. Existing root access and privacy-epoch checks remain authoritative.

## Verify actual Doc drawing behavior separately from its registered refresh handler

**Date/status:** 2026-10-26, accepted evidence clarification by implementing
agents; the independent reviewers must assess it against the original ticket.

The pinned OSS `@univerjs/docs-drawing-ui` 1.1.0 registers and exports
`ClearDocDrawingTransformerOperation`. Inspection of the public OSS bundle finds
the operation definition and registration entries, but no caller executing that
operation ID. Actual Doc image selection, resize and focus paths call
`transformer.refreshControls()` directly. The Sheet counterpart does have
callers. The original ticket's request to exercise the actual Doc UI producer
therefore cannot honestly be demonstrated by manually invoking the operation
and labeling it a UI emission.

Verification has two distinct parts. The native drawing Storybook interaction
uses the actual insert-image command, image decoder/file chooser and renderer
selection/deselection with the real capture queue; document writes enter pending
state and renderer-only refreshes do not add document work. The direct public
registered-handler boundary test separately proves exact-ID exclusion, including
that unrelated unknown operation-shaped mutations refuse. The flag-on browser
test uses the actual application toolbar and image upload, confirms durable Doc
drawing state, then edits text and reloads both editors. Neither test asserts that
the pinned UI emits an event it does not emit. The pinned public source is
`@univerjs/docs-drawing-ui/lib/es/index.js`: `DocDrawingTransformUpdateController`
subscribes engine resize and scene scale, refreshes controls after transform and
wrapping-style commands, and restores selected controls directly. Search that
OSS bundle for the operation symbol and `refreshControls` to reproduce the
definition/registration-versus-caller distinction.

**Personas:** Owners, Collaborators and Link guests retain real native drawing
behavior and explicit unsupported-edit handling. Operators and reviewers get
reproducible evidence that distinguishes UI coverage from a boundary injection,
without changing the product contract or inspecting Pro implementation code.

## Keep the native Doc drawing resource current through save and reopen

**Date/status:** 2026-10-26, accepted correctness repair after the hosted
full-snapshot comparison found a browser/server resource mismatch.

The public Docs drawing plugin serializes the canonical `drawings` map and
`drawingsOrder` as `DOC_DRAWING_PLUGIN`, then restores those fields from the
resource on load. The browser registers this plugin. Leaving it out of the
headless server and confirmed client replica loses that managed serialization;
preserving it as an opaque resource can instead retain an older drawing state
that overwrites newer canonical fields when reopened.

Both headless hosts now register the same pinned public plugin, after their
Doc hyperlink and general drawing plugins. Native insertion, resize and removal
update canonical fields and their serialized resource together. Existing
unrecognized resource bytes remain untouched. Browser/server comparisons retain
the full resource contents; they do not filter out the mismatch. Regressions use
actual public drawing commands and compare complete snapshots through capture,
server commit, replica application and reopening in all three model stacks.
Separate cases exercise resource-only persisted images and malformed known
resource JSON.

**Personas:** Owners, Collaborators and editing Link guests keep their current
images and deletions after reconnect or reload. Operators retain the existing
snapshot format and public OSS dependency versions without a migration or a
second drawing serializer.
