## 1. Acceptance and delivery boundary

The [original ticket](https://github.com/mxbaylee/spinel/blob/f59140a9d8df7ef3fd5c28c93bacb77511c86686/docs/todo/SPN-091.md)
and [Space design](../design/spaces.md) are authoritative. SPN-047's composition
was approved in [decision #126](https://github.com/mxbaylee/spinel/issues/126).
Implement the real account experience using SPN-078's durable model:

- Create a Space in an existing owned folder and open its persisted empty state.
- Add and edit real native Docs and Sheets; add folders; support children of all
  three kinds. Rename, reorder and nest without requiring drag-and-drop.
- Retain order and identity across reloads. Remember selection, support stable
  deep links and browser Back/Forward, and distinguish opening from expansion.
- Provide account-only internal Trash as a collection. Restore entire subtrees
  to a currently readable original location or the Space root with an explanation.
  The Owner alone may permanently delete a freshly confirmed exact subtree.
- View never mutates; Edit manages internal content/tree and restores. Root
  administration stays owner-only. Never introduce child grants or guest links.
- Recheck access after async work and in open editors for revocation, downgrade,
  trash and disabled owners. Offline management is unavailable and says so.

Ordinary Space creation, discovery and navigation remain disabled until SPN-092
proves guests and the remaining integrations, including backups and owner
transfer. SPN-091 therefore needs an explicit **server-controlled, default-off
review surface** that exercises real persistence and permissions. A hidden button,
query parameter, client-only feature flag or privileged authorization bypass is
not sufficient. Every review request still requires an active everyday session
and the current Space role; Operators, guests and assistant tokens gain nothing.

SPN-092 retains guest navigation, Doc Formula/cross-file acceptance, MCP/export
integration and operational backup/ownership-transfer proof. SPN-079 retains
delegated file Admin. Unsupported capabilities must continue to refuse access;
do not enable them incidentally by broadening ordinary `WorkspaceStore.get()`.

## 2. Existing code and implementation responsibilities

their native IDs. No parallel persistence model or content engine is needed.

The current app renders the ordinary `Rail` and `Dashboard`; Dashboard embeds
native `DocEditor`/`SheetEditor` within outer-file chrome. The Space screen must
replace that composition, not add another sidebar beside it. Native editors use
the shared collaboration service, images, presence, save and connection controls.
Their current ordinary endpoints intentionally refuse all Space children.

## 3. Server and API contracts

The review option defaults to false. Disabled review routes return unavailable
and cannot be enabled by headers, query parameters or browser storage. Explicit
test/review configuration may enable them for an account-authenticated review.
Keep ordinary `ITEM_KINDS`, lists, search, grants, links, Trash and offline
catalogs unchanged.

Use the dedicated account namespace `/api/spaces`, with mutations
requiring the configured Origin and appropriate JSON/content type. Validate
unknown fields, IDs and payload bounds; use current session identity at the
boundary, not an actor supplied in the body. Every result is `no-store`.

| Operation                   | Required capability and behavior                                                                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Create root                 | Active everyday Owner; existing owned ordinary folder or My files root; `SpaceStore.createRoot`.                                     |
| Read tree                   | Current inherited View/Edit/Owner; one bounded live tree; stable IDs, parent IDs, explicit positions and role.                       |
| Create/update child         | Current Edit/Owner; Doc/Sheet/folder allowlist; same-Space destination, no cycles or conversions; transactional native IDs retained. |
| Trash child                 | Current Edit/Owner; persist complete subtree and original location metadata; revalidate open clients.                                |
| List/restore internal Trash | Current Edit/Owner; use the existing recovery projection and fallback result; no unreadable location leakage.                        |
| Preview permanent deletion  | Current Owner; server-produced exact affected set/counts/version.                                                                    |
| Confirm permanent deletion  | Current Owner plus unchanged preview version; cancellation sends no deletion; stale previews require a fresh confirmation.           |
| Read/edit native child      | Explicit account Space scope and exact membership at each boundary and after async work; no unscoped fallback.                       |

Native Doc/Sheet content, generations, images and collaboration stay in their
existing stores. Preserve public SDK use only; do not inspect or modify Pro
internals. Native protocol HTTP requests, room tickets, upgrades, JOINs, mutations,
reconnects and broadcasts must carry/recheck the same authenticated scope. A
ticket for one Space or child cannot be replayed for another or an ordinary file.
Known generations/aliases must resolve to the same currently authorized member.

Only the operations required to edit and review SPN-091 are admitted. Doc Formula,
cross-file formula, guest, export, history and assistant surfaces not explicitly integrated
and verified remain disabled in this screen and rejected on the server.
Existing ordinary-file/guest behavior and tests remain intact.

## 4. UI and Storybook contract

Use the approved `PlannedSpace*` and `PlannedSpaceTrash*` stories as the visual
and interaction reference, not as persistence code. Their name-keyed mock tree
must not be copied into production; duplicate names and renames are valid.

- One 224 px internal tree and a full-width compact utility header. Do not render
  the ordinary rail/sidebar simultaneously. Use a local Pages control when the
  tree is hidden and a modal drawer at tablet/phone widths (900 px and below).
- Space identity and selected page identity are distinct. Reuse the connection
  control and existing save presentation; do not add competing status rows.
- Separate page-open and expand buttons. Expose expanded/current state and names
  to assistive technology. More actions remain visible for mouse and touch.
- Reorder/move dialogs provide keyboard and touch alternatives. Folder, Doc and
  Sheet destinations remain available within the current Space; exclude the
  moved subtree and reject stale/invalid choices on the server too.
- Reuse SPN-077 entity icons, palette tokens, Base UI menus/dialogs/drawers, focus
  restoration and 44 px touch targets. Preserve the existing 613 px mouse path.
- Empty, loading, error/retry, view-only, editing, offline/unreachable, no-longer-
  available and mutation-failure states need real component stories.
- Trash rows include type/name, readable original location, deletion time,
  descendant information and permitted Restore/Delete controls. Owner deletion
  confirmation names the affected subtree and its counts; Cancel preserves it.

Existing approved patterns cover this work. If implementation reveals a new
pattern, add it to the playbook in its own PR first, as AGENTS.md requires;
do not silently invent an alternative Space composition.

## 5. Navigation, pending edits and freshness

The review route is planned as `/review/spaces` and `/review/spaces/:spaceId`.
Selection uses stable item IDs in the URL, not names or ancestry paths. Explicit
deep links take priority over a remembered selection. A remembered ID is only a
hint and must be validated against the current authorized tree.

My files returns to the prior ordinary file view. Remember that file view,
the last Space root, and each Space's selected child separately, scoped to the
current account; the explicit URL always wins over remembered state.

Account-scoped browser memory may retain only navigation IDs/preferences, never
an authorization grant or cached native content. Storage failure must not block
navigation. Switching accounts must not reuse another account's selection.

All exits and selection changes, including Back/Forward, obey the existing
unsaved-change guard. Cancellation keeps the editor and coherent browser history;
accepted navigation disposes the previous editor and subscriptions. Late fetches
for an older Space/page must never overwrite the current view. Native callbacks
must not keep a departed page's dirty or connection state active.

Refresh role/tree state on relevant focus/visibility events and with a bounded
poll consistent with the existing app. Clear inaccessible tree metadata and
stop mutations as soon as access changes. Preserve the existing explicit handling
of pending edits/read-only access changes; never silently discard an unsaved
editor merely because a background list refresh failed. Reconnection must use
current roles, membership and trash state.

Offline/unreachable management is disabled rather than queued optimistically.
No bulk Space offline download or unrelated offline architecture is introduced.

## 7. Persona tradeoffs

- **Owner:** real content, recoverable organization, stable IDs and predictable
  navigation take priority over exposing unfinished integrations.
- **Collaborator:** inherited View/Edit is visible and enforced; an editor can
  recover internal content without receiving outer sharing or permanent deletion.
- **Link guest:** no new guest surface, identity or recovery collection is exposed;
  SPN-092 owns that separately scoped acceptance.
- **Operator:** explicit default-off review activation, one existing data store,
  bounded work and no document privileges keep the operational boundary small.
