## Independent review rubric

Two nonimplementing reviewers assess the same committed candidate independently.
They receive the original ticket, complete implementation diff, all four personas,
reproducible evidence and this rubric. Review contexts exclude prior grades,
requested grades and the other reviewer's conclusion. Each reviewer records concrete
deductions, severity, evidence and a proposed correction.

| Category | Points | Required assessment |
| --- | ---: | --- |
| Ticket completion | 35 | Stock core, aligned release, full removal and retained native/upgrade obligations |
| Correctness and integrity | 25 | Concurrent edit intent, identity, history, access boundaries and persisted state |
| Regression evidence | 20 | Meaningful native failures, convergence/fuzz, stock-byte proof and browser acceptance |
| CI and operations | 10 | Reproducible installs, independent guards, diagnostics and required check results |
| Maintainability | 10 | Smallest complete integration, clear boundaries, maintained docs and no unnecessary abstraction |

The implementation and verification are still in progress. No completed ticket,
passing final review, clean upgrade or merge is claimed by this checkpoint.

## Retain the aligned release while removing the core patch

Accepted implementation direction, 2026-11-01, agent judgment under the current
request and the stock-behavior adaptation rule. The user requested core unpatching,
not a latest-version upgrade. The selected release is the existing aligned,
published **1.1.0**. All dependencies and offline SDK identity stay on that release;
no partial Univer upgrade is introduced.

The official 1.3.1 package audit found all existing core defect forms still present
in both builds. All 23 direct Univer packages were available at 1.3.1, but its
independent drawing implementation also changed materially and an upgrade would
require an actual offline SDK transition. The three other guard repairs could be
requalified without semantic changes; their diagnostic run passed 146 of 148
checks, with the two mixed-publication cases exposing stock-core custom-range
fragmentation. This was an exploratory candidate, not accepted migration evidence.

Keeping 1.1.0 is the smallest complete route to the requested outcome: adapt native
application boundaries, prove the former core regression cases and convergence,
and verify both installed core builds are the official unmodified bytes. It avoids
coupling core removal to unrelated drawing and offline migration changes. The
independent Docs composition, UI resize, drawing refresh and Docs callback guards
remain exactly as previously qualified. A future SDK upgrade must reassess all of
them; the 1.3.1 exploration is not counted as a completed upgrade.

Owner, Collaborator and editable Link guest retain the same editor/runtime and
persisted formats. The Operator gains an unchanged core install without taking on
an unqualified broader release. No accepted core data-integrity outcome is deferred.

Local diagnostics use host Node 24.22.1 under the serial runner and 2 GiB process-tree
watchdog. The repository-required Node 26.12.1 archive was verified against its
official SHA-256 but its binary exits with SIGSEGV before `--version` in this host,
both inside and outside the restricted process sandbox. Local results are diagnostic;
required hosted CI uses the repository-pinned runtime for acceptance.
