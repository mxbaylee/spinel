1. **Close-first control:** establish a real 101 socket and freeze its identity;
   request server close code 1008, observe that exact server ws and underlying TCP
   socket close, then navigate. Record direct CDP and page events. Require the
   observer to recognize actual closure within the unchanged 5,000 ms deadline.
2. **Navigation-first ordering:** establish a fresh connection and allow a real

3. **Live-socket negative:** establish a fresh real connection and deliberately

The declared probe ran locally on the Mac: Node 26.13.0, Playwright 1.64.1,
installed Chromium revision 1248, one worker, no retries, three fresh contexts,
a task-owned loopback HTTP/ws server and the existing `observeSessionRevocation`.
It used no app build and no sleeps. The probe ran **twice**: the second run only
confirmed case 3 after its first output was truncated. It was not a
repeat-until-green; the second navigation-first result was not inspected.

| Case                 | Server ws / TCP                                                                               | Direct CDP observer                                                                     | Playwright page event         |
| -------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ----------------------------- |
| Close-first          | 1008 close, TCP closed at 1,313 ms                                                            | `socket-closed` at +1 ms, then navigation; `isClosed()` true                            | page close at the same moment |
| Navigation-first     | already closed by the browser with **1001** before the server could request close; TCP closed | **no `socket-closed`**, one open socket after the 5,000 ms deadline; `isClosed()` false | **no page close**             |
| Live-socket negative | closed only by owned cleanup                                                                  | `isClosed()` false before cleanup; `assertRevoked(401)` rejected                        | not needed                    |

**What this shows:** physical closure happened in every ordering, so there is no
evidence of a leak or an authority failure and no product-scope checkpoint is
triggered. When navigation wins, Chromium closes the socket with 1001 and neither
the direct CDP session nor Playwright delivers a close event. That matches the
original d22 retry-zero receipt (navigation +55 ms after revocation, no close
event, one open target). It is a present **observation boundary**, not a
physical outcome. Case 3 confirms the negative control already works.

## ✅ Decision and implementation (2026-11-16)

**Chosen witness: a loopback relay** (owner, chat 2026-11-16, over a server-side
witness). The revoked login's browser context uses a per-context HTTP proxy owned
by the test ([`e2e/socket-relay.ts`](../../e2e/socket-relay.ts)); Chromium carries
its WebSocket in a CONNECT tunnel. A tunnel earns an ordinal only if its first
request is an upgrade for the exact socket path. It is closed only when the
browser's own TCP connection to the relay is fully gone; the relay never drops a
tunnel on purpose before `stop()`, and a tunnel closed by `stop()` is never evidence.
An upstream reset or crash destroys the browser socket too, but marks the tunnel
`failed`, so it is reported and never accepted. The production server closes with
the WebSocket close handshake (`remove(entry, 1008, …)` in
`src/server/sync/transport.ts`), so an abrupt reset on revoke would be a finding,
not an accepted close.
Production code, the app server and the production diagnostic emitters are
unchanged.

`observeSessionRevocation` takes the relay as an optional third argument. With
it, `beforeRevoke` freezes the open tunnels and requires the relay and CDP to
agree on how many sockets were established; acceptance needs every frozen tunnel
closed, no tunnel opened afterwards, no observer loss or overflow, and a 401. A
browser close event, navigation or a close-method call alone never passes.
Without a relay the old CDP-only behavior is unchanged.

**Evidence run locally (not hosted CI):**

- Real Chromium, `e2e/socket-relay.spec.ts`: close-first, navigation-first (CDP
  silent, `closedTargets` 0, relay closed) and live-socket-negative all pass.
- `scripts/ci/socket-relay.test.ts` (real sockets) and the added observer cases in
  `scripts/ci/session-revocation.test.ts` cover absent, stale, wrong-count,
  reopened, live-plus-401, closed-plus-200, stop-only, overflow and observer-loss
  rejections. 48 tests pass with `plan.test.ts`.
- The existing two-login case passed at retry zero in the development project
  and in the production project (about 6 s each on the final tree), with the
  revoked login now an owned context behind the relay. In development the page
  also opens Vite's HMR socket on another port; the relay refuses that foreign
  authority, so the two-login case asserts `failed` is 0 but not `unexpected`
  in development, and asserts `unexpected` is 0 in production (the app-independent
  spec asserts both).
- Hosted acceptance, the exact-head reviews and CI are still pending.

**Acceptance interpretation (agent decision, owner confirmed in chat 2026-11-16):** the
ticket says navigation cannot satisfy the witness. It is read as: no navigation,
close-method call, 401 or browser event is *itself* evidence; the evidence is the
physical close of the exact tunnel the revoked login held. The relay cannot tell a
server close from a browser-teardown close, and Chromium closes the document's
socket with 1001 either way, so initiator is not proven. Parsing close frames was
rejected: it adds a protocol parser and can fail a correct run when the server's
frame is still in flight at navigation. The two-login journey stays meaningful
because its navigation is the server-driven 401 handoff, and the server side
closes with the 1008 handshake. A test pins this reading, so changing it is deliberate.

**Limits, stated plainly:** the relay and CDP are matched by count, not bound
tunnel-to-socket. Binding by order adds nothing fail-closed (every frozen tunnel
must close regardless) and could fail a correct run if two sockets open in a
different order on each side. A reset or crashed server marks a tunnel failed and
is never evidence. The relay also records, as a receipt only, whether the server ended
its side first (`upstreamEndedMs`); the real-Chromium close-first case asserts it, while
navigation-first cannot, because navigation can win.
The probe ran twice against the ticket's once; the owner accepted that
deviation in chat 2026-11-16, with the one-time push exception below.

**Diagnostics no-impact:** this is fixture-only. No production emitter, transport
operation, metric or schema changed, so the
[emitter inventory](../diagnostics.md#emitter-maintenance-inventory) is
unchanged. The relay and observer receipts keep ordinals, relative monotonic
times, event kinds, counts and status only.

**Review gate:** the exact-tree reviews scored 88 and 90 (no blockers); every remaining deduction was an owner decision or hosted-only, and the owner granted a one-time push exception in chat 2026-11-16 (accepting initiator-agnostic closure and the twice-run probe).
