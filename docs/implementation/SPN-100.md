## Reuse the bounded updater configuration

Date: 2026-10-23. Status: accepted implementation choice, pending independent
review and CI. Decider: agent judgment under the owner's backlog-run delegation.
Scope comes from the original SPN-100 ticket and the owner's
[undeployed-product decision](grooming-dependency-registration-2026-10-23.md#align-work-with-the-undeployed-product).

Question: how should Spinel enable reviewed dependency proposals without bringing
back the retired live-host maintenance routine?

Reuse only the prepared `.github/dependabot.yml` from the unmerged SPN-062 worktree
(base `48f6777e67dfd95978360b94729956046c6cc25b`; configuration was untracked).
Its SHA-256 is `0a9dbb3c5ea17ac96496df7de7c0134a1b0f9d67c784389d06e4d6ce3efa51c0`.
The alternative was a new updater service or custom scheduled workflow. Four
existing Dependabot ecosystems suffice, with no runtime dependency, new secrets,
privileged PR workflow, automatic merge, deployment or version bump in this PR.
The npm job's `increase` strategy retains exact manifest pins while allowing
reviewed upgrades; grouping applies to the existing SDK packages, not new Pro use.
Maintained rules live in [development](../development.md#reviewed-dependency-updates).

Operator gets bounded weekly proposals through existing review gates. Owner and
Collaborator retain document behavior and benefit only when a reviewed update
later lands; no live restart or data migration occurs here. Link guest gains no
new access, account surface or telemetry. All four personas retain existing
security boundaries. A cooldown is delay, not security approval.
