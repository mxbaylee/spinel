## Phone Doc fit investigation and supported fallback

The installed public open-source `@univerjs/docs-ui` API exports
`SetDocZoomRatioOperation` (`unitId`, `zoomRatio`) and `SetDocZoomRatioCommand`
(`documentId`, `zoomRatio`). There is no public FDocument zoom facade. Public
source inspection shows that the command also records undo, and both routes
ultimately call the document model's `setZoomRatio`, writing snapshot
`settings.zoomRatio` and marking a mutation. An operation is therefore not
proof of a device-only visual preference. Auto-running either API on a phone
would require additional proof about collaboration, save/export and viewer
permission effects.

Decision: retain native document zoom and pan, page geometry and the mounted
selection. Do not mutate a shared document on opening it at 390 px, CSS-scale
its canvas, rewrite page size, or restore only a body-text selection. The public
FDocument `setSelection(start,end)` cannot losslessly restore headers, footers,
table/multiple ranges. This fallback is within SPN-049's explicit exploration
scope; full phone editing/reflow remains SPN-072. Owner and Collaborator avoid
unexpected shared layout/history changes; Link guest/viewer permissions stay
intact; Operator gets no unsupported renderer fork.

Source evidence was independently researched against installed public OSS
`docs-ui` and core APIs by `sync_sheet_review`; no Pro internals were inspected.
The original theatre browser cases exercise editable and viewer Docs at 390 px
with unchanged snapshots and native selection/focus, but do not operate native
pan/zoom. The additional `e2e/doc-phone-navigation.spec.ts` now authors that
missing interaction coverage, as described below. It is not yet executed.
Interaction results and rendered readability/caret review remain required
acceptance evidence before merge; source inspection or unchanged snapshots alone
do not prove them. Unresolved mobile limitations belong in SPN-072.

### Native phone navigation evidence repair

Date: 2026-10-23. Status: authored, unverified; no runtime change or visual approval.

Further inspection of the installed public OSS SDK 1.1.0 found a distinct
`IUniverDocsUIConfig.fitToWidth` option and exported `DocViewScaleService`.
The public config supports `mode: 'fit-width'`, viewport/container targeting,
padding, minimum/maximum scale and alignment. The default desktop plugin uses
`mode: 'none'`; the mobile plugin defaults to fit-width with a maximum scale of
one. Its view-scale service multiplies the stored user zoom by a computed fit
scale, and its resize path updates the scene rather than calling `setZoomRatio`.
This is a promising separate public route: the mutation finding about the two
zoom commands does **not** establish that every fitting API changes the snapshot.
The installed core preset's public config only forwards `toc` from Docs UI,
so adopting fit requires a supported plugin/config integration and rendered
selection, collaboration, save/export and viewer verification. That work remains
in SPN-072; this repair does not silently change presets or document geometry.
Sources: installed public `docs-ui/lib/types/config/config.d.ts`, its exported
`DocViewScaleService` declaration, the OSS config/view-scale/zoom implementations,
and `preset-docs-core/lib/types/preset.d.ts`; no Pro internals inspected.

The new two browser cases seed a real multi-paragraph native Doc, then exercise
an editing account and a separate anonymous viewer at 390×844 in light and dark.
They use the native footer's accessible Zoom textbox, horizontal and vertical
wheel input over the actual canvas, return panning, 100%→50%→100% zoom, repeated
theatre entry and reload. Each pan/zoom must change more than 1,000 interior
canvas pixels across more than 25 rows and 60 columns. Focus is moved to the
header and successive canvas captures must settle before each comparison;
outer scrollbars are excluded, so a caret blink, hover scrollbar, connection
label or encoded image metadata cannot alone satisfy the movement assertion.
The percentage control must also report the requested native zoom. Captures
retain full phone chrome and text at both zoom levels and both panning positions.

After navigating, the editable case moves to the document start and end with
native keys and inserts distinct prefixes/suffixes, checking the exact saved
text. The public native input host is positioned by the OSS selection renderer
at its canvas caret anchor; its geometry must stay inside the canvas, and start
and end captures allow independent inspection of the rendered caret. Host
geometry is not a claim that the hidden input itself is a visible caret.
The viewer case attempts typing, retains disabled formatting, checks the full
unchanged body and the absence of account/export actions. Both retain page
geometry, mounted canvas identity through theatre toggles and persisted content
after reload. Existing theatre tests retain guest revocation coverage.

Owner and Collaborator gain evidence for navigating/editing the existing canvas
without a new shared zoom or layout policy. Link guest gets populated read-only
navigation checks without account data or expanded permissions. Operator gets
bounded existing-browser tests and no dependency, server or rendering-service
change. Agent decision under delegated persona agreement: keep the native
fallback while testing it honestly, and carry the separate fit investigation to
SPN-072. Wheel input at phone width is not physical touch/pinch support; these
tests do not prove soft-keyboard avoidance, IME, reflow or human readability.
CI execution plus independent review of the retained pixels remain outstanding.
