# SPN-071 — Personal hiding, access provenance and live upgrades

## Scope and capability checkpoint

**2026-11-01 · Accepted implementation direction · agent judgment.** The complete L-sized outcome retains all three scenarios from SPN-071: personal Hide/Show hidden discovery, privacy-safe granting-ancestor details including the Space boundary, and an open viewer becoming editable without reload or lost position. Declining shares, notifications and personal pinning remain out of scope.

Current-main investigation found two unconditional role-mismatch fences: the sync transport closes upgraded sockets and the client treats upgraded metadata as terminal denial. Native permissions already project Spinel grants at the public cache boundary. The implementation will reuse those boundaries, admitting only verified account-role increases on the same native unit. Downgrades, revocation, guest epochs, document generations, maintenance and account changes retain their existing fences. A real Doc and Sheet upgrade is the first capability check; no test pass is claimed in this checkpoint.

Hiding remains a separate per-account discovery preference. It does not change grants, canonical parent, ownership, personal filing or prepared offline bytes. A Space is hidden as its outer file. Access details use current account authorization and expose only readable granting sources; Space children retain the outer Space sharing boundary.

### Persona tradeoffs

- **Collaborator:** fewer stale shares, an explanation of effective access, and live editing without losing their current work or place.
- **Owner:** ownership, sharing and canonical organization remain authoritative; personal hiding cannot remove a document or alter a grant.
- **Link guest:** no account discovery or provenance metadata; existing link revocation and privacy epochs remain authoritative.
- **Operator:** no new service or background polling system; existing bounded collaboration scans and SQLite storage are reused.

## Personal hiding without changing access

**2026-11-01 · Accepted · agent judgment.** The question was whether hiding should
reuse personal filing, remove a grant or add an independent discovery preference.
The original ticket and [personal organization decision](SPN-021.md#legacy-decision-30-trash-batches-and-exact-set-deletion)
require the latter. A private `workspace_hidden` table records only account/item
pairs. Authorization is checked before each change. Owners, Operators, guests,
revoked accounts and Space children cannot use that endpoint to create unrelated
preferences. Cascading foreign keys remove preferences with their account or item.

Ordinary shared/search responses filter hidden rows. The account catalog can
request the complete authorized inventory, carrying only a `hidden` flag, so
**Show hidden** and cold offline launch remain useful. Search retains the complete
graph for scope traversal and filters hidden result rows afterward. This hides
the selected outer file, not every descendant: hidden folders remain traversable
where the person has current access. Filed references and downloaded bundles are
not removed. An outer Space is one preference, without independent child hiding,
filing or grants. Existing sign-out and revocation cleanup stays authoritative.

The UI composes existing menus, badges, status text and focus restoration. It
exposes **Hide**, **Show**, and the Shared with me title menu's **Show hidden** /
**Hide hidden**. Failed requests leave confirmed state visible; pending operations
use the existing serialized shared-item mutation path. Personal pinning remains
removed under [decision #128](SPN-047.md#legacy-decision-128-remove-personal-pinning).

**Personas:** the Collaborator controls discovery without losing access or
downloaded work; the Owner's grants and canonical organization are unchanged;
the Link guest receives no account catalog; the Operator maintains one small
SQLite preference table, with restore and sync-transition inventory updated.

## Privacy-safe access provenance

**2026-11-01 · Accepted · agent judgment.** Reusing cached parent labels could
reveal an ancestor after access changed. Instead, a dedicated account-only access
endpoint resolves the current effective role and its source in one transaction.
It chooses the nearest readable grant matching the effective role; direct access
wins an equal-strength tie. Stronger inherited access still wins over a weaker
direct grant, following [first integration grooming](grooming-2026-10-17.md#legacy-decision-23-first-integration-grooming).
Every candidate ancestor must independently be readable before its name is sent.
Explicit Space scope cannot fall back to ordinary routes, and child grants cannot
escape the outer Space sharing boundary from
[decision #116](SPN-078.md#legacy-decision-116-spaces-remain-files-in-folders).

The existing read-only modal presents **Editor through Budgets** or direct/owner
access, plus the Space boundary when applicable. It fetches only while open,
rechecks on focus/visibility/online and every five seconds, and clears old names
on offline/hidden/error states. Request generations reject stale responses. It
offers no grant editing and never includes other accounts' grants.

**Personas:** the Collaborator learns why they can edit; the Owner retains
private ancestor names and grant authority; the Link guest receives no account
provenance; the Operator gets a bounded resolver and current authorization, with
no new cached permission model. This uses existing modal/menu patterns from the
[approved composed design](SPN-047.md#legacy-decision-126-approved-redesign-and-its-limits).

## Live upgrades with current authority

**2026-11-01 · Accepted · agent judgment.** The capability checkpoint established
that public native root permission points can be changed without rebuilding a
Doc or Sheet. The transport now accepts only monotonic account-role increases
through its existing access scan; precommit authorization still checks every
edit. Guests, downgrades, revocations, account changes, route mismatches, maintenance
and replaced generations keep their existing fences. Old-role one-use tickets
remain invalid. No new polling mechanism or SDK dependency is introduced.

The existing client access check admits an upgrade only on the same live unit.
It updates root permissions and native input controls without selecting,
scrolling, focusing, recreating the unit or reconnecting its socket. Range,
worksheet and paragraph policies remain in force. The generic image renderer has
a separate edit flag from the Sheet drawing service. Independent review found
that setting it true at upgrade could attach late image controls on a protected
worksheet. Its flag now follows the real composite workbook/active-worksheet
policy, including point registration, sheet changes and disposal; the SDK retains
control of existing object transformers. Live phone Docs keep
their reversible UI containers: Modern layout can enable editing, while
Traditional layout and changed-layout restrictions remain read-only. Static
snapshot behavior is unchanged.

A prepared viewer first acquires the existing exclusive writer under offline
editor admission. The durable update compares account, Space scope, generation,
base snapshot, revision offset, SDK/schema and maintenance identity, refusing
pending/recovery/uncertain state or a newer stored checkpoint. Only the role and
read-only metadata change; native base/image bytes remain intact. The current
checkpoint is then persisted before native input is enabled. Partial promotion
is idempotent, failures remain visible and can retry, and a viewer projection
caused by a lost writer or save failure cannot be thawed as a grant upgrade.

**Personas:** the Collaborator continues at their current place and retains local
work; the Owner's current authority still decides every durable edit; Link guest
privacy epochs and guest role changes remain terminal; the Operator reuses the
existing transport, scan, public permission API, storage lock and recovery fences.
