## Legacy decision 10: First-admin setup proof

**Recorded:** 2026-10-17. **Status:** accepted.
**Authority:** Agent bootstrap implementation judgment.
**Source:** [original decision #10](https://github.com/mxbaylee/spinel/issues/10).

**Question:** How should an operator claim the first admin without sending the setup secret over the
network or creating an account before its passkey works?

**Options considered in the original source:**

A — Generate an ephemeral Ed25519 signing key in the CLI, store only its public key, print the
private key in the URL fragment, and let the browser sign a session-bound registration challenge and
response. B — POST a bearer secret, which conflicts with the no-network-secret rule. C — Create a
provisional admin before verification, which can leave an unusable claimed instance.

**Outcome, rationale and current boundary:**

Keep an ephemeral Ed25519 private setup key only in the console link fragment, clear the fragment
before requests, and send only the public selector and domain-separated signed proof. The server
stores the public key. Reissuing invalidates older links; issuance and final claim transactionally
require zero users. Create admin and credential only after successful verification, consume setup
and rotate the session atomically. Setup expires after 30 minutes, ceremonies after five. This is no
network issuance endpoint, password bypass or replacement for WebAuthn.

**Persona tradeoffs recorded at the time:**

The Operator needs a console-issued link and a race-safe claim. The Owner needs admin and everyday
accounts kept separate. The Collaborator needs an already claimed instance to reject new setup
attempts. The Link guest must never gain workspace access through setup.
