### Scoped execution result repair

Review found that the CLI used the full three-lane capability aggregate as its
exit decision even for an explicitly selected Safari or Chrome scope. A successful
selected lane therefore exited unsuccessfully because the other lanes were
unrun/blocked; a selected failure could be flattened into `incomplete`.

The CLI now uses `capabilityRunOutcome`: `status` and exit code describe execution
of the requested `capabilityScope`; `fullMatrixStatus` separately reports the
complete three-browser **capability** aggregate. A successful selected scope may
report `passed` / `incomplete` and exit zero. This never means every authored,
ordinary-tab or monthly acceptance contract passed. A failed selected operation,
unknown HTTP500, missing execution evidence, uncertain allocation or failed
network/session/fixture cleanup cannot pass. Missing/duplicate/invalid lane
records and selected unrun work remain incomplete with a nonzero exit. Default
`all` still cannot pass with an incomplete lane. Firefox's historical HTTP400
remains `blocked` raw evidence with an explicit route-limit classification; its
accepted coverage disposition is not a fabricated native pass.

The prepared-journal reader binds the new field to its initial incomplete state.
Accounting consumes the existing receipt and does not reinterpret result fields;
admission, reservations, charging assumptions and reconciliation are unchanged.
Existing capability/receipt tests own this regression at the CLI-used seam;
accounting integration tests check that early failure and cleanup still release
only known reconciled reservations. Current validation and independent review
identities are recorded below and in the PR description after execution.

### Chrome readiness HTTP 500 cause: Appium status unwrapping

**2026-11-02; updated 2026-11-03 for the scope amendment.** The Chrome
readiness HTTP 500 in run 41395124342 arrived 51 ms after a verified
`location.assign` navigation, and receipt
41486191988 left its terminal `UnknownError` unclassified. With owner approval,
the completed session's Appium log was read once, locally and read-only. Only
that log's terminal-error lines and the proxy lines in the same second were
printed. No log text was saved or committed, because raw provider log text is
never retained; reviewers cannot re-read it. The claim rests on the cited
Appium source and on the old script, which returned a top-level `status: ''`
whenever the save status was blank. An optional later run would confirm it.

ChromeDriver answered the readiness `execute/sync` with HTTP 200. Its value was a
ready document (`phase: 'editor'`, `readyState: 'complete'`) whose save status
was still empty, returned as `status: ''`. Appium 1.17.0 logged
`Matched JSONWP error code  to UnknownError` and responded with HTTP 500. Its
base driver treats any command result with a top-level `status` that is not
numerically 0 as a legacy JSONWP error envelope
([appium-base-driver v5.3.1 `protocol.js` L355-L358](https://github.com/appium/appium-base-driver/blob/v5.3.1/lib/protocol/protocol.js#L355-L358);
Appium 1.17.0's `npm-shrinkwrap.json` pins v5.3.1, and v5.8.1 has the same lines).
An empty string passes `!isNaN('')`, but `parseInt('', 10)` is `NaN`, so the
check throws. A non-empty, non-numeric status fails `isNaN` and passes through.
That makes this a race: it fires only while the save status is still blank,
which fits the first read right after navigation. The terminal line is
therefore Appium's generic `UnknownError` text with no `Original error:` suffix,
and no ChromeDriver cause exists to classify.

The readiness script now returns the text as `saveStatus`, and
`itemReadinessSatisfied` reads that field. A cited comment on the script
also names Appium's second envelope check (L357: a top-level `value` object with a
truthy `error`) and states which keys synchronous and wrapped asynchronous results
must avoid. The other device scripts nest theirs
(the transport probe keeps its per-path `status` inside `checks`). The new
regression runs the real script against a blank save status. It asserts the
editor phase, no own `status` key and no throw under the cited Appium predicate.
It also checks that the predicate rejects `{status: ''}`.

That regression protects one script, so the predicate is now enforced for every
script the capability harness executes (the separate smoke check in
`browserstack.ts` returns only the user-agent string, which no rule matches). `appiumEnvelopeHazard` mirrors both L355-L358 checks, and the harness
`command()` wrapper fails any `execute/sync` or `execute/async` result that
would trip any of these with `capability-appium-envelope-<rule>`, naming the
rule that fired (`status` or `value-error`). The earlier
[L319-L324](https://github.com/appium/appium-base-driver/blob/v5.3.1/lib/protocol/protocol.js#L319-L324)
`protocol` unwrap is not a script hazard: Appium 1.17's `AppiumDriver.executeCommand`
([lib/appium.js L529-L538](https://github.com/appium/appium/blob/v1.17.0/lib/appium.js#L529-L538))
always returns its own `{protocol, value}` wrapper, which L319-L324 removes once,
so a script result's own `protocol` key passes through. An earlier draft of the
guard also rejected that key; review against this source withdrew it.
BrowserStack's own `browserstack_executor:` commands (Safari `acceptSsl`) are
answered by the hub with an unobserved shape, so the guard checks every other execute result (page scripts and `mobile:` commands). UiAutomator2 v1.44.2 proxies Chrome's `execute/async` to ChromeDriver, so applying the rules there is stricter than Appium: such a result fails with the envelope reason instead of its own, and never passes. A future script
that returns a top-level `status` fails in the mocked tests and on any driver,
not only on Appium 1.x as an unexplained HTTP 500. A table test pins the
predicate (`''`, `' '` and `13` trip it; `'0'`, `0`, prose and `null` do not;
a wrapped `value.error` trips it), and a mocked Chrome readiness response with
`status: ''` now fails with that reason, and a wrapped `execute/async` result
with `value.error` fails the same way. Limiting the check to `execute/sync`
fails the async test. Capability tests pass 50/50.

**Withdrawn before commit.** ChromeDriver's
[`cannot determine loading status`](https://github.com/chromium/chromium/blob/152.0.7977.54/chrome/test/chromedriver/chrome/navigation_tracker.cc#L22-L35)
wrapper was tried as a diagnostic cause; the log showed no ChromeDriver error
around the 500. A tolerance for up to three phrase-matched readiness 500s was
tried too; the anchored classifier already covered those phrases and the change
would have hidden this deterministic defect. The four earlier `execute/sync` HTTP
405 records are unrelated Appium `NotImplementedError` responses.

This is a diagnosed harness defect with a repair, not a Chrome capability pass.
A later paid run would confirm the repair; it is out of scope and not required.
