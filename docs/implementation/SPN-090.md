## BrowserStack CI plan

**Accepted, 2026-10-27.** Owner asked to verify BrowserStack Android/iOS support,
expand the ticket, verify the existing credentials before merging, and include a
working sample where useful. Secret names supplied by the owner are
`BS_USERNAME` and `BS_ACCESS_KEY`. Agent judgment chooses a bounded infrastructure

The documented native contexts and Firefox support justify trying Automate.

Use the framework whose observed native operations meet the contract; the small

## Infrastructure sample

The [workflow](../../.github/workflows/browserstack.yml) is manually runnable on
GitHub and runs when the exact `ci-real-devices` label is added to a
same-repository PR. The [2026-10-29 budget decision](#lifetime-budget-and-monthly-reporting)
replaces automatic file-change triggers, so editing this ticket does not allocate
devices. Fork PRs do not receive secrets. The workflow uses the
repo's pinned Node version and immutable action revisions, read-only repository
permissions and no application dependency installation.

1. `node scripts/ci/browserstack.ts credentials` checks Automate's plan and
   inventory using Basic authentication in HTTPS headers. A successful inventory
   lookup is a catalogue check, not proof of mobile entitlement.
2. The official actions receive `username: ${{ secrets.BS_USERNAME }}` and
   `access-key: ${{ secrets.BS_ACCESS_KEY }}`. Local starts with a unique identifier
   and bounded startup. The action revision is pinned; the vendor's downloaded
   Local binary is not claimed to be immutable.
3. `node scripts/ci/browserstack.ts smoke` opens Android Chrome, Android Firefox
   and iPhone Safari sequentially, with `realMobile: true` and that Local ID.
   Current stable physical-phone entries come from inventory; Firefox is requested
   explicitly because its inventory row can be absent. iPhone inventory can say
   `iphone`, while the session requests `safari`.
4. A loopback HTTP server serves only a random synthetic title at
   `http://bs-local.com:8173`. Matching that title proves reachability to this
   runner. Returned browser capabilities are retained as evidence; checks of the
   unmodified running user agent distinguish the requested browser. Each allocated
   session is deleted in `finally`; cleanup failure fails
   the sample. A creation timeout without an ID is reported as uncertain cleanup,
   with a short server-side idle timeout as the fallback.
5. Local stops with `if: always()`. Vendor binary log artifacts are disabled;
   only allowlisted JSON reports are retained for 14 days. They include source
   and tested merge SHAs, run URL, device/version, browser identity and result.
   Raw credentials, authorization headers, responses and exception messages are
   never logged. GitHub console masking alone is not artifact redaction.

The code uses `BS_USERNAME` / `BS_ACCESS_KEY` directly; the action's standard
`BROWSERSTACK_*` environment exports are implementation details. No GitHub token
is a substitute for the BrowserStack access key. Credentials are verified inside
GitHub; no secret value needs to be copied into chat or the repository.

This sample proves only authentication, real mobile session allocation and the
private-runner tunnel. Its plain HTTP fixture intentionally makes no PWA or
secure-context claim. Live run evidence belongs in the grooming PR and a later
verification checkpoint; no result is assumed before execution.

### Balance and accounting evidence

Official references checked on 2026-10-29 distinguish these APIs:

- The [Automate Plan API](https://www.browserstack.com/docs/automate/api-reference/selenium/plan)
  documents parallel-session limits/usage, not a remaining-minutes balance. A
  successful `plan.json` response proves neither unused time nor a new allowance.
- The [Automate Session API](https://www.browserstack.com/docs/automate/api-reference/selenium/session)
  exposes session duration. Reconcile all statuses, failed/partial sessions,
  retries, manual invocations and usage elsewhere on this account, deduplicated by
  provider session ID. Wall-clock workflow duration is not measured device cost.
- [Enterprise Usage Reports](https://www.browserstack.com/docs/enterprise/api-reference/usage-reports/overview)
  offer historical reporting with a six-month lookback. Access for this free
  account remains unverified; a limited history is not proof of lifetime usage.
- The legacy [JavaScript Testing API](https://github.com/browserstack/api)
  `/5/status` response reports seconds. Its applicability to this Automate
  allowance is unverified;
  do not substitute its values for an authoritative Automate balance.

Prefer a verified provider balance for the actual Automate allowance, with its
timestamp and units. Otherwise maintain a durable ledger of unique session IDs
and charged durations, plus a known starting-usage offset with timestamp,
provenance and clear coverage boundaries to prevent double counting. Include
account usage outside this repository. Persist the ledger and redacted evidence
before provider retention removes history. Missing duration, incomplete history,
an uncertain session allocation or an unverified offset stays unknown or bounded;
never treat it as zero or claim an exact remaining balance. A balance/ledger
disagreement requires reconciliation before spending.

The [first](SPN-090-browserstack-first.json) and
[verified](SPN-090-browserstack-verified.json) smoke reports retain six allocated
session IDs but no durations. Their passes, failures and session deletion do not
establish current remaining minutes or an honest remaining-run count.

The next validation is a finite **quota-only** job using existing `BS_USERNAME`
and `BS_ACCESS_KEY` GitHub secrets: one Plan request, the six known session-detail
requests, within 60 seconds with
bounded per-request deadlines and no automatic retries. Retain only allowlisted
status, timestamp, units, duration and coverage fields; never credentials or raw
provider errors. Do not start Local, create a WebDriver session or invoke the
existing manual smoke as a substitute for this job. Report denied/unavailable or
expired records explicitly. This probe establishes API capability and available
history; completing account-wide history or an authoritative starting offset is
separate work if the response is incomplete.

### Read-only quota evidence increment

**Implemented locally, 2026-10-29; agent decision under the owner's budget and
full-scope instructions. No provider dispatch or physical allocation performed.**
The isolated SPN-090 branch starts at main
`ea874c9787a6ca4b074062576c1592812e290e50`. Full SPN-090 remains XL and open:
account-wide accounting, monthly admission/reporting, installed-context capability
and every physical offline acceptance lane remain required. This small increment
is an investigation tool, not a completed quota guard or a split completion.

The question is how to obtain evidence without spending the finite allowance.
The chosen `quota` mode makes at most seven authenticated GET requests: Plan and
exactly the six retained session IDs above. It has a 60-second overall deadline,
an eight-second per-request deadline including body reads, a 64 KiB decoded body
limit, redirects refused and no retry. Every missing/denied/expired, malformed,
oversized or timed-out response is retained as an allowlisted failure; remaining
unstarted requests are recorded when the overall budget expires. Missing
credentials make no network request. No inventory, WebDriver, Local, report-job
creation, arbitrary URL or other account operation is reachable from this mode.

A response retains only fixed local session IDs, numeric Plan counters, duration
seconds, separately allowlisted test/execution status, normalized timestamps and
locally constructed failure codes. Raw provider error bodies, project/session
names, logs, public URLs and video URLs are discarded; session API examples
contain authentication tokens in those URLs. Missing/invalid duration is `null`,
not zero. Even when all seven reads pass, the report says account-wide history
and remaining minutes are unknown, charged-duration mapping is unverified,
complete-offline-matrix cost is unknown and allocation is disallowed. A successful
read is not a successful spending admission. The future scheduled quota check
must still visibly fail on unknown sufficiency.

Manual dispatch now defaults to `mode=quota`, in a separate job with no
BrowserStack setup or tunnel actions. Explicit `mode=smoke` and the existing exact
same-repository `ci-real-devices` label retain the old device smoke. No schedule
is added before accounting/admission exists. The safe invocation, **not executed**,
is `node scripts/ci/browserstack.ts quota` with the existing credentials supplied
through environment, or later a reviewed workflow dispatch with `mode=quota`.
The output is `artifacts/browserstack-quota.json`; the workflow artifact still has
14-day retention and must be preserved with source/run identity before expiry.
It is not a lifetime ledger. No push or dispatch is part of this increment.

The initial plan mentioned a Usage Reports access probe. Further official
research corrects that assumption: [report generation and retrieval](https://www.browserstack.com/docs/enterprise/api-reference/usage-reports/access)
requires `POST /reports/usage/v1/user` before GET status/result. There is no
documented single read-only access probe without an existing report job. The
published Automate report fields count tests/parallels; `minutes_used` is documented
for Live/App Live, not this Automate allowance. [Enterprise access](https://www.browserstack.com/docs/enterprise/api-reference/usage-reports)
also requires the appropriate plan, Owner/Admin role and enablement. Rather than
invent an endpoint or silently create a report job, this mode records the limit
and makes no report request. This is not evidence that this account lacks access.
The [Plan](https://www.browserstack.com/docs/automate/api-reference/selenium/plan)
and [Session](https://www.browserstack.com/docs/automate/api-reference/selenium/session)
APIs remain the supported read-only evidence sources. Their session durations
are not asserted to be an authoritative balance or proven billing rounding rule.

The next evidence decision is whether those six session records remain available
and which numeric/status fields this account returns. Unknown initial or outside
usage will still require authoritative balance evidence or a proven offset and
coverage boundary. Avoid speculative ledger storage until this read is reviewed.
BrowserStack [session retention](https://www.browserstack.com/support/faq/automate/features-automate/for-how-long-are-session-details-available-on-the-automate-dashboard)
is 60 days, with recordings/logs generally 30 days; the later ledger cannot rely
on provider retention or monthly collection alone. Installed-context work also
needs proof of actual authentication and native lifecycle: the documented
[Live WebAuthn setup](https://www.browserstack.com/docs/live/device-settings/webauth-device-passcode)
is paid-plan Android Live support, not evidence for Automate's required iPhone
Home Screen context. No acceptance is removed because that capability is unknown.

Persona decision: the Operator receives explicit uncertainty and a safe default
that does not start devices. Owner and Collaborator retain the full three-device
offline/data-loss acceptance, rather than accepting an accounting pass as phone
verification. Link guest scope, revocation and exclusion from private offline

The tradeoff is that the first report may remain incomplete and cannot fund a

### Required report and forecast

Every monthly, label or manual run must publish the checked balance or bounds,
measured complete three-device matrix cost, estimated successful complete runs,
the next monthly dates, projected exhaustion/first unfundable date, assumptions
and uncertainty. Record both pre-admission and post-run accounting, including
failed/partial sessions and cleanup. Identify the measured suite/source: an
infrastructure smoke's cost does not price the future complete offline suite.
Use conservative cost/reservation bounds
before allocating; unknown sufficient quota or less than a complete matrix's
budget must visibly fail without opening devices. Serialize or reserve against
the same allowance across all trigger types so concurrent jobs cannot each
spend the same balance. Keep the report/check alive after exhaustion.

Estimate run count from remaining usable minutes divided by measured matrix
cost, rounding down and exposing uncertainty about overhead, billing units and
future failures. Recompute the calendar forecast after extra label/manual runs,
retries or other account use; these advance exhaustion. Do not reduce device
coverage or count a partially completed matrix as a successful run.

**Illustration only:** if all 60 minutes were still available, each of three
devices cost exactly two minutes and no overhead/failures/extra runs occurred,
one full matrix would cost six minutes and ten full runs would fit. If the first
monthly date were 2026-11-01 UTC, the tenth would be 2027-08-01 and the first
unfundable, eleventh date would be 2027-09-01. None of those remaining-minute,
cost or calendar assumptions is a measurement or the implemented schedule.

## Installed-context capability spike

Before expanding the existing Playwright suite, prove these capabilities on each
of Android Chrome, Android Firefox and iPhone Safari Home Screen:

| Capability | Required evidence |
| --- | --- |
| Origin and production runtime | Stable trusted HTTPS hostname, matching `APP_ORIGIN`, working secure context/service worker, actual production manifest/assets through Local. An ignored TLS error or HTTP page is insufficient. |
| Authentication and preparation | Disposable test accounts/data, authenticated in the actual launch context; download Doc/Sheet/image bytes there. Do not infer iOS tab/install storage sharing or restore private storage from a fixture. |
| Install and entry point | Observed OS install/shortcut steps and exact item/Space-child target. Record supported fallbacks; a manifest menu is not universal per-item Home Screen support. |
| Offline control | Record the real control and device behavior, including `navigator.onLine` and app/API/socket unreachability. Android's airplane-mode capability and iOS's no-network profile are not identical. A stopped tunnel alone is not OS offline proof. |
| Ordinary restart | Terminate the actual browser/app, relaunch from Home Screen and repeat offline in the same reserved device session/profile. New device sessions are reset by the provider and do not test persistence. |
| Restore and cleanup | Reconnect, compare local/server state, restore networking and release device/tunnel even after assertion failure. Record any unsupported operation as unavailable rather than passing. |

If a required native operation is unavailable, retain a reproducible blocker and
evaluate an alternative physical-device runner capable of that operation.
Automate's documented native context makes this an execution question, not a
reason to declare the whole approach unsupported before trying it. A mobile tab,
desktop WebKit, viewport emulation or native wrapper cannot substitute for the
installed-context requirement.
