## Legacy decision 55: Atomic native restore and generation replacement

**Recorded:** 2026-10-18. **Status:** accepted; later engineering resolution replaces earlier
approach.
**Authority:** Owner restore semantics; agent public-API implementation resolution.
**Source:** [original decision #55](https://github.com/mxbaylee/spinel/issues/55).

**Question:** Should SPN-025 introduce a durable mapping from each Spinel document to replaceable
collaboration-unit generations, or wait for a documented SDK operation that can restore any retained
native snapshot in place?

**Options considered in the original source:**

A — obtain a documented vendor-supported arbitrary-snapshot restore path and verify it in the pinned
SDK or a separately reviewed upgrade; preserves current identity architecture but depends on that
API. B — build an application-owned logical-document-to-SDK-generation mapping with durable
replacement pointer, exact pre-state preservation, stale-request fencing, current ACL checks, client
remount and crash/retry tests; a larger migration affecting transport, history, images and backup. C
— limit restore to collaboration-era versions; this would exclude already retained native
checkpoints and is not recommended without explicitly changing acceptance.

**Outcome, rationale and current boundary:**

Restore must freeze/drain the live document, preserve an exact Before restore checkpoint, retain
stable logical IDs and reject stale/offline writes rather than silently merge them. Earlier comments
recorded a Sheet-only probe and warned against speculative migration; neither proved full restore.
The final engineering comment resolves the compatibility gap with public createUnitFromData and
replacement SDK generations, revision offsets and a durable logical-ID mapping. Bind restore
receipts to actor/item/checkpoint; stage and validate first, then atomically preserve pre-state,
switch the generation and queue cleanup. Cancel unfinished pre-switch attempts on restart, fence
stale units and deny raw SDK revert. Retained native checkpoints remain available; this agent
implementation conclusion is not a new owner authorization or a history-format discard.

**Persona tradeoffs recorded at the time:**

Owner needs every retained version to remain recoverable, including versions before collaboration
migration. Collaborator needs pre-restore edits preserved and stale/offline edits visibly fenced.
Operator benefits from supported SDK APIs and a small recoverable storage model; a generation
mapping increases lifecycle/backup complexity. Link guest needs the same current document-level
permission checks across history and any replacement generation, without old-unit access lingering.

**Source chronology:**

- [Comment 6251038147](https://github.com/mxbaylee/spinel/issues/55#issuecomment-6251038147): A Sheet collaboration-revision revert probe passed; arbitrary retained native snapshots, Docs/resources and crash/offline behavior remained unproved.
- [Comment 6252423674](https://github.com/mxbaylee/spinel/issues/55#issuecomment-6252423674): Owner discussion 2026-10-18 proposes freeze, drain, exact Before restore capture and refresh; it waives no retained data or acceptance.
- [Comment 6252452958](https://github.com/mxbaylee/spinel/issues/55#issuecomment-6252452958): Owner discussion 2026-10-18 removes the abstract owner-choice blocker, while arbitrary native compatibility remains an engineering gap. A speculative migration was not yet justified.
- [Comment 6253170879](https://github.com/mxbaylee/spinel/issues/55#issuecomment-6253170879): Agent engineering decision 2026-10-18 resolves that gap with supported generation replacement, stable logical identity, atomic pre-state/switch/receipt and deterministic restart cleanup. Verification was still required in PR #54.

## Legacy decision 68: Single SQLite runtime and consistent copies

**Recorded:** 2026-10-18. **Status:** accepted, pre-production implementation choice.
**Authority:** Agent storage compatibility repair.
**Source:** [original decision #68](https://github.com/mxbaylee/spinel/issues/68).

**Question:** Should Spinel share the SDK adapter's SQLite runtime rather than opening the same file
with node:sqlite and libsql in one process?

**Options considered in the original source:**

A — use the exact libsql runtime already used by the public SDK adapter for application connections
too; B — isolate the SDK in another process, adding RPC, lifecycle and memory costs; C — retain two
runtime copies despite the observed recovery failure.

**Outcome, rationale and current boundary:**

Use the exact selected libsql runtime across application and public SDK adapter so both share one
compatible database connection model. Repair integration without changing the schema; replace
node:sqlite and the earlier online-backup API with SQLite VACUUM INTO for a consistent copy. Backup
verification still requires actual restored collaboration state, snapshots, images and access
metadata. This supersedes the mechanism in decisions
[#2](SPN-001.md#legacy-decision-2-one-process-and-initial-sqlite-adapter),
[#36](SPN-030.md#legacy-decision-36-encrypted-nightly-recovery-bundle) and
[#37](SPN-012.md#legacy-decision-37-one-database-for-collaboration-recovery), not their durability
boundaries, and does not make SQLite a permanent backend requirement before launch.

**Persona tradeoffs recorded at the time:**

Operator needs reliable restart/backup with one small-host database; Owner needs preserved
documents; Collaborator needs accepted edits to survive recovery; Link guest needs unchanged
document access boundaries. All favor one runtime over independent lock registries. Browser-facing
permissions and document IDs are unchanged.
