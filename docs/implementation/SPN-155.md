## 🪲 Follow-up: the phone Doc replay race (rolled into this record, 2026-11-24)

**Date/status/source:** 2026-11-24, accepted; Owner, chat 2026-11-24. Hosted acceptance pending.

**Owner, chat 2026-11-24:** fix the failing `sync-production` test with the work that exposed
it, not as a separate ticket, so this follow-up has no ticket ID. SPN-155's phone Doc journey
reconnects from the file list and opens the Doc without waiting for background replay, by
design. On hosted Linux it produced "Your offline changes were saved as Offline doc (offline
copy, …)" instead of "Synced", so `failOnFlakyTests` turned `sync-production` red on main
([run 45463717032](https://github.com/mxbaylee/spinel/actions/runs/45463717032)) and on a
later PR run that did not touch `web/` or `e2e/`.

- **Product bug, not a fixture race.** Opening the editor stops the background replay. When the
  replay had already sent its request, the server committed it (revision 2 on the original) but
  the stop cut the replay off before the acknowledgement. The editor then resumed from the old
  revision, saw `stale` (offline mode deliberately never rebases) and saved a duplicate recovery
  copy with `possibleReplayCrash`. The Owner got the edit twice.
- **Fix** (`web/offline/replayHost.ts`): a stop request received while the replay holds a durable
  queue lets it finish saving (synced or failed) for up to 2 s before yielding. Opening the
  editor stops the replay twice (file list, then editor admission), and the second stop does not
  shorten the window. Unit test: `a stopped background replay keeps its sent request alive until
it %s, even when stopped twice` (run for `settles` and `times out`); it fails without the change.
- **Rejected:** deferring the editor's automatic recovery until the sent request resolves. In
  offline mode the client ignores receipts after a failure, so in a local trial the editor sat on
  "Needs attention" until the e2e test's 30 s expectation timed out (author-observed, not kept).
- **Evidence is author-run and local, not in the repo.** Method: a temporary, uncommitted line in
  the phone journey (`e2e/offline-editing.spec.ts`) sent `Emulation.setCPUThrottlingRate` rate 4
  through a CDP session after the download, then ran
  `SPINEL_E2E_PROJECT=sync-production CI=1 playwright test --project=sync-production -g "phone doc: durable edits" --repeat-each N --retries 0 --workers 1`.
  The server database (`test-results/sync-production/app.sqlite`, tables `spinel_sync_revisions`
  and `workspace_offline_recoveries`) was read with `sqlite3` after failing runs: the edit was
  revision 2 on the original and one recovery row existed. Counts:
  - Baseline, 4x: recovery copy in 12 of 12 runs.
  - First version of the fix (a repeat stop could still cut the window), 4x: 0 of 12 and 0 of 10.
  - Final version, 4x: 0 of 12. All 4x runs still failed later on SPN-155's `falseOffline` assertion.
  - Unthrottled: baseline 16 of 16 passed; first version 39 of 40 (the miss was `falseOffline`); final version 16 of 16.
- **Limits:** the 2 s bound is a ceiling, not a guarantee; a replay that cannot finish in 2 s
  still yields and can still leave the stale base. Every stop received after the replay has attached now waits up to 2 s, including account and
  visibility changes. SPN-155's `falseOffline` assertion still fails under the throttle (12 of 12
  at 4x, before and after the first version of this fix); that is a separate hosted-load
  question. Hosted `sync-production` is still pending.

**All four personas:** Owner and Collaborator no longer get a duplicate recovery copy when they
open a Doc right after reconnecting, at the cost of up to 2 s before the editor opens in that
case. Link guest is unaffected (signed-in offline replay only) and gains no access. Operator sees
no new diagnostics; the recovery copy count simply stops rising from this race.
