## Legacy decision 69: Bounded native file transfer

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Agent import/export judgment and comment clarification.
**Source:** [original decision #69](https://github.com/mxbaylee/spinel/issues/69).

**Question:** How should native Univer files carry images and stay within the small-server memory
budget?

**Options considered in the original source:**

A — Keep the native Univer JSON shape, replace supported image sources with standard data URLs, cap
a portable file at 20 MiB and native content at the existing 10 MiB limit, decode/validate images
before one atomic publish. B — Introduce a ZIP container with a larger binary budget, adding a new
format and archive processing.

**Outcome, rationale and current boundary:**

Support complete native JSON with inline image data, a 20 MiB transfer limit and existing 10 MiB
native-content limit, one active transfer, bounded decoding and atomic publication. Reject external
image URLs and preserve existing account access/guest export restrictions. The follow-up sets import
dimensions: at most 100 sheets, 100,000 rows and 1,024 columns per sheet, 250,000 rows and 4,096
columns across the workbook, 100,000 populated cells, and one million Doc characters, with all
grid/layout indexes in bounds. These are conservative import budgets, not measured capacity.
Validate the complete candidate before creating a visible file; failed or revoked creation leaves no
partial document.

**Persona tradeoffs recorded at the time:**

The Operator needs bounded memory and no remote URL fetches; the Owner needs a portable, lossless
document copy; the Collaborator needs current accepted edits and unchanged access boundaries; the
Link guest must gain no dashboard or private-image access through file routes.

**Source chronology:**

- [Comment 6253957018](https://github.com/mxbaylee/spinel/issues/69#issuecomment-6253957018): Conservative import expansion limits prevent tiny JSON from allocating enormous native grids. Bounds are not measured editor capacity; reject before publication and never truncate.

## Legacy decision 70: Original browser printing

**Recorded:** 2026-10-18. **Status:** superseded.
**Authority:** Historical client-print integration judgment.
**Source:** [original decision #70](https://github.com/mxbaylee/spinel/issues/70).

**Question:** Which supported PDF path should Spinel expose?

**Options considered in the original source:**

A — Register the published print plugins and use their public menu/facade APIs, retaining all
checks, limits and watermarks. B — Build a separate snapshot-to-HTML/PDF renderer with its own
pagination, fonts, tables and drawings, increasing scope and fidelity risk.

**Outcome, rationale and current boundary:**

The earlier choice used the native Pro client print path to avoid an extra renderer/service, with
current read access and preserved live edits. Decision
[#103](SPN-075.md#legacy-decision-103-direct-pdf-for-every-current-reader) replaces the product
target with direct watermark-free PDF download and removal of the Pro print dependency. That
replacement remains governed by its own implementation/verification; the historical print result is
not proof of PDF fidelity. PDF access for current readers does not extend native-file export to
guests.

**Persona tradeoffs recorded at the time:**

The Operator wants no additional print server, renderer process or paid service; the Owner wants
native layout and images in a readable copy; the Collaborator needs printing to preserve live edit
state; the Link guest must retain their document-only access boundary when link sharing is added.
