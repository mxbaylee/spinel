### 🧭 Implementation recommendation and retained scope

Proceed with the bounded nonvisual host; complete effort remains **L**. No new
native engine or parallel sync protocol is justified by this probe. Reuse
`NativeReplica` and introduce a narrow binding attachment path for an already
created unit, retaining `loadSpinelDocument` for ordinary editor creation. Reuse
the binding's `OfflineSession`, scoped authority, maintenance, immutable request
and recovery behavior. Keep one pending item active per prepared account.

The application lifecycle still needs a quiet/drain/join boundary: stop transport
and new event work, finish or fence in-flight persistence, then release the item
writer and dispose the host. Existing `SyncClient.persistNow()` provides the
commit barrier while alive; synchronous binding/session `dispose()` alone is
not a verified handoff. Extend existing same-tab editor admission to request and
await background replay relinquishment, with admission reservation preventing a
new background writer from slipping in. Other-tab contention remains nonblocking.
Do not wrap `OfflineSession.activate()` inside `withOfflineItemWriter()` because
both would try to acquire the same item Web Lock.

The coordinator should live with existing offline application owners, react to
account-scoped online/foreground/durable changes, exclude the foreground item,
and stop or retain attention on failures. Account switch, removal, revocation,
recovery-copy behavior, image canonicalization, transient disconnect, missing
storage and failed acknowledgement persistence still need integrated negatives.
The existing native recovery/resource tests own specialized authored structures;
this bounded text/cell probe does not claim new drawing/formula/image coverage.

All four persona tradeoffs remain as recorded above: bounded resource ownership
for Operator; durable, authority-safe content and usable foreground editing for
Owner and Collaborator; no private offline capability for Link guest. Actual
file-list replay, browser/second-device evidence and installed-phone verification
remain open. No owner decision or synchronous question is required to implement
these existing contracts; physical access remains an acceptance prerequisite.

## ✅ Accepted agent architecture and first implementation

**Decision:** accepted by the delivery manager under the standing four-persona
authority, 2026-11-13, following capability commit
`0c4816955df9f8e2e16e7bc867c62e08853af150`. Human product sign-off is not required.
Implement a shared account-scoped, event-driven coordinator, lazily loading one
bounded nonvisual native host at a time. Reuse `NativeReplica`, the existing
sync binding and `OfflineSession` rather than introducing another native engine,
uploader, queue or authority protocol. Full outcome remains **L**; this first
production slice has not exposed a wider architecture requirement.

A distinct account-level Web Lock bounds replay across tabs as well as mounted
file-list surfaces. It does not replace or nest acquisition of the item lock.
A same-account remount waits for the retiring owner's complete run to release
that account lock. A contended tab skips replay until a later foreground or
reconnect event; no polling loop waits for ownership.

Foreground editor and device-maintenance admission reserve their place before
requesting replay to stop. The existing binding gains a quiet/commit/dispose
boundary: stop transport and event producers, join native checkpoint persistence,
then release the item writer. Background session activation uses that reservation
without acquiring the same Web Lock twice. Contention in another tab remains
nonblocking. Account changes invalidate the same preparation/read/HTTP fences.

Only existing queued downloads are eligible. Offline creation rules remain with
their current owner. Pending conflicts and lost acknowledgements retain the
existing conservative attention policy. The nonvisual host disables automatic
recovery-copy publication; the visible recovery entry remains responsible for
that existing flow. It does not invent a hidden editor or navigate the file list.
No visible component or new state is introduced by this slice.

**All four personas:** Operator gets a single bounded native pair per account,
lazy loading and teardown rather than idle polling. Owner keeps durable work and
foreground editing priority; disk failure cannot release an unjoined normal
handoff as successful sync. Collaborator receives exact native content through
the existing server acknowledgement path, with revocation checked before replay.
Link guest never enters the account-only file-list owner or private device store.
