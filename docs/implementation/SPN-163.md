# SPN-163 — show which files still need to sync, without asking for action

## 🔔 Decision: ordinary pending work is informational

**2026-11-18, agent delivery judgment** under the [standing four-persona delegation](grooming-2026-10-26.md#agent-decisions-and-visual-review).

Observed in the SPN-156 own-phone run (2026-11-16): a downloaded Doc with a saved offline edit showed the
**Offline changes on this device** banner with a **Recover** action and no per-row badge. Root cause:
`offlineState` in `web/Dashboard.tsx` returned `not-synced` only for offline-created items, so an existing
downloaded file with pending edits fell through to `available`, while the banner treated every pending
non-creation item as recovery. The perceived lag is a hypothesis from the code path, not measured, pending the own-phone repeat: the full page load to `/?offlineRecovery=…` plus an
IndexedDB read that showed only a status line.

### Taxonomy

`downloadSummary` now sets `retained` for work that needs a deliberate choice: unverifiable data, an
in-progress copy, a failed replay, or retained recovery state. Pending work without it syncs on its own.

| State                                  | Row cue            | List banner                            |
| -------------------------------------- | ------------------ | -------------------------------------- |
| Ordinary pending (edits, no failure)   | **Not synced yet** | **Needs to sync**, informational, none |
| Retained (uncertain, failed, recovery) | unchanged          | **Offline changes**, **Recover** links |
| Offline-created, pending               | **Not synced yet** | unchanged                              |

Pending files are pinned first in whichever listing is shown (stable sort). The badge is text, never
interactive; the notice uses `role="status"` with the accent on icon and word only, per the design playbook.
Replay, authority and checkpoint behavior are unchanged (out of scope).

### Personas

- **Owner:** nothing is asked of them while edits send by themselves; recovery stays for real recovery. Pinning
  pending files above folders trades a stable folder-first layout for a visible cue that something is waiting;
  the cue clears on acknowledgement, so the layout returns to normal without action.
- **Collaborator:** sees the same state for their own edits, in shared files and folders alike.
- **Operator:** no server, authority, maintenance or diagnostics change; `retained` is a client-only summary flag.
- **Auditor:** no change to what is recorded; the notice is a read-only reflection of existing local state.

### Lead: "not yet downloaded" cue

Recorded, not built. Before going offline nothing says a document is not yet downloaded. A cue needs a
download-intent model that does not exist yet, so it is deferred to a future ticket if the owner still wants it.

### Failure and recovery transitions

The pending notice updates only `pending` (`applyPendingChange`). Delivery leaves `retained` alone, since it is
inert while nothing is pending and a recovery record that outlives delivery keeps its Recover link. New work on a
settled row starts ordinary, so it drops the stale mark. The hook re-reads the summary on every start or finish
of pending work, so every row is classified from the stored truth within 250 ms. `saveCheckpoint` in
`web/offline/offlineStore.ts` also publishes a plain change notice when a checkpoint moves a file into or out of
a failed or recovery state (`retainsWork`) while its pending flag does not change, so the hook re-reads the
summary and the file moves from the notice to the **Offline changes** banner without waiting for a foreground
refresh. Owner approved this one checkpoint-write notice, chat 2026-11-19; it changes no replay, authority or
checkpoint behavior. A write that changes neither flag emits nothing, so keystroke saves stay cheap.

The **Needs to sync** notice appears on the root list only and counts every pending file, including ones in
folders or Spaces; row badges and ordering apply wherever the file is listed. Root-only is a decision: the
count answers "is anything on this device waiting?" in one place, so it is not repeated inside folders. A
folder-view story is not added because local-mode folders do not open with the empty Storybook API
(`PendingEditsInFolder` failed for that reason on 2026-11-19). Observed diagnostic operations are unchanged:
the new notice is a local UI event, not a diagnostic emission, and no emitter, sync or replay operation is
added or altered.

### Notice and the design playbook

The playbook allows one banner per view, for conditions present on load, and puts changing status in the header
slots. The **Needs to sync** notice follows pending state while the view is open, so it is a status line in the
view body, not the post-restore banner, and it may sit above the **Offline changes** section, which is a list of
actions, not a banner. This is a deliberate reading, not a playbook change: the playbook edit belongs in its own
PR, so adding a line there for this pattern is left as an owner step.

### Retained rows keep their row cue

A retained pending row keeps its existing row state and is listed in the **Offline changes** banner with a
Recover link: that banner is the single place that asks for a choice, so a second row cue would repeat it.

### Spaces

A Space carries no edits itself; its pages do. `itemNeedsSync` in `web/OfflineStatus.tsx` treats a Space as needing
sync when any of its page copies does, so the row shows **Not synced yet**, the notice count and the pinned order
agree, and a Space with pending pages is not hidden behind **pages available**.

### Ordering

Pending files are pinned above everything else in the listing, including folders: the ticket asks for them
near the top, and a pinned file is the cue that something is waiting. Unverifiable (`uncertain`) work keeps its
recovery entry when a delivery notice arrives, since its pending state cannot be cleared by a notice.
