# SPN-163 — one sync status for files that haven't reached the server

## 🔔 Decision: a single Sync status banner with three phases

**2026-11-18, agent delivery judgment; redesigned 2026-11-20 on the owner's direction** under the
[standing four-persona delegation](grooming-2026-10-26.md#agent-decisions-and-visual-review).

Observed in the SPN-156 own-phone run (2026-11-16): a downloaded Doc with a saved offline edit showed the
**Offline changes on this device** banner with a **Recover** action and no per-row badge. Root cause:
`offlineState` in `web/Dashboard.tsx` returned `not-synced` only for offline-created items, so an existing
downloaded file with pending edits fell through to `available`, while the banner treated every pending
non-creation item as recovery. The perceived lag is a hypothesis from the code path, not measured.

The first design (a **Needs to sync** notice beside a separate recovery list) read as two redundant dialogs. The
owner asked for one component, so both are replaced by `SyncStatus` (`web/SyncStatus.tsx`).

### Phases

| Phase                  | Meaning                                                    | Line text       | Action                           |
| ---------------------- | ---------------------------------------------------------- | --------------- | -------------------------------- |
| 📤 **Waiting to sync** | Saved edits send by themselves; no connection yet          | Waiting to sync | **Try now** (recheck connection) |
| 🔄 **Syncing now**     | Online and sending                                         | Syncing now     | none                             |
| ⚠️ **Needs attention** | Retained work (uncertain, failed, recovery) needs a choice | Needs attention | **Recover _name_**, one per file |

- **Overlap rule:** waiting and syncing follow the connection, so they never coexist. Needs attention can sit beside
  either, and every phase that applies gets its own line (attention first), not one winner.
- **One action line.** The banner has status lines and one wrapping row that holds only actions, each a button-sized
  (44 px) target. Recover is a link styled as a button, since it navigates; Try now is a real button.
- **Try now** keeps saying "syncing" while already online until the probe answers, so the banner does not flicker. It
  dispatches `spinel-connection-check` (`CONNECTION_CHECK_EVENT`, `web/connectionState.ts`). The existing
  `/api/health` probe and the replay owner (`web/offline/replay.ts`) both listen, so one press rechecks the
  connection and, if it succeeds, retries the queue. No new endpoint, replay rule or authority path.
- **Syncing is connection-driven**, not a replay status output: online with pending work reads as syncing until the
  pending flag clears. A replay that is skipped (read-only, uncertain, foreground item) therefore still reads as
  syncing while online; the rows stay pinned until acknowledged. Recorded as a known simplification.
- **No distinct colour** for attention (owner, chat 2026-11-20): the accent sits on icon and word only; the shape
  (triangle, arrow, rotating arrows) and the word carry the difference. The syncing arrows stop spinning under
  reduced motion.
- `role="alert"` when attention exists, otherwise `role="status"`; `aria-label="Sync status"`. Nothing renders when
  nothing is saved on the device.

### Taxonomy

`downloadSummary` sets `retained` for work that needs a deliberate choice: unverifiable data, an in-progress copy,
a failed replay, or retained recovery state. Pending work without it syncs on its own.

| State                                  | Row badge           | Banner line                       |
| -------------------------------------- | ------------------- | --------------------------------- |
| Ordinary pending, offline              | **Waiting to sync** | Waiting to sync + Try now         |
| Ordinary pending, online               | **Syncing now**     | Syncing now                       |
| Retained (uncertain, failed, recovery) | **Needs attention** | Needs attention + Recover         |
| Offline-created, pending               | **Not synced yet**  | unchanged (creation owns its cue) |

Pending files are pinned first in whichever listing is shown (stable sort). Badges are text, never interactive.
Replay, authority and checkpoint behavior are unchanged apart from the extra wake event.

Open edge (pinned by a unit test): an ordinary pending file that is read-only or uncertain is not excluded by `needsSync`, so it reads as
Waiting or Syncing. Uncertain work is already `retained`, so it lands in Needs attention; a read-only pending copy is
the remaining case and is left as is.

### Personas

- **Owner:** one place to see what is waiting and one button to act; recovery appears only for real recovery. Pinning
  pending files above folders trades a stable layout for a visible cue; it clears when delivery is acknowledged.
- **Collaborator:** the same status for their own edits, in shared files and folders alike.
- **Operator:** no server, authority, maintenance or diagnostics change; `retained` is a client-only flag. Try now is
  a local event that triggers the existing probe, so no new diagnostic emission or emitter-inventory change.
- **Auditor:** no change to what is recorded; the banner reflects existing local state.

### Lead: "not yet downloaded" cue

Recorded, not built. A cue needs a download-intent model that does not exist yet; deferred to a future ticket.

### Failure and recovery transitions

The pending-change event updates only `pending` (`applyPendingChange`). Delivery leaves `retained` alone, since it is inert
while nothing is pending and a recovery record that outlives delivery keeps its Recover button. New work on a settled
row starts ordinary. The hook re-reads the summary on every start or finish of pending work, so every row is
classified from the stored truth within 250 ms. `saveCheckpoint` in `web/offline/offlineStore.ts` also publishes a
plain change event when a checkpoint moves a file into or out of a failed or recovery state (`retainsWork`) while its
pending flag does not change, so a file moves between lines without waiting for a foreground refresh. The event
carries `checkpoint: true`, and the editor's sync binding (`downloaded` in `web/spinelSync.ts`) ignores it; without
that guard the binding re-persisted its own recovery write and broke the recovery e2e (`offline-recovery.spec.ts`,
2026-11-19). Owner approved this one checkpoint-write event, chat 2026-11-19. A write that changes neither flag emits
nothing, so keystroke saves stay cheap.

### Placement and the design playbook

The banner is on the root list only and counts every pending file, including ones in folders or Spaces; row badges
and ordering apply wherever the file is listed. Root-only is a decision: it answers "is anything on this device
waiting?" in one place. A folder-view story is not added because local-mode folders do not open with the empty
Storybook API.

The playbook allows one banner per view, for conditions present on load, and puts changing status in the header
slots. The sync status follows pending state and the connection while the view is open, so it is a status region in
the view body, and it is the only banner in the view. This is a deliberate reading, not a playbook change; adding the
status-line pattern to the playbook belongs in its own PR and is left as an owner step.

### Spaces

A Space carries no edits itself; its pages do. `itemNeedsSync` in `web/OfflineStatus.tsx` treats a Space as needing
sync when any of its page copies does, so the badge, the banner count and the pinned order agree.

Pending: hosted Storybook and e2e, and independent visual review of the new captures. The own-phone observation and
Recover-lag measurement are waived by the owner (chat 2026-11-19). A Space story and a rendered hook test are not
added (no fixture for a Space copy, no `renderHook` tooling); the decisions are tested through the pure helpers.

`OfflineRecoveryEntry` keeps its own editor frame; its context label now reads "Needs attention: changes saved on this
device", so the removed banner's name no longer appears anywhere. Try now ends when the probe answers
(`spinel-connection-checked`, sent by `watchServerConnection` after its probe); a 2.5 s timer is only a fallback.
`pendingBadge` in `web/OfflineStatus.tsx` is the one place that maps a stored copy to its row badge.

Notes from review: files that need attention are not pinned first (`pendingFirst` follows `needsSync`); their badge
and the banner's Recover button already ask for the choice, and pinning is reserved for ordinary pending files.
The syncing row badge is static; only the banner icon rotates, and it stops under reduced motion. The one-line
`SPN-054.md` edit points its old "Offline changes on this device" description at this ticket. The playbook
status-line PR is an owner step with no backlog ticket yet; create one with `npm run backlog:new` if wanted.
Try now's listener and fallback timer are one effect in `Dashboard.tsx`; an offline browser answers in the same
tick, so the button can clear at once.

Visual review notes (2026-11-20): the banner covers saved edits only. An offline-created file whose folder is gone
shows **Needs attention** in its row with the fix in the row text and its menu (**Choose another folder…**, SPN-051),
so it has no Recover button and is not pinned. Needs attention rows keep their list position by design. "Needs a
connection" is the existing fifth badge for files that can't open offline. Long names wrap inside the button, which
now has vertical padding so the label never touches the border.
