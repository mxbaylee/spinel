## Legacy decision 31: Collaboration independent of the soak

**Recorded:** 2026-10-18. **Status:** accepted, historical scheduling choice.
**Authority:** Owner, chat 2026-10-17.
**Source:** [original decision #31](https://github.com/mxbaylee/spinel/issues/31).

**Question:** Should production collaboration wait for the full limits experiment?

**Options considered in the original source:**

A — allow authenticated collaboration to be selected by normal points while keeping the experiment
independent. B — wait for the complete duration experiment before integration.

**Outcome, rationale and current boundary:**

Remove SPN-010 as a prerequisite of authenticated SPN-012, while preserving ordinary score-based
order. Neither the short matrix nor this scheduling change proved unrestricted licensing or a
completed soak. Production still needed current grants, trusted identity, two-user editing,
reconnect and data retention. Use public Pro APIs without bypassing licensing. The disposable
permissive harness stays separate. Decision
[#76](SPN-010.md#legacy-decision-76-cancel-the-duration-soak) later cancels the experiment; this
record does not restore that retired requirement.

**Persona tradeoffs recorded at the time:**

The Operator needs one authenticated Node service with persistent SQLite and explicit licensing
behavior. The Owner wants working co-editing now and no lost existing documents. The Collaborator
benefits from real-world use revealing reachable limits, with clear save/connection states. The Link
guest must not inherit the spike's permissive authorization.

## Legacy decision 37: One database for collaboration recovery

**Recorded:** 2026-10-18. **Status:** superseded in part.
**Authority:** Agent collaboration storage judgment.
**Source:** [original decision #37](https://github.com/mxbaylee/spinel/issues/37).

**Question:** Should collaboration use the existing application SQLite file so recovery remains a
single consistent database backup?

**Options considered in the original source:**

A — use the same SQLite file with the public Univer adapter and a guarded, idempotent per-document
migration; B — use a separate collaboration database and extend the archive format/consistency
protocol.

**Outcome, rationale and current boundary:**

Use the public collaboration SQLite adapter against the application database, avoiding inconsistent
multi-database backups. Guard migration idempotently, preserve the current native state as the
initial unit and disable legacy snapshot writes once migration begins. Enforce current grants on
reads, joins, submissions and revocation and verify encrypted recovery of acknowledged edits.
Decision [#68](SPN-025.md#legacy-decision-68-single-sqlite-runtime-and-consistent-copies) replaces
the original driver/online-backup mechanism; one database was an implementation choice, not a
permanent storage requirement or permission to modify closed-source SDK internals.

**Persona tradeoffs recorded at the time:**

Operator benefits from one encrypted file and the proven offsite recovery path; Owner keeps existing
documents and acknowledged edits through migration; Collaborator needs the same durable shared state
on reconnect; Link guest needs existing authorization boundaries to remain authoritative.

## Legacy decision 43: Authenticated collaboration boundary

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Agent collaboration integration judgment.
**Source:** [original decision #43](https://github.com/mxbaylee/spinel/issues/43).

**Question:** Keep live authorization, snapshot validation and permanent deletion under Spinel
control?

**Options considered in the original source:**

A — enforce access at ingress, room join, presence, and commit; evict invalid recipients before
broadcasts; validate candidate native data; write a durable deletion outbox atomically with
workspace deletion and retry SDK hard-delete. B — trust client state or delete only workspace
metadata, weakening confidentiality or retention.

**Outcome, rationale and current boundary:**

Authenticate every protocol operation, validate request origin and WebSocket admission, and
re-resolve grants for join, presence and commit. Validate candidate native state and enforce active
accounts; revoke live room access when grants change. Use durable retryable SDK cleanup/deletion
outboxes rather than awaiting SDK work inside a SQLite transaction. One process with explicit limits
and ordinary backed-up storage is preferable to disconnected authorization paths or new
infrastructure.

**Persona tradeoffs recorded at the time:**

Operator gets one process, explicit limits and retryable cleanup. Owner keeps native data validation
and recovery guarantees. Collaborator gets immediate room eviction when access changes, without
losing confirmed changes. Link guest receives no implicit authenticated access; link identity
remains separate work.

## Legacy decision 44: Cold offline layout assets

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Agent supported-integration judgment.
**Source:** [original decision #44](https://github.com/mxbaylee/spinel/issues/44).

**Question:** Should layout dictionaries ship with the editor renderer so an open document can edit
text offline?

**Options considered in the original source:**

A — use the documented bundler grouping option to include the renderer and its dictionaries in one
eagerly loaded renderer chunk; B — depend on runtime internal preload APIs; C — allow the first
offline text edit to fail.

**Outcome, rationale and current boundary:**

Bundle open-source layout dictionaries through the public bundler/grouping configuration so the
first offline text edit works even in a language not previously typed. This accepts initial
asset/build cost in exchange for deterministic offline layout. Do not patch or preload private Pro
internals. Existing access and guest scope remain unchanged, and loading layout assets alone is not
offline document availability.

**Persona tradeoffs recorded at the time:**

The Operator prefers a deterministic build without modifying SDK packages; the Owner and
Collaborator need their first offline text edit to work, including text in a language not typed
previously; Link guests need the same dependable viewer/editor assets without broader document
access.

## Legacy decision 45: Offline ephemeral cursor handling

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Agent supported-integration judgment.
**Source:** [original decision #45](https://github.com/mxbaylee/spinel/issues/45).

**Question:** How should cursor publication behave while a collaboration session is offline?

**Options considered in the original source:**

A — return app-owned forwarding session handles that omit only ephemeral UPDATE_CURSOR events while
offline; all changesets, joins, status streams and other operations delegate unchanged. B — disable
the native collaboration UI and implement its presence/rendering again, increasing scope and
regression risk.

**Outcome, rationale and current boundary:**

Wrap the public client forwarding session and suppress only ephemeral UPDATE_CURSOR sends while
offline. Forward every durable mutation unchanged. This avoids uncaught stale-cursor errors without
discarding edits, altering the server protocol or patching closed-source SDK code. Guests retain
their ordinary current-link authorization; the wrapper itself grants no offline account capability.

**Persona tradeoffs recorded at the time:**

The Operator benefits from supported integration without modifying closed-source packages. The Owner
and Collaborator need offline edits preserved and no uncaught error from stale cursor updates. Link
guests retain the same server-side access checks.

## Legacy decision 46: Guarded open-source paragraph repair

**Recorded:** 2026-10-18. **Status:** accepted, version-specific workaround.
**Authority:** Agent correctness repair.
**Source:** [original decision #46](https://github.com/mxbaylee/spinel/issues/46).

**Question:** How should Spinel handle the pinned open-source core's paragraph replacement
composition defect?

**Options considered in the original source:**

A — keep a narrow TypeScript install-time repair of Apache-2.0 @univerjs/core 1.1.0, with whole-file
SHA-256/version guards, ESM/CJS parity, original license notice and tests comparing sequential
versus composed application. B — ship incorrect saved formatting. C — block all collaboration until
an upstream release.

**Outcome, rationale and current boundary:**

Repair open-source Univer 1.1.0 paragraph REPLACE behavior while preserving stable paragraph IDs,
distinguishing explicit empty formatting from omitted fields and leaving COVER behavior intact.
Pin/check expected version and hashes, patch both relevant module distributions idempotently, and
fail clearly if the upstream shape changes. This narrow open-source repair is not authority to alter
Pro code. SPN-099 tracks later upstream-removal work; until then the fixed public behavior and
reproducible installs are required.

**Persona tradeoffs recorded at the time:**

The Owner and Collaborator need formatting after save/reconnect to match their live edits. The
Operator needs reproducible installs and upgrades that fail clearly if a patch no longer applies.
Link guests benefit from the same unmodified access boundary; this repair does not change
permissions.

## Legacy decision 47: Truthful Saved acknowledgement

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Agent durability repair.
**Source:** [original decision #47](https://github.com/mxbaylee/spinel/issues/47).

**Question:** When should a collaboration editor report ready or fully saved?

**Options considered in the original source:**

A — warm the candidate validator during preparation and await the recovery-cache flush before
reporting saved; B — accept a slow first edit and advertise saved immediately on acknowledgement,
leaving an unsafe reload window.

**Outcome, rationale and current boundary:**

Warm the validator and await the public recovery-cache flush before reporting Saved. Protect newer
edits with generation checks and never clear pending state merely because an earlier operation
completed. The first shared edit and reload after acknowledgement must preserve exactly the
confirmed native data. Bounded initialization is a performance concern, not a reason to skip
validation; later app-owned outbox work in decision
[#97](SPN-039.md#legacy-decision-97-app-owned-offline-outbox) must retain this truthful durability
contract.

**Persona tradeoffs recorded at the time:**

The Operator needs bounded initialization without dropped validation. The Owner needs a reload after
“All changes saved” to preserve exactly the acknowledged document. The Collaborator needs the first
shared edit to arrive within a second and later edits to keep their navigation guard. Link guests
need the same access checks before and after asynchronous work.

## Legacy decision 48: Bounded strict browser validation

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Agent test-resource judgment.
**Source:** [original decision #48](https://github.com/mxbaylee/spinel/issues/48).

**Question:** Should development and production browser checks keep both app servers running at
once?

**Options considered in the original source:**

A — run development and production sequentially with only the matching server alive and separate
disposable databases/traces; B — retain both app processes throughout every test; C — loosen latency
thresholds.

**Outcome, rationale and current boundary:**

Run development and production browser servers sequentially, bound child fixtures and use
first-retry traces plus fail-on-flaky behavior. Keep the existing strict
first-edit/save/reload/offline assertions and fixed-source no-watch development fixture. Do not
relax the 1000 ms latency target or replace a failed workload with an unsupported pass. Resource
sequencing changes how evidence is obtained, not required behavior.

**Persona tradeoffs recorded at the time:**

The Operator needs reproducible checks within a small machine's resources. The Owner and
Collaborator need the same strict first-edit latency, save/reload and offline recovery tests in both
builds. Link guests need all denial and revocation checks preserved, regardless of how test
processes are scheduled.
