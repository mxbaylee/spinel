## 🗂️ Rendered contents fence

**2026-11-03 — implementation checkpoint, agent judgment.**
`openPreparedFolder` now waits for the requested view's `Folder contents` list
to be attached after retaining its heading and New-button assertions. Dashboard
mounts that list only after the current folder response finishes and populates
`views.current`; a pending request renders the loading state instead. Attachment
is the appropriate signal because the existing callers prepare an empty folder,
whose list can have no visible area. No production behavior or catalog persistence
code changes. The existing default five-second expectation bound and 180-second
scenario deadline remain unchanged.

Two controls extend the existing `e2e/offline-creation.spec.ts` browser suite:

- **Held, then released:** hold only the exact shared-folder GET. Observe the
  heading, New button and loading state while the offline continuation has not
  begun. Release the response; preparation must then complete, the browser must
  become offline, and the actual empty folder contents must remain rendered.
- **Withheld:** keep that GET pending through the existing expectation bound.
  Require the specific contents-readiness error at 5,000 ms, no offline
  continuation, an online browser and the still-pending loading state. Release
  the owned route in cleanup, await preparation and route completion, and close
  the existing fixture on both paths.

These controls exercise the actual Dashboard preparation boundary. They add no
scenario retries, sleeps, response recovery, timeout increases, native-input
substitutes or weakening of the original creation, reload, identity, access,
retained-content and single-publication assertions. SPN-120's general cleanup
and first-cause work remains separate.
