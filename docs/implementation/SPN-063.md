# SPN-063: storage choices and repeatable recovery

**Recorded:** 2026-10-27. **Status:** accepted SQLite/no-database-adapter decision;
recovery implementation remains proposed.
**Authority:** agent analysis following the owner's 2026-10-27 request to compare
SQLite, database adapters and backend-specific backup approaches before building
SPN-063. The owner values portable storage and straightforward setup for a less
experienced Operator, then directed: if SQLite's capacity is acceptable, retain
it with no adapter pattern and write up the limits first. Agent analysis accepts
that direction for the intended deployment using the capacity evidence below.
Recurring recovery verification and a measured production operating envelope
remain implementation work. The owner's subsequent backup-options discussion
permits destination adapters while retaining one database engine; the proposal
below distinguishes those boundaries.

**Scope:** documentation and bounded, synthetic local experiments. Keep
[SPN-063](../todo/SPN-063.md) open, in the launch phase, with its existing
acceptance. Public launch remains dependent on verified recovery. No cloud
resources, production data, secrets, deployment changes or database adapters are
created by this investigation.

## Recommendation and decision boundary

### Accepted decision: keep SQLite without database adapters

**Decision:** retain **local SQLite with one application instance** and implement
SPN-063 directly against its existing encrypted recovery path. Introduce **no
database-engine adapters or backend-selection setup flow**. This supersedes the
initial proposal to leave backend selection open and define general persistence
and recovery-provider abstractions. A narrow backup-destination boundary may
support manual downloads and configured S3-compatible storage, as requested in
the owner's later follow-up. Owner direction and agent assessment, 2026-10-27.

It gives this roughly two-person workspace a useful property: accounts, native
documents, images, history and access state can be recovered at one database
snapshot boundary, without running a separate database server. Preserve the
existing encrypted offsite bundle while measuring its limits. The conclusion is
about this product and its operating model, not a general ranking of databases.

The [capacity writeup](SPN-063-capacity.md) separates SQLite's engine limits from
Spinel's current request budgets and from unmeasured production capacity. The
actual build's configured file ceiling is approximately 16 TiB; application
listing, native-model work, image/history growth and recovery resources arrive
much earlier. A bounded metadata experiment found indexed lookups remained
similar at 1,000/10,000/100,000 rows, while full listing took 54.617/843.349 ms at
1,000/10,000 and refused 10,001 items. These are narrow observations, not a
supported document/user count or sustained throughput result.

Retain existing concrete classes and correctness contracts, including
`DatabaseSync` and `SyncStorage`; this decision does not remove existing
interfaces or freeze dependency/security maintenance. SQLite snapshot/restore
remains concrete; archive transport can vary independently. Launch still
requires recovery acceptance and representative
two-editor measurements; keeping SQLite is not a waiver of those gates.

The options below preserve the requested comparison. **Managed PostgreSQL** is
a future candidate if a measured requirement warrants reopening this decision.
No challenger prototype or second backend is required merely to finish SPN-063.

### Conditions that would change the recommendation

| Observed requirement or failure | Next comparison |
| --- | --- |
| Nightly recovery points lose too much acknowledged work | More frequent bounded SQLite snapshots versus continuous SQLite replication versus managed PostgreSQL PITR; compare encryption and complete recovery, not just upload frequency. |
| Snapshot or integrity work disrupts two active editors | A bounded isolated worker using the same supported SQLite runtime versus a different snapshot mechanism; change databases only if the measured problem remains. |
| The Operator cannot complete a cold restore reliably | Improve packaging and the recovery command, then compare a provider-managed restore using the same novice task and full application acceptance. |
| Persistent write contention or required multiple application writers | Prototype PostgreSQL domain transactions and distributed collaboration ownership before promising horizontal scale. |
| A host outage must recover automatically within minutes | Compare the entire application, connection routing, database and recovery control plane. Database failover by itself is insufficient. |

### Proposed backup options and assisted restore

**Status:** proposed, 2026-10-27. **Source:** the owner's follow-up requesting
manual admin downloads, automatic S3/DigitalOcean destinations, per-database
retention/configuration, UI restore and lock/unlock/scheduled downtime messaging.
Agent recommendation and detailed rationale are in
[backup options and assisted restore](SPN-063-backup-options.md).

Keep the full application database as one **workspace** recovery dataset.
Configure **diagnostics** separately: propose seven-day live-event retention,
manual export, and automatic backup off by default. Live-data expiry, remote
backup retention and document history are independent policies. Manual workspace
download and automatic backup are complementary; both use the same encrypted,
versioned bundle. AWS S3 and DigitalOcean Spaces can be tested presets of one
destination implementation, extending the existing remote-storage seam.

Deployment owns policy and secret references; the UI presents safe effective
configuration, creates/downloads backups and prepares a selected or uploaded
bundle. Routine consistent backups do not require a maintenance window. Assisted
live restore requires a server-enforced edit pause, drain, external operation
journal, controlled stop/replacement/restart, security reconciliation and rollback
evidence. The application's auth database is itself being replaced, so the
recovery control path must survive outside it. Scheduled notices communicate an
explicit time/zone; they do not implicitly authorize destructive restoration.

| Persona | Proposed effect and tradeoff |
| --- | --- |
| Operator | Manual download and tested destination presets simplify routine operation; deployment remains the configuration source of truth. Assisted restore adds a supervisor and recovery-control lifecycle, so stage it after the verifier instead of hiding that complexity in an HTTP endpoint. |
| Owner | Preserve one coherent workspace and independent recovery copies. Make restore time/data loss explicit; encrypted export does not grant an ordinary Operator content browsing. |
| Collaborator | Advance notice and acknowledged/pending-edit status reduce surprise. Every write path must obey pause and recovery fencing, including offline retries. |
| Link guest | Receive a minimal maintenance notice without private backup details; old guest authority must not revive after restoration. |

**Proposed sequence:** configuration/export and tested destinations; recurring
isolated verification; restart-safe maintenance controls; assisted live restore
and notices. Keep SPN-063's original acceptance open and decompose these coherent
increments when implementation starts. This preparation installs none of the
new schema, expiry jobs, destinations, UI actions or maintenance controls.

## Options and tradeoffs

These are deployment alternatives, not a commitment to implement every row.
Provider and engine behavior must be rechecked against the exact release and
account selected for launch. Primary references are collected below.

| Option | Recovery approach | Advantages here | Costs and limits | Disposition |
| --- | --- | --- | --- | --- |
| Local SQLite + encrypted snapshot bundles | Existing consistent copy, offsite authenticated bundle, isolated restore | Few services; local latency; one application snapshot includes current image blobs; provider-independent downloaded restore | Synchronous copy/integrity work; storage growth; host failure requires application recovery; nightly schedule's loss window | Selected; finish application verification and measure disruption. No database adapters. |
| Local SQLite + continuous replication, such as Litestream | Replicate database changes to remote storage; restore a selected point; preserve configuration/assets separately | Potentially shorter loss window while retaining embedded operation | Another process and recovery chain; replication lag/retention/version compatibility; encryption policy needs separate proof | Conditional experiment if snapshot frequency cannot meet the chosen recovery objective. |
| LiteFS-style replicated SQLite | Primary writer plus replicated files and primary-aware request routing | Local reads and a failover architecture for suitable hosting | Consensus/leases, routing, filesystem integration, split-brain precautions and operational support; replicas also carry bad writes | Not a novice launch default; do not add it for backup verification. |
| Remote libSQL / Turso / embedded replicas | Product-specific primary/replica and recovery facilities | Managed storage and local read options; potentially useful for a different deployment model | Current local driver is not a remote adapter; consistency, tokens, offline-write conflicts, async commits, service limits and export must be proved | Investigate only for a concrete deployment need. Distinguish legacy libSQL and newer Turso engine/SDKs. |
| Self-hosted PostgreSQL | Logical exports, or physical base backups plus continuous WAL archiving/PITR | Mature transactional concurrency and tools; portable logical exports | Another service, credentials, upgrades, storage and WAL management on a small host; operator owns restoration and monitoring | Useful comparison/control; weak fit for the “less experienced operator” goal. |
| Managed PostgreSQL | Provider backup/PITR + independent encrypted logical export + configuration recovery | Transfers database maintenance and some recovery work to provider; eligible plans can supply failover | Ongoing cost, networking, credentials/TLS/pooling, edition limits, provider account dependency; app availability still separate | Strongest alternative if measured objectives justify it. |
| VM snapshots / attached-volume redundancy alone | Infrastructure-level copies or replicas | Useful extra infrastructure protection | Does not establish application consistency, portable recovery, complete volume/config coverage or protection from logical deletion | Supplement only; cannot satisfy SPN-063 by itself. |

PostgreSQL [`pg_dump`](https://www.postgresql.org/docs/current/backup-dump.html)
supplies a consistent logical database export while the database is in use, but
cluster-level roles/tablespaces need their own treatment. Physical backups and
[PITR](https://www.postgresql.org/docs/current/continuous-archiving.html) have
different version and WAL-chain requirements.
Neither is interchangeable with copying PostgreSQL's live data directory.
SQLite WAL also makes copying only the active main file unsafe: committed data
may still be in the WAL. See the primary sources and local experiment record.

### Current product-specific caveats

- **Litestream:** current [restore documentation](https://litestream.io/reference/restore/)
  describes recovery at retained LTX-file boundaries; compaction changes older
  granularity. Its [migration guide](https://litestream.io/docs/migration/#age-encryption-migration)
  says Age encryption is unavailable in v0.5.0+. It cannot simply replace Spinel's
  client-encrypted bundles without proving an equivalent encryption policy.
- **LiteFS:** Fly currently marks it [outside its support scope](https://docs.fly.io/litefs)
  and warns that autostop/autostart can promote a stale machine and lose data.
  That strengthens the case against selecting it as this Operator's default.
- **Turso:** [embedded replicas](https://docs.turso.tech/features/embedded-replicas/introduction)
  remain production-supported. Their default writes go to the primary; other
  replicas refresh on sync, and an offline-write option exists. New Turso Sync
  uses a different engine. Prove authoritative access decisions and transaction
  semantics; do not assume local replica reads preserve immediate revocation.
- **DigitalOcean PostgreSQL:** [features](https://docs.digitalocean.com/products/databases/postgresql/details/features/)
  document daily backups and seven-day PITR; standby configurations provide
  failover. [Restore](https://docs.digitalocean.com/products/databases/postgresql/how-to/restore-from-backups/)
  creates a new target and needs available quota; destroying a cluster destroys
  its backups. Preserve independent encrypted exports for account/cluster loss
  and Spinel's longer retention. [Edition limits](https://docs.digitalocean.com/products/databases/postgresql/details/limits/)
  change on 15 October/30 November 2026 according to account eligibility, so
  check actual standby eligibility and total cost rather than assuming a cheap
  standard plan includes high availability. No provider pricing is measured here.

### Portability has three meanings

- **Move the running instance:** preserve the database, matching application
  version, configuration, origin and keys. SQLite simplifies the data-file part.
- **Leave the hosting provider:** possess an independently readable recovery
  artifact and access to keys/images outside the provider account. Managed
  snapshots tied to that account do not prove this.
- **Change database engines:** use a versioned logical application export/import
  preserving IDs, binary values, grants, timestamps, revisions and receipts.
  A SQLite file is not a PostgreSQL migration, and a generic CRUD adapter does
  not create an interoperable export format.

Pre-production allows a clean cutover without inventing zero-downtime migration.
Deliberately retained data still needs export, validation and a rollback plan.
After launch, supporting old backups and application/schema versions becomes an
ongoing obligation regardless of backend.

## Things easy to miss in the database choice

### Recovery objectives describe different promises

**RPO** is how much committed work a disaster can lose; **RTO** is how long it
takes to restore usable service. A weekly verification cadence is neither.
Today's nightly snapshot schedule has roughly a one-day nominal loss window
when backups succeed; failures or delayed uploads can make it longer. A green
“last backup” timestamp must not be presented as zero data loss.

Separate a browser-local saved edit, a server-acknowledged commit, a replica
acknowledgment and an offsite recoverable point. Only the last one satisfies the
offsite RPO claim. Server backups cannot include edits still only in IndexedDB.
Browser pending-edit durability remains [offline storage](../offline.md) work.

Replication and failover address availability; they may quickly replicate an
accidental deletion or malicious write. Retained historical recovery points
address a different failure. Even a perfect content digest only proves fidelity
to the selected source state, not that the source state was what its owner wanted.

### A restore also rolls back authority and client history

An old database may contain sessions, API tokens, invitations, disabled-account
state and share-link capabilities that were later revoked. It also contains old
document generations and mutation/offline-creation receipts. A returning browser
may have seen a later revision than the restored server or may retry an edit
whose receipt was lost in the rollback.

Before reopening a disaster restore, require an explicit **restore activation**
procedure: invalidate session/token/link capabilities as appropriate for the
incident, reconcile account/grant changes from a trusted post-backup source or
fail closed, and fence old browser streams/retries with a new instance recovery
epoch. Preserve access credentials needed for controlled account recovery;
do not casually erase passkeys. Choose and test the exact policy during
implementation, including changed-origin WebAuthn recovery. This is a proposal,
not a claim the current protocol already has that epoch.

A weekly disposable verification must not activate the restored authority or
revive its schedules. Exact recovered-state checks happen before deliberate
activation changes; record those changes separately so they do not conceal a
bad restore. Test an offline tab, a revoked guest and an old retry against a
restored instance using synthetic credentials.

### One recovery point must cover the whole application

Current image bytes live inside the database. Moving blobs to object storage
may improve backup size but introduces an atomicity problem: a database snapshot
must identify exact immutable blob versions, including versions referenced by
history and trash. Retain those objects until every referencing backup expires.
A database timestamp plus “whatever is in the bucket now” is not a recovery point.

Use an explicit inventory for accounts/passkeys, access grants, outer tree and
Space children/order, live snapshots, generations, accepted mutations/receipts,
history/pins, restore receipts, previous deletion batches, images and necessary
configuration. Preserve unknown durable tables or fail with a coverage error;
do not silently skip a newly introduced feature. Mark disposable caches,
diagnostics and operational leases separately. Restored leases must not make a
test worker believe it owns a production job.

An immutable application-image reference is only useful while that image remains
obtainable. Keep a durable registry/archive and record architecture, application
revision, database schema and bundle format. Restore the recorded compatible
version first; test upgrades on a copy. A migration that runs implicitly before
the verifier examines the old snapshot can hide the very compatibility problem
the check is meant to reveal.

Configuration also has a consistency boundary: the current backup reads the
runtime environment before it snapshots the database. Serialize configuration
updates with backup publication or capture an immutable configuration revision
referenced by the snapshot; do not claim a coherent deployment from independently
changing files.

### Encryption and independent failure domains are product features

Client-side encrypted backups and provider encryption at rest answer different
trust questions. The current Operator application account cannot read documents,
but anyone with infrastructure/database access or the backup and its key can.
Do not imply a database switch creates end-to-end encryption.

Rotation needs a nonsecret key identifier, an independently held keyring for all
retained recovery points, a new-backup/current-key drill and an old-backup/old-key
drill. Rotating a compromised key does not make an already stolen backup secret
again. Revoking provider credentials is different from destroying a decryption
key; deletion of the latter must wait until retention and recovery obligations
allow it. Test wrong and unavailable keys without exposing their values.

Separate backup credentials and recovery access from ordinary application
credentials. A compromised machine with delete access can remove its backups;
consider provider-supported immutable retention or an independent destination
where justified, with explicit deletion/cost policy. The existing Spaces policy
disables versioning and prunes recognized keys; do not silently enable versioning
or object lock and assume the same retention code will remove historical objects.

### Resources, concurrency and recovery cost are part of correctness

SQLite's one-writer property is not itself a two-user capacity result. Measure
actual transactions, history growth, image volume, backup overlap and the event
loop. A network DB adds round trips to authorization and transaction boundaries;
many small queries can matter even at low user counts.

Snapshot size, WAL growth, temporary plaintext, encrypted archives and restore
expansion compete for disk. The backup's existing `2.1 × database + 256 MiB`
staging guard is not a restore decompression bound. Define streamed byte limits,
memory/process limits, runtime deadlines, available disk and cleanup for the
verifier; enforce them in a separate process so a stalled event loop cannot
disable its own watchdog. Run only one heavy local workload at a time on the
small host. Skip visibly when the configured safe envelope is unavailable.

Record the actual embedded engine, not only the npm driver version. The local
probe reports SQLite **3.45.1** through `libsql` 0.5.29. SQLite documents a rare
[WAL-reset corruption bug](https://sqlite.org/wal.html#the_wal_reset_bug) fixed in
3.51.3 and selected backports, triggered by concurrent connections in separate
threads/processes writing/checkpointing one WAL database. This investigation did
not establish the libSQL fork's patch status or observe that bug. Before launch
or adding a backup worker/replicator, verify the exact fork/build's fix provenance
or select a supported patched runtime, preserving the single-runtime rule. A
successful small probe cannot waive that prerequisite.

Each supported backend adds driver/schema migrations, fixtures, upgrade/rollback
proofs, native integrity tools, export compatibility, least-privilege roles,
operating documentation and recurring restore tests. Each recovery method adds
credential/key rotation and provider failure tests. Limit supported combinations
to named deployment profiles; do not imply every database works with every
backup method. Count operator time and restore-drill costs alongside hosting,
storage, object requests, network transfer and retained application images.

## Proposed implementation shape

### Implement recovery directly for SQLite

Extend the existing archive/CLI, scheduling lease and backup-status code. Select
an immutable encrypted bundle, check compatible format/application/key references,
restore to a private disposable SQLite file, run native and application checks,
and dispose of the file and scratch resources. Keep versioned inventory and
resource estimates in that concrete implementation. The verifier receives its
private file and typed inventory, never arbitrary shell text.

Use ordinary functions/classes where they make this code readable. Do not add a
generic database-engine interface or a general backend recovery framework.
Extend the existing remote-storage boundary only for supported destination
operations as described in the backup-options proposal. Maintain the current
atomic authorization, revision, receipt and commit contracts. The next section
specifies the concrete SQLite verification lifecycle.

For context, a later PostgreSQL migration would require async call-chain changes,
transaction-scoped authorization/rechecks, optimistic revision conflicts,
rollback/retry rules, deadlock handling, SQL/type/collation differences and an
explicit migration strategy. Multiple database writers would still leave
in-memory collaboration units, sockets, timers, caches and presence to coordinate
across application instances. Those costs explain why that alternative remains
a conditional future comparison, with no preparatory framework in this ticket.

### Weekly verification state machine

1. Claim a verification lease distinct from backup publication. Find the newest
   published recovery point and check its required artifacts. A corrupt/incomplete
   newest point is a visible failure; an optional older-point check must not turn
   that attempt green. Keep the source for investigation.
   Coordinate retention with verification: hold the selected point during the
   run and protect failed points for a documented, bounded inspection period.
   The nightly retention job must not immediately prune the failed source.
2. Preflight available keys, compatible application image, resource envelope and
   download access and cleanup limits. Record a clear skipped/blocked outcome if
   prerequisites are missing, while preserving the last successful result.
   The coordinator alone gets least-privilege download access;
   the verification worker gets only its isolated target and private inventory.
3. Restore to private disposable storage. Authentication, native integrity and
   inventory checks must finish before application services read the restored data.
   Legacy bundles without the new inventory have explicit limited coverage;
   they cannot silently receive a full-verification result.
4. Instantiate an inert verification harness with explicit services. Normal
   `createApp` startup currently initializes maintenance and background jobs;
   simply booting it against a restored production config is unsafe. Do not load
   archived environment values into the test process or execute archive-provided
   commands. Block production filesystem access and general outbound networking
   at the process level. The SQLite verification worker needs no database-network
   access; it must not contact production, metadata services or notification
   destinations.
5. Check application invariants and exact opaque digests against the inventory
   captured at the **same snapshot boundary**. Test active native behavior and
   role denial with separate synthetic fixtures or rollback-only transactions,
   without changing the recovery artifact. Use current accepted native Space
   fixtures for tree/order/history/images/handover and prior-deletion coverage.
6. Always dispose of the target, including after timeout, authentication failure
   or an interrupted worker. Persist cleanup failure and retry/reconcile abandoned
   run-owned resources; successful data checks cannot hide failed cleanup.
7. Persist attempt and last-success records separately. Schedule weekly, catch up
   missed work, retry failures with bounded delay and reuse idempotent run IDs.
   Show verification time, recovery-point time, coverage, safe failure category
   and last good result together in Backups & health. No document content,
   filenames, formulas, secret values or raw provider exceptions in status/logs.

Keep a bounded rotation-coverage ledger as well as the newest-point result:
verify at least one retained artifact for each active format/key generation after
rotation and before retiring old recovery tooling. The regular newest-point check
alone cannot show that an older key is still available. Routine production checks
can validate stored passkey/public-key records and authorization logic; they cannot
prove possession of a person's authenticator. Use synthetic cryptographic
credentials in the repeatable cold-restore acceptance and report that distinction.

The result needs method/version, run ID, artifact IDs, key identifier, selected
recovery time, source application/schema version, checks performed, durations,
resource peaks and cleanup outcome. Keep sensitive manifests/digests private;
the admin view gets aggregate counts/status. Preserve an independently accessible
receipt for disaster recovery if live-instance status is lost. This is evidence,
not a substitute for the protected backup itself or external alerting in SPN-032.

## Experiments and evidence

The [complete experiment record](SPN-063-experiments.md) contains reproducible
TypeScript, the unmodified source hashes, original outputs, guard results and
environment. All three probes used Node **26.12.1**, `libsql` **0.5.29** and the
actual production `database.ts` / `archive.ts`, with synthetic data on a Linux
local overlay filesystem. One bounded workload at a time; no provider resources
or production data. The process-tree guard observed **176.0 MiB** peak and no abort.

| Probe | Observed result | What it establishes |
| --- | --- | --- |
| Active-WAL main-file copy versus production snapshot | Live source had one committed sentinel; raw main-file copy had zero, `VACUUM INTO` copy had one. Both copies passed integrity checks. | Portable recovery must use a consistent snapshot. Structural integrity alone does not establish completeness. The current snapshot method handles this case correctly. |
| Production snapshot with 1 / 16 / 64 MiB blob payloads, three copies each | Copy medians: **4.088 / 33.820 / 83.915 ms**; observed maximum **157.812 ms** at 64 MiB. A timer scheduled before each copy was delayed for comparable time. | The current synchronous copy blocks the event loop despite its `async` signature. Include backup interference in realistic edit/ack tests. |
| Real encrypted round trip with exact sync-table schema | A valid row, invalid JSON and wrong snapshot identity all restored successfully with one row and passing integrity/FKs. A separate JSON/identity predicate rejected both faults. | Add semantic verification. Authentication, counts and hashes can faithfully preserve a source that was already invalid. This is not an encryption failure. |

Three synthetic timing samples are **not** p95/p99, an RTO, a production capacity
claim or a SQLite/PostgreSQL comparison. The semantic probe is a narrow table
fixture, not full native acceptance. No application under concurrent editing,
cloud transfer, patched-runtime comparison, physical host failure or managed
database restore was exercised. The measured evidence supports retaining SQLite
and strengthening recovery; it does not prove it meets launch
performance or loss objectives.

The later [capacity experiment](SPN-063-capacity-experiments.md) records the actual
engine configuration, indexed metadata reads, full-list costs and the 10,001-item
refusal boundary. Its first broader attempt exceeded the 512 MiB process-tree
guard and was aborted; the reduced probe completed within the same guard. Both
attempts are recorded. No supported concurrency or document-count claim follows
from either experiment.

### Next experiments, ordered by decision value

1. **Declare the recovery promise and measure the baseline:** on target hardware,
   use realistic native snapshots/history/images and two editors while backup and
   verification run. Measure the metrics below. Include growth near the planned
   disk/upload envelope. A failure should identify the specific mechanism at fault.
2. **Try the smaller SQLite improvement if needed:** isolate copy/integrity work
   with a compatible patched runtime or test a supported incremental backup API.
   SQLite's [Backup API](https://www.sqlite.org/backup.html) is incremental;
   current driver availability must be proved. Never combine independent SQLite
   runtimes in one process. Repeat the same fixture and interruption tests.
3. **Restore a prior timeline:** exercise the old-tab, revocation and retry cases
   above, plus old/new-key recovery, missing assets and cleanup after termination.
   These findings determine the SQLite recovery activation design.
4. **Run a novice recovery walkthrough:** provide only the documented recovery
   kit on an empty disposable target; measure required decisions, commands,
   mistakes, hands-on time and total RTO. No presumed familiarity with provider
   consoles, SQL, volumes or WebAuthn relying-party rules.
5. **Prototype one challenger only if required:** use managed PostgreSQL for an
   operating/recovery failure, or continuous SQLite replication for an RPO failure.
   Compare the same acceptance and cost model. Provider experiments need actual
   account/region/edition access and an approved spending/cleanup envelope before
   provisioning; this research has neither created resources nor measured them.

Before the baseline, record numeric pass/fail budgets in this record. At minimum:
maximum tolerated loss of server-acknowledged work, full fresh-target RTO,
foreground save latency/pause during maintenance, and verifier memory/disk/time
limits within the chosen host's budget. The current nightly/26-hour warning and
2 GiB host are existing behavior/planning constraints, not newly demonstrated
SLOs. Select budgets explicitly at implementation; do not derive convenient
thresholds after seeing the measurements.

## Implementation acceptance and independent review

Use this matrix for the selected backend; do not waive application behavior merely
because a managed provider reports a successful restore.

| Area | Required evidence |
| --- | --- |
| Fidelity | Exact native snapshot/image and stable-ID checks; complete inventory coverage; Space tree/order, formulas, generations, checkpoint/pin and deletion-batch invariants. Counts alone cannot pass. |
| Authority | Operator isolation; Owner/Collaborator permissions; guest scope; disabled/transferred accounts; revoked capabilities; a controlled disaster-activation policy. |
| Replay after rollback | Reconnect an old browser/guest, pending offline edits, duplicate mutations and restored receipts; no silent overwrite, privilege revival or replay under an obsolete recovery epoch. |
| Corruption and incompleteness | Missing/truncated archive, bad authentication/key, wrong schema/image, missing table/blob, valid-SQL semantic corruption, and incomplete newest point with an older good point available. |
| Resource and interruption safety | Insufficient disk/memory, decompression bound, timeout/kill, worker failure, lease expiry, retry, cleanup failure, source preservation and abandoned-target reconciliation. |
| Rotation and compromise | Current/retained key coverage, replaced storage credentials, provider-account/host loss and no secret/content leakage. |
| Usability | A fresh compatible target with only the documented recovery kit; time actual Operator actions and total RTO, then confirm read/edit/deny behavior and the next backup. |
| Presentation | Last success and current failure visible together; skipped/incomplete coverage distinct from success; independent current light/dark/phone review when that UI is implemented. |

Before choosing a stricter RPO or availability tier, record the objective, fixture
and environment. Compare the **same** documents, images, retained history, two
editors, backup overlap and recovery tasks. Collect transaction/ack latency
(p50/p95/p99 with adequate sample counts), busy/conflict/retry counts, event-loop
delay, RSS/container/host memory separately, disk/WAL/temp peaks, archive bytes,
upload/verification durations, recoverable-point lag, full RTO, setup actions and
recurring cost. State sample counts and instrumentation overhead. A three-run
microbenchmark can report its samples/range, not a credible p99 or capacity SLO.

Use the existing [diagnostic contract](../../lib/diagnostics/README.md) for safe
numeric observations and registered operations; do not log SQL arguments,
document content, keys or raw errors. First prove performance metrics do not
change correctness or materially perturb the workload. Record adverse and first
attempts; reruns explain failures rather than erasing them.

Two nonimplementing reviewers independently assess the same final implementation
commit using the [repository rubric](../run-backlog.md#3-get-two-independent-grades):
scope/acceptance 35, correctness/data/access 25, evidence/regression 20,
operations 10, maintainability/complexity 10. Each must score **above 95/100**
with no unresolved blockers, and applicable CI/visual gates must pass. For this
planning PR, review source fidelity, experiment reproducibility, honest limits
and executable acceptance criteria; do not grade unbuilt runtime behavior as done.

## Persona decision record

**Question:** retain SQLite, migrate before launch, or immediately support several
database/recovery adapters? **Status:** accepted, 2026-10-27. The owner requested
retaining SQLite without database adapters if capacity is acceptable; agent assessment
accepts that choice for the intended deployment using the code audit, primary
sources and bounded experiments. Performance/recovery implementation gates remain.

| Persona | Recommendation's effect and tradeoff |
| --- | --- |
| Operator | One supported default and one recovery kit reduce setup choices. Strong resource guards, key instructions and independent restore evidence add necessary work; multiple adapters would multiply the support burden. Managed PostgreSQL remains a meaningful alternative if it makes measured operations easier. |
| Owner | Portable encrypted snapshots protect the complete workspace. Explicit loss windows and semantic recovery tests avoid overstating safety; retaining SQLite cannot justify losing acknowledged work beyond the selected RPO. |
| Collaborator | Preserve atomic authorized commits, revision/retry fidelity and recovered ownership/grants, including reconnect after rollback. Native-document processing and backup overlap still require measurements. |
| Link guest | Narrow scope and revocation must survive normal operation and disaster activation. Verification must never publish recovered guest capabilities or expose restored content. |

**Outcome:** retain the existing SQLite backend and build its recurring recovery
verification directly, with no new database adapters. Backup-destination support
can vary independently under the proposed operating model above. Preserve
portability and simple setup. Revisit the engine only when measured operating
limits or an actual multi-host/availability requirement justify the change.
Capacity tuning remains contingent on evidence; this documentation changes no
runtime limits and does not advertise untested user/document counts.
