# SPN-106 — view-only Doc initialization

## Capability and decision checkpoint

2026-11-02 — implementation in progress, not accepted. Current main is
`18a8759c498574a1d9cc24a969a558cd97a798ed`. The pinned OSS Docs UI 1.1.0
dispatches `doc.command.refresh-header-footer-fields` with the document's unit ID
and `onOpen: true` when its current model first appears. The native permission
controller emits a denial before that command can determine that a viewer has
no editable fields. The original browser evidence is retained in SPN-075; fresh
viewer-startup verification remains required here.

The public `CommandService`, `ICommandService` and dependency override API expose
a boundary before command listeners and execution. Use a small subclass through
the existing grant binding: refuse only that exact initialization command for
the binding's current viewer grant and exact unit ID. Delegate all other commands
and mutations, including explicit field refresh and real edits, unchanged. A
refused initialization returns false and never changes document fields, native
permission points, notification delivery or collaboration credentials. No SDK
source patch, private controller replacement or notification suppression is needed.
Both synchronous and asynchronous public entry points retain this contract.

Public references: [dependency overrides](https://docs.univer.ai/zh-CN/blog/univer)
and the installed `@univerjs/core` public declarations for `CommandService`.
This is a proposed supported-boundary implementation; native permission controls
and real application startup must verify its wiring before acceptance.

Owner retains saved content, fields and sharing grants. Collaborator and Link
guest can read without a false warning while denied edits still produce truthful
feedback. Operator gains no document access or service. The existing binding's
live downgrade/upgrade state also governs initialization refusal. Internal editor
units and other commands keep their native behavior.

### 🧪 Snapshot failure: source-supported hypothesis and causal limit

Historical CI `41521815332`, attempt 1, tested merge
`36d7e3cada11b2e6bfb964267c723ec92278e93d` from original source `b9e57e46`.
Development job `125551436967` failed the desktop account viewer; production
job `125551437095` failed all four new viewer cases at
`e2e/documents.spec.ts:131`. Full snapshot comparison observed five native
resource entries and `rev: 1` added to the response. The first attempts and
configured retries failed. No runtime pass follows from those retries, and no
later screenshot/denial/concurrent-editor assertion can be credited for those
failed paths. The original Safari failure is a separate boundary.

The fixture saves directly through `DocumentStore.save`, then reads
`/api/items/:id/doc` before opening a browser editor. In
`src/server/workspace/routes.ts`, that GET returns the legacy `doc_snapshots`
representation until `workspace_collaboration` exists; afterwards it delegates
to `CollaborationStore.load`. Account and guest collaboration POST routes call
`CollaborationStore.prepare`. Its `prepareUnit` materializes the initial native
model with `rev: 1`, atomically creates the initial `spinel_sync_units` row and
the readiness fence, and retains the original snapshot table. The native model's
resource loader emits registered plugin resources. Subsequent sync loads
serialize those resources and report the current sync revision.

**Hypothesis:** the failing assertion compares the unprepared legacy representation
with the newly prepared native representation. This source path explains the
observed additions without establishing an authored browser edit. The earlier
inventory's phrase “saved snapshot mutation” describes the changed HTTP result,
not proven unauthorized mutation of an established native head. Actual retained
rows/receipts at the failure were not inspected, so source tracing alone does
not conclusively attribute the historical run or excuse current integrity.

Do not remove resource/revision fields, replace full equality with a partial
match, or baseline after the viewer has already performed the behavior under
test. Proposed correction, conditional on a focused control, is to prepare the
native fixture through the existing owner collaboration endpoint **before** the
viewer navigation; assert preparation preserves authored body, stale date
fields and grants; capture the complete native HTTP response and durable row;
then require exact equality of that baseline and unchanged sync receipts across
each viewer load/reload. Keep a distinct focused preparation control so the
transition is explicit rather than hidden by normalization.
