**Extension, 2026-10-28:** [SPN-069](SPN-069.md) extends the original own-folder
admission below to prepared editable shared folders. Its canonical folder-owner
and creator rules supersede this record's historical shared-folder deferral; the

## Stable creation before native replay

**Accepted, 2026-10-27 — agent decision under the owner's standing delegation.**
The owner requested offline creation on 2026-10-19, with stable client-generated
item IDs (grooming, 2026-10-19). This ticket extends SPN-053's existing native
checkpoint rather than introducing another mutation queue or uploading a changing
replacement snapshot.

An already prepared everyday account can create a Sheet or Doc in My files or
an owned ordinary folder from its cached catalog. Before opening the editor, one
IndexedDB transaction commits the deterministic blank bundle, the immutable
creation request, an empty native checkpoint and a pending creation marker. A
failed storage write opens no editor and makes no saved claim. The complete
compatible public runtime and account catalog must already exist; this does not
implicitly prepare an unprepared device.

The item UUID is its permanent application route. A second UUID identifies its
native generation. `POST /api/items/offline-create` creates the empty server base
and a durable receipt in the same transaction. Both peers use the shared blank
factory, including deterministic initial Doc paragraph and section identities.
The response confirms only that initial base; existing native acknowledgement
and outbox cleanup rules determine when every edit is **Synced**.

The receipt binds the complete normalized request and account. It survives item
deletion. A lost acknowledgement retries those same bytes and cannot duplicate,
move, reseed or resurrect a previously accepted item. Item and generation IDs
are checked against live, retained, restore, purge and receipt identities before
admission. The server checks the expected account before revealing item access,
and rechecks the active session inside the synchronous commit.

**Alternatives:** uploading the latest local snapshot would require another
mutable retry protocol and could diverge from the native edit queue. Server-only
IDs would require remapping routes and pending mutations. Stable empty-base
admission preserves the existing native sync contract with a small separate
creation receipt.

**Personas:** Owners and Collaborators can begin work in their own files and
retain their chosen folder without duplicate uploads. Shared-folder creation
still waits for SPN-069; cached edit rights do not expand that permission.
Operators gain neither document access nor a new service to operate. Link guests
gain no private catalog, offline creation or persistent token; existing online
Edit-guest Space-child creation is unchanged.

## Pending creation and compatibility

**Accepted, 2026-10-27 — agent decision.** A new empty document is valuable work
before the first keystroke. `StoredItem.creation` keeps its immutable request and
destination outcome; `OfflineOutbox.creation: true` also makes that work visible
to older runtimes. SPN-055's older queue validator rejects unknown outbox fields
and therefore retains the record as uncertain/pending instead of refreshing or
deleting an apparently clean, nonexistent server item. The current runtime
validates both fields together. Every checkpoint preserves the marker until a
verified server acknowledgement and local metadata update commit together.

New files are overlaid from the account's durable item store, not only its
last-online catalog. Background catalog refresh cannot erase them. A successful
creation also updates the retained catalog before clearing its marker, keeping
the stable route useful after another offline restart. The mounted native editor
stays in place through acceptance, preserving unfinished input and its one writer.
Acknowledged metadata bridges a catalog requested before that local acknowledgement;
a full catalog requested afterward takes precedence, including moves and deletion.
Each acknowledgement advances an account-local revision in the same transaction.
A full-list request reads that revision before issuing HTTP and saves it with its
catalog. This ordering does not depend on clock changes or delayed responses, and
keeps a later online trash action effective after a cold offline restart as well.
While that bridge is needed, accepted metadata also joins the ordinary in-memory
catalog. Renaming, tagging and removing the device download therefore keep their
normal metadata behavior without requiring a full-list refresh.

Existing one-writer, account epoch, failed-save, explicit-discard and storage
protection rules apply, including empty creations. The native editor attempts
upload/replay when opened, on reconnect and on foreground return. Like SPN-053,
this adds no background writer or promise of work while the app is closed. Rows
explain that a retained new file can be opened to upload when connected.

Returning to My files releases the document writer. Reconnecting there keeps the
new file **Not synced yet** until it is opened; opening resumes the same saved
creation request and native edits. This deliberately uses the reconnect entry
points already accepted for downloaded documents in SPN-053. Creating a second
queue or mounting hidden editors to upload closed files would introduce new
writer coordination and memory costs. The ticket's exactly-once admission and
destination checks apply whenever that existing writer reconnects, including an
offline restart. The row's explicit upload instruction keeps this boundary
visible to Owners and Collaborators, with no extra service for Operators or
new offline access for Link guests.

This protects Owner/Collaborator work across application updates and account
changes; Operators retain the same bounded storage model. Guest boundaries and
the existing online creation behavior are unaffected.

## A rejected folder stays with the file

**Accepted, 2026-10-27 — implementation of the approved SPN-047 design.**
File rows show **Not synced yet** until server creation is acknowledged. A
definitive `folder-unavailable` response proves no creation receipt exists and
changes the row to **Needs attention**. Its own menu offers **Choose another
folder…** using the existing destination dialog. Choosing an owned folder or
My files changes only the saved destination, preserves both stable IDs and the
native queue, and requires the same server admission on the next opening.

A lost network response is ambiguous, so it does not authorize changing the
request. A conflicting receipt or an already accepted item that was subsequently
deleted/restored also does not authorize silently creating another file. Its
saved work remains available for explicit Univer export or discard. The ordinary
SPN-054 automatic copy path is suppressed while a creation remains unconfirmed.

Owners retain their work and make a deliberate destination choice. Collaborators
cannot write into a revoked or shared folder merely because it was cached.
Operators and Link guests receive no new access. Row placement, modal titles,
keyboard focus, theme tokens and phone targets reuse the maintained playbook;
no new design pattern is introduced. PR screenshots require independent
theme/persona review, disclosed as **agent review only**.
