# SPN-057 — Spinel sync server

## Status

Implementation in progress on `codex/spn-057-sync-server`. The original acceptance
is [SPN-057 at the starting base](https://github.com/mxbaylee/spinel/blob/8a5135643e8ed9b3030251d9cd21e4c8c9430037/docs/todo/SPN-057.md).
This record is a design and evidence checkpoint, not a completed review.

## 1. Keep the new server isolated until integrated review

- **Date/status:** 2026-10-26, accepted implementation decision.
- **Question:** How can the server land without switching existing clients?
- **Context:** SPN-104 supplies the transform; SPN-058 supplies the new browser
  protocol and SPN-056 retains the independent integrated review. SPN-059 owns
  activation, retained-data conversion and Pro removal.
- **Options:** Replace the active transport immediately, or expose the new
  server only under an explicit disabled-by-default server flag.
- **Outcome:** Use `SPINEL_SYNC_SERVER=1` only for development/integration of the
  new protocol. Default behavior retains the current transport. Reject an
  attempted new-server open of an already prepared legacy unit; converting
  retained collaboration data belongs to SPN-059.
- **Personas:** Operators retain the current deployment path; Owners and
  Collaborators retain their accepted edits and history; Link guests keep
  exact document and Space scope, root privacy epochs and immediate revocation.
- **Source:** Agent implementation choice within the owner's staged landing
  direction, [staging record](sync-staged-landing-2026-10-25.md).

## 2. One durable authorization boundary

- **Date/status:** 2026-10-26, accepted implementation decision.
- **Question:** Where should final access checks and accepted edits commit?
- **Context:** Authorization can change while asynchronous materialization or
  transport work runs. The library must remain independent of application code.
- **Options:** A separate authorization check before storage, or a synchronous
  guard within the adapter's compare-and-swap transaction.
- **Outcome:** `lib/sync-server` owns ordering, exact-base transformation,
  bounded headless materialization and hashes. The SQLite adapter in
  `src/server/sync` owns durable receipts, revision rows and one current
  snapshot per unit. It invokes the application's final credential, ancestry,
  role, privacy and generation guard inside the same transaction as the
  revision write. Retries carry a stable actor/mutation identity and payload
  fingerprint.
- **Personas:** Operators get one recoverable database; Owners and Collaborators
  get durable acknowledgments and reconnect retries; Link guests cannot use
  revoked access or cross-document mutations.
- **Source:** Agent implementation choice preserving SPN-057's existing rules.

## Verification plan

Cover ordering and exact-base transforms; durable acknowledgement and failed
commit rollback; duplicate/restarted retries; malformed/unsupported/refused
batches; whole-workbook and size invariants; two real sockets; divergence and
metrics privacy; revoked credentials and Space scope; assistant exact-revision
writes; history, restore generation fencing and retryable purge. Reuse OSS
Univer handlers, retain Native Formula metadata, and keep eight loaded units
with idle eviction.

Final evidence must include all seven required checks, a complete independent
review anchored to the committed head, every finding's disposition, and landing
bookkeeping. No grade or passing runtime result is claimed by this checkpoint.
