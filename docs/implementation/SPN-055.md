# SPN-055 — Protect pending edits and show offline storage limits

Implements the shared device lifecycle from [the offline contract](../offline.md).
SPN-053 supplies durable native editing and SPN-054 supplies recovery copies and
local export. This change keeps those copies identifiable and protected through
storage failures, account departure and application updates. Physical installed
phone behavior remains SPN-090; desktop browser compatibility remains SPN-052.

## Account-scoped inventory and explicit removal

**2026-10-27 — accepted, agent judgment under the owner's standing delegation.**

Use the existing **Profile → This device** section. Mount private inventory only
for the current everyday account while that section is visible; Appearance stays
available for Operators. Show each retained document's original stable link,
pending/read-only/attention state and logical bytes. Count UTF-8 stored metadata,
snapshot, queue/recovery data and every stored image byte, including orphan image
bytes for that item. These are logical estimates, separately labeled from the
browser's origin-wide usage/quota, which includes other accounts and app files.
Unreadable sizes stay unknown.

Observation does not call `persist()`. Explicit preparation and **Request storage
protection** request it and report the actual granted, denied, unsupported or
failed outcome. A negative `persisted()` read before any request means protection
has not been requested, not that the browser denied a request. Browser/user
deletion or device loss can destroy the only pending copy; neither persistence
nor server backups guarantee recovery of work that never reached the server.

Storage exhaustion retains its meaning across the public worker boundary and
the private document/catalog writes. A browser quota exception can have an empty
message; it still produces the actionable out-of-space notice. Other empty
storage errors receive a nonempty fallback for the operation that failed.

A record alone is insufficient for **Available offline**. Inventory checks the
account/item/Space identity, known format, image references, image hashes/sizes
and complete compatible public runtime, plus the saved account and catalog needed
for a cold offline start. Missing account/catalog metadata keeps the retained
records visible with attention status; it never turns them into a fresh download.
Missing stores, incomplete images and
unreadable/unknown queues remain explicit. Unknown or foreign metadata never
supplies another account's title. Uncertain retained data is protected as work,
not inferred to be clean from an unfamiliar queue shape.
The lightweight stored-base check also matches the native loader's minimum
revision, native-kind discriminator and bundle/checkpoint/recovery identities.
A record the editor cannot admit is not advertised as available or treated as a
clean candidate for replacement. Inspection does not initialize the native SDK.

Read stores without requesting a version and abort `oldVersion === 0` creation.
This works when `indexedDB.databases()` is absent and prevents empty per-account
databases during startup, sign-in, inventory or recovery observation. Actual
preparation remains the only private-store creation path. Failed reads, blocked
opening and unknown schema are not evidence of an empty account. No existing
private database is upgraded or deleted by this change; its version remains 1.

**Remove from device** obtains the same account/item writer lock as the editor
and rereads the record in its deletion transaction. An open writer prevents
removal even if its last checkpoint looked clean. A pending or uncertain record
hands off to recovery/management without mutation. Explicit discard has its own
confirmation, then rechecks the lock and account scope. It never deletes a server
document. Account-wide explicit deletion holds the catalog lock, obtains every
item writer nonblockingly, and clears the account in one transaction; a failed
lock or transaction leaves its private data intact. Public hold release happens
only after the private clear and fresh empty check.

Pending-transition notices update an already-known row without hashing every
image on each keystroke. Foreground and explicit refreshes revalidate inventory.
Notices arriving during a read take precedence over its older pending summary.
Departure or account change clears rendered private summaries immediately.
Committed download/removal notices are delivered after the temporary item writer
has released. An editor reacting to a newly prepared copy must not mistake that
same operation's lock for a competing tab and permanently become read-only.
Passive account invalidation locks the whole tab and retires its unfinished
startup, without automatically authenticating again or reopening the old route.
An explicit reopen begins a new admission. This prevents an old tab from silently
resuming under a replacement cookie or recovering a queue after its account fence
has ended.
An access check also keeps the response contract it chose when starting. If
preparation activates the mounted editor while an older metadata request is in
flight, retire that response and immediately check the current account-bound
contract. Interpreting the older response as a collaboration response would
incorrectly freeze a valid editor as an account or document-version change.

**Personas.** Owners can manage disk use without silently discarding work.
Collaborators retain the same safeguards with their original viewer/editor scope.
Operators get no document inventory and no new document access. Link guests have
no preparation/removal actions or private stored catalog.

## Immediate local lock and truthful deferred logout

**2026-10-27 — accepted, agent judgment under the owner's standing delegation.**

Respect the existing unsaved/unfinished-input departure warning. Once the person
accepts departure, synchronously clear private UI, cancel the old local access
epoch and record a noncredential exit intent before awaiting inventory or network.
The locked exit screen receives counts only. **Keep on this device** and a separate
explicit deletion confirmation apply to the original account captured by that
intent, even if remote logout finishes first. A later account generation or exit
invalidates the capability. Operators skip private inventory.

The durable intent includes its version, unique ID, original account (or a
verified anonymous exit), cancellation/authentication generations and whether the
original account could own offline data. It contains no credential or document
content. Legacy pending markers remain conservative barriers. Only a real 204
response clears the exact matching intent; network errors, non-204 results and
late responses cannot claim remote sign-out or clear a newer intent. Normal,
setup and invitation startup all drain the barrier before starting authentication.

Serialize authentication ceremonies and logout for the origin through full
response-body settlement. Where Web Locks are unavailable, scoped operation
markers refuse an overlapping/unknown transition without expiring it into a
false safe state; an isolated ordinary online sign-in still works. Once passkey
verification dispatches, show it as non-cancellable until that request settles.
An obsolete request's headers/body must finish before its transition releases.
If cancellation precedes a delayed options response, retain only its validated
challenge ID for server cancellation after the body settles; stale options never
reach the credential prompt. That cleanup stays inside the owned transition.
Operation markers distinguish a fully settled options response/local passkey
prompt from a dispatched network request. Acquiring the actual exclusive origin
Web Lock proves an earlier lock-owning prompt has no live owner, so only that
strictly validated prompt marker may be retired after a closed/crashed tab. The
marker returns durably to network phase before verification dispatch. Unknown,
legacy, no-lock and outstanding network markers do not become safe merely with
age. Browser coverage closes a real prompt renderer and checks subsequent entry.
If an unknown network/no-lock operation loses its owner, its ambiguity can remain
blocked; the application does not silently erase that evidence or private data
to regain availability. This is a conservative limitation, distinct from the
recoverable settled-options prompt case and from a confirmed server logout.

Logout sends the expected original account. The server rejects a different live
account or newer anonymous ceremony, revokes only the matching presented session,
and sends **no Set-Cookie**. A delayed logout therefore cannot delete a newer
ceremony/session cookie. Invalid or absent sessions can return 204 without
revealing another account. Existing origin, JSON and `no-store` checks remain.

Independent review found that an anonymous intent must not omit its expectation:
an omitted header belongs to the legacy unconditional logout route. Fresh verified
anonymous exits now send an explicit `anonymous` expectation. Any authenticated
session returns 409 unchanged; absent/invalid or anonymous credentials return a
204 no-op without cancelling an unrelated anonymous ceremony or setting a cookie.
This confirms that no authenticated account needs revocation, without persisting
a credential or introducing a session-token comparison protocol.

**Personas.** Owners and Collaborators see local locking immediately and retain
an explicit choice about their pending work. Operators retain their separate
administration role and may sign out without opening a private device store.
Link guests gain no private access, and setup/invite credentials are never
copied into the offline intent or runtime registry.

## Retain a complete compatible public runtime

**2026-10-27 — accepted, agent judgment under the owner's standing delegation.**

Activation used to delete older public shell caches. That is unsafe when an old
tab still needs a lazy editor chunk or retained private work needs an earlier
offline format. Replace it with a public protocol-1 manifest describing the
content-derived build ID, compatibility pair, application entry, CSS and exact
public asset allowlist. The small emitted bootstrap selects that runtime before
importing React or native editors. The actual private format and pinned SDK remain
1 and 1.1.0; the browser upgrade fixture declares a second format solely to test
compatibility admission, without changing private data or SDK code.

The public control database stores manifests, account compatibility requirements
and real browser `Client.id` build holds. It contains no catalog, document,
credential, authentication response or entry token. Preparation reserves the
runtime requirement under the account catalog lock before committing private
bytes. Empty checks and release share that ordering. Worker mutations serialize
through an origin lock, verify request deadlines and complete ahead of later
reservations; a timed-out page cannot reorder a stale release after a new hold.
An authenticated startup that proves its own private store empty under the
catalog lock can release a reservation left before an interrupted first write.
It cannot release another account or the independent legacy requirement. During
first preparation, that same verified-empty current account is excluded from
legacy name discovery; a newly created empty store must not manufacture a
permanent requirement for an older editor. Every other name and uncertain
enumeration remains conservative.

Keep at most two complete published builds and one candidate. A candidate becomes
complete only after every allowlisted asset and matching public `/sign-in` HTML
have been fetched without credentials and verified; HTML is written last. Reject
missing assets, redirects, HTML disguised as JavaScript/CSS and a descriptor from
a different deployment. Failed updates leave previous complete builds intact.
If live clients or retained compatibility requirements consume the slots, refuse
the update with actionable feedback rather than evicting needed code. Only public
app caches participate; private snapshots, images and queues never enter them.

Account requirements remain after sign-out. On first adoption, metadata-only
database-name enumeration may establish that no legacy account exists; it never
opens another account's private store. If enumeration is unavailable or uncertain,
retain a conservative format-1/SDK-1.1.0 requirement even when old cache metadata
has disappeared. One empty account cannot release unknown signed-out accounts'
compatibility. An unreadable registry refuses mutation rather than starting over.

Service-worker activation does not reload pages or delete old caches. Exact live
client holds keep lazy assets for open editors. An authenticated startup may select
the compatible retained runtime before exposing private data; it retires only its
unpublished startup attempt and mounts once. CSS stays disabled until verified
switch completion, and theme/app listeners are cleaned up. Active editor input is
never retired merely because a service worker updated.

**Personas.** Owners and Collaborators keep a usable editor for their retained
copies, including while signed out. Operators get a fixed public cache bound
instead of an unbounded version archive. Link guests still use the server; no
share/setup/invite page or token becomes an offline app cache entry.

## Verification and limits

The PR must carry current-head CI results, actual light/dark/phone images and two
independent nonimplementing reviews, each above 95/100. Visual approval is **agent
review only** under the standing policy. Planned checks are not recorded as passes.

Focused tests exercise unknown queues and exact scope, byte/image completeness,
persistence truth, noncreating reads, transaction/writer/account fences, runtime
capacity/legacy holds, public manifest validation and full-body auth ordering.
The real logout HTTP tests use sessions and origin validation, not response mocks.

`offline-device.spec.ts` runs against a real production build and covers native
pending edits, actual browser quota override, image-request failure, external
store/image deletion, unavailable database enumeration, writer refusal, recovery
handoff and explicit discard while comparing retained bytes and server originals.
The quota fixture first observes a genuine browser transaction fail with
`QuotaExceededError` in a separate probe store. It retains bounded synthetic probe
bytes so cleanup cannot change the measured budget, then measures usage again and
reserves space for the small runtime/catalog records. A larger probe must still
fail under that final limit before the real image download. This accounts for
Chromium's cached quota allowance without substituting a mocked storage failure
or consuming the control records' headroom through repeated put/delete commits.
The real document download must then fail while the prior pending copy and image
bytes stay unchanged. Independent production scenarios all run even if an earlier
case fails; failures and retries still fail the required check.
`offline-sign-out.spec.ts` covers offline Keep/Delete, normal/invite/setup entry,
two-account isolation and retained runtime holds, a real delayed logout without
Web Locks, and a fresh same-origin unclaimed server with the prior browser store.

The required `offline-upgrade` browser partition owns three sequential emitted
Vite builds (the SPN-054 baseline and two current compatibility fixtures), a
same-origin server/proxy and a persistent Chromium profile. Test-only
format namespaces ensure old lazy chunk URLs truly do not exist in the new
server's directory. It checks interrupted/invalid candidates, real aborted
IndexedDB upgrade, pending native Sheet/Doc content, active unfinished input,
worker replacement and a cold offline browser restart with the compatible build.
It also loads the newer app while signed out, then admits the original account
and requires the older compatible host before any private UI appears. A separate
adoption case builds the immutable pre-change SPN-054 source and upgrades its
eager loader/legacy worker with pending native data intact; the CI checkout is
test evidence, never a runtime dependency.
The normal production partition remains free of the native observation fixture.

CI phone-sized screenshots establish layout only. SPN-090 still owns physical
Android/iPhone installation and storage-context verification; SPN-052 owns the
recorded macOS Chrome/Firefox/Safari compatibility matrix. External storage
deletion and device loss remain unrecoverable when they remove the only copy.
