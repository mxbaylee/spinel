## Routing and evidence decision

Each required name has one workflow owner: `Pull request` in PR policy, and six
code checks in CI. A static run name supplies event identity; actual job/check
IDs in the current suite supply admission. Full admission additionally requires
the successful `Coverage selected: full` classifier marker; the static full flag
does not prove selected coverage. The digest-bound plan remains execution
evidence. The current checkout must equal the event merge with its exact
base/head parents.

The router uses its new credential only for the reserved label, with no PR source
execution. Existing full-on-edit behavior remains on main until this draft passes
its acceptance and can be deliberately adopted. Configuration and automatic
target-event delivery cannot be inferred from a candidate workflow on a PR.

Code events now share one cancelling per-PR group, including labels. This is an
explicit refinement of SPN-115's label isolation: an old-base label-triggered run
must not outlive new-base validation. Exact text edits have their own policy group
and never request or cancel code, even after a full-validation obligation arises.
Their independent classification jobs are not cancelled when a newer policy job
supersedes an older one.

Explicit and automatic timeline base changes, historical reserved-label additions/removals, and
ambiguous/full classification history retain the full requirement for the PR's
remaining lifetime. Missing keys, failed additions, manual removal, and later
pushes cannot erase it. Unknown or unavailable history conservatively requires
full validation. Policy reads history initially and before success, retains any
observed full requirement, and repeats history reads during waits only while
classification remains pending.

Partial retries require all job executions from `filter=all`, selecting the
latest execution of each required name while retaining genuine earlier successes
from the same run and suite. Every required code gate also rechecks live
source/base as its final step. This protects an old-base individual or failed-job
retry even after policy has already become green; reusing an earlier classifier
does not bypass the live guard.

The final guard also verifies the original coverage-plan digest and immutable
identities, and rejects a targeted plan when current history requires full
coverage. This closes same-source/base retries after an ambiguous edit. A pending
text classification preserves the code result while the independent required
policy job waits. Storybook's shared classifier receives the same read-only API
permissions and token; caller wiring is covered by the workflow regression.

GitHub now permits Actions run/check retention as short as one day. At 24 hours
of PR age, classification conservatively requires full coverage rather than
treating empty surviving history as proof. This is a disclosed extra cost for
longer-lived PRs and can require an explicit revalidation of an earlier targeted
pass. Supported operation retains open-PR policy runs; before manual cleanup,
apply the reserved label to retain the obligation in the PR timeline. The setup
guide records this limitation and recovery procedure.

Freshness is separate from coverage scope: full requests retain their latest
recorded creation timestamp, and both policy admission and every code guard
require a genuinely new CI run created after it. A retry changes an attempt's
start time, not the run's creation time, and therefore cannot borrow old full
results after an ambiguous edit. Equality with the actual request remains blocking.
Only label notifications attributed by the timeline to the configured router App
use an inclusive additional bound, alongside the independent strict request
boundary. Manual or unattributed label requests stay strict. This permits genuine
router notification/CI timestamp ties and gives trusted-router replay a recovery
path without a source change. App attribution is retained hosted acceptance. Unknown
or incomplete API history cannot prove that boundary; known legacy or failed
classification records conservatively use their recorded creation time so a
later genuine full run can recover. All requests are scanned so an early label
does not conceal a later ambiguous edit.

History queries begin at the later of PR creation and the existing 24-hour
freshness horizon. This avoids exhausting bounded pagination merely because
weeks of other PRs' policy runs accumulated; unreadable history inside the
bounded interval still remains explicitly blocking.

Policy polls code admission at sixty-second intervals for at most ninety minutes,
inside a ninety-five-minute workflow allowance. Queueing beyond that bound or
missing evidence remains blocking. Three metadata runner allocations and actual
waiting time must appear in cost evidence; no lower compute claim is inferred
from fewer code runs alone. The [hosted matrix](../ci-pr-edits.md#validate-before-activation)
includes missing-key and failed-add source pushes, rapid text edits, and old-base
partial retries after a green policy result.

## Older-PR preservation is still incomplete

The 24-hour floor is a substantive qualification of the original requirement:
an unchanged PR with passing targeted validation at age 23 hours becomes
inadmissible after a text edit at age 25 hours. An older full result also becomes
inadmissible when its creation falls outside the rolling horizon. The text edit
does not itself request replacement code work. This is not completed acceptance
or an implicit scope waiver merely because the conservative behavior is documented.

A repair needs durable, authenticated event evidence with an explicit incomplete
history state. A latest-summary comment cannot safely certify completeness after
an earlier write failed. Investigation identified contiguous workflow run numbers
as a possible registered-run gap detector, but a complete model also needs an
activation baseline, authenticated receipts, pagination/tamper handling and a
reviewed delivery boundary. This is an unimplemented design direction, not proof
that the limitation has been repaired. The original requirement remains in SPN-129.

## Immutable classification facts, 2026-11-02

**Decision: agent implementation decision with two independent nonimplementing
architecture reviews; implementation and full acceptance remain in progress.**
The history-preservation investigation exposed an unnecessary coupling between
classifier execution status and immutable event meaning. `exactTextEdit` is a
pure predicate of the original event; it reads no clock, current PR state,
credentials or network. A later actual edit is a new event. GitHub reruns retain
the original SHA and ref ([platform contract](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)).

The earlier latest-classifier-attempt rule could turn proven text into a new
full requirement merely because a retry's setup failed. That was conservative
implementation behavior, not a retained product requirement. The selected rule
preserves a correctly bound successful text proof across pending, cancelled,
timed-out or failed classifier retries. A full proof remains full at its original
request time. With no successful proof, pending remains unresolved and terminal
failure remains conservative full validation. Malformed/foreign identities remain
blocking; contradictory successful text/full proofs for the same event have no
trusted freshness boundary and cannot be admitted. Genuine code checks retain
all existing latest-attempt, source/base, full-plan and freshness guards.

Alternatives considered: keeping the old retry rule makes a history checkpoint
unsafe when an earlier run is retried and then expires; reading only surviving
old attempts cannot detect that lost execution. A signed comment ledger would
add credential/storage/lifecycle machinery. Both reviewers independently agreed
that immutable classification facts remove this artificial retry obligation
without weakening actual code acceptance. No new writer, credential or permission
has been introduced. Operator avoids unjustified reruns; Owner, Collaborator and
Link guest keep actual content, persistence and access failures blocking.

This is one necessary component, **not the age-preservation repair's completed
outcome**. The 24-hour floor remains. The next design is a versioned, authenticated
history checkpoint with an independently proved initial global sequence and
contiguous suffix through the current event. Checkpoints must retain complete
folded full obligations and strict/inclusive boundaries, work independently of
pending/failed code or invalid titles, and never replace original code results.
Do not seal unknown history, self-certify a missing prefix, treat a replacement
workflow's first run as activation proof, or infer complete event delivery from
run numbers. Missing underlying history and all covering checkpoints remain
missing evidence. No checkpoint has been implemented or counted as acceptance.
