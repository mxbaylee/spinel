# SPN-105 — Request-body parser security update

## Register the existing parser advisory

**Accepted — agent scope decision with independent review, 2026-10-26.** During
[SPN-067 PR #185](https://github.com/mxbaylee/spinel/pull/185), CI's dependency audit
reported GHSA-27r3-jxmh-p828. The base `72bec811423f9bad3eb1bdf535266d94421d989f`
and archive head `876cd35924bef59a4d90d92e53f1aba974f68f68` both resolve the same
body-parser 2.3.0. The new ZIP dependencies did not introduce the finding.

The [maintainer advisory](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828)
identifies an unhandled decoder error from a compressed frame followed by trailing
bytes. It affects 2.x before 2.4.0 and is fixed in 2.4.0. Existing authentication
routes already use the affected JSON parser before session checks. Archive ZIP
uploads reject Content-Encoding and bypass body-parser; their one-hour deadline
does not fix the existing decoder error.

The options were to bundle an application-wide dependency repair into the archive
feature, leave the audit finding implicit, or register a focused repair with its
own regression. The repository's scope-first process supports the last option:
SPN-067 can be reviewed against its own acceptance, while this unresolved defect
has a concrete pre-launch completion boundary. No current deployment is assumed,
and this decision does not authorize deployment or waive a failing CI gate.

Use a verified compatible fixed dependency and a subprocess regression, so the
reproducer can demonstrate process survival without taking down the test runner.
Do not use a broad automatic dependency update. Operator gains availability and
auditable patch evidence; Owner, Collaborator and Link guest keep service when a
bad request arrives. No persona receives new document permissions or UI behavior.

## Compatible parser repair and process-survival evidence

**Accepted — agent implementation decision, 2026-10-28.** The owner requested
implementation and merge of SPN-105. Express remains pinned at 5.3.0; its existing
`^2.3.0` parser range accepts the upstream fixed body-parser 2.4.0. Refresh only
that lockfile entry, including its registry integrity and dependency requirements.
The required content-type 2.1.0, iconv-lite 0.7.3 and qs 6.16.1 are already resolved,
so no other package version changes. There is no new direct dependency or override.

The alternatives were disabling compressed bodies or changing request middleware.
The compatible upstream repair preserves compressed JSON and the existing route
ordering, strict JSON parsing, decoded-byte limits, authentication and Origin
policy. Body-parser 2.4.0 also supports zstd; the compatibility regression includes
it alongside gzip, deflate and Brotli rather than claiming the upstream input
surface is identical. See the [release](https://github.com/expressjs/body-parser/releases/tag/v2.4.0)
and [package manifest](https://github.com/expressjs/body-parser/blob/v2.4.0/package.json).
Archive upload deadlines are not a decoder mitigation; the fixed parser must be
present before deployment or public exposure.

`server/request-body.test.ts` starts the real application in a disposable Node
subprocess using the production heap bounds. Its fixture has no uncaught-exception
handler. A valid compressed JSON frame and NUL byte reach the actual auth parser
with the configured Origin but no cookie. Only after its 401 response does the
client send 100 KiB of trailing bytes, followed by an authenticated health request
on the same connection. Successful draining, that response, another ordinary
request, and a clean child exit are required for gzip, deflate and Brotli.

The separate compatibility scenario verifies plain/compressed profile writes,
the exact 64 KiB decoded-body boundary and one byte over, strict and malformed JSON,
missing/invalid credentials, missing/foreign Origin and incorrect content type.
Auth's existing generic HTTP 400 parser-error response remains; workspace HTTP
413 and raw-image access/limit regressions remain in the existing suite.

Operator gains a narrow dependency repair and a regression that detects process
termination. Owner and Collaborator retain profile writes, request bounds and
availability; Link guest benefits from instance availability without any new
document access. All four retain the existing permission and Origin boundaries.
This change has no UI or deployment action.

body-parser 2.3.0: the child exited 1 with an unhandled Gunzip `Z_DATA_ERROR`
(`incorrect header check`). After the lockfile update and a fresh `npm ci`, all

```sh
npx vitest run server/request-body.test.ts server/http.test.ts server/app.test.ts \

  src/server/workspace/documents-http.test.ts \
  src/server/workspace/offline-creation-http.test.ts
npm ls body-parser --all
npm audit --json
```

The installed tree reports only Express 5.3.0 → body-parser 2.4.0. The audit
completed successfully with zero reported vulnerabilities, including no
GHSA-27r3-jxmh-p828. Local workloads were serialized and monitored; the focused
suite peaked at 2,045.2 MiB process-tree RSS and did not exceed the 2 GiB limit.
The first sandboxed test attempt could not collect process usage and produced no
validation result; the successful run used working process monitoring. Full CI
and both independent reviews are recorded against the final commit in the PR.
