## Contract

Account grants accept Viewer, Editor and File admin. Effective access takes the
strongest grant from the file and its ordinary ancestors; ownership remains a
separate, unique property above Admin. Every Space child uses its root role.
No child sharing or Admin guest link is introduced. The separate guest role type
remains View/Edit, with the existing HTTP/SQL validation.

File admins can manage other everyday accounts' View/Edit/Admin grants, guest
links, rename and recoverable outer trash. They cannot change the Owner, their
own direct grant, server accounts, permanent deletion or ownership handover.
Disabled recipients cannot receive a grant; disabled actors and stale/revoked
credentials remain refused by existing native/integration boundaries.

Moves authorize both the source and destination, preserve the file's owner and
never enter a Space through ordinary routes. Destination requires Admin on an
ordinary folder of the same owner. Only the Owner can choose their My files root.
A raw parent walk checks cycles after destination authorization, without exposing
private ancestor names. Rename reads the stored parent rather than substituting
the privacy-redacted projection. Personal filing remains separate, including
removing a reference for an Admin without moving/trashing the canonical item.

Recoverable outer trash enters the Owner's existing collection. Whole-Space
trash preserves earlier internal deletion batches. Account Admin includes Edit
for internal Space tree/recovery, but internal permanent deletion stays owner-only.
Ownership handover remains SPN-064. Server Operators stay content-blind; guest
links remain anonymous View/Edit, and OAuth/MCP retain their own scope ceilings.

The grants leaf-table migration preserves existing rows, original share dates,
foreign keys and indexes while extending its role constraint. It is transactional
and idempotent; it does not replace native content tables or add a storage engine.

## Legacy decision 145: Delegated File Admin boundaries

**Recorded:** 2026-10-22. **Status:** accepted.
**Authority:** Owner delegated administration direction; agent role implementation.
**Source:** [original decision #145](https://github.com/mxbaylee/spinel/issues/145).

**Question:** How should delegated file administrators move shared files without gaining ownership
or unrelated-folder authority?

**Options considered in the original source:**

A — require Admin on the source and destination, preserve the same owner, reserve the owner's root
destination for the owner, and return only authorized same-owner folders; B — accept any writable
destination, requiring cross-owner ownership semantics and potentially escalating inherited access.

**Outcome, rationale and current boundary:**

File Admin may manage grants and move within same-owner ordinary folders only when administering
both source and destination; the owner's root remains Owner-only. Do not permit own-grant
modification, transfer of ownership or moving into a Space through the ordinary folder path.
Preserve truthful direct/inherited role provenance and omit private ancestor paths. Guests never
become Admin and account Operators gain no document authority. This is the explicit extension of the
earlier owner-only outer administration in decision
[#118](SPN-078.md#legacy-decision-118-space-roles-and-internal-editing).

**Persona tradeoffs recorded at the time:**

Owner retains the sole ownership boundary and permanent deletion/recovery control. Collaborator can
manage sharing and organize files in destinations they administer, with truthful role provenance.
Operator gains no content access and retains a single grant schema. Link guest remains View/Edit
only within its existing scope.

## Legacy decision 147: Measured desktop Storybook timeout

**Recorded:** 2026-10-22. **Status:** accepted.
**Authority:** Agent CI resource judgment.
**Source:** [original decision #147](https://github.com/mxbaylee/spinel/issues/147).

**Question:** How should SPN-079 retain complete acceptance checks when desktop Storybook dependency
setup consumes its job budget?

**Options considered in the original source:**

A — keep retrying the 15-minute job and hope for a faster mirror; B — increase only the desktop job
timeout to 25 minutes while preserving every suite, assertion timeout, artifact, full-PR story
selection and aggregate gate; C — skip or narrow the failing gate.

**Outcome, rationale and current boundary:**

Increase only the desktop Storybook job to 25 minutes after measured Ubuntu dependency installation
consumed 12 minutes 18 seconds. Preserve the complete desktop catalog/interactions/native proofs,
other viewport coverage, aggregate gate and review requirements. This bounds infrastructure variance
rather than loosening product assertions or discarding screenshots. The previous audit-request
optimization in decision
[#138](SPN-091.md#legacy-decision-138-avoid-duplicate-registry-audit-requests) remains distinct;
neither proves a successful audit when the endpoint is unavailable.

**Persona tradeoffs recorded at the time:**

Operator benefits from bounded, reliable CI rather than repeated infrastructure timeouts. Owner
retains full regression and screenshot evidence before merge. Collaborator retains every
interaction/layout assertion. Link guest retains all anonymity, scope and unavailable-state checks.
None gains a product capability or weaker authorization.
