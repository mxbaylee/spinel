## Legacy decision 130: Literal bounded CSV import

**Recorded:** 2026-10-21. **Status:** accepted, post-launch implementation pending.
**Authority:** Agent grooming semantics, 2026-10-21.
**Source:** [original decision #130](https://github.com/mxbaylee/spinel/issues/130).

**Question:** Should the first CSV import preserve all fields literally, or infer formulas, dates,
numbers and headers automatically?

**Options considered in the original source:**

A — import UTF-8 comma-separated fields literally, preserving row/field order, empty values, quoted
commas/newlines, escaped quotes, leading zeros and the first row as data; B — automatically infer
numeric/date/formula/header meaning, risking irreversible reinterpretation and a broader validation
surface; C — add mapping, type and data-cleaning controls to the foundation, expanding scope.

**Outcome, rationale and current boundary:**

Import UTF-8 comma-separated fields literally, preserving BOM support, CRLF/LF, Unicode, row/field
order, empties, quoted commas/newlines, escaped quotes, leading zeros and the first row. Do not
infer dates/numbers/headers or execute formula-looking fields. Reuse bounded native validation,
creation access and cleanup; invalid/oversize or revoked creation leaves no partial document. This
chooses the narrow SPN-093 behavior after launch, not a delivered importer or owner preference for
future mapping controls. Guests gain no import capability.

**Persona tradeoffs recorded at the time:**

- Owner: literal imports preserve leading zeros, identifiers, quoted content, Unicode and the first row; automatic typing could save cleanup but can silently change data.
- Collaborator: predictable literal cells avoid formula execution and interpretation that differs from the source, while ordinary creation permissions still apply.
- Operator: bounded CSV parsing with no inference framework is easier to maintain; no remote fetching or additional conversion service is needed.
- Link guest: no import or broader document access is added. Preserving formula-looking text avoids introducing behavior into a document that a guest may later be allowed to view.

## 📥 CSV and TSV scope

2026-11-22 — accepted. Source: owner backlog-grooming chat; implementation assessment by the agent.

Support two common delimited-text types, CSV and TSV, with the same literal-value, bounded UTF-8 and atomic native publication contract. This extends decision #130 from comma to comma/tab; no proprietary or Office formats such as XLSX, plugins, delimiter guessing, implicit formulas or coercion. Effort stays M: one parser contract with two explicit delimiters and shared publication/access/cleanup; reassess if native import integration changes. Owner and Collaborator can bring common tables; Operator has no converter service, and Link guest gains no creation access.

### Effort check and first checkpoint

Ticket effort **M**, rechecked 2026-11-22. Rechecked against the code on 2026-11-24 before building: **M holds**.

- The native importer (`PortableFiles.import` → `prepare` → `publish`) already owns access, fresh IDs
  (`snapshotIdentity`), the 20 MiB transfer limit, the 10 MiB native-content limit, layout limits
  (`validatePortableLayout`) and one-transaction publication, so the new work is a parser, one
  conversion to a native workbook, and widening the client picker. No new route, table or CI suite.
- **Checkpoint (before coding):** the smallest complete slice is (1) a pure, bounded delimited-text
  parser, (2) a workbook builder that writes every non-empty field as a string cell, (3) an `import` branch
  on `.csv`/`.tsv` filenames that calls the existing `prepare`/`publish`, (4) the Import dialog accepting
  both types, and (5) tests, stories and docs. **Revise to L immediately** if any of these turn out to be
  true: Univer renders or edits string cells as coerced numbers/dates, so literal values need a style or
  format per cell; the existing layout validation cannot bound a parse whose input is within the byte
  limit; or the shared transfer admission cannot cover a text body.
- Decisions made while implementing (agent, using all four personas):
  - **Parse on the server.** The client sends the decoded text; the server owns limits, atomicity and
    cleanup, so a hostile client cannot skip them. The client rejects non-UTF-8 bytes first (fatal
    `TextDecoder`) because a lossy decode would silently change data.
  - **Type by filename only.** `.csv` is comma, `.tsv` is tab; the file's content is never sniffed. Any
    other extension (including `.txt`, `.tab`, `.psv`) is refused with the supported list named.
  - **Strict quoting.** An unterminated quote, a quote inside an unquoted field, or text after a closing
    quote is malformed and refused, rather than repaired by guessing.
  - **Rows keep their own length.** Short rows are not padded or rejected; the sheet is as wide as the
    widest row. A blank line is a row with one empty field. One trailing line break does not add a row.
  - **Empty fields write no cell**, so an empty value stays empty and does not count toward the
    populated-cell budget.
  - **One worksheet named `Sheet1`**, workbook named from the filename without its extension.
  - **Waiting uses the shared compact runner.** The import dialog's one waiting row (native and
    archive) uses `LoadingReview` at compact size, per the owner's direction that loading concepts are
    common components ([states.md](../design/states.md#loading)). Owner, chat 2026-11-24.
  - **Empty fields are budgeted in total.** They spend no cell budget, so a 20 MiB file of bare
    delimiters parsed to about 21 million fields (about +300 MB, measured in review). Total fields are
    capped at 2,000,000, counting empty ones, and refused at the first excess.
  - **Playbook edits ride in this PR by owner request.** AGENTS.md says a playbook pattern normally
    lands in its own PR first. The owner asked, mid-review on 2026-11-24, for the loading guidance to be
    updated before this push so the miss does not recur, so `docs/design/README.md`, `states.md` and
    `review-runbook.md` change here. The rule covers every region that waits for content: at the owner's request the existing
    standalone text-only rows that load, open or check content (52 rows in 39 files under `web/`) now use
    the compact runner in this PR. Left as text on purpose: button labels ("Saving…"), the editors' save
    slot, loading text that shares one status line with a result or access message (PDF export, appearance access, search count, the worksheet picker placeholder), and an action's progress line beside its pending button (for example "Waiting for your
    passkey…", "Requesting your backup…", "Sending feedback…", "Backup in progress…").
  - **Fields are sliced, not built per character.** A review measured about 1.3 GB of server memory
    for one hostile 20 MiB quoted field built character by character. Fields are now cut out with
    `slice` and doubled quotes undone with one `split`/`join`; the same quote-heavy input peaked at
    about 225 MB locally (Node 26.13.0, `process.memoryUsage().rss`, one run).
