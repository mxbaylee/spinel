# SPN-081 — Apply the approved sharing dialog design

## Preserve current permissions in the approved dialog

**Date:** 2026-10-23. **Status:** accepted implementation direction; verification pending.
**Authority:** agent implementation judgment with independent parent-agent concurrence,
under the owner's current backlog instruction to proceed on all-persona agreement.
The [approved sharing design](../design/sharing.md) and
[SPN-047 approval](SPN-047.md#legacy-decision-126-approved-redesign-and-its-limits)
govern appearance; [SPN-079](SPN-079.md#contract) governs the implemented roles.
This is not owner screenshot approval or a new permission policy.

The choice is to apply the approved people-first dialog and guest-link menu while
preserving the current File admin and whole-Space behavior. Implementing the old
two-role mock literally would regress SPN-079; retaining competing inline panels
would leave the approved migration unfinished. Sharing owns the Base UI modal;
Dashboard and Space action callers must not wrap it in another sharing modal.
The separate replacement/Space confirmation is the existing approved confirmation
pattern, with its own semantic title and focus return.

Owner retains exclusive ownership and recovery; their role cannot be reassigned
here. Collaborators see confirmed effective access, inherited access without a
private ancestor name, and explicit staged direct changes. A File admin cannot
change the Owner or their own direct grant. Link guests remain anonymous View/Edit
only; a Space link covers all current and future contents and never child-specific
sharing. Operator accounts remain excluded by the server and gain no file access.
The API and authorization policy are unchanged.

## Implementation boundaries

- Use the shared Base UI Modal, Button and ActionMenu with existing theme tokens.
  Native role selects retain disabled-option and platform keyboard/touch behavior.
  File admin is present only for account grants, never guest links.
- Keep confirmed people and guest-link state until a successful response. Failed
  writes retain the selected draft and expose retry. Applying one person does not
  discard another person's staged choice. Failed network responses show the last
  confirmed state without claiming that the server could not have committed.
- Reset state and invalidate pending responses on item/access change or unmount.
  Guard `itemsRequest` before its sign-in redirect, then guard state publication
  after JSON decoding. A late old-item response cannot navigate or reopen the next
  view. Mutation refs also reject duplicate activation before React rerenders.
- Copy the account address from the footer. Clipboard denial exposes manual copy.
  A guest address is retained only from successful creation/replacement in this
  mounted dialog; GET cannot recover it, and closing/reopening removes it. Replace
  requires confirmation for every supported file; Space create and turn-off keep
  explicit all-contents confirmation. Guest role selection alone never rotates a
  link. Existing guest-revocation browser assertions remain intact.
- Dialog and menu focus stay trapped/return to their stable trigger. Close and Done
  are disabled during a mutation; navigating externally still invalidates results.
  People and guest-link load failures have separate retries. Each permission scope
  continues to be rechecked by the existing server on every mutation.
