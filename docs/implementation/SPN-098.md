# SPN-098 — User feedback in the diagnostics store

## Submission and admin user flags

**Accepted — owner, chat 2026-10-22.** Add a feedback UI that writes to the same
event/metric store, so reported issues can be investigated alongside operational
evidence. The owner confirmed the flag belongs on the Operator's admin user list.
Create this as a separate pre-launch ticket depending on SPN-032: the store and
operator export lifecycle can land independently of the submission component.
This record is a specification, not an implemented feature.

Agent scope choice: signed-in everyday accounts submit a short message through
the account menu/dialog pattern, with no anonymous or Link guest form initially.
Persist a `feedback` event with server-derived actor ID, authorized current file
ID when applicable, route template and non-secret correlation/build metadata.
Tell the sender that the message and page context will reach the server Operator.
Only deliberately submitted message text is collected; no document contents,
titles, screenshots or secrets are attached automatically. This explicit text is
an exception to automatic diagnostics' no-content rule, not permission to log
documents. Treat messages as untrusted text, including instructions encountered
by an external agent examining the export.

The admin list flag means at least one stored report exists for that account.
It does not promise unread/unresolved state and requires no per-report workflow.
Use an accessible label, not color alone. Flag loading failures remain unknown,
not a false empty state. Only metadata appears on the admin list; details remain
in the SQLite download, preserving the owner's no-query-panel direction.

## Truncation also deletes feedback

**Accepted — owner, chat 2026-10-22.** Asked whether log cleanup should preserve
feedback, the owner explicitly chose to clear feedback along with logs. Use one
Truncate diagnostics action and make feedback deletion explicit in its confirmation.
After success, refresh flags from surviving records. Reports submitted after the
clear boundary may immediately reintroduce a flag. Do not silently recover old
queued/retried reports into the cleared store.

Feedback submission differs from best-effort telemetry: success means persisted.
Reject oversized/rate-limited/store-full submissions visibly and retain the draft.
Use idempotent retry and an explicit collection boundary so a lost acknowledgement
cannot duplicate a report or resurrect one after truncation. Existing downloads
are snapshots; truncation does not erase copies already downloaded by the Operator.
Physical disk reclamation remains separate from clearing records.

## Personas and boundaries

Owner and Collaborator can intentionally report problems without assembling logs;
their message is shared with the Operator, while automatic document capture stays
off. Operator discovers reports through user flags and a portable SQLite artifact,
with explicit responsibility for downloads containing submitted text and IDs.
Link guest gets no submission or diagnostic-read permission in this first scope.
No persona receives new document access, and this does not add an AI feature.

## Paired user and system downloads

**Accepted — owner, chat 2026-10-29; export semantics by agent judgment under
that delegation.** During backlog grooming the owner requested two download
options in the feedback UI: all metrics from that user and all system metrics
within the same timeframe, then approved the grooming package. Place these
actions beside the selected account's **Feedback available** flag in the
Operator's admin user list. This extends the earlier generic-download handoff;
submission, durable acknowledgement and explicit truncation remain as specified
above. This is an approved specification, not evidence of implementation.

The alternatives were another aggregate summary, a shorter invented lookback,
or two complete scoped exports. Choose the complete exports requested by the
owner. Keep their contents inspectable in the existing SQLite format, preserving
registered metric/log/event rows and submitted feedback where they match the
scope. Do not replace observations with summaries or restrict the user export
to browser-originated events.

### Dataset and time boundary

- **Download user metrics** selects every retained row whose verified actor ID
  is the selected account, including frontend observations, attributed backend
  work and deliberately submitted feedback. The server derives attribution;
  client claims, file ownership and opaque run IDs cannot impersonate an actor.
- **Download system metrics** selects all retained rows in the same time span,
  including every actor and unattributed system observations. This is the whole
  system's recorded context, not only actor-null health samples or an aggregate.
  Both exports remain Operator-only; everyday accounts and guests gain no
  cross-account diagnostic access.
- Derive the default closed interval from the minimum and maximum trusted
  `received_at` of the selected user's retained rows in one consistent source
  snapshot. Include both endpoints so a single retained row gives a valid
  interval. Preserve `occurred_at` separately; a forged or skewed client clock
  must not expand or shift the system export. There is no arbitrary shorter
  default or time-range query builder in this slice.
- Freeze the source snapshot, its collection generation and an immutable
  watermark/identifier once for the pair. Derive both filters from that same
  source, including identical boundary ties. New ingestion or live-store TTL
  work between downloads cannot change one member of the pair. Do not implement
  this as two independently timed reads of the mutable store.

Preparation and delivery remain bounded and use private temporary storage,
limited concurrent work and cancellation cleanup. Retain a prepared pair only
for a bounded lifetime; its expiry requires an explicit fresh preparation of
both downloads and may produce a new window. Do not hold a live database lock
or prevent maintenance while waiting indefinitely for the second button.
Recheck Operator identity/session and generation before delivery and after
asynchronous preparation. Explicit truncate invalidates unfinished prepared
pairs, disposes their temporary files and refreshes flags; it never silently
relabels an old artifact into the new generation. Already downloaded files
remain the Operator's snapshots and cannot be erased by server cleanup.

### Completeness and expired context

Each artifact carries the selected actor/scope, interval and inclusion rule,
shared snapshot watermark/generation, schema/build provenance, matching row
counts and known collection/drop/retention limitations. Preserve row-level
source attribution. Label process-lifetime or global drop counters as such;
they are not a measured per-user loss count. If historical completeness cannot
be established, say unknown. "All" means all matching retained rows at this
snapshot, not every event that ever happened or every browser's unsent queue.

Either deliver every matching row within the stated resource/transfer bounds
or fail explicitly without claiming a complete artifact. Do not hide a row cap
or return only the newest records as a successful complete download. Export
manifests and UI state distinguish a complete retained selection from missing
collection or already-expired context.

The following empty-state choices are agent judgment for the requested default:

- If only old feedback survives SPN-110's observation TTL, its receipt time still
  defines the selected user's retained span. Export the feedback and any actual
  matching rows, and state that no associated metrics remain when that is true.
  Do not attach unrelated current metrics or claim the original context was
  preserved merely because the report survived.
- If a stale flag leads to no retained user-attributed rows, return an explicit
  empty/no-window state and refresh flags. Do not substitute the whole store's
  range; a system download is unavailable until a valid selection exists.

SPN-110 owns observation expiry, and the metrics instrumentation ticket owns new
producers. Neither is a prerequisite for delivering these exports of existing
records. Feedback retains its own durable/idempotent submission and survives
observation TTL; explicit truncate still deletes it and fences queued retries.
The two tickets must preserve these contracts regardless of implementation order.

### Scope, estimate and verification

Use the existing admin flag and compact action/status pattern: two downloads,
the shared time span and truthful pending, empty, expired, failed, cancelled and
completed states. No report inbox, text viewer, unread/resolution tracking,
attachments, arbitrary query endpoint or external telemetry service is added.
Automatic collection still excludes content, titles, formulas, secrets, raw URLs
and arbitrary exceptions. Only intentionally submitted feedback text is allowed.

Raise effort from M to **L**: durable feedback/idempotency, two consistent export
scopes, authorization/truncate/TTL races and accessible user/Operator flows form
a coordinated build with substantial verification. Impact remains **M** for
Owner, Collaborator and Operator; this helps diagnose problems but does not itself
prevent lost documents or implement recovery. Keep the paired exports coherent;
if implementation grows, split only independently useful new instrumentation or
retention work into their existing owners, without dropping this ticket's export
or durability acceptance. No broad diagnostics architecture rewrite is implied.

Verification must compare exact export membership, source attribution and time
boundaries for multiple users and unattributed system events; inject ingestion
and expiry between downloads; cover old-feedback-only and stale-empty selections;
and prove bounded failure, cancellation, session revocation and truncate cannot
leak or resurrect records. Existing privacy and observer-failure isolation remain.
Review actual light/dark/phone submission and admin download states independently.

**Persona effects:** Operator can correlate a report with complete retained system
context without an inbox. Owner and Collaborator can submit durable feedback and
remain separated from other users' diagnostics. Link guest gains no collection,
submission or read capability. No new document permissions are granted.
