## 🧭 Bound recovery to unresolved application construction

**2026-11-04, accepted implementation choice; agent judgment under the owner's
request to continue SPN-120. Real-platform acceptance remains pending.**

The preserved native trace locates the failure inside `Application(pid)`, before
its return and before the requested `doJavaScript` invocation. Apple's
[JXA reference](https://developer.apple.com/library/archive/releasenotes/InterapplicationCommunication/RN-JavaScriptForAutomation/Articles/OSX10-10.html)
documents PID addressing, object specifiers, property-get calls and command calls
as distinct operations. A local, noninteractive `osascript` invocation addressing
nonexistent PID 2147483647 on macOS 26.5.2 observed the exact constructor exception:
`message="Application can't be found."`, `errorNumber=-2700`. It touched no live
Safari profile and proves only error shape, not the hosted failure's OS cause or
whether another resolution attempt succeeds.

Choose at most one immediate second construction of the **same numeric PID**, only
when both that numeric error and message match in the constructor's own catch.
Before the second construction, positively re-read PID, liveness, bundle,
executable and launch time and require the original identity. Do not sleep,
restart the browser, select by name/path, change consent, spawn another helper,
or restart a command budget. If revalidation or the second construction fails,
retain both errors and throw the original constructor failure. A constructor
success is followed by another exact identity check before action dispatch.
The host-observed executable is also checked at the beginning of each request.

This does not assume every `-2700` is transient: an unclassified constructor
failure is fatal, as is the same exception thrown by a title read, evaluation,
quit or baseline action. No requested action exists inside the recovery catch.
The supported safety boundary is narrowly established by control flow and the
native exception shape; hosted validation must determine whether it is useful
for the demonstrated restart failure. Unknown OS cause remains explicit.

Reject blanket request retries and permission-error recovery. Replacing JXA with
a different automation protocol would introduce dictionary/dispatch/lifecycle
scope beyond this finite repair. Preserve the existing AppKit loader, normal
consent, 8-second identity/default request, 5-second baseline and original
remaining consent-request budgets. The same single host process bounds both
constructions and the one requested action. Complete scope remains **L**, including
native investigation, shared-action controls, evidence and integration.

Every request now retains mode, target, source hash, timeout, elapsed time,
success/failure and complete bounded stderr in `safari-profile-probe.json`, even

Design limits, stated plainly:

- Identity is revalidated immediately before dispatch, but a process swap between that
  check and the dispatch itself (TOCTOU) cannot be closed from JXA; the exact
  PID/bundle/executable/launch-time check narrows it and native runs must show it holds.
- Helpers throw the first error: polling and consent loops (`waitForSafariValue`,
  `observeSafariTitle`, `readSafariBaseline`, `requestSafari`) rethrow instead of
  swallowing, and required baseline errors are kept separate from the optional
  `captureError`. Native validation treats a polling failure as fatal, with no retry.
- The constructor error text and number the recovery matches (`-2700`,
  "Application can't be found.") come from the recorded original failure; native
  acceptance still must show the recovery fires and preserves every attempt.

One native Desktop offline workflow, two exact-head reviews and every selected gate
remain required; none is claimed here.
