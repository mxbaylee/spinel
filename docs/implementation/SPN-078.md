## 1. Product contract and delivery boundary

The authoritative acceptance is the [original SPN-078 ticket](https://github.com/mxbaylee/spinel/blob/febaaa44f53798b1131c99426e2950fe026067f5/docs/todo/SPN-078.md), with the
[Space design and delivery slices](../design/spaces.md). Decisions
[#116](https://github.com/mxbaylee/spinel/issues/116),
[#117](https://github.com/mxbaylee/spinel/issues/117),
[#118](https://github.com/mxbaylee/spinel/issues/118), and
[#126](https://github.com/mxbaylee/spinel/issues/126) remain in force.

- A Space is one real file inside the existing outer folder system. Existing
  folders and standalone Docs/Sheets continue to work unchanged.
- Exactly one everyday account owns the Space and every descendant. Effective
  View/Edit comes from the Space and its readable outer folder ancestry; children
  cannot override it, acquire direct grants, or have their own guest links.
- A Doc, Sheet, or grouping folder can contain children. Children have stable
  identities, explicit sibling order, and the same Space boundary at every depth.
- View reads; Edit manages internal content/tree and account recovery; Owner also
  controls outer sharing, rename, move, trash, and permanent deletion. The server
  Operator never acquires content access. Delegated Admin belongs to SPN-079.
- Whole-Space moves, trash/restore, persistence and serialization preserve IDs,
  content, order, formula bindings, and existing internal trash batches.
- Ordinary creation/navigation stays disabled through this foundation and SPN-091
  until SPN-092 proves guest and cross-feature integration. A supported internal
  operation must authorize Space scope; every incomplete public capability fails
  closed. A hidden UI is not an authorization boundary.

SPN-091 owns authenticated UI wiring, selection/history/deep links, and account
Trash. SPN-092 owns guest links/navigation, cross-feature acceptance, backup and
ownership-transfer integration. Neither follow-up excuses an unchecked route in
this PR. No standalone-to-Space conversion, child extraction, nested Spaces,
bulk offline download, new export format, or new formula syntax is introduced.

## 3. Current code and chosen implementation shape

`WorkspaceStore` owns `workspace_items`, inherited grants, personal filing and
metadata access. Native Doc/Sheet snapshots, images, collaboration generations,
history and formula bindings already use its item IDs. Preserve those IDs and
services; do not create another content engine or copy native snapshots on moves.

`src/server/backup/spaces.ts` is **DigitalOcean object storage**, not a product
Space model. Do not confuse its `SpacesStore` with the implementation below.

Storage choice: [routine decision #135](https://github.com/mxbaylee/spinel/issues/135),
closed as decided on 2026-10-21 after weighing all four personas:

1. Extend the stored `workspace_items.kind` constraint with real `space` roots.
   Keep the ordinary create-kind allowlist restricted to Folder/Sheet/Doc.
2. Add nullable `space_id` and integer `space_position` to internal items. Ordinary
   items and the outer Space root have neither. A child always belongs to one
   Space, never another child or an unrelated root.
3. Keep `workspace_items.parent_id` as the canonical current parent. A Space root
   may live in an ordinary same-owner folder; an internal item has a parent inside
   the same Space, or the Space root. Persist sibling order separately from name.
4. Persist one recovery record per internally trashed subtree root: Space ID,
   item ID, original parent ID, original sibling position, deletion timestamp,
   deleting actor, and trash batch. Reuse existing `trashed_at`/`trash_batch`.
5. Detach an internally trashed subtree root to the Space root while preserving
   its descendants. This lets its former parent disappear without violating the
   existing restrictive parent foreign key. Original parent identity remains in
   recovery metadata, not in a dangling foreign key or a pre-authorized name.

Implementation files under `src/server/workspace/`: `space-schema.ts`
(migration), `space-scope.ts` (account authorization), `space-structure.ts`
(bounded complete-graph validation), `spaces.ts` (transactional tree service),
`space-recovery.ts` (internal recovery), `space-lifecycle.ts` (owner-only outer
lifecycle), and `ordinary-scope.ts` (legacy exclusion), with focused adjacent
tests. The small explicit services reuse existing IDs and native cleanup hooks;
there is no generic policy framework or parallel content engine.

### Schema and integrity requirements

- A Space root has `kind='space'`, no `space_id`, and no internal position.
- Each internal item is Folder/Doc/Sheet, has the root's owner, a nonnegative
  integer sibling position, and an acyclic parent chain ending at that same root.
- No per-child grants, links, or personal placement entries are valid. Existing
  ordinary-item data is not silently reinterpreted or converted.
- Index scope/parent/order lookups. Avoid loading snapshots merely to list the
  tree. Use iterative/recursive-SQL traversal with cycle detection, bounded input
  and request work, rather than an arbitrary product nesting limit.
- Write sibling reordering, reparenting and recovery changes in one existing
  `AuthStore.transaction`. Re-read authorization within that transaction. A failed
  validation leaves the entire tree and native content unchanged.
- SQLite is pre-production. A transactional migration is acceptable; do not invent
  a live-production or zero-downtime requirement. Preserve deliberately retained
  existing data, foreign keys, indexes, native IDs and snapshots. Test both fresh
  and upgraded databases and an injected rollback before enabling startup wiring.
- SQLite CHECK changes may require a table rebuild. Use the documented safe rebuild
  order, restore foreign-key enforcement even on failure, and run foreign-key
  verification. Do not rename the live table first or use `writable_schema`.
  Follow [SQLite's generalized ALTER TABLE procedure](https://www.sqlite.org/lang_altertable.html#otheralter).
  Preserve existing `collaboration_deleted` and `spinel_generation_deleted`
  cleanup triggers along with all other table indexes/triggers. Startup wiring
  must precede the collaboration SDK connection. The migration was published
  unwired first; startup now calls it after the migration tests, legacy boundary
  implementation and real HTTP/MCP refusal tests established that boundary.

## 4. Access model and service operations

The ordinary `WorkspaceStore.get()` contract must not silently start admitting
Space children to every legacy route. Keep an explicit distinction between
legacy file capability and a deliberately scoped Space operation. Centralize
effective-role resolution rather than duplicating grant SQL in each feature.

Resolve a child from `(actor, spaceId, childId, requiredCapability)` and verify:

1. Active everyday caller; reject Operator and all guest principals in this slice.
2. A valid, active Space root with an active owner and no trashed outer ancestor.
3. Exact child membership, same owner, valid same-Space ancestry, and appropriate
   live/trash status. A caller-supplied Space ID is never trusted on its own.
4. Most generous root/outer-folder grant; never inspect a child grant for access.
5. Capability: read, internal edit/recovery, outer owner operation, or permanent
   deletion. The same checks run again after awaited work and before committing or
   emitting data. A captured role or an earlier successful read is not a permit.

Disabled-owner handling is **Space-specific**: current standalone history
explicitly permits an active collaborator to retain access to a disabled owner's
file. Preserve that unrelated behavior; do not globally change all file policy.

Implemented service operations, internal and tested rather than registered as
ordinary application endpoints:

- Create a root under an owned outer folder; list/resolve the authorized tree.
- Create a Doc/Sheet/folder with server-generated ID, inherited owner and scope.
- Rename, move and reorder within that Space; reject cycles, foreign children,
  foreign parents, nested Spaces and conversion/extraction attempts atomically.
- Trash an internal subtree; list account recovery roots; restore the original
  subtree to a readable valid original parent or root with a fallback reason.
- Permanently delete a confirmed subtree as Owner, including bounded content and
  image cleanup; preserve all content on cancellation or an invalid stale request.
- Move/trash/restore the outer Space using owner-only existing file semantics,
  retaining earlier internal trash records and all child identities.

Reuse snapshot/image/collaboration/history services only through an explicit
authorized Space capability. Do not add a raw internal bypass to their public
methods. Wiring of each supported operation needs its own authorization tests;
until then that operation remains unavailable.

## 6. Recovery and persistence acceptance

- Duplicate names, deep trees and reorder/rename survive closing and reopening the
  database with exact IDs, parent edges, positions and original native snapshots.
- Whole-Space move changes only the outer parent; references never use paths.
- Internal trash keeps one recoverable deletion root and its descendant boundary;
  earlier independently trashed subtrees retain their own batches.
- Whole-Space trash/restore hides/unhides the collection without reviving its
  earlier internal tombstones. A trashed ancestor denies live child access.
- Restore checks its current Space and original parent afresh. A missing,
  unreadable, trashed or invalid original parent causes a root fallback; its name
  is never disclosed from saved metadata without present read permission.
- Ordinary My files Trash does not list internal nodes. Account editors may use
  the internal recovery collection; viewers and guests cannot query tombstones.
- Persistent IDs/native contents/formula bindings and recovery records round-trip
  through serialization. Exercise dangling membership, cross-owner ancestry and
  malformed cycles as refusal cases, not partial-success recovery.

### Implemented behavior

- Transactional migration preserves native IDs/data, indexes, foreign keys and
  cleanup triggers, rejects partial/unrecognized schemas and rolls back on
  failure. Startup now calls it immediately after `WorkspaceStore` initialization,
  before the collaboration SDK opens its connection.
- `resolveSpaceScope` supplies fresh live account View/Edit and root-only Owner
  checks. `SpaceStore` creates/reads roots and children, shares roots, and changes
  names/parents/order atomically. The bounded complete-graph validator includes
  tombstones and recovery records, rejects malformed/foreign attachments, and
  uses indexed parent traversal. These services have no public routes.
- Ordinary discovery, direct-ID operations, grants, tags, placements, search,
  links and Trash refuse hidden roots/members. Cleanup retains an entire ordinary
  subtree containing a Space while unrelated eligible ordinary trash can expire.
  Actual HTTP, socket-upgrade and MCP denial fixtures cover the broader boundary
  inventory, including stale guest credentials and native images/content.
- `SpaceRecoveryStore` implements account-editor internal trash/list/restore and
  owner-only confirmed deletion. Recovery preserves original location/order,
  independent deletion batches, native content and identity. Unavailable original
  parents fall back to the Space root without disclosing their locations.
- `SpaceLifecycleStore` implements owner-only whole-Space trash, restore and
  confirmed deletion. Root-only trash leaves child data and earlier batches
  unchanged; restoration does not revive earlier tombstones. Deletion validates
  the exact graph/version, retains cleanup hooks, and rolls back on late failure.
- No automatic Space expiry is enabled. Decision #135 requires a retention choice
  before enabling it. Operational backup/owner-transfer acceptance, UI and guest
  integrations remain in SPN-091/092/079 as described above.
