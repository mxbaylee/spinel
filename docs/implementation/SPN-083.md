# SPN-083 — Entry and consent screens

## Quiet entry without changing authentication

2026-10-23 · accepted implementation choice; visual acceptance pending.

The approved SPN-047 [account design](../design/account.md) provides a quiet
single-task arrival, setup, invitation, recovery and consent layout. Reusing the
prototype's local passkey simulation would replace real cancellation semantics;
retaining the workspace rail would keep competing navigation. A small
presentation-only `EntryFrame` and controlled `AuthEntry` instead leave App's
WebAuthn ceremony, setup proof, invite validation, secret stripping, cancellation
fencing, session checks and validated Space/connection returns intact. Console
recovery already uses the approved composition and retains its independent
finishing boundary unchanged.

Arrival and existing sign-in links show “Your workspace.” and one passkey action.
Invitations still require a name; recovery names the existing account and warns
about replacing passkeys and signing out other devices. Setup separates the
Operator account from the everyday document account. Invalid links cannot start
a ceremony. Loading, unreachable, pending, cancelled and failed states retain
truthful status and retry. Cancel preserves the entered name. Keyboard focus
follows the pending/retry action without pulling focus out of the help dialog.

Need help appears once, opening a dialog with a semantic key title icon. Member
guidance precedes expandable Operator commands. Commands are text only, including
the existing console admin recovery command; setup cannot recover an existing
account. Appearance uses the existing browser-local store and direct header
control, with 44 px phone/coarse targets.

Owner and Collaborator get consistent arrival, recovery and retry. Operator keeps
its separate privileges, setup proof and console recovery. Link guests remain on
their guest routes; entry exposes no files or new permissions. No authentication
method, dependency, service or server route is introduced. Agent judgment applying
approved SPN-047 direction; parent review concurred with all-persona scope.

## Consent preserves the pending transaction

2026-10-23 · accepted implementation choice; visual acceptance pending.

Consent uses the quiet frame and Base UI actions, retaining the unverified client
name, callback origin, signed-in account, exact read/edit scopes and reminder to
approve only a request the person started. Read-only requests explicitly cannot
edit. Existing expiry, unavailable-session, Operator restriction, request/submit
failure and connection-limit states remain. At the limit, Allow is disabled while
Cancel remains usable. The server still decides grants and redirects; the page
accepts no callback URL. Sign out and account/administration return remain
available outside a pending decision.

The old rail's Sign out discarded the pending request when switching accounts.
On `/connect` only, successful sign-out now uses the existing `signInPath()`
validator to retain its opaque UUID. Arbitrary return URLs and malformed IDs are
discarded. Other sign-out destinations and offline queuing remain unchanged.
This preserves the return address without weakening the existing session binding.
An Operator cannot load consent details, so an unbound request can continue after
signing in with an everyday account. Once an everyday session has viewed consent,
the server binds the request to that session. Signing out does not release or
rebind it: another session, including the same account after a fresh sign-in, is
refused and must start again from the assistant. The unavailable state explains
that next step. Owner/Collaborator retain deliberate approval in the bound session;
Operator still cannot grant document access; Link guests gain no account capability.
Agent judgment within the explicit pending-return requirement, clarified after
independent source review. This is not a general promise to transfer consent
between accounts.
