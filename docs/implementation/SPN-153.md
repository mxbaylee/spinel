## ✅ Test plan and evidence (2026-11-25)

**Source/runtime:** branch from `origin/main` `652a4799`, Node 26.13.0, macOS
(`/var` → `/private/var`), fresh `npm ci` in the worktree so the postinstall patch
ran on the installed `@univerjs/core`. All runs went through `scripts/serial.ts`.

**Original failures kept:** `node --test` on the two focused files failed exactly
the two named tests (`/private/var/…` actual against `/var/…` expected); the full
`npm test` script suites ran 1027 tests, 1022 passed, 2 failed (the same two), 3
skipped. The third named test, "the shipped, patched @univerjs/core has one pooled
helper…", **passed** in both runs.

**Repair:** `scripts/ci/offline-upgrade-dependencies.test.ts` wraps each expected
path in `fs.realpathSync` (`real()`), because Node reports resolved modules by real
path. The assertions still compare the exact resolved file, so a wrong tree still
fails. Five expectations in each of the two tests needed it (ten in all); each
test stops at its first failed assertion, so the run showed only one per test. No
production code changed.

**After:** focused run 21 of 21 pass; full script suites 1027 tests, 1024 pass,
0 fail, 3 skipped.

**Detecting negative:** in a scratch copy (the repository and installed package
untouched) the archived-lock comparison `isDeepStrictEqual(entry, current.packages[path])`
in `e2e/offline-upgrade-dependencies.ts` was disabled. With the new `real()`
expectations, "external dependency drift is rejected…" and "an isolated historical
install preserves transitive externals…" then fail and the other seven pass.
Normalising paths does not hide drift.

### 🔎 Bounded assessment of the pooled-helper failure

- **Not reproduced under normal conditions.** The case passed on the first
  focused run, 6 of 6 repeated focused runs (1.1 to 5.1 s each) and both full
  runs. The original failure output was not kept, so what failed is unknown.
- **One reproduced mechanism, under synthetic saturation only.** `runChild`
  kills each child after 5 s and the test then fails with `child hung or
crashed` (`SIGTERM`). With 24 busy loops on 12 cores (shared host, load average
  above 70) that failure occurred in 3 of 3 runs. A direct probe of the same
  throwing-child script took about 0.5 s alone (4 s once, cold) but 57 to over 60 s
  under 12 or 24 busy loops.
- **Raising the limit does not help**, so no change was made: with `timeout`
  at 30 s, 3 of 3 loaded runs still failed.
- **Cause not assigned.** The slowdown is far larger than a 1x to 2x CPU
  oversubscription explains, and it was not isolated (uncontrolled host, other
  agents' work running). The result shows the case can fail when the machine is
  saturated; it does not show that this was the original failure.
- **No repair, so S stands.** Finding why a child starves that badly (child
  startup against the pooled `MessageChannel` scheduler) would be investigation
  of the scheduler/dependency boundary and would need the estimate reassessed.
  The installed package was never mutated.
