## Retention guidance in the download result

2026-10-29, agent judgment under the standing four-persona delegation.

**Question:** How does a person retain downloads when the browser does not grant
persistent storage? Existing download preparation requests and reports the real
Storage API result, but its confirmation lacks the promised help action.

**Decision:** Reuse the production device-storage explanation from every download
confirmation, with a direct **How to keep them** action for unprotected storage.
Explain ordinary profiles, clearing data, reconnecting to synchronize and the
browsers' retention limits. Keep help in place so unsynchronized editor work is
not interrupted. Installation is optional and never a requirement for this ticket.

**Alternatives:** Duplicated editor/Space guidance would drift; requiring a visit
to Profile would interrupt the immediate task. Browser-specific persistence
claims without observed results would promise more than the platform guarantees.

**Personas:** Owner and Collaborator gain immediate retention guidance and keep
their edits in place. Operator gains accurate support information without access
to private documents or a new service. Link guests retain their existing online
boundary and gain no private catalog or offline privilege.

### Native Safari environment and input lifetime

2026-10-30, agent judgment under standing delegation. Select standard
`macos-15-intel` for the maintained Safari gate: it executes current Safari 27.2
with ordinary profile retention, working automation and visible native editor
images. Preserve the other measured hosts' failures without assigning architecture
as their cause. Every original lifecycle assertion remains required; environment
qualification alone does not complete the ticket.

The pointer helper now keeps its at most one move or two click-event allocations
for that short child process's lifetime. Each invocation is awaited, returns
immediately after posting and has a ten-second bound. Process exit reclaims its
allocations; see Apple's [process-termination memory guidance](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/MemoryMgmt/Articles/mmRules.html).
This is deliberately limited to the short-lived helper, not an exception to
[normal Core Foundation ownership](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFMemoryMgmt/Concepts/Ownership.html)
in a persistent process. No autorelease or double-free explanation is assumed.
Successful child exit and separately observed trusted DOM movement, target and
coordinates, caret, content and images remain mandatory. A new native bridge
solely to free these tiny per-call allocations would add unnecessary complexity;
ignoring child failure or dropping native-input checks would weaken acceptance.

Owner and Collaborator retain real evidence that native edits and images survive.
