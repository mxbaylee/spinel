## Legacy decision 12: Invitations and credential recovery

**Recorded:** 2026-10-17. **Status:** accepted.
**Authority:** Agent invitation implementation judgment.
**Source:** [original decision #12](https://github.com/mxbaylee/spinel/issues/12).

**Question:** How should invite lifetimes, copying and lost-passkey recovery behave?

**Options considered in the original source:**

A — Show the link only when created, list metadata/status afterwards, support
1-hour/1-day/7-day/30-day expiry choices, and replace existing credentials/sessions only after
successful recovery. B — Store plaintext links for repeated copying and leave lost
credentials/sessions active after recovery.

**Outcome, rationale and current boundary:**

Return a random 256-bit invitation once and retain only its SHA-256 hash. Offer 1-hour, 1-day, 7-day
default and 30-day lifetimes; lost plaintext links must be replaced. Verify registration before
creating an account or consuming its invitation. Recovery preserves the existing identity/name/role
and atomically replaces old passkeys, revokes sessions and other recovery invitations only at
success; it never reactivates disabled accounts. Recheck authorization and expiry after awaited
verification. Clear the invite query and use no-store/no-referrer; the operator delivers links
manually, without an email service.

**Persona tradeoffs recorded at the time:**

The Operator needs simple expiry choices and explicit recovery consequences. The Owner needs
documents to stay attached to their existing identity after recovery. The Collaborator needs a
single valid enrollment without accidental duplicate accounts. The Link guest must not receive
workspace access without an unused valid invitation and verified passkey.
