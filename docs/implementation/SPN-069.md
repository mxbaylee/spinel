# SPN-069 — creation in shared folders

## Folder ownership and creator attribution

**2026-10-28 — accepted, agent judgment under the standing delegation.**

The original ticket requires a signed-in editor to create children inside an
editable shared folder while preserving the folder owner's canonical tree.
Creation applies to folders, Sheets, Docs and enabled outer Space files, as well
as the existing native import path. Internal Space pages retain their existing
content permissions. A separate copy action remains SPN-065.

Use the existing effective folder grant to admit creation. The server resolves
the canonical owner from that folder inside the creation transaction, rather
than accepting an owner supplied by the caller. My files still creates under the
current everyday account. Viewer, disabled-account, Operator and anonymous-guest
boundaries remain enforced. Creating an item grants no new rename, move, trash
or sharing authority to an Editor.

Retain the creating account's identity and a display-name fallback independently
of its continued access. Account-authorized file metadata exposes `createdByName`
for the dashboard's **Created by** attribution; anonymous guest responses expose
neither the creator nor owner account details. Historical records with no creator
evidence retain unknown attribution rather than guessing it.

Options considered were creator-owned children, a new direct creator grant, and
the folder-owner rule. The first two would break the Owner's single tree or keep
access after revocation. The folder-owner rule satisfies the ticket and reuses
the existing inherited permission model.

- **Owner:** keeps the file after a collaborator leaves and can identify who added it.
- **Collaborator:** creates where the shared project lives, with visible ownership
  and the same edit access as other folder contents.
- **Link guest:** sees only the existing document/Space content surface, with no
  new creation privilege or account identity.
- **Operator:** gains no document access; creation uses the existing database and
  authorization paths without another service or role.

## Offline publication uses the same destination rule

**2026-10-28 — accepted, agent judgment.**

A prepared account may create an ordinary Sheet or Doc in a cached folder with
Owner, File admin or Editor access. Save the local identity, destination and
attribution before opening the editor. The server revalidates the current folder
grant at publication and binds the creator and folder owner to the existing
immutable receipt. A lost response retries the same item, generation and request;
it never moves an accepted item or silently chooses another destination.

Revoked, deleted or downgraded destinations leave local work available for the
existing explicit destination/export/discard recovery. Only a definitive refusal
allows a changed destination. Offline folders and Space trees remain excluded.
Guest and Operator offline access stays excluded. Prepared shared files belong
in the shared catalog, and pending files remain discoverable after restart or a
stale catalog response without being mislabeled as owned files.

This extends SPN-051's existing record and receipt lifecycle instead of creating
a second upload mechanism. The Owner receives one file, the Collaborator keeps
recoverable work, the Operator keeps one synchronization path, and the Link guest
receives no new local storage or identity exposure.

## UI and verification

The production dashboard uses its existing New menu, creation dialog and file
row patterns. Editors and File admins see New inside an accessible shared folder;
viewers do not. Creation explains ownership, and authorized rows show the creator.
There is no SPN-069-owned Redesign example remaining to migrate.

Verification must cover effective grants, canonical ownership, creator retention,
native imports and outer Spaces, ordinary editor action limits, guest privacy,
offline restart, lost responses, duplicate publication, rejected destinations and
explicit recovery. Browser coverage must demonstrate a collaborator creating and
editing a Sheet and its owner refreshing and opening the same file. Current
light, dark and phone images require independent visual review, **agent review
only**, alongside the two independent rubric reviews and all required CI checks.
