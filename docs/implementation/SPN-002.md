## Legacy decision 8: Passkey-bound sessions

**Recorded:** 2026-10-17. **Status:** accepted.
**Authority:** Agent security implementation judgment.
**Source:** [original decision #8](https://github.com/mxbaylee/spinel/issues/8).

**Question:** How should passkey sign-in establish and bind sessions before account-creation tickets
land?

**Options considered in the original source:**

A — fixed 30-day authenticated sessions, 5-minute anonymous sessions, hashed 256-bit cookie tokens,
rotation at sign-in, strict configured origin/RP binding, registration only for existing signed-in
users, and a separate loopback-only disposable manual fixture; B — expose public development signup
or weaken cookie security to ease testing.

**Outcome, rationale and current boundary:**

Use hashed 256-bit cookie tokens, fixed 30-day authenticated and five-minute anonymous sessions,
rotation at sign-in, strict configured RP/origin binding and one-use session-bound challenges.
Consume challenges atomically and recheck session/account state after asynchronous verification.
Keep production signup absent; a separately invoked loopback fixture is not an environment bypass.
Secure cookies remain secure locally. Operator accounts never gain document access; real
browser/1Password/Proton Pass acceptance cannot be inferred from virtual authenticators.

**Persona tradeoffs recorded at the time:**

Operator favours explicit origin configuration, revocable server sessions and no public signup;
Owner favours persistent sign-in without recurring passwords; Collaborator favours their own
credentials and isolation; Link guest must not inherit authenticated access or see other accounts.
All need one-use challenges and verified user presence.
