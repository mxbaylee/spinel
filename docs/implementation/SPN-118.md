Resuming the same bundle into a destination that has served newer native edits
must refuse to certify it as the original conversion. Refusal preserves its
saved content, native edit receipts, history, images, identities, ownership,
grants and revocation state without overwrite or republication. Source and
bundle provenance, interrupted import/export fences and the separate wrong-source
rejection remain required. A transition retry is not a restore operation.

The repair stays within the existing SQLite adapter and verification lifecycle.
It does not replace SQLite, redesign migration, add recovery features, alter
browser fixtures or change CI routing. The existing digest and refusal assertions
remain in place; failed attempts are evidence, not candidates for retry-until-green.

## Why verification could change database bytes

The [original failed CI job](https://github.com/mxbaylee/spinel/actions/runs/40537669633/job/122307404648)
refused the same-bundle resume but failed the subsequent main-file digest at
`transition.test.ts:120`. Its second workflow attempt passed on the same SHA.
The [registration record](ci-reliability-2026-10-28.md#runtime-and-destination-follow-ups)
correctly left WAL cleanup versus unexpected writes unresolved. Those logs do
not identify which connection changed that historical file, nor establish lost
documents.

Investigation used base `bc05dbc0d2595750f0bbf9502c2aba7e3d0b7463`, Node
`26.12.1` and the locked `libsql` `0.5.29`. The first unchanged transition-suite
run passed all 20 tests: the spontaneous intermittent failure did not reproduce.
Two pinned driver behaviors explain the demonstrated mechanism:

- The [JavaScript constructor](https://github.com/tursodatabase/libsql-js/blob/55bee86d1c284f1ddf2b9e280e870d2b6cef884a/index.js)
  ignores the advertised `readonly` and `fileMustExist` options. Passing those
  options in `DatabaseSync` did not enforce read-only access.
- The [native close implementation](https://github.com/tursodatabase/libsql-js/blob/55bee86d1c284f1ddf2b9e280e870d2b6cef884a/src/database.rs)
  releases the database object's connection reference, while
  [prepared statements](https://github.com/tursodatabase/libsql-js/blob/55bee86d1c284f1ddf2b9e280e870d2b6cef884a/src/statement.rs)
  retain theirs until finalization. The last actual connection close can therefore
  occur after `close()` returns. SQLite may then
  [checkpoint the WAL](https://sqlite.org/wal.html#the_wal_file).

The controlled probe kept the importer policy unchanged. A nominal read-only
reader executing a `SELECT` and closing changed a 4,096-byte main file to 8,192
bytes and removed its committed WAL. A URI opened with `mode=ro` read the WAL
without that checkpoint. The ignored options also created a missing database;
`mode=ro` refused the missing path. `immutable=1` missed the newer table in WAL
and is unsuitable for this verification.

The full native fixture then reproduced delayed checkpointing after a successful
same-bundle refusal. The main file grew from 376,832 to 413,696 bytes and the
659,232-byte WAL disappeared after the first of three fixed diagnostic GC turns.
An independent read of the saved before/after images found identical schema and
all 70 rows across 33 tables, including the surviving native content and access
metadata. Their logical-state SHA-256 was
`d14452f79b9fa959e5ab18ad410170d67c21c7100af0e8213317b0f7adff759b`.
The [evidence record](evidence/SPN-118.json) retains the physical before/after
digests and lengths, and a compact [synthetic image archive](evidence/SPN-118-synthetic-checkpoint.zip)
retains the exact main/WAL images and complete logical state. This establishes checkpoint-driven byte changes with
preserved logical state in the reproduction; it does not retroactively prove
the exact connection timing of the historical CI failure.

## Enforce read-only opens and settle verification fixtures

**2026-10-28 — accepted, agent judgment.** The question is how to prevent the
verifier from changing a completed destination while measuring preservation at
a boundary where the fixture's own writes have finished.

Retaining the ignored options does not enforce the existing contract. SQLite's
`immutable=1` changes WAL/change-detection semantics and can inspect stale data.
Removing the digest assertion would lose the physical preservation guarantee.
A driver replacement or broad shutdown redesign is unnecessary for this repair.

Use an escaped `file:` URI produced by `pathToFileURL`, with SQLite's supported
[`mode=ro`](https://sqlite.org/uri.html) parameter, for `DatabaseSync` read-only
opens. This keeps the pinned runtime and current WAL-aware reads while rejecting
writes and missing paths. Filename characters such as `?`, `#` and `%` remain
filename data. The driver object's hard-coded `.readonly` property is not used
as evidence; regression checks exercise actual writes, reads and file creation.

After awaiting history and collaboration shutdown, verification fixtures explicitly
checkpoint and check the result before closing their writable database and
recording the baseline digest. The later native-purge fixture uses the same
settled boundary. This moves the fixture's own durable write completion before
the preservation measurement; the importer does not checkpoint the destination.
Prepared-statement finalization can no longer move those committed fixture pages
into the main file during the refused-resume assertion.

The synthetic transition unit fixture separately compares physical main/WAL
contents and complete native/application schema and rows, independent of the
importer's preservation allowlist. Its logical observer uses enforced read-only
access in a separate, completed process, so retained observer statements cannot
hide the checkpoint being tested. A direct empty-WAL assertion checks the native
fixture's settled boundary before opening the observer. The retained public-SDK integration keeps
its public API checks and byte-preservation assertion; it does not inspect
proprietary SDK tables. SHM contains transient read coordination data and is
diagnostic evidence rather than a byte-identity contract. Source hashes, refusal
behavior and the original digest assertion retain their own checks.

- **Owner:** newer authored content, history, images and ownership survive a
  refused old bundle; L impact protects the existing document-preservation contract.
- **Collaborator:** saved native changes, access and edit receipts remain intact;
  L impact does not imply that the historical failure lost documents.
- **Operator:** verification uses enforced read-only access and a deterministic
  fixture boundary, with no new driver, service or recovery procedure.
- **Link guest:** gains no capability or identity exposure; existing scope and
  revocation metadata remain part of preservation acceptance.

## Bounded verification and landing

The investigation used one unchanged transition-suite attempt, exploratory driver
probes and one full-fixture lifecycle diagnostic with three fixed GC turns. An
initial probe had a script syntax error and was corrected. Its first prepared-
statement observation still had pending finalizers; the subsequent `exec` probe
isolated physical close. The lifecycle diagnostic's inline logical observer
produced empty output and is not logical-state evidence; a separate observer
compared its retained before/after images and produced the 33-table result above.

The new database regressions failed against the old implementation for all three
intended reasons: writes were allowed, missing files were created, and the
reader changed main-file bytes. Their initial sandboxed attempt observed the
first two defects but blocked the child-process WAL setup with `EPERM`; a single
rerun outside that restriction established the third failure. The two focused
transition regressions then failed before repair: 650,992 committed WAL bytes
remained after fixture shutdown, and a refused import changed the WAL-backed
destination's main bytes. The 19 unrelated cases were filtered out of that
diagnostic run, not disabled in the suite.

The first complete post-repair database/transition run passed **26/26 tests**,
including all 20 original transition cases. Its combined process-tree peak was
931 MiB under the 2 GiB watchdog. Retained public-SDK transition acceptance and
required final-head CI are the remaining validation gates. A new failure requires
diagnosis before another attempt. No timeout, retry policy, preservation assertion
or CI gate is relaxed.

Ticket retirement and the completion counter prepare this PR to land; they do
not claim that reviews, CI or merge have completed. The PR must record every
attempt, final acceptance results, both independent nonimplementing rubric
reviews above 95/100 on the same current SHA, and all seven required CI gates
before a guarded squash merge. This change has no UI state requiring visual
approval. The PR records final CI, acceptance and review results without treating
