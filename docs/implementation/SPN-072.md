# SPN-072 — phone Docs

## Public mobile Docs integration

**Date/status:** 2026-10-26, accepted implementation approach; verification in progress.
**Authority:** agent judgment within SPN-072's public-API requirement and fallback rule.

**Question/context:** Can the pinned OSS 1.1.0 SDK reflow a Doc without changing
its shared page geometry? SPN-049 correctly found that the public zoom commands
can change the snapshot. That does not rule out the SDK's separate mobile layout.

The pinned package exports `UniverDocsMobileUIPlugin` and `UniverMobileUIPlugin`.
Its [mobile render controller](https://github.com/dream-num/univer/blob/v1.1.0/packages/docs-ui/src/controllers/render-controllers/mobile/doc.render-controller.ts)
passes the available modern page width and horizontal margin to the layout
executor, without changing the document snapshot. The
[mobile view-scale service](https://github.com/dream-num/univer/blob/v1.1.0/packages/docs-ui/src/services/mobile/doc-view-scale.ts)
keeps modern Docs at their user zoom and fits traditional pages separately.
`getDocsEmptySnapshot`, which Spinel uses for new Docs, defaults to modern Docs.
The [installation guidance](https://docs.univer.ai/guides/docs/getting-started/installation#mobile-support)
describes replacing UI plugins before creating a unit; its current documentation
version is newer, so the installed 1.1.0 exports and source are the integration
authority here.

**Options:** retain the desktop canvas on phones; change stored page dimensions
or zoom; build another document renderer; or select the SDK's supported mobile
UI, drawing and hyperlink plugins. Choose the public mobile plugins, retaining
the same model, collaboration, save, image and Formula paths. No dependency,
vendor patch, CSS canvas scaling or competing editing model is added.

`web/docPreset.ts` selects mobile controls for a coarse pointer at up to 900 CSS
pixels. The live editor captures that choice once; rotation, theatre mode and
keyboard changes must not recreate an editor with pending edits. Modern Docs
reflow to the container. Opening a Doc does not focus the keyboard automatically.
The native Edit action enters editing; the SDK owns touch selection, keyboard
avoidance, compact formatting and headings/lists. The existing editor frame
retains title, save/connection slots, People and More. Formula insertion/editing
uses the existing scoped dialog, and its readout retains every result row.

Read-only history/offline viewers use the same supported mobile presentation,
with no collaboration or autosave transport. Live viewers retain server access
checks and local permission fences. Because the SDK's Edit affordance is not an
authorization boundary, mobile viewers also hide native editing UI through
public preset/visibility APIs. A later access downgrade hides it too.
The native touch controller can still focus its hidden input independently of
root edit permission. A shared observer on the public `onFocus$` stream exits
mobile edit mode for read-only live, history and offline views; the same public
exit is applied when a live view becomes read-only. This is a keyboard/UI fence;
the existing permissions remain authoritative for mutations. The mobile method
is declared through the package's exported type path, so no unexported runtime
class import or vendor modification is required.

**Personas:** Owner and Collaborator can use the same document and saved layout
on either device. Link guests receive the same phone presentation within their
existing document/Space scope, with viewer and revocation boundaries retained.
Operator gains no server, storage migration or new dependency.

## Saved zoom and local phone scale

**Date/status:** 2026-10-26, accepted implementation approach; rendered verification in progress.
**Authority:** agent judgment under the ticket's public-API and saved-layout constraints.

The native mobile service returns a fit factor of one for modern Docs but still
multiplies by their saved zoom. It disables modern horizontal pan and pinch, so a
Doc saved at 50% remains too small and one saved at 200% can clip its text. Merely
choosing the mobile plugin does not establish readable reflow for existing Docs.

`web/docPhoneView.ts` specializes the exported `DocViewScaleService` through the
public `IRenderManagerService.registerRenderModule` dependency API. The app
plugin registers during `onStarting`, after its declared render-engine dependency
and before the mobile Docs plugin's `onReady` registration. The pinned registry
retains the first dependency for an identifier. The specialization returns a
local scale of one for external modern Docs, including explicit saved-zoom
arguments from native layout controllers. It does not change any model setting,
command, prototype or vendor file. Traditional and embedded editor units retain
the mobile service's existing behavior. Desktop presets omit this plugin.

This small app presentation adapter keeps Owner and Collaborator text readable
without altering their authored document, export or desktop zoom. Link guests
and isolated history/offline viewers share the same local-scale policy and
existing permissions. Operator gets no new dependency or storage. The rejected
alternatives were resetting the shared zoom, CSS-scaling the canvas, retaining
clipped content behind a read-only label, or creating a second document renderer.

Actual native Storybook scenes at saved zoom 0.5 and 2 must remain at scale one,
fit the host with readable glyphs, and preserve the pre-create snapshot across
resizes. Live browser cases must additionally touch, format, save and reload
without changing that saved zoom. These tests are required on SDK upgrades
because render registration and explicit-zoom layout calls are integration
contracts, not assumptions to infer from a screenshot.

Source: pinned OSS [view-scale service](https://github.com/dream-num/univer/blob/v1.1.0/packages/docs-ui/src/services/doc-view-scale.ts),
[mobile plugin](https://github.com/dream-num/univer/blob/v1.1.0/packages/docs-ui/src/mobile-plugin.ts)
and [render-module registry](https://github.com/dream-num/univer/blob/v1.1.0/packages/engine-render/src/render-manager/render-manager.service.ts).

## Selected-text formatting and list controls

**Date/status:** 2026-10-27, accepted implementation approach; interaction verification in progress.
**Authority:** agent judgment within SPN-072's selection, formatting and public-API requirements.

The pinned mobile UI dismisses keyboard input when a held touch selects a word.
Its keyboard toolbar then disappears, while the resulting selection drawer has
no inline-formatting controls. The app's mobile plugin uses the exported
`IMenuManagerService.mergeMenu` API in `onRendered` to add the native Bold and
Italic menu factories to that drawer. Their existing selection, active-style
and edit-permission observables remain authoritative. No keyboard event is
invented to make an unreachable toolbar appear.

The Heading quick menu also includes native list-style pickers, but its custom
option renderer does not supply the callback those pickers require. The same
pickers work in the native More drawer. The app replaces only the ordered and
unordered list leaves in the quick menu's public schema. Headings remain in
Heading; both list commands and their style choices remain in More. Desktop
menus are unchanged, and there is no vendor modification or global command
suppression.

Owner and Collaborator can format a selected range without losing it or reopening
the keyboard. Link guests retain their actual edit permission, including the
existing viewer fence. Operator gets one small addition to the existing mobile
presentation plugin, with no dependency or storage change. The alternatives were
to retain unreachable controls, create another toolbar and selection model, or
fall back to read-only for all phone Docs; the public menu extension preserves
native commands and the working editor.

The native selection-menu story verifies the visible controls and exact styled
substring. Live browser tests must reach that menu with a held touch, persist
Italic on exactly the selected word, verify that the quick menu has no broken
list entries, and apply a bullet through More's real style picker.

A controlled Chrome 156 run against the compiled native phone story also found
that the held touch opens this drawer before release, then its release produces
a compatibility click on the newly overlaid Cancel backdrop and closes it. The
shared phone guard listens to touch events on the public canvas element. Only
when a single touch starts with the menu closed and ends with a native expanded
selection and an open menu does it cancel that release's default action. This
follows the browser's [touch-to-mouse event contract](https://w3c.github.io/touch-events/#interaction-with-mouse-events-and-click).
The native selection, commands and event propagation are unchanged. Mouse input,
ordinary taps, multi-touch and later deliberate backdrop taps keep their default
behavior. Live coverage must dismiss the drawer intentionally, select the word
again and persist its exact formatting. The diagnostic reproduction is not a
physical-phone pass; the candidate fix still requires the pinned CI run.

That deliberate-dismissal reproduction exposed a separate native cache: closing
the backdrop hides the drawer without clearing the float-menu service's remembered
range, so a later held selection of the same word does not reopen it. At a fresh
single writable canvas touch with the drawer already closed, the guard calls the
root-exported `DocFloatMenuService.hideFloatMenu()` to clear that stale menu state.
The next actual native selection opens its own menu normally. This does not alter
the selected range, issue an editing command or bypass the SDK's permission checks.
The same-word dismiss/reselect regression is retained rather than requiring an
extra tap or a different selection to recover.

Native drawers mount in a body portal outside the Doc host. The phone-only
control sizing covers those mobile drawer components while a mobile Doc is open,
so their More and Cancel controls also retain 44-pixel touch targets. The story
queries the actual body portal and checks those controls rather than assuming
the drawer is a descendant of the canvas host.

## Traditional page-layout fallback

**Date/status:** 2026-10-26, accepted implementation approach; verification in progress.
**Authority:** agent judgment applying SPN-072's explicit read-only fallback.

Traditional Docs fit their page onto a phone by scaling; they do not have modern
Docs' readable-width reflow. Converting their flavor or changing shared margins
would alter the saved/exported layout. On a phone, preserve that layout, use a
read-only native view and show **“Edit on a larger screen. This Doc keeps its page
layout.”** Do not offer Formula insertion/editing in this fallback. Desktop
editing and document permissions are unchanged.

Owner and Collaborator keep their authored layout and get an explicit next step.
Link guests cannot mistake a limited phone presentation for permission to edit;
the server remains authoritative. Operator has no conversion or migration to
support. This is a presentation fallback, not a claim that fitting a whole page
makes its text comfortable to read.

## A peer changes the page mode

**Date/status:** 2026-10-27, accepted implementation approach; verification in progress.
**Authority:** agent judgment within the phone fallback and pending-edit requirements.

The public document model can receive a page-flavor change from a peer even
though the current desktop menus do not expose a mode switch. The mobile SDK
installs some gesture and resize listeners according to the initial flavor.
Changing only the local fit service cannot establish a complete live transition.

Observe completed rich-text mutations through the public command service and
read the model's current flavor after validation. If it changes after opening,
keep the mounted unit and synchronization queue, end local editing through the
public selection service, and apply the existing local permission fence. Show
**“This Doc’s page layout changed. Reopen it to continue.”** Reopening chooses
the current flavor through ordinary initialization. The fence remains for that
editor's lifetime even if a peer changes the flavor back. It never changes the
server grant or the snapshot. Pending and failed saves keep their existing
messages; the reopen status appears only after changes are confirmed.

Owner and Collaborator keep their accepted and pending work without editing
through stale phone gesture rules. Link guests retain their actual grant and
the same view-only behavior. Operator gets no new protocol or storage state.
This bounded fallback is preferred to remounting an editor with pending work or
adding a second reversible permission and page-layout system.

The rendered fallback has its own native story. A live peer-protocol test must
change the flavor while a phone edit is held, retain that edit after release,
keep the same canvas and connection, and prevent subsequent local edits. This
is supported peer-mutation coverage, not a claim that a page-mode menu exists.

The native sync protocol broadcasts senderless edits before acknowledgments. It
deliberately holds those revisions while a local submit has an unknown outcome;
the matching acknowledgment identifies the local revision and releases earlier
peer edits. The initial `fd2315c` test waited for the layout fence while holding
that first submit, so the peer mutation had reached the socket but could not yet
reach the visible model. All three production attempts showed revision 2 arriving
while the confirmed client remained at revision 1, with no browser errors.

The regression now types `P`, waits for its intercepted submit, and types
`ending ` into the pending buffer. After the peer's flavor change is acknowledged,
it releases only the first phone submit and holds subsequent writes separately.
The normal native acknowledgment path then applies the peer mutation while the
suffix remains pending. The test requires the fallback note, read-only input,
unchanged canvas and full visible `Pending ` prefix while the server contains
only the first `P`. Releasing the remaining queue must persist the entire prefix,
unchanged settings, correctly shifted Formula ranges and the original owner grant.
This follows the documented [inflight ordering contract](../../lib/sync-client/README.md#three-distinct-states)
without altering the client or relaxing the pending-work acceptance.

At `a7ec03c`, that pending-work sequence passed in both sync builds. The later
forbidden-input probe failed to locate the preserved traditional page's tiny
glyphs: the screenshot's first line had only three qualifying raster rows,
below the editable-text helper's four-row threshold. The read-only probe now
uses the existing native caret observer, verifying its unit, exact offset/text,
finite positive-height bounds and a real canvas hit before tapping and trying
forbidden input. It does not move the selection. Actual writing and selection
tests retain their rendered-glyph targets and exact persistence assertions.

## Browser caret in the native phone input

**Date/status:** 2026-10-27, initial caret repair superseded by input sizing;
candidate runtime verification pending.
**Authority:** agent judgment under the ticket's native-input and public-API requirements.

The mobile HTTPS diagnostics at `8a0313d` show the native contenteditable focused
through every ordinary keydown, with no prevented events, but the browser
selection has zero ranges. No DOM `beforeinput`/`input` or native input callback
follows. A provisional browser-caret repair established a contained DOM selection
but still produced no input events. The later pinned mobile HTTPS diagnostics at
`7c4627a` measured a zero-height native input, even after its host was no longer
inert and while the input was focused, visible and editable.

A controlled Chrome 156 comparison against the compiled Storybook build isolated
the cause: the ordinary story accepts all six characters of `Probe `; adding only
the live editor's temporary inert loading state reproduces the zero-height input
and loses all six input events. Keeping that loading state and setting only the
public `inputElement`'s minimum height to one CSS pixel restores all six ordinary
`beforeinput`/`input` events. Repeating this on the earlier `8a0313d` build, without
the provisional caret repair, also establishes a contained browser caret and
accepts every character. The native input's zero width is present in the working
case and is not changed.

The shared guard now supplies that minimum height and restores the previous
inline value when disposed. The loading and permission fences stay in place.
The provisional browser-selection and composition observers are removed: native
focus, selection and IME handling remain with the SDK. Read-only focus still
exits mobile edit mode through its public API. No keydown hook, logical-range
change, synthetic text insertion, vendor edit or new dependency is involved.

Owner, Collaborator and authorized editing guests retain their touch-selected
insertion point and normal native input pipeline. Reader and page-layout
fallback permissions are unchanged; Operator gains no storage or migration.
Existing real-touch writing, formatting, save/reload and read-only cases remain
the regression checks. Physical keyboard and IME verification remains pending.

Source: pinned OSS [selection service](https://github.com/dream-num/univer/blob/v1.1.0/packages/docs-ui/src/services/selection/doc-selection-render.service.ts)
and [mobile selection service](https://github.com/dream-num/univer/blob/v1.1.0/packages/docs-ui/src/services/mobile/doc-selection-render.service.ts).

## Verification boundaries

Automated browser and native Storybook checks are being added for reflow,
unchanged saved geometry, actual touch entry, persistence, formatting, Formula
results/dialogs, viewer permissions and current light/dark/phone captures.
Emulated viewport reduction checks the browser response to a keyboard-sized
inset; it does not prove an iOS/Android software keyboard, touch selection or IME.

SPN-049's earlier narrow-width desktop pan/zoom tests remain regression coverage
for that mode. This ticket does not reinterpret them as mobile acceptance.
SPN-090 retains offline launch, persistence and reconnect on physical phones;
SPN-072 retains its own physical Doc input checks. No iPhone or Android manual run
has been recorded for this candidate, and this execution environment has no
connected physical phones. The next step is to run the checklist in
[`docs/mobile.md`](../mobile.md#docs) on both platforms and record the exact
device, OS/browser, commit and result. Emulation cannot supply that evidence.
