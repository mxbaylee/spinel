# 🪤 SPN-169 — Resolved, won't fix: Chromium activation hang

## ✅ Resolution and ownership

**2026-11-23 — accepted owner decision.** Close SPN-169 as **resolved, won't
fix** and delete its open ticket. Owner, chat: “Let's merge this as resolved
won't fix, talk about why (this isn't our problem) and delete the ticket.”

The captured hang is a **Chromium service-worker lifecycle defect**. A fetch
arriving while the old worker stops queues a restart. Chromium starts a fresh
renderer without restoring activation urgency or its zero idle delay. Normal,
completed fetch traffic then prevents renderer idleness, leaving the replacement
worker installed and waiting. Spinel exposes this dependency defect; repairing
Chromium and maintaining a custom browser are outside Spinel's responsibility.

This resolution accepts the known browser limitation. It does **not** mean the
hang is fixed, every historical timeout has the same cause, or upgrades are
guaranteed to succeed on the affected browser. A future failure still fails the
existing test. No retries, exclusions, longer deadlines, relaxed assertions or
forced worker shutdown are introduced.

**Scope change:** the owner's closure decision supersedes the earlier request
to build a browser repair, prove its native regression and run repaired-browser
acceptance. Those obligations are withdrawn, not passed or deferred into a new
Spinel ticket. The remaining outcome is a documentation-only closure: preserve
the diagnosis, correct maintained references, remove SPN-169, regenerate the
index, independently review, pass applicable current-head gates and squash
merge. No unrelated backlog grooming or follow-up is created.

The exploratory diagnostic code and uncompiled native patch are preserved in
verified private archives. They are not part of this merge. Product code, browser
dependencies, test instrumentation, CI selection and the diagnostics emitter
contract remain unchanged. No UI or design acceptance applies.

## 🔎 Captured failure and actual holder

The full emitted-worker reproduction used diagnostic source
`6dab33a03cfe1bd9b8af36daa1d61c8c4a42638c`, based on the historical SPN-154
tested merge plus the diagnostic overlay. It retained the immutable legacy
`c2e8cac0fcdec36d992d6ebf3f377c9b579a8002` and previous
`3a0e2238fb5be3907d04120eabda2aafd6565d63` checkouts. Docker supplied the
documented single-CPU scheduling environment; local runs established observer
coverage and the restart boundary. Both used pinned Node 26.13.0, serial
workloads and the memory watchdog.

The first failure was case 8, attempt 1, after seven passes; collection stopped
at that failure. The replacement installed in 99 ms and remained installed for
120007 ms. The lock snapshot contained only the page's per-item offline lock,
with no pending locks. The old-worker ledger reported empty/not-tracking state.
All 23 process receipts were complete; the failed process retained 5385 native
events with no drops and one deadline marker. Its 12 observed browser request
lifetimes completed, with no HTTP request pending.

The decisive native sequence, in trace microseconds, was:

- `292015456`: replacement installed.
- `292015780`: old version, still activated, starts stopping.
- `292016913`: renderer termination permitted.
- `292018787`: a real collaboration POST arrives during shutdown.
- `292023946`: a fetch start is queued.
- `292024199`: `OnStopped` takes `Restart:true`.

The old worker changes thread from `3942:3980` to `3942:4026`. The restarted
renderer serves 162 fetches through the deadline, with maximum inter-fetch gap
1046.751 ms and the last fetch 651.970 ms before the deadline. These are completed
requests, not a continuously held message, response body or runtime Web Lock.
The restarted global also explains why its earlier in-flight ledger was lost.

Pinned Chromium `156.0.8078.4`, commit
`f842f52ef39fd97b449eb27cff414bf05a98ddce`, explains the captured behavior:
`OnStoppedInternal` restarts for the queued fetch and bypasses its no-work branch;
`StartWorkerInternal` clears `needs_to_be_terminated_asap_`; the new renderer's
event queue uses its default 30 s idle delay. Each ordinary fetch resets that
timer. The observed traffic never provides the required idle interval.

[idle-delay constant](https://chromium.googlesource.com/chromium/src/+/f842f52ef39fd97b449eb27cff414bf05a98ddce/third_party/blink/public/mojom/service_worker/service_worker.mojom).

  `d65b02f2eebb7d6d0ba926d8b0216f1e6c5c16a7f3650132084de396fbdc3e15`.
  The new Docker capture matches its observable signature, not unrecorded
  internals. Candidate worker bytes match; old-worker bytes differ in 21 of 41
  JavaScript asset filenames. Do not claim byte-identical old workers or an OS
  cause.
- **Observer capability:** a controlled held message demonstrated the
  late-attachment gap; attachment before the event named it. Empty ledgers do
  not establish that no native lifecycle blocker exists. These controls
  diagnose coverage, not the original hang.
- **Restart controls:** probe 1 used an empty fetch handler optimized away and
  was invalid. Probe 2 dispatched fetches but missed the restart boundary.
  Probe 3 reproduced `Restart:true` with a real completed HTTP body and five
  subsequent requests while the candidate stayed installed for 5 s. Probe 4's
  first attempt missed the boundary (`Restart:false`) and failed explicitly;
  it was not retried or counted as passing. Public CDP notification was not a
  deterministic scheduling barrier. The full emitted capture above, rather
  than a synthetic green run, supplies the 120 s failure evidence.
- **Native repair exploration:** an upstream C++ draft and eight parameterized
  cases were authored and statically reviewed. Patch application/reversal and
  hashes passed. It was never compiled, executed or installed, and no repaired
  browser was produced. Native source-subset commit
  `08289bf1430f27815aeba7db8e2b0bc038a8184c` is a local preservation identity,
  not an upstream commit. The owner has discontinued this repair effort.
- **Resource failures:** historical dependency installs hit the memory watchdog
  three times; Docker's disk filled. These were preserved as infrastructure
  failures, not passing checks. The owner authorized a 40 GiB Docker disk;
  memory was restored to 3072 MiB and Docker stopped after capture. No unrelated
  process or work was removed to obtain a pass.
