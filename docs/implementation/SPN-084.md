## Generic states keep the existing guest probe

2026-10-23 · accepted · agent judgment under the owner's delegated all-persona
decision authority.

The approved Guest/RevokedLink/OfflineLaunch/MissingFile designs distinguish a
network failure from an authoritative denial. Before a guest loads content, use
one generic state instead of a connection badge plus an indefinite loading
paragraph. Retry invokes the existing bounded, serialized guest exchange/probe;
it does not reload, drop a fragment token or create an account-session probe.
401/403/404 ends the standalone link check and has no Retry. The existing Web
Locks guard remains before capability exchange. A Space tree failure before any
page loads follows the same generic presentation without showing the root name.
An already-open live editor keeps its established connection/save behavior.

The alternative was to reload on every retry or share the new SPN-083 account
entry controller. Reload can lose the in-memory exchange state; an account entry
dependency is unnecessary and would couple unrelated authorization lifetimes.
The small AccessState component shares only existing controls, theme and tokens.

- Owner: no changes to grants or saved data; generic errors do not reveal titles.
- Collaborator: missing-file and offline meanings remain distinct, with an
  explicit route back to files where the account can use it.
- Link guest: no account route, identity, access-request control or export is
  added; unavailable and offline screens contain no private metadata.
- Operator: no new service, storage or background probe; API and resource bounds
  remain unchanged.

## Dirty Space guest revocation needs a privacy/recovery decision

2026-10-23 · needs-owner · investigation by the implementing agent and parent
reviewer; no decision or changed behavior is claimed.

The accepted guest design removes title, content and actions after revocation.
The existing collaboration controller instead makes a denied dirty editor
read-only, preserves its pending buffer and says to copy unsaved changes before
leaving. Space deliberately retains that engine while dirty; clean guest
revocation unmounts it. SPN-049's new title fallback is being repaired separately
to preserve the old generic `Space unavailable` heading. That repair does not
settle access to the retained dirty content.

**Question:** after authoritative root-link revocation with unsaved Space guest
input, should Spinel (A) hide all previously delivered content immediately,
retain the buffer only in memory and give a truthful generic unsaved warning,
or (B) allow a clearly limited recovery view for copying already-delivered
unsaved input, with no new reads/writes/account/native-export access? A removes
the existing manual-copy route; B is an explicit exception to the approved
revocation presentation. Neither option is silently implemented here. A hidden
editor must never promise that the guest can copy from it.

- Owner: A best honors immediate hiding; B helps avoid losing contributed work
  but leaves a visible recovery exception after revocation.
- Collaborator: preserve existing private-account recovery independently; this
  question changes only anonymous Space guests, not account grants.
- Link guest: A keeps the pending buffer but makes it inaccessible; B preserves
  recovery while requiring precise boundaries and truthful warnings.
- Operator: either requires native dirty Doc/Sheet regression coverage; no new
  recovery store or export service should be introduced as a visual workaround.

Until resolved, the existing dirty Space guest behavior is preserved. This is a
known acceptance gap, not visual approval or permission to land. Required future
coverage holds a real dirty Doc and Sheet write, revokes the root link, and
checks the chosen visibility/recovery behavior, denied writes and absence of
account identity across all open children.
