### What exists today

- The image identity (`Recovery.image`) is written into `spinel_recovery` **inside
  the encrypted archive**. Only a full decrypt, inventory check and
  `verification.ts` comparison can read it, so the restore catalog cannot say
  anything about it. It lists keys and times only (`RestoreRegistry.catalog`).
- Archives are `SPINEL01` + 12-byte IV (20 bytes, the GCM AAD) + ciphertext +
  16-byte tag. `archive.ts` is the only reader of that header.
- Stores (`FilesystemStore`, `SpacesStore`) implement `put/list/remove/download`.
  Neither can read part of an object.

### Decision: an authenticated stamp in the archive header

Question: where may the catalog learn a backup's image without decrypting it?

| Option                                                    | Outcome                                                                                                                                                   |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Object name or tag                                        | Rejected: unauthenticated by definition. Kept only as the existing hint.                                                                                  |
| Sidecar object with a MAC                                 | Rejected: a second object per backup in two hardened stores. It can be missing, orphaned or pruned apart from its archive, and publication is not atomic. |
| **Stamp in the archive header, MAC'd with a derived key** | **Chosen.** One object, so the stamp cannot be orphaned or pruned separately. It travels with the bytes and old archives simply have none.                |

Format `SPINEL02`: `MAGIC(8) | iv(12) | length(2) | stamp JSON | mac(32)`. The
whole header is still the GCM AAD, so a stamp spliced onto other ciphertext fails
full verification. The stamp holds `image`, `createdAt` and `keyId` only: no
origin, runtime environment, path or secret. The MAC is
HMAC-SHA256 under a key derived from the backup key with a fixed label, so the
encryption key is never used for two purposes. `SPINEL01` archives still restore
unchanged and are classified `unknown`.

A new optional `RemoteStore.head(key, bytes, signal)` reads a bounded prefix.
The filesystem store uses its existing nofollow open; Spaces uses a ranged GET.

### Catalog marking

`catalog()` returns each entry with `image: 'compatible' | 'incompatible' | 'unknown'`.

- `compatible`: MAC verifies under a configured key and the stamp image equals the running image.
- `incompatible`: MAC verifies and the image differs. The UI shows the fresh-host path.
- `unknown`: no stamp, bad MAC, unreadable head, or no matching key. This is the
  forged/missing case. It is **not** shown as incompatible and not blocked: full verification decides.

The mark is advisory. `create()` and `prepareCatalog` are unchanged, so every
point, including one marked compatible, still goes through full verification, and
one marked incompatible is still refused by the same preparation if selected by
a direct request. The UI disables selecting an incompatible point and links
[Restore onto a fresh host](../backups.md#restore-onto-a-fresh-host). A head
read failure degrades only that entry to `unknown`; it never fails the catalog.

### Persona effects

- **Operator**: sees which points this image can restore before choosing, and the recovery path for the rest. A mark never hides a point, so nothing is lost if the mark is wrong.
- **Owner and Collaborator**: indirect. They are protected from a restore that cannot succeed. The catalog stays Operator-only, and the image digest never leaves the server: the response carries only the three-state mark.
- **Link guest**: unaffected.
