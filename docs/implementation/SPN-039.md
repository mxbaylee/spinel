## Legacy decision 83: Complete opted-in offline product

**Recorded:** 2026-10-19. **Status:** accepted, implementation obligations remain.
**Authority:** Owner offline requirement; agent integration planning.
**Source:** [original decision #83](https://github.com/mxbaylee/spinel/issues/83).

**Question:** How does the requested signed-in offline feature relate to SPN-028's network-only
installation scope?

**Options considered in the original source:**

A — Register one large outcome ticket with its complete contract, explicit public-API feasibility
work and preserved acceptance when splitting; keep SPN-028's network-only behavior until SPN-039
implements and verifies an opted-in signed-in path. B — Fold all of offline persistence and
synchronization into the installation ticket. C — Reduce the request to a generic offline screen or
short open-tab disconnect.

**Outcome, rationale and current boundary:**

Selected signed-in Sheets/Docs, committed edits and existing images must survive offline restarts
with current Viewer/Editor boundaries and honest availability. Real Android/iOS verification is
distinct from emulation. A probe or partial slice does not complete the contract: decisions
[#88](SPN-039.md#legacy-decision-88-complete-public-replay-evidence)/[#89](SPN-039.md#legacy-decision-89-preserve-existing-sheet-images) retain complete
replay/image evidence;
[#91](SPN-039.md#legacy-decision-91-offline-prerequisites-without-partial-completion) splits
prerequisites; [#97](SPN-039.md#legacy-decision-97-app-owned-offline-outbox) selects the app-owned
outbox. Current offline follow-ups retain unfinished acceptance, including reconnect conflict
behavior and access-loss handling. Guest links acquire no offline account capability.

**Persona tradeoffs recorded at the time:**

The Owner needs selected Sheets and Docs, existing images and committed edits to survive offline app
restarts. The Collaborator needs the same durability within viewer/editor permissions, with
concurrent edits reconciled and revoked or replaced generations never written. The Operator needs
bounded, diagnosable device storage, no document access through the admin account and no new paid
infrastructure assumption. The Link guest must retain document-only online access without a private
offline catalog, cached link token or offline document download.

## Legacy decision 88: Complete public replay evidence

**Recorded:** 2026-10-19. **Status:** accepted evidence boundary; mechanism later superseded in
part.
**Authority:** Agent public-API investigation.
**Source:** [original decision #88](https://github.com/mxbaylee/spinel/issues/88).

**Question:** How should an offline download obtain a complete, revision-specific SDK replay base?

**Options considered in the original source:**

A — add an authenticated account-only replay-base read using this public API, retain all binary
fields and generation-scoped opaque resources, and recheck session/access/generation after
asynchronous acquisition. Acquire images, app assets and local permissions separately before marking
any download complete. B — infer completeness by caching observed browser requests, risking omitted
blocks/resources and mixing permissions with authentication response caching.

**Outcome, rationale and current boundary:**

Materialize a complete revision-targeted unit through public getUnitLoadDataWithBlocks, treating
binary block IDs as opaque and checking current authorization/generation throughout. A viewport
cache or base snapshot alone cannot prove Available offline or Saved. Images and application assets
require their separate complete preparation. Decision
[#97](SPN-039.md#legacy-decision-97-app-owned-offline-outbox) replaces reliance on Pro
recovery-cache persistence with an app-owned outbox; it does not waive complete scoped replay
evidence or allow unsupported Pro internals.

**Persona tradeoffs recorded at the time:**

The Owner and Collaborator need offscreen cells, image references and pending operation identities
retained, not just whichever requests a viewport happened to make. The Operator needs a bounded
public integration with no extra paid service. The Link guest must remain excluded from private
offline preparation and account data.

## Legacy decision 89: Preserve existing Sheet images

**Recorded:** 2026-10-19. **Status:** accepted.
**Authority:** Agent image-boundary judgment.
**Source:** [original decision #89](https://github.com/mxbaylee/spinel/issues/89).

**Question:** How should SPN-039 obtain supported existing Sheet images for complete offline
documents?

**Options considered in the original source:**

A — Enable existing embedded Sheet images through native import, with floating/cell/background
validation, item-scoped reads, native export, history and mobile rendering; keep new Sheet
upload/paste insertion unavailable. B — Build a new Sheet upload UX too, adding unrelated
insertion/persistence scope. C — Omit Sheet images, which does not meet the accepted contract.

**Outcome, rationale and current boundary:**

Preserve existing embedded Sheet images through import, native snapshots, history, scoped reads and
offline preparation using bounded instance-local bytes. This slice does not add new image insertion
or remote URL fetching. Recheck current document read/edit scope and keep image references coherent
with the native revision. Existing Doc and Sheet image requirements remain part of the full offline
product, not proof that all offline work is complete.

**Persona tradeoffs recorded at the time:**

Operator needs bounded, instance-local image storage and no remote fetches. Owner needs existing
images to survive import, history and offline reopening. Collaborator needs the same content with
current read/edit permissions. Link guest may view permitted live images but receives no private
offline store and loses access when the link is revoked.

## Legacy decision 90: Public Pro recovery coordinator proposal

**Recorded:** 2026-10-19. **Status:** superseded.
**Authority:** Agent implementation proposal; later owner choice.
**Source:** [original decision #90](https://github.com/mxbaylee/spinel/issues/90).

**Question:** Which public integration boundary should SPN-039 use after the cold-restart probe?

**Options considered in the original source:**

A — implement a host offline coordinator using complete revision-specific bundles,
account/generation-scoped durable storage, public snapshot/authz/image/cache adapters, and a
pre-network access barrier; retain the exact-identity compatibility layer only with fail-closed
replay accounting and preserved originals. This adds integration work but preserves all personas'
access and durability requirements. B — treat browser response recording or the prototype alone as
the feature; this is smaller but fails Owner/Collaborator durability and Link guest/account
boundaries. C — replace the collaboration engine or require a paid vendor change; this is outside
this ticket and retains existing owner decisions.

**Outcome, rationale and current boundary:**

The proposed pinned public coordinator would preserve operation identities and await recovery
persistence rather than trust arbitrary cache contents. Decision
[#97](SPN-039.md#legacy-decision-97-app-owned-offline-outbox) replaces this mechanism with an
application-owned IndexedDB outbox, revision-aware replay and a conflict copy on divergence.
Preserve the durability and no-duplication intent; do not keep Pro recovery-cache reliance as a
second authoritative implementation or declare the offline contract complete from this proposal.

**Persona tradeoffs recorded at the time:**

The Operator needs a pinned, testable public integration without a new service or privileged access
to documents. The Owner needs saved edits to survive restarts without duplication. The Collaborator
needs the same durability with permissions and concurrent changes preserved. The Link guest needs
exclusion from private offline stores and no delayed authorization bypass.

## Legacy decision 91: Offline prerequisites without partial completion

**Recorded:** 2026-10-19. **Status:** accepted, historical split.
**Authority:** Agent scope and sequencing judgment.
**Source:** [original decision #91](https://github.com/mxbaylee/spinel/issues/91).

**Question:** Should independently useful image support and replay-base acquisition land as
implementation dependencies while SPN-039 keeps its complete offline contract?

**Options considered in the original source:**

A — register SPN-040 for existing Sheet-image import/render/export/history and access restrictions,
then SPN-041 for complete authorized replay bases; keep SPN-039 open with both implementation
dependencies and its original acceptance intact. B — continue all work in one much larger PR. C —
rename SPN-039 into a partial feature and move its entire user experience elsewhere, increasing the
risk of losing requirements.

**Outcome, rationale and current boundary:**

Split existing-image preservation and complete revision/replay preparation into SPN-040/SPN-041
prerequisites, while SPN-039 retains the full promised offline workflow. A merged prerequisite is
useful but cannot be represented as complete offline editing. Preserve existing grants, Viewer
behavior, image bytes and pending-edit guarantees. Decision
[#97](SPN-039.md#legacy-decision-97-app-owned-offline-outbox) subsequently changes the persistence
mechanism; the original all-or-nothing acceptance claims remain honest.

**Persona tradeoffs recorded at the time:**

Owner needs the complete promised offline workflow and useful image preservation without a
misleading partial completion. Collaborator needs unchanged document permissions, viewer behavior
and pending-edit guarantees. Operator benefits from smaller independently reviewed changes, bounded
resources and no additional service. Link guest retains online-only document access and must gain no
private replay bundle or offline store.

## Legacy decision 97: App-owned offline outbox

**Recorded:** 2026-10-19. **Status:** accepted, implementation obligations remain.
**Authority:** Owner product choice.
**Source:** [original decision #97](https://github.com/mxbaylee/spinel/issues/97).

**Question:** Should Spinel keep its own offline outbox instead of relying on Univer Pro's internal
offline cache, and save a conflicted copy when the live document changed?

**Options considered in the original source:**

A — app-owned outbox, replayed only onto an unchanged revision, conflicted copy otherwise; costs
live merging of offline edits. B — keep proving Pro's cache (#86); depends on undocumented behaviour
with no completion signal.

**Outcome, rationale and current boundary:**

Use an application-owned IndexedDB outbox instead of depending on Pro client recovery-cache
internals. Replay only against the unchanged revision, preserving mutation identity; on divergence
retain the edits in a separate conflict copy for deliberate reconciliation rather than silently
losing, duplicating or merging them. The occasional copy is the accepted usability tradeoff for
integrity. Keep complete revision/image preparation and current scope checks from
[#88](SPN-039.md#legacy-decision-88-complete-public-replay-evidence)/[#89](SPN-039.md#legacy-decision-89-preserve-existing-sheet-images). This supersedes the
mechanism in [#90](SPN-039.md#legacy-decision-90-public-pro-recovery-coordinator-proposal), not the
full offline acceptance or the ban on guest offline account access.

**Persona tradeoffs recorded at the time:**

Owner and Collaborator — edits are never silently lost or duplicated, at the cost of an occasional
copy to reconcile by hand. Operator — no new service or Pro internals. Link guest — unaffected; no
offline access.
