## Prepare inside the existing isolated verifier

**Accepted, 2026-10-29 — agent judgment under the standing delegation.**

The catalog and upload inputs need one preparation operation. Reuse the existing
permission-restricted archive verifier, including authenticated inventory,
native content/image/access semantics, memory admission, timeout and cancellation.
Do not add a second in-process decoder or a second verification definition.

Preparation requires the exact currently configured immutable image and origin.
It retains the private verified database and reports its byte count and SHA-256
after closing the verifier's database handle. The normal weekly verifier still
disposes its copy. Preparation does not pause, change the current database,
authorize activation, or promise that a rollback has been prepared.

Only snapshot time, origin and immutable image are returned as recovery metadata.
The separately extracted archived environment file is removed before handoff;
uploaded endpoints, secrets and schedules cannot become deployment instructions.
The authenticated source bundle remains unchanged. The caller owns cleanup until
the supervisor durably takes custody; interrupted preparation removes its private
copy. Generation custody, capacity planning, revocation reconciliation and the
activation journal remain required integration work.

Operator gets one bounded preparation path with clear compatibility failures.
Owner and Collaborator keep newer live work until a separately authorized cutover.
Link guest gains no access: preparation is internal, exposes no document content,
and grants no authority from the candidate database. Preserving current authority
and revoked access across activation remains a separate mandatory acceptance gate.

source/live data; no deployment environment in returned metadata or extracted
handoff files; compatibility rejection; worker deadline cleanup; and repeated
