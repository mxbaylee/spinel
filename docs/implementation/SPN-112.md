## Closed-file custody and opening barrier

**Accepted boundary, 2026-10-28 Pacific — agent judgment with independent design review.**

Keep the current database inode and its existing exclusive workspace leases during
cutover. Renaming another inode over the path would require redesigning both the
supervisor's and its children's ownership handoff. In-place copying is not atomic:
it is allowed only after application/verifier processes exit and all database/WAL
handles are proven closed, with durable originals and destructive intent recorded
first. Copies of original database, WAL and SHM plus the self-contained reconciled
candidate remain private, hashed evidence. Rollback restores database and matching
WAL, rebuilding SHM instead of reviving its lock state.

An adjacent durable opening barrier closes ordinary application and cold CLI
admission after interruption. Inode identity and SQLite quick_check cannot by
themselves prove that a partially overwritten file is the intended generation.
Supervisor ownership remains available for recovery, while ordinary verify, start,
resume and corrupt-journal acceptance refuse the barrier. Its publication is
atomic after file fsync; an incomplete temporary marker cannot authorize mutation.
Capacity is checked per filesystem before copying and again immediately before
activation or rollback. These checks are allowances, not physical reservations;
every write/fsync error still keeps recovery closed and source evidence retained.

The controller must durably commit verified generation/epoch state before removing
the barrier and reopening writes. Restart after that commit must finish reopening
the committed generation, never automatically roll it back over newly accepted
work. This controller integration is not implemented yet. File primitives are
internal and do not grant activation authority, perform SQLite health verification,
or make Admin restore available.

Operator gets a recoverable filesystem boundary without a second lease design.
Owner and Collaborator retain the original generation and cannot silently lose
post-commit work on restart. Link guest admission remains closed during recovery;
this boundary does not replace the required current-authority reconciliation.

Independent nonimplementing reviewer B identified partial-marker recovery and stale
capacity admission gaps in the interim code. Atomic publication and immediate
admission checks address those findings; regression tests were added but have not
run. This is design/interim review, not a passing whole-ticket score or acceptance
evidence. Real process cuts, actual SQLite/WAL recovery, host/provider acceptance,
UI and independent final reviews remain required.

## Current authority reconciliation constraints

**Design constraints, 2026-10-28 Pacific — independent reviewer A and agent analysis.**

Freeze current authority only after admission closes. Preserve current account
states and full passkey records using non-destructive upserts; archived-only users
must not regain credentials. Clear session, challenge, invite, setup/recovery,
token, OAuth and guest capability families. Copying direct grants alone is unsafe:
restored parent/Space membership can broaden a current grant. Final effective
permissions must be capped by frozen current permissions, including admin rights.
Current ownership transfers, archive-only items without current ownership evidence,
and accepted offline/restore receipts need explicit reconciliation. Validate
executable schema before copying current authority into a candidate, then validate
the reconciled structure/content again. These are unresolved integration work,
not claims that access reconciliation has shipped.

## Credential overlay on a frozen working copy

**Accepted internal step, 2026-10-28 Pacific — agent judgment and independent source review.**

Before current credentials enter a candidate, compare its complete executable
schema with the frozen current generation. Only the canonical archive metadata
table is exempt; its triggers are not. Unknown authority tables require an explicit
policy, including names with different capitalization. Reject source/target inode
aliases. This conservative same-image/same-schema boundary refuses unsupported
schema differences rather than running uploaded triggers or foreign-key actions
with current credentials present.

Copy current account state and passkey records without deleting or replacing user
rows, because those operations cascade into retained documents. Archive-only users
become disabled non-admin identities with no keys. Current profiles replace old

## Current sharing on the restored hierarchy

**Accepted internal step, 2026-10-28 Pacific — agent judgment and independent source review.**

Question: how can current sharing survive when restoring an older folder tree
would put previously removed documents under an otherwise still-current grant?
Copying archived grants revives revocations; copying current grants without
checking inherited access also revives access. Dropping every grant would avoid
that risk but needlessly remove unaffected collaboration.

After current credentials and ownership have been reconciled, copy only current
direct grants to current enabled ordinary accounts. Preserve their original share
date. Ignore Space member grants, which never confer access. Use the application's
ordinary account and Space resolvers to cap every contributing folder/root grant
at the recipient's current effective access to restored descendants. The ordinary
account resolver shares the production read boundary without materializing file
names, appearance or personal tags. Verify the completed result again before
committing; any error rolls back all grant and placement changes.

Changed ancestry receives the cap even when the candidate is currently hidden by
trash or a disabled Space owner: later untrash/reactivation must not revive dormant
inherited access. Common IDs must already have their current owners and unchanged
kind/Space membership; unsupported capability-namespace changes are refused.
Candidate-only content needs isolated disabled non-admin identities without keys,
absent from current authority. This is a guard, not an implementation or approval
of the still-pending ownership quarantine and retention policy.

This deliberately can remove or downgrade a folder grant for unaffected siblings
as well. All archived personal placements are discarded. The confirmation must
disclose these sharing/filing losses, with counts rather than document names for
the Operator; do not claim all current sharing survives. Owner can explicitly
re-share after recovery. Operator gets a bounded, fail-closed operation; Owner
keeps current ownership with clear consequences; Collaborator keeps unaffected
grants without regaining revoked scope; Link guests remain separately revoked by
the credential step.

Refuse more than 10,000 items per generation, 8,192 current grants, 8 MiB per
projection, 100,000 authorization calls or a conservative one-million weighted
ancestry-work allowance. Linear memoized ancestry validation detects cycles and
missing parents before service resolution. These are refusal budgets, not partial
proofs or product nesting limits. The isolated reconciliation worker still needs
its own elapsed-time/RSS enforcement when integrated.

Reviewer A found dormant inherited access and uncounted deep-ancestry work in the
first helper. Both were repaired and revalidated in source. New regression cases
cover actual untrash/reactivation after reconciliation, ordinary/Space inheritance,
current revocations and ownership transfer, disabled accounts/owners, identity
isolation guards, rollback and complete-proof/depth refusal. They remain unrun
while memory pressure is elevated. No whole-ticket grade or runtime approval has
been issued.
