## Legacy decision 120: Unstyled accessible controls

**Recorded:** 2026-10-20. **Status:** accepted.
**Authority:** Owner UI foundation choice.
**Source:** [original decision #120](https://github.com/mxbaylee/spinel/issues/120).

**Question:** Which component foundation should the redesign adopt, and should icons wait for it?

**Options considered in the original source:**

A — Base UI with existing CSS/theme tokens. B — Radix primitives with existing CSS. C — A pre-styled
library/starter with a broader styling adoption.

**Outcome, rationale and current boundary:**

Use Base UI's unstyled accessible primitives with the existing CSS/token system rather than adding
Tailwind or a second styling pipeline. Preserve gem identity, keyboard/touch behavior, readable
states and accessible names. Icon-family work remains separately scoped in SPN-077. A chosen library
is not approval of every resulting screen or a substitute for actual light/dark/phone evidence.

**Persona tradeoffs recorded at the time:**

The Operator needs maintainable dependencies without a second styling pipeline. The Owner wants
consistent, recognizable controls and the gem identity. Collaborators need predictable
keyboard/touch behavior. Link guests need the same accessible controls without new access or
discovery surfaces.

## Legacy decision 126: Approved redesign and its limits

**Recorded:** 2026-10-21. **Status:** accepted, scoped owner approval.
**Authority:** Owner final comment; earlier agent recommendations remain historical.
**Source:** [original decision #126](https://github.com/mxbaylee/spinel/issues/126).

**Question:** Should Spinel adopt the whole-product layouts and connected journeys shown in PR #125?

**Options considered in the original source:**

The source records a composed design proposal awaiting whole-product owner review, rather than a
final enumerated option selection. The final owner comment approves that specific design as-is with
follow-ups and ordinary implementation gates; earlier sample review did not supply that approval.

**Outcome, rationale and current boundary:**

Separate proposed Storybook designs from delivered application UI. Earlier sampled grades were
withdrawn as evidence of whole-product approval; the final owner comment approves the specific
design for merge as-is. Remove the temporary Pages exception before merge and preserve all ordinary
product/access requirements. Decision [#128](SPN-047.md#legacy-decision-128-remove-personal-pinning)
removes pins. Later [SPN-088 eight-choice adaptive-palette work](SPN-088.md#retain-native-colors-and-retire-the-extra-palette-proposal) was explicitly cancelled on
2026-10-23, not delivered by native adaptive colors. Native editor appearance evidence does not
establish print/raster parity. This design approval creates no standing authority to approve
unrelated screens or skip runtime evidence.

**Persona tradeoffs recorded at the time:**

Owner needs fast retrieval and confidence that work is safe. Collaborator needs truthful access/save
status and preserved return context. Operator needs setup, invitations, recovery and health without
document access. Link guests need only their shared content and permitted actions, including on
phones.

**Accepted design details:** The maintained [dashboard](../design/dashboard.md) specifies discovery,
query/filter controls and return context; [editor](../design/editor.md) specifies title-adjacent
save/connection status and native tools; [account](../design/account.md) specifies
appearance/profile/security controls; [guest](../design/guest.md) keeps anonymous scoped navigation;
[states](../design/states.md) specifies error, empty and offline behavior. The [composed
redesign](../design/redesign.md) and [walkthrough](../design/walkthrough.md) retain the complete
connected proposal and follow-up ownership. These local references carry the concrete accepted

## Legacy decision 128: Remove personal pinning

**Recorded:** 2026-10-21. **Status:** accepted; supersedes pins.
**Authority:** Owner, chat 2026-10-21.
**Source:** [original decision #128](https://github.com/mxbaylee/spinel/issues/128).

**Question:** Should Spinel retain personal pinning and pinned-item UI in the redesign?

**Options considered in the original source:**

A — retain pinning as a shortcut list or hidden action, preserving a redundant retrieval mechanism;
B — remove personal pinning and its UI, preserving folders, tags, search and shared filing. The
owner chose B.

**Outcome, rationale and current boundary:**

Remove personal pins and all pin UI, including hidden/disabled or renamed favorites/shortcuts
variants. Retain My files, Shared with me, folders, personal tags/search and existing shared filing;
never delete documents or change grants. This supersedes decision
[#64](SPN-020.md#legacy-decision-64-personal-pins) and pin-preservation parts of the earlier
redesign proposal. Named versions, pinned dependencies, home-screen installation and offline
downloads are unaffected. Icon-only My files still needs its accessible name/tooltip; Space headers
omit redundant Back navigation.

**Persona tradeoffs recorded at the time:**

- Owner: accepts losing personal pin shortcuts to reduce navigation clutter and maintain fewer retrieval mechanisms. Existing files, folders, tags and search remain available.
- Collaborator: loses personal pins but retains shared-file access, personal filing and search. Removal must not change grants, ownership or the underlying shared document.
- Operator: fewer personal-navigation controls and feature-specific operations to maintain; account administration still grants no document visibility.
- Link guest: no personal pinning existed in the guest scope; the linked-document boundary remains unchanged.
