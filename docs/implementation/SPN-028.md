## Legacy decision 77: Maintained installability verification

**Recorded:** 2026-10-18. **Status:** accepted.
**Authority:** Agent, 2026-10-18.
**Source:** [original decision #77](https://github.com/mxbaylee/spinel/issues/77).

**Question:** How should SPN-028 verify installability now that Lighthouse's PWA audits are
deprecated?

**Options considered in the original source:**

- A — Replace the obsolete audit with current Chromium installability checks plus manifest/icon and service-worker/offline tests in CI, retaining mobile touch verification. This exercises the intended outcomes using maintained tooling.
- B — Pin an obsolete Lighthouse release. This preserves an outdated score rather than current installability and adds maintenance cost.
- C — Drop installability verification. This loses acceptance evidence and is rejected.

**Outcome, rationale and current boundary:**

Replace removed Lighthouse PWA audits with current Chromium installability checks plus manifest/icon
and service-worker/offline tests. Retain mobile touch checks and configured HTTPS-origin
verification, followed by public-origin verification after approved launch. Pinning an obsolete
audit or dropping installability evidence would not establish intended behavior. No private content
cache, real-device acceptance waiver or deployment permission follows from this tooling
substitution.

**Persona tradeoffs recorded at the time:**

- Operator: reproducible CI checks on supported browser tooling, without caching private data.
- Owner: home-screen installation with Spinel's name/icon, touch editing and a clear offline screen.
- Collaborator: the same usable installed experience without weakening access or unsaved-edit warnings.
- Link guest: document-only access; installation and offline handling must not cache links, tokens or document contents.

## Legacy decision 82: Initial mobile and installable shell

**Recorded:** 2026-10-18. **Status:** superseded in part.
**Authority:** Agent PWA/mobile implementation judgment.
**Source:** [original decision #82](https://github.com/mxbaylee/spinel/issues/82).

**Question:** How should phone installation and touch controls work without retaining private
documents offline?

**Options considered in the original source:**

A — Choose the public mobile Sheet UI plugins at editor creation for a coarse pointer at up to 900
CSS pixels, preserving models and collaboration; use a network-only navigation service worker with
fixed generic offline HTML and no CacheStorage. B — Keep desktop controls on phones. C — Add private
offline document caching and reconciliation, which contradicts the ticket's agreed scope and
increases revocation/data-loss risk.

**Outcome, rationale and current boundary:**

Choose coarse-pointer mobile controls at mount when width is at most 900 px; avoid
rotation-triggered editor remount/data loss. The initial service worker was network-only with public
manifest/icons and a clear offline screen, not private cached documents. Decision
[#83](SPN-039.md#legacy-decision-83-complete-opted-in-offline-product) later extends signed-in
opt-in offline access; anonymous guests remain excluded. Installation acceptance and current
per-document authorization remain required on actual supported devices.

**Persona tradeoffs recorded at the time:**

The Operator gets a small public manifest/icon surface and no private service-worker cache to
manage. The Owner gets the existing Spinel icon, standalone launch and the SDK's phone Sheet
controls. The Collaborator keeps existing save warnings and authorization while changing controls.
The Link guest retains document-only access and generic offline copy without saved guest pages or
tokens.
