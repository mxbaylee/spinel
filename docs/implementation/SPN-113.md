### Callback lifetime invariants

The desired repair preserves the existing cursor cadence: initially visible,
hidden after 500 ms, visible at each 1,000 ms interval, then hidden 500 ms later.
The bound is per live native range, including short-lived validation ranges;
it is not a count of every selection ever constructed.

| Owner                | Allowed pending work                                                                         | On replacement or disposal                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Live text range      | At most one 500 ms hide timeout and one 1,000 ms blink interval                              | Replacement cancels its predecessor; disposal leaves zero timers and no later graphic writes or reinstallation |
| Live zoom controller | At most one skeleton-driven update timeout, plus its separately owned initialization timeout | Superseded update is cancelled or coalesced; disposal leaves zero timers and no later view update              |

Source-level tests must prove these bounds for 10, 100 and 4,000 successive
replacements, both before the first cursor timeout and between an interval and
its following hide callback. Include repeated disposal and stale callback races.
Zoom tests must preserve the latest effective ratio, document/unit ownership,
explicit zoom commands, fit-to-width and the Sheet inline editor case.

### Browser evidence

Run separate first-attempt desktop and mobile callback traces on each source,
sequentially on the same runner. Desktop is 1,440 × 1,000; mobile is 390 × 844,
touch/coarse pointer and 4× CPU throttling. Mobile is an emulation, not a claim
about a physical phone or OS keyboard.

Start the Chrome DevTools Protocol trace before mounting the measured Doc and
retain it through ordinary route closure/editor disposal and at least one full
1,000 ms cursor period afterward. Preserve the entire raw stream, source and
lockfile hashes, browser/Node/Playwright versions, trace categories and complete
source attribution. Explicitly report trace completeness and data loss. Do not
replace or wrap global timer functions, mutate SDK state, suppress work or read
the native snapshot on every key.

Account for timer installation, removal and firing using renderer/thread/frame
identity, timer ID and successive installation generations. A one-shot firing
retires its pending callback; an interval firing does not. A removed timer is
not pending. Unknown sources, duplicate lifetimes, unpaired firings and a trace
that starts after installation must remain visible as unknown/incomplete,
never silently count as zero. Zero dropped data and complete attribution of
the two target families are prerequisites for acceptance.

Report each family's installations, removals, firings, live pending high-water,
pending work at the final key and after disposal, callbacks after disposal,
and direct callback wall spans. Preserve all task spans and distinguish their
union from summed callback spans. Counts and wall coverage do not establish
that all elapsed time or heap growth belongs to these callbacks. Heap/RSS
observations retain their process, garbage-collection and sampling limitations.

Source tests establish the per-object lifecycle bounds; the mounted trace must
corroborate cancellation and zero residual target-family work after disposal.
A low global high-water count alone is not proof of correct object ownership.
Keep normal cursor blinking, ordinary zoom, selection and input interactions.

## Supported integration investigation

**Date/status:** 2026-10-27, supported integration blocked; source repair preparation.
**Authority:** agent source/API inspection under the ticket's existing Rules.

The pinned OSS 1.1.0 implementation loses the initial and nested cursor timeout
handles. `TextRange.dispose()` only clears its interval. Skeleton notifications
overwrite `DocZoomRenderController._updateTimer` without cancelling predecessors.
The latest published SDK, v1.2.0 (October 22), and current upstream development
still contain both defects:

- [v1.2.0 cursor source](https://github.com/dream-num/univer/blob/v1.2.0/packages/docs-ui/src/services/selection/text-range.ts)
- [v1.2.0 zoom source](https://github.com/dream-num/univer/blob/v1.2.0/packages/docs-ui/src/controllers/render-controllers/zoom.render-controller.ts)
- [v1.1.0 plugin registration](https://github.com/dream-num/univer/blob/v1.1.0/packages/docs-ui/src/plugin.ts)
- [v1.1.0 public exports](https://github.com/dream-num/univer/blob/v1.1.0/packages/docs-ui/src/index.ts)
- [upstream API stability policy](https://github.com/dream-num/univer/blob/dev/docs/API_STABILITY.md)

`TextRange` is exported, but native selection construction has no public timer
or range-factory hook. Calling its public `dispose()` cannot recover a timeout
handle it never retained. The zoom controller is not a public runtime export;
the installed package contains bundled runtime files, not the controller path
that exists in its declaration tree. Docs UI's `override` applies to its service
dependencies, not its hardcoded render-module registration. No supported
application-only repair was found.

**Options and outcome:** a routine version bump does not repair these defects.
A private-field/prototype/global-timer workaround violates the ticket and is
rejected. A complete selection/plugin replacement would duplicate substantial
native behavior for a small lifecycle bug. Prepare a narrow upstream OSS source
repair and its tests, then consume a suitable aligned release. A locally patched
or renamed SDK package is not silently equivalent to that supported release.
The existing unrelated core/UI/drawing compatibility patches do not override
SPN-113's explicit prohibition on patching installed packages.

**Personas:** Owner, Collaborator and Link guest need retained caret, zoom,
content and editing semantics as well as bounded work; none gains new access or
telemetry. Operator benefits from a small upstream-owned repair and avoids
another unsupported selection implementation or service. Waiting for a supported
release delays the performance improvement; a proposed temporary OSS patch
would need an explicit exception to the current ticket rule before integration.

**Next action:** finish and independently review the source repair and lifecycle
tests. Keep SPN-113 open and any Spinel PR draft until a suitable supported build
exists, or the owner explicitly authorizes the narrow temporary OSS repair.
Neither a prepared patch nor a passing source test proves browser acceptance.
