## Wait for the loaded folder view

**2026-10-28 — accepted, agent judgment following controlled reproduction.**
The fixture currently observes the shared folder's heading and immediately
disconnects its transport. The Dashboard can render that heading and its New
button from the shared list while its separate folder request is still loading.
The account's durable shared row can already have Editor access even though
`catalog.views[folder.id]` has not been prepared. Disconnecting at that point
aborts the request and leaves no loaded folder view for the intended offline
journey.

Before changing the readiness condition, the investigation declared exactly
three fresh-profile controlled probes, without retries. All three held the
folder request and observed the same state: the heading and one New button were
visible, loading remained visible, the durable shared row had Editor access,
and `folderViewPrepared` was false. Disconnecting then produced the missing
screen with zero New buttons. These are successful diagnostic reproductions of
the false readiness signal, not passes of the complete restart journey.
The retained [held-folder probe patch](evidence/SPN-116-held-folder-probe.patch)
records the diagnostic instrumentation applied to the main base.

The correction waits for both prepared seed documents to appear in the requested
folder's actual contents before transport is disconnected. Rendering those rows
proves that the folder response has populated the Dashboard's synchronous
`views.current` state. The shared row or heading alone does not satisfy that
condition. Missing readiness must fail at that stage rather than proceeding
into offline creation and timing out later.

This observation is not a new IndexedDB durability fence. `saveCatalog` remains
asynchronous on the existing shared serial queue. The later saved-draft and
two actual browser-process restart checks establish persistence; the fixture
does not claim that catalog commit has completed merely because the folder
contents are visible.

The fixture retains the original complete journey: create a Sheet and Doc in
the shared folder offline, retain exact drafts and immutable creation identities
through a real browser-process restart using the same profile, publish each
once to the folder owner, and preserve the accepted native content through a
second offline restart without republication. Current-role publication checks,
creator attribution, account isolation and exactly-once assertions remain.

Keep diagnostics limited to readiness stages, bounded state summaries, request
outcomes and process/cleanup errors. They must retain the original failure
without credentials or document contents. Use observable state and the existing
timeout contract; no arbitrary sleep, blanket timeout increase, unconditional
request retry or removal of a correctness assertion belongs in this repair.

- **Operator:** obtains a deterministic preparation boundary and a first-attempt
  failure that names the unfinished phase.
- **Owner:** retains the same canonical folder ownership and publication checks;
  this fixture change grants no new content access.
- **Collaborator:** keeps the full saved-draft, browser-restart, current-access
  and exactly-once shared-publication acceptance contract.
- **Link guest:** gains no account or offline capability; its existing scope and
  revocation checks remain part of required CI.
