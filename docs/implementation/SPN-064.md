- `AdminStore` lists account/passkey metadata, disables accounts and removes
  passkeys. Disabling currently deletes sessions and invitations but leaves
  credentials blocked by account state. Simply clearing `disabled` is unsafe.
- `authRoutes` already conceals administration from non-Operators, requires the
  configured Origin and JSON for mutations, sets `no-store`, and awaits the
  application's `realtime.revalidate()` hook after access changes.
- `WorkspaceStore` holds ownership, grants, personal placements and tags.
  Space roots and all internal rows use the same `owner_id`; native snapshots,
  images, history and formula bindings refer to stable item IDs.
- Ordinary guest capabilities have epochs, token/preview hashes and guest
  sessions. Disabled-owner checks alone would let a surviving link revive when
  ownership moves to an active person.
- Native HTTP/socket and Formula services already recheck current session,
  role, host and source access across asynchronous work. Reuse these checks and
  prove their behavior during transfer; do not introduce a parallel engine.
- Existing approved People actions, `Modal`, `Choice` and shared controls cover
  these dialogs. Full administration section/navigation migration stays SPN-082.

## Reactivation

`POST /api/auth/admin/users/:id/reactivate` accepts an empty JSON object and
returns 204 only after the mutation and live-access revalidation succeed.

In one synchronous application transaction, require a current active Operator
and a disabled target. Permanently invalidate the target's old passkeys,
sessions/pending ceremonies, unused invitations, OAuth connections and
authorization/access/refresh credentials, and personal access tokens. Only then
set the account active. Existing optional credential schemas are handled without
creating unrelated services merely to perform cleanup.

Do not change documents, ownership, grants, tags, history or trash. A recovery
invite is a separate deliberate Operator action using the current invitation
service. A disabled secondary admin may be reactivated and recovered; it never
becomes an ownership-transfer destination. Existing lockout protection remains.

The UI explains that old sign-ins remain invalid and a recovery invite is needed.
Success refreshes accounts and invitation recipients; it does not generate or
send an invitation automatically.

Reactivation preserves the same owner's deliberate document-link configuration:
an otherwise active, unexpired link can work again, while already revoked or
rotated links stay invalid. This is document sharing, not an account credential.
Ownership handover instead forces all transferred links off and advances epochs.
The distinction is recorded in decision #141 and tested explicitly.

## Ownership handover

[Decision #140](https://github.com/mxbaylee/spinel/issues/140) records the routine
counts-only confirmation, stable-identity and guest-capability choices.

### API contract

`GET /api/auth/admin/users/:id/transfer-preview` returns:

```ts
type TransferPreview = {
  source: { id: string; name: string };
  recipients: { id: string; name: string }[];
  counts: { items: number; folders: number; links: number };
  confirmation: string;
};
```

`items` counts non-folder rows, including Space roots and native Docs/Sheets;
`folders` includes internal and ordinary folders. Both include trash. `links`
counts existing link records attached to those rows, all of which remain off
after handover. No item IDs, names, locations, content, image data, history or
source values enter the Operator response. Account names/IDs are existing
Operator metadata. Only active everyday accounts appear as recipients.

`POST /api/auth/admin/users/:id/transfer` accepts
`{ targetId: string, confirmation: string }`, returning 204 (or counts only)
after the transaction and live-access hook. A stale preview returns a conflict
and requires another explicit confirmation of fresh details. An empty source
does not create an unexplained empty wrapper folder.

### Transaction and preservation

1. Recheck active Operator, disabled source, distinct active non-admin target,
   complete bounded structural set and confirmation inside the transaction.
2. Read structural metadata only. Reject corrupt mixed-owner ancestry, cross-
   Space attachments, cycles and over-budget trees rather than repairing them
   silently. Internal Space parents may be Docs/Sheets as well as folders.
   Recheck recipient capacity inside the transaction: all existing owned rows,
   the complete incoming set and the containing folder must fit the current
   10,000-row discovery budget. An accepted handover must leave a usable dashboard.
3. Create one private containing folder owned by the recipient, named after
   the departed account. Replace folder-forbidden slash, backslash and control
   characters with spaces; use `Transferred files` if no usable name remains.
   Duplicate display names remain separate through their stable IDs.
4. Move only ordinary outer roots into that folder. Change every source-owned
   outer and internal row together. Preserve IDs, internal parent/order,
   timestamps/content identity, trash batches and Space recovery records.
5. Preserve other accounts' grants and valid private placements. Remove old-owner
   access and redundant recipient grants/placements. Never transfer another
   account's private tags or turn personal placement into a content grant.
6. Turn every transferred guest-link record off, advance its epoch, clear old
   token/preview hashes and remove its guest sessions. A new owner must deliberately
   create a fresh capability; old URLs/cookies/previews cannot revive.
7. Commit atomically, then await existing live-access revalidation before success.

The fingerprint covers source identity and the complete structural set, including
stable IDs, parent/Space/order/trash state and guest capability state. Equal counts
with different rows are not equivalent. Target eligibility is checked inside
the same transaction. Replaying a successful request cannot move the recipient's
newly owned rows or create another containing folder.

A database failure rolls back the complete transfer. A later connection-refresh
hook failure is different: return an explicit 503 message saying that ownership
was transferred (or the account reactivated) but open connections could not
refresh. Existing live request/write checks remain authoritative. The UI refreshes
current accounts/preview before any retry and never claims the data was unchanged
after an ambiguous or committed failure. Verify both failure modes independently.

Snapshots, live generations, history, images and stable Formula bindings are not
copied or rewritten. A transferred Doc gains no source permission that the new
owner lacks. Recovered old accounts remain unable to access transferred files.

## UI/UX contract

- Disabled account contextual actions offer Reactivate; disabled everyday
  accounts additionally offer Transfer ownership. Preserve current disable and
  passkey controls and their lockout protections.
- Dialogs identify source and selected recipient accounts and aggregate counts,
  with concise consequences. The destination initially requires an explicit
  choice. Explain retained history/trash/grants and inactive guest links.
- Show truthful loading, failed load/retry, no eligible recipient, no owned
  content, stale preview, submitting, failure and success states. Loading must
  never look like an empty list. Preserve valid selections through retry.
- Cancel and Escape before submission change nothing. Pending submission
  prevents duplicate writes/dismissal. Restore focus to a surviving action.
- Use the approved shared semantic icons, modal, choice, action menu and theme
  tokens. Verify keyboard, focus, readable long names, phone touch targets,
  content bounds and light/dark contrast. No new layout system or dependency.
- Operator cannot preview any document. Owner sees a recognizable containing
  folder and preserved work. Collaborator retains existing access. Guest sees
  the existing unavailable state, with no account identity leak.
