# 🛂 SPN-079 Delegate administration of shared files without server access

## Story

As the [Owner](../product/personas.md#owner), I want to delegate administration of a shared file without giving away ownership, so that a trusted [Collaborator](../product/personas.md#collaborator) can manage access while I remain its sole owner.

## Scenarios

### One owner, multiple administrators

Given a file has one Owner,
When that Owner grants another account Admin access,
Then both can administer it, the Owner retains all Admin permissions, and exactly one Owner remains,
And removing an Admin grant never removes or demotes the Owner.

### Top-level roles apply consistently

Given a Doc, Sheet, folder or Space grants View, Edit or Admin,
When the recipient acts on it,
Then View reads, Edit changes content, and Admin additionally manages sharing and file organization within authorized destinations,
And a Space applies its effective role to every internal page/sheet without child overrides.

### File administrators are not server operators

Given I administer a shared file,
When I use it,
Then I gain no server administration, account-management or unrelated-file access,
And a server Operator still cannot receive content grants or read files.

## Rules

- SPN-047 handoff: File admin is an explicit account-only role; owner remains unique, guests View/Edit, Operator content-blind. Follow [the composed design](../design/spaces.md) and decision #126 (2026-10-20); preserve current behavior and owner screenshot approval.

- Current file roles are Viewer/Editor plus ownership; server Admin is content-blind. Add delegated file Admin after Space navigation, recovery, guest and integration acceptance (SPN-078 → SPN-091 → SPN-092), not as a prerequisite of artwork or initial Spaces. Owner, chat 2026-10-20; #118; grooming 2026-10-21.
- Exactly one Owner per file, inheriting every Admin permission. Admin grants may be multiple; grant APIs cannot create a second Owner, transfer ownership or demote the Owner. Ownership handover remains SPN-064. Owner, chat 2026-10-20.
- Document the capability matrix in the playbook before UI work: Admin includes View/Edit, grant/revoke View/Edit/Admin, link management, rename, permitted move and recoverable trash. Permanent deletion and ownership transfer stay owner/operator-controlled under their existing rules.
- Retain most-generous inherited access (Admin above Edit above View), show its provenance, and recheck both source administration and destination authority for moves. No cross-owner or cross-Space boundary escalation; inaccessible ancestors stay undisclosed.
- Guest links remain View/Edit only, never Admin. Revoke/downgrade and disabled-account checks apply to live sockets, content/image/export routes, source formulas and OAuth/MCP; scoped tokens cannot acquire a stronger authority than their user.

## Out of scope

- Multiple owners, new server Operator powers, public Admin links, account deletion or a new ownership-transfer flow.

## Verify

- Unit/API: complete role matrix, inherited combinations, sole-owner invariant, grant escalation, move boundaries, token scopes, revoke/downgrade and operator/guest isolation.
- Browser: delegate, administer shares, revoke and downgrade on each outer file type; Space children stay uniform. Stories and owner-approved light/dark/phone screenshots distinguish file Admin from server administration.
