# ✏️ SPN-162 Make actions and buttons consistent across Spinel

## Story

As the [Owner](../product/personas.md#owner), I want buttons and menu commands to describe consistently what they do, so that I can predict the result on every screen. Collaborators, Operators and link guests need the same clarity within their allowed actions.

## Scenarios

### One action has consistent language and behavior

Given buttons, menus, toolbars, dialogs and command-triggered actions across dashboard, editor, Spaces, account, Admin and guest views,
When the same operation is offered in multiple places,
Then its wording, semantic icon, emphasis, enabled/pending state and feedback are consistent,
And keyboard, touch and command invocations retain the same permission and destructive-confirmation boundaries.

### Commands describe an action

Given a Sheet or Doc not downloaded on this device,
When its row menu opens,
Then **Make available offline** names the download command; already-downloaded actions and status badges remain unambiguous.

## Rules

- [Cross-product action consistency](../implementation/SPN-162.md#-cross-product-action-consistency), owner chat 2026-11-22, expands the original offline-label request. Effort M: inventory existing action surfaces and native/public command paths, reuse established patterns, and reassess if architecture or a new design pattern is needed.
- Use verb-led commands where they describe operations; retain clear noun destinations, type choices and state labels. Do not mechanically rename every label to a verb or introduce a command palette/framework.
- Record a shared action/placement inventory and intended exceptions. Compare labels, accessible names, icons, button priority, destructive treatment, disabled reasons, busy/success/failure feedback, focus return and touch targets. Include command-based actions through existing public SDK APIs.
- Preserve current operation semantics, access checks, confirmation and recovery behavior. A command route may not bypass a disabled/denied UI; a discovered correctness gap needs a bounded regression and explicit scope reassessment.
- Follow the [design playbook](../design/README.md), [sustainable testing](../testing.md) and production-story rule. Missing patterns land in a separate reviewed design PR first. SPN-150 owns brand/type artwork; SPN-089 owns dialog title icons.
- Known offline wording sites: `web/Dashboard.tsx`, `web/OfflineStatus.stories.tsx`, `e2e/offline-upgrade.spec.ts`, `docs/offline.md` and `docs/design/dashboard.md`. Inspect current source before editing; historical decision quotes remain provenance.

## Out of scope

- New actions, command infrastructure, a wholesale navigation redesign or changed offline storage semantics.

## Verify

- Contract/negative: equivalent actions have consistent meaning and cannot bypass permission/confirmation checks via another invocation. Use existing unit/command tests for dispatch/authority and production stories for labels, states and focus.
- Reuse isolated existing fixtures and observable pending/settled readiness, resetting action state. Existing offline-upgrade e2e owns actual download/edit/reload; do not duplicate its journey for each wording variant.
- Track edited action definitions, SDK integration, shared button/menu components, styles, stories and application fixtures in CI routing. Search current user-facing wording while preserving historical quotes and legitimate status text.
- Retain the action audit and negative controls, proposed designs and actual light/dark/phone captures for independent visual approval (agent review only).
