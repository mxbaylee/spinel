# 🔎 SPN-120 Resolve the remaining recorded browser fixture failures

## Story

As the [Operator](../product/personas.md#operator), I want browser checks to wait for the state they actually need and explain failures, so that I can update Spinel without uncertain reruns.

## Scenarios

### Each remaining recorded failure has a useful first-attempt result

Given the recorded readiness, navigation, connection and teardown failures,
When they are rechecked against a recorded current main, pinned runtime and browser,
Then confirmed fixture races are repaired using observable state,
And missing readiness or a crashed server still fails clearly with the original cause preserved.

## Rules

- Effort L, full-scope review 2026-10-29: Keep the finite historical failure inventory and explicit per-case disposition. Prove readiness, eligible setup-retry classification and fatal negative controls before enabling recovery; unrelated product fixes and a generic retry framework are separate outcomes. [All-ticket assessment](../implementation/grooming-2026-10-29.md#all-ticket-effort-and-impact-review).

- Preserve the original SPN-116 audit after its [explicit scope split](../implementation/SPN-116.md#scope-split), agent judgment 2026-10-28, originating from SPN-118 / PR #213. SPN-116 owns only the demonstrated shared-creation restart preparation boundary; it does not establish dispositions for these remaining historical symptoms.
- Use the [bounded failure audit](../implementation/ci-reliability-2026-10-28.md#failure-evidence), agent judgment 2026-10-28. Its auth-heading, phone-navigation, offline-recovery-close and snapshot-reset cases occurred on different historical revisions; establish their current status before changing code.
- Record each case as reproduced, fixed by an identified later change, or not reproduced in a predeclared bounded sample. Retry success or an unrelated green run alone does not establish a fix.
- Repair demonstrated shared fixture/state-observation races. Preserve authentication, account switching, saved content, cancellation, revocation and unsaved-work contracts. Use no arbitrary sleeps, blanket timeout increases or unconditional request retries.
- Cleanup must be bounded, tolerate already-closed resources and retain the initial failure alongside cleanup errors. Record source SHA, test/attempt, relevant readiness and process-exit state without credentials or document contents.
- For non-authentication scenarios, use deterministic authenticated fixtures and verify the actual identity/session before the feature flow. Keep full login/passkey, denial, expiry, account-switch and revocation behavior in their own first-attempt security coverage. [Approved refinement](../implementation/grooming-2026-10-29.md#timely-and-resilient-tests), owner 2026-10-29.
- Permit at most one explicitly classified retry of idempotent setup/transport preparation inside its existing time budget, only while the owned server is healthy; retain both attempts/reasons. Never retry an authentication mutation, wrong identity, denied/expired session, crashed process or failed product assertion as setup noise. Negative controls must prove those conditions still fail.
- Keep a bounded post-readiness stdout/stderr tail in the shared owned-process fixture and surface unexpected exit promptly. Capture first-attempt phase/readiness/process evidence; evaluate retain-on-failure tracing for non-performance cases without instrumenting primary latency samples.
- Retain `failOnFlakyTests` and every correctness assertion; do not skip, mark expected-failing or accept a test/scenario retry to obtain a green gate. The narrowly classified setup recovery above remains inside one scenario attempt and cannot rerun a failed assertion. Keep runtime crashes, storage-integrity investigations and native callback work under their own ownership; diagnose a product defect before assigning its repair.
- This is independent of SPN-115 routing. Operator gets reliable maintenance evidence; Owner, Collaborator and Link guest retain the existing content and access gates.
- Keep L scope to the named historical cases and shared setup/process boundary. A newly reproduced product defect receives its own evidence-backed owner and estimate; do not expand this into a replacement test framework or an open-ended every-test rewrite.

## Out of scope

- Changing runtime pins, weakening latency/content/immutability contracts, repairing native callback ownership, or treating an uncompleted typing workload as proven data loss.
- Duplicating SPN-116's confirmed shared-creation restart readiness repair.

## Verify

- Choose and record a small fixed repetition count before execution, using fresh profiles and first attempts for each affected scenario. Require that repair-proof sample to pass without test/scenario retries or setup recovery; retain every attempt and report its limits. Separately exercise the allowed setup-recovery path and record both preparation attempts; recovered setup alone does not prove the historical race fixed.
- Withheld readiness, wrong-account/denied authentication, retry exhaustion and a terminated server must still fail clearly within the original budget. Verify bounded logs and cleanup with the first cause preserved. Run required final-SHA checks and record each original failure's supported disposition.
