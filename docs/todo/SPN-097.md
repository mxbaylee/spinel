# 🔬 SPN-097 Choose a PDF renderer and split its implementation

## Story

As the [Owner](../product/personas.md#owner), I want the PDF approach proven before the full export implementation, so that unsupported layout or resource assumptions do not become a late launch surprise.

## Scenarios

### A supported approach with evidence
Given SPN-075's Sheet and Doc export contract,
When the available public rendering/library APIs and licensing are evaluated with small representative fixtures,
Then a local implementation record recommends an approach with measured fidelity, resource limits and known gaps,
And every SPN-075 requirement has a delivery slice or an explicit unresolved question before implementation starts.

## Rules

- High impact for the Owner, as explicitly requested in owner chat 2026-10-23; the PDF feasibility result protects complete portable documents and determines the export delivery plan. Effort and acceptance are unchanged ([updated priority](../implementation/SPN-097.md#raise-pdf-feasibility-impact)).
- Owner accepted early PDF feasibility/split review during grooming, 2026-10-22; [decision and sequencing](../implementation/SPN-097.md). This prerequisite brings the investigation forward without inflating SPN-075's product impact or making unrelated tickets depend on it.
- Start with the existing native public models and public renderer APIs. No new Pro package, private SDK patch, or browser Print flow. Compare a small credible set of options and record dependency/licensing constraints; do not build multiple production renderers.
- Prove representative Sheet pagination/merges/image extent and Doc paragraphs/tables/page breaks, including a long Formula table. Retain PDFs/rendered evidence and record unsupported fidelity honestly; fixtures are bounded feasibility probes, not the full renderer acceptance suite.
- Assess current server-confirmed snapshots, authenticated images, exact Space child access, revocation before download and Formula-source privacy without implementing a second access boundary. Bound the proposed path for the 2 GB server and record whether work runs in browser or server.
- Split renderer and integration work only at independently verifiable boundaries, preserving all SPN-075 acceptance and final Pro removal. Register necessary slices with fresh IDs in this PR; keep SPN-075 as the final complete-export integration if that is the clearest shape.
- Owner/Collaborator need complete portable content, Link guest needs current scoped access and anonymous output, and Operator needs bounded resource use without document visibility. Record these tradeoffs in the implementation notes.

## Out of scope

- Shipping the production PDF action, a complete renderer, new export settings, or changing the accepted PDF product behavior.

## Verify

- Reproducible fixture commands, rendered PDF evidence, measured resource observations, public API/licensing references and an honest acceptance-gap mapping.
- Independent design review confirms the chosen approach, slice boundaries and retained acceptance criteria. Backlog index and dependencies validate; no feasibility probe changes production behavior.
