# 🚪 SPN-083 Apply the approved entry and consent screens

## Story

As the [Owner](../product/personas.md#owner), I want to sign in and approve connections without confusing or competing prompts, so that the interface supports my task without clutter.

## Scenarios

### One task at a time

Given the approved SPN-047 design and current access,
When I use this screen on desktop or phone,
Then the composed layout follows [the playbook](../design/account.md),
And loading, empty, error and restricted states keep the same clear hierarchy.

## Rules

- Use the quiet entry layout and Base UI actions; preserve passkey registration, setup claim, invite/recovery validation, consent capabilities/origins, cancellation and pending-request return paths.
- Build from `Redesign/Screens`: SignIn, Setup, Invite, Recovery, Consent, ConsentExpired; reuse the shared controls, tokens and screenshot runner. Proposed in SPN-047, 2026-10-20, decision #126; owner visual approval required before migration.
- Weigh all four personas: preserve content privacy for Operator/guests, recovery for Owner, and truthful access for Collaborator. No permissions are changed by visual consolidation.
- Adopt the shared semantic modal title icon for dialogs changed here. SPN-089 audits remaining omissions after screen migrations; do not defer this screen's pattern to that audit. Owner-approved grooming, 2026-10-21.

## Out of scope

- New authentication methods, OAuth protocol changes, profile navigation (SPN-045).

## Verify

- Browser: current successful and failure/access flows, keyboard focus/return, touch, and light/dark/phone screenshots against the approved mockups.
- Storybook: composed screen and relevant states; owner approval of implementation screenshots.
