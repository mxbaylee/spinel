# 🕰️ SPN-085 Apply the approved history browser design

## Story

As the [Owner](../product/personas.md#owner), I want to browse and restore earlier work without crowding the live editor, so that the interface supports my task without clutter.

## Scenarios

### Preview before restoring

Given the approved SPN-047 design and current access,
When I use this screen on desktop or phone,
Then the composed layout follows [the playbook](../design/editor.md),
And loading, empty, error and restricted states keep the same clear hierarchy.

## Rules

- History is per native Space child, not a versioned Space tree. Preserve exact root/child navigation, Viewer preview and account Editor/File admin/Owner naming/restore authority; guests remain excluded. Test Before restore, images and generation fencing inside a Space. Grooming, 2026-10-22.

- Versions opens isolated history with Today and Older days navigation, full retained version selection, UTC labels and the existing confirmed restore flow. Named and Before restore checkpoints remain reachable.
- Build from `Redesign/Screens`: History, HistoryCalendar; reuse the shared controls, tokens and screenshot runner. Proposed in SPN-047, 2026-10-20, decision #126; owner visual approval required before migration.
- Weigh all four personas: preserve content privacy for Operator/guests, recovery for Owner, and truthful access for Collaborator. No permissions are changed by visual consolidation.
- Adopt the shared semantic modal title icon for dialogs changed here. SPN-089 audits remaining omissions after screen migrations; do not defer this screen's pattern to that audit. Owner-approved grooming, 2026-10-21.

## Out of scope

- Changing retention, capture, restore generations, export formats or storage.

## Verify

- Browser: current successful and failure/access flows, keyboard focus/return, touch, and light/dark/phone screenshots against the approved mockups.
- Storybook: composed screen and relevant states; owner approval of implementation screenshots.
