# 🎲 SPN-167 Find and fix the offline-upgrade emitted worker that never activates

## Story

As the [Operator](../product/personas.md#operator), I want the `offline-upgrade` smoke project to pass or fail for real reasons, so that a green gate means the upgrade path works and a stuck worker does not cost a re-run.

## Scenarios

### An emitted worker that installs also activates

Given the old worker controls the page and the emitted worker has installed,
When it is told to skip waiting,
Then it activates within the case's budget, or the case fails naming what held it.

## Rules

- Follow [sustainable testing](../testing.md); keep the Verify plan and progress evidence current. [Policy](../implementation/SPN-115.md#guidance-for-every-open-ticket-and-progress-checkpoint), owner 2026-11-01.
- Split from [SPN-166](../implementation/SPN-166.md#offline-upgrade-worker-that-never-activates) with its full remaining estimate: the cause is narrowed (installed within 21 to 518 ms, `skipWaiting()` never takes effect, old worker stays active for 120 s) and not fixed. The case `offline-upgrade.spec.ts` "interrupted emitted updates…" flaked in 2 runs and passed on retry.
- Do not weaken the gate: no exclusion, added retry, longer 120 s budget or relaxed assertion. A flaky pass keeps failing the job.
- First use the lock snapshot SPN-166 added to the timeout error (`Locks {held, pending}`): the next failure names the holder. Confirm or discard the leading suspect, the old worker's `message` handler holding the runtime Web Lock (`web/service-worker.ts`, up to 180 s), before changing product code. The case cannot run locally without the immutable legacy checkout.

## Out of scope

- The 13 outright failures of the SPN-054 eager-client case on the `codex/spn-146-mobile-flush` branch.

## Verify

- Contract/negative case: the worker activates, or a held lock or message that does not drain fails with the holder named; suite/layer/fixture: the existing `offline-upgrade` project and emitted-worker fixture.
- Fixture readiness/cleanup: the immutable legacy checkout and the owned worker lifecycle.
- Environment and source/shared dependencies: `web/service-worker.ts`, `e2e/offline-upgrade.spec.ts`, the CI plan for `offline-upgrade`.
- Evidence: repeated `offline-upgrade` runs with no flake, linked by run id, and the holder named from a captured failure.
