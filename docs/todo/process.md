# How the Spinel backlog works

The backlog lives in this folder and is run by agents. The owner (@mxbaylee) sets
direction and answers the questions only they can answer. The owner may merge,
or authorize agents to merge through the [backlog runbook](../run-backlog.md).
`npm run backlog:check` and the CI pull-request job enforce ticket/index shape,
IDs, PR titles and size rules. Review scores, finding disposition and merge
readiness are agent-enforced; GitHub protections must be configured separately.

To process tickets continuously, say **“Read `docs/run-backlog.md` and start working.”**
That invokes implementation, independent review, repair/splitting, CI, squash
merge and next-ticket selection until finished, blocked or execution-limited.
Simply reading or editing these docs does not start that run.

| File                     | What it is                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| `SPN-NNN.md`             | One file per open ticket. The ticket is the spec.                                            |
| `readme.md`              | Every open ticket in pick order. Generated by `npm run backlog:index`; never edited by hand. |
| `backlog.json`           | Next ID, grooming counter, PR size limits and title exceptions.                              |
| `../product/personas.md` | Who Spinel is for. Every ticket's story names one of them.                                   |

The original PRD was groomed into tickets on 2026-10-17 and removed. It is in
history at [`c67d377`](https://github.com/mxbaylee/spinel/blob/c67d377/docs/todo/readme.md).
The tickets are authoritative now.

## Tickets

Create one with `npm run backlog:new -- <emoji> <title>`. That takes the next ID
and bumps `next_id`. IDs are never reused, renumbered or recycled.

```markdown
---
id: SPN-012
emoji: 🪞
effort: M # S | M | L | XL
# phase: pre_launch # optional; pre_launch (default) | launch | post_launch
impact_owner: L # S | M | L, one line per persona it affects:
impact_guest: S #   impact_operator, impact_owner, impact_collaborator, impact_guest
score: 5 # written by npm run backlog:index; never edit by hand
depends_on: [SPN-004]
decisions: [7] # legacy issue numbers only; new decisions link to docs/implementation/SPN-NNN.md
owner_input: "Approve the restore wording" # optional; shown in the index
---

# 🪞 SPN-012 Restore a document from yesterday's checkpoint

## Story

As the [Owner](../product/personas.md#owner), I want ..., so that ....

## Scenarios

### Restoring replaces the live document

Given ...,
When ...,
Then ...,
And ....

## Rules

- Pinned versions are never pruned. Decided 2026-10-17 in #7.

## Out of scope

- ...

## Verify

- Unit: ... E2E: ... What a reviewer should see.
```

- **Story** is what the person wants and why, without implementation words.
- **Scenarios** are observable outcomes in Given / When / Then. Edge cases go here.
- **Rules** hold decisions and constraints, each with its date and source, linked to its
  decision in `docs/implementation/SPN-NNN.md` (legacy issue links remain valid).
- **Out of scope** names the nearby work that belongs to other tickets.
- **Verify** says what proves it: tests, and what a reviewer should see.

Aim for 30–50 lines; the checker warns past 50. A ticket needs enough for an
agent to build it without asking, and no more. Each ticket gets its own emoji,
used as little as possible elsewhere. The size and type marks below are
reserved.

## Sizing and scoring

- **Effort:** 🌱 **S** one focused change with its tests, or low-effort
  work such as scaffolding however many lines it is · 🌿 **M** several
  coordinated changes, or one design choice inside a known shape · 🌳 **L**
  design plus a multi-part build or migration · 🏔️ **XL** sustained algorithmic
  or architectural work with substantial investigation and verification, even
  when the resulting diff is small. Owner, chat 2026-10-21.
- **Impact**, judged for each persona it affects: 🤍 **S** polish, internal
  quality or an option to explore · 💜 **M** noticeable friction or trust for
  that persona · 🩷 **L** protects their documents or access, or unblocks their
  main job. A ticket's impact is the highest of its persona impacts. Judge at
  least one; leave out personas it doesn't touch. Owner, chat 2026-10-19.

|        | 3 points | 2 points | 1 point | 0 points |
| ------ | -------- | -------- | ------- | -------- |
| Impact | 🩷 L     | 💜 M     | 🤍 S    | —        |
| Effort | 🌱 S     | 🌿 M     | 🌳 L    | 🏔️ XL    |

A ticket's own points run from 1 to 6. Its **score** is the higher of its own
points and one more than the score of any ticket that depends on it, applied up
the whole chain. A prerequisite therefore always outranks what waits on it, and
working highest-first never skips one. Owner, chat 2026-10-19. The score is
stored in the ticket's frontmatter; `npm run backlog:index` rewrites it and the
checker fails when it is stale. The index shows a raised score as `5 (own 3)`.

Sizes are estimates: when starting a ticket shows one is wrong, fix it in the
same PR. Size the expected reasoning and verification as well as implementation;
elapsed time and line count are evidence, not automatic size thresholds. XL makes
prolonged work visible in the index; it does not create an XL impact rating or
waive the split review, PR size limits, acceptance criteria or independent review.
Owner, chat 2026-10-21.

## Picking the next ticket

`readme.md` lists every open ticket by lifecycle phase first: **Before launch**
(`pre_launch`, the default), **Launch** (`launch`), then **After launch**
(`post_launch`). Complete the current phase before advancing; if it is blocked,
record the blocker rather than starting a later phase. SPN-038 is the launch
milestone; optional CSV import (SPN-093) and document-type/converter plugins
(SPN-094) follow it. Phase records this owner sequencing, without implying that
CSV or plugins technically need public HTTPS. Owner, chat 2026-10-21. The fixed
three-phase implementation and persona tradeoffs are recorded in
[decision #129](../implementation/backlog-workflow.md#legacy-decision-129-fixed-lifecycle-phases).

Within each phase, the highest score comes first, with
ties going to the ticket that unblocks another, then higher impact, then lower
effort, then lower ID. Each row shows the tie-break that put it ahead of the
next. Take the first ticket in the current phase that isn't waiting on an open
`depends_on`. Score calculation and dependency inheritance are unchanged. A
prerequisite must be in the same or an earlier phase; the checker rejects a
dependency on later-phase work. SPN-093/094 also name SPN-038 as an explicit
launch sequencing dependency. These are timing constraints, not technical
requirements for a converter or document-type plugin.

Tickets that need owner input still rank normally. Do all the preparation, ask
once for exactly that input, and work the next ticket while waiting.

**UI changes need the owner's eye.** A PR that changes what a screen looks like
includes light, dark and phone-width screenshots of every changed screen, and
merges only after the owner approves them in the PR. While it waits, start the
next eligible ticket. Owner, chat 2026-10-19.

## Working a ticket

1. Re-read the ticket and check it is still true against the code.
2. Branch from `main`. One ticket, one branch, one PR, one squashed commit.
3. Build it with its tests. Make decisions as they come up (below).
4. **Split when it grows.** Past ~10k changed lines, or ~3 days in progress, look
   for a split. 100k is the hard limit and CI fails past it. Lockfiles and
   generated files don't count; the list is in `backlog.json`. Land the coherent
   part and file the rest as new tickets that name this one. Effort-S tickets
   are exempt: their changes are low effort, such as scaffolding or generated
   code, so a large diff is still easy to review. CI reads the effort from the
   base branch's copy of the ticket.
5. **Independent review.** Have a subagent that did not implement the change
   inspect and verify it, using the original ticket, full diff and evidence,
   without a prior or hoped-for grade. Require **at least 95/100 and no unresolved
   blockers**, following the [rubric and repair/split rules](../run-backlog.md#3-get-an-independent-grade).
   Explicitly assess over-complexity within the rubric's 10 maintainability points,
   with actionable deductions for unnecessary abstractions, dependencies or
   speculative flexibility (owner, chat 2026-10-20,
   [#105](../implementation/backlog-workflow.md#legacy-decision-105-deduct-unnecessary-complexity)).
   Weigh scope overlap before changed-line limits: fix acceptance gaps here;
   ticket separable work without hiding a blocker. Re-review repairs, and put
   the score, reviewed SHA and every finding’s disposition in the PR.
6. **Prepare to land.** In the same PR:
   - Delete the ticket file.
   - Move its Rules and their reasons into the maintained docs under `docs/`,
     where the next reader will look. Add a short "why" comment to any test
     whose expected value is a product decision.
   - Remove its ID from dependent tickets' `depends_on`.
   - Append its ID to `grooming.completed_since` in `backlog.json`.
   - Run `npm run backlog:index`.
   - Title the PR `<ticket emoji> SPN-NNN <ticket title>`, the ticket's own
     heading.
7. **Merge when authorized.** With independent review complete, all required
   checks passing for the current head, an up-to-date base, and required owner
   input/verification resolved, squash-merge the verified SHA. Confirm the merge.
   During a [backlog run](../run-backlog.md), continue from current main to the next eligible
   ticket without another permission prompt. Outside a run, follow the owner's
   requested scope; do not infer a whole-backlog run from a single-ticket request.

New tickets must be present on main before their implementation PR can pass the
checker. Register follow-ups in the current ticket PR, or use a grooming PR if
there is no current ticket to land. Never bypass the base-ticket check.

## Decisions

Agents make routine decisions themselves. Weigh **every** persona, not only the
one the ticket is for, and preserve the rationale alongside implementation notes.

- **New decisions:** create or extend `docs/implementation/SPN-NNN.md`, following
  [the record convention](../implementation/README.md). Link its heading from the
  ticket's Rules. Record date/status, question, context, options, outcome/reason,
  all four persona effects, and the deciding person/source. No new decision issue
  is required. Owner, chat 2026-10-22.
- **Needs the owner:** record `needs-owner`, add the precise question to the ticket's
  `owner_input`, ask the owner, and keep working on independent work. The Markdown
  record does not grant approval. Update it and the Rules when the answer arrives.
- **Cross-ticket policy:** use one named record under `docs/implementation/` and
  link related tickets to it; do not duplicate competing decisions.
- **Legacy decisions:** use [SPN-096's inventory](../implementation/SPN-096.md) to
  find the canonical local entry, with original issue/comment provenance and
  status intact. Migrated active tickets link entries from Rules and use an empty
  `decisions` list. The CLI still accepts numeric issue lists from older branches
  and history; do not create issue numbers for local records or erase old sources.

Implementation records survive ticket deletion. Maintained product/design/process
docs still carry the resulting behavior and link to the rationale. An implementation
note or agent recommendation is never evidence of owner approval or a completed check.

## Grooming

After **7** landed tickets, show a nonblocking reminder for the next manual
grooming with the owner. The count never fails checks, blocks a ticket/merge or
forces an agent to groom. Keep recording completions past seven; the owner chooses
when to review. Owner, chat 2026-10-22. Grooming captures context learned while building.

Every backlog grooming includes a review of open Dependabot PRs for security,
compatibility, current CI results and sensible grouping. Record the disposition of
updates that need follow-up; review does not imply automatic merge. Existing PRs
remain open for that review. Owner, chat 2026-10-23;
[decision](../implementation/backlog-workflow.md#review-dependabot-prs-at-every-backlog-grooming).

A full owner-led grooming, recorded in a PR titled `🧹 Groom backlog …`:

- Rechecks every ticket against the code: still true, still needed, sized right.
- Captures context learned since the last grooming into the tickets it affects.
- Checks persona coverage: walks each persona's journey (Operator, Owner,
  Collaborator, Link guest), rechecks each ticket's persona impacts, and files
  tickets for what is missing.
- Turns answered decision records (including legacy issues) into Rules, and files tickets for gaps.
- Resets `grooming.completed_since` to `[]`, sets `grooming.last` to today, and
  regenerates the index.

A focused backlog maintenance PR can use the same title without claiming a full
grooming: preserve both the completion list and last-groomed date. Reset them only
when the manual review is complete. Grooming isn't a ticket and doesn't count
toward the reminder.

## Pull requests and `main`

- `main` is protected. Changes arrive by squash merge only, and the PR title
  becomes the commit message.
- Titles: `<ticket emoji> SPN-NNN <title>`. Two exceptions carry no ID:
  `🧹 Groom backlog …` and `⬆️ Bump …` for dependency updates.
- Only a grooming PR may change the settings in `backlog.json` or remove a
  ticket other than the one landing. The PR check reads its limits from the
  base branch, so a PR can't loosen its own.
- CI runs the PR's own copy of the checker. Review any change under
  `scripts/backlog/` or `.github/` as a change to the rules.
- The **Backlog**, **Pull request**, **Lint**, **Typecheck**, **Unit tests**,
  **Lib tests** and **Playwright smoke** CI jobs are required. Lib tests runs
  `lib/` on its own and passes at once when nothing it tests changed.
  Playwright smoke builds the app and checks development and production servers
  (SPN-001).

Documentation-only CI keeps Backlog, Pull request and Lint validation, while
Typecheck, Unit tests, Playwright smoke and Build Storybook report explicitly
that application validation is not applicable. Storybook still builds and deploys
on main pushes/manual runs so a docs push cannot displace a queued code deploy. The allowlist is Markdown under
`docs/`, root `README.md`, `AGENTS.md`, `THIRD-PARTY-NOTICES.md`, and exactly
`docs/todo/backlog.json` (which still gets backlog validation). Other JSON,
executable mockups, code, tests, dependencies, workflows and unknown paths run
the full suite. Classification uses the complete PR/push diff with both sides
of renames; uncertain ranges and manual runs use full validation. A failed or
cancelled classification never passes the browser gate. This is an applicability
check, not a waiver for failures. Owner, chat 2026-10-20,
[decision #121](../implementation/backlog-workflow.md#legacy-decision-121-documentation-only-ci-applicability).

Owner setup, once, in the repository settings:

1. General → Pull Requests: allow only squash merging; default commit message
   "Pull request title"; delete head branches automatically.
2. Rules → new branch ruleset for `main`: require a pull request, require the
   status checks **Backlog**, **Pull request**, **Lint**, **Typecheck**, **Unit tests**,
   **Lib tests** and **Playwright smoke**, require branches to be up to
   date before merging, block force pushes and deletions. Up to date matters:
   the checks compare against `main` as it was when they ran.
3. Legacy decision issues retain their labels; new decisions use implementation records, not new issue labels.

## Commands

CI may be the default for all checks, including typecheck, lint and backlog.
Draft pushes do not require local checks first. Keep unverified work draft and
retain every required CI, independent review and visual/merge gate. Local work
still follows the [memory watchdog](../run-backlog.md#2-implement-one-ticket).
Owner, chat 2026-10-23;
[decision](../implementation/backlog-workflow.md#ci-as-the-default-validation-environment).

```bash
npm run typecheck                          # type-check every .ts and .tsx file
npm test                                   # backlog and application unit tests
npm run backlog:check                      # validate tickets and the index
npm run backlog:index                      # regenerate readme.md
npm run backlog:new -- 🪞 "Restore a document"   # new ticket with the next ID
npm run backlog:pr -- --base origin/main --title "🪞 SPN-012 Restore a document"
```
