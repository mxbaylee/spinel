# 🧾 SPN-118 Preserve an edited destination when transition resume is refused

## Story

As the [Owner](../product/personas.md#owner), I want a refused transition resume to preserve edits made in the converted workspace, so that an old migration bundle cannot disturb newer work.

## Scenarios

### Refusing the same bundle preserves an edited destination

Given a converted destination that has since served real native edits,
When the same migration bundle is resumed into it,
Then verification refuses to claim it is the original output,
And the destination's newer content and metadata remain intact without overwrite or republication.

## Rules

- Investigate the [first-attempt digest failure](../implementation/ci-reliability-2026-10-28.md#runtime-and-destination-follow-ups), agent judgment 2026-10-28. The same-bundle refusal succeeded but byte preservation failed at `transition.test.ts:120`; this is not the separate wrong-dataset case, and changed bytes do not establish lost documents.
- Determine whether an outstanding writer, SQLite/WAL lifecycle/checkpoint or importer mutation changed the file. Retain before/after byte-level evidence and independently compare logical native content and metadata. The importer already opens completed destinations read-only; do not propose that alone as a fix.
- Preserve source provenance, interrupted/resumed transition fences, current saved edits, identities/grants and separate wrong-source rejection. Establish the cause before changing any preservation assertion; no retry-until-green or skipped failure.
- Choose the smallest demonstrated lifecycle or importer correction and add a regression for its actual cause. Record the pinned source/runtime and a bounded first-attempt verification plan.
- Owner and Collaborator document preservation justify L impact even though actual data loss is unproven. Operator gains deterministic recovery verification; Link guest has no new capability and existing scope/revocation remain protected.

## Out of scope

- Replacing SQLite, broad migration redesign, new restore features, or browser-fixture/performance routing changes.

## Verify

- Reproduce or otherwise establish the original digest change; preserve complete native content, metadata, source evidence and rejection behavior before/after the focused repair.
- Run the existing transition tests, retained-data acceptance and required final-SHA CI. Report every bounded attempt and distinguish a demonstrated fix from a case not reproduced.
