# 🩹 SPN-062 Keep the server, its images and dependencies patched

## Story

As the [Operator](../product/personas.md#operator), I want a short routine for patching the droplet, the pinned images and Spinel's dependencies, so that the server doesn't drift out of date before it is exposed publicly.

## Scenarios

### A monthly patch

Given the deployed droplet,
When I follow the patching section of docs/deployment.md,
Then I update the OS, Docker and Tailscale, refresh the Caddy and Node image digests, reboot, unlock the volume and confirm the app is healthy, in that order, with a rollback for each step.

### Dependency updates arrive on their own

Given a new release of an npm dependency, a pinned base image or a GitHub Action,
When the weekly check runs,
Then a `⬆️ Bump …` PR opens that the backlog checker accepts, and CI tests it like any other.

## Rules

- Today only the `SPINEL_IMAGE` update is documented (docs/deployment.md). Caddy and the Node base image are pinned by digest in `deploy/compose.yaml` and the Dockerfile, with no refresh procedure.
- Configure Dependabot (or Renovate) for npm, Docker and GitHub Actions. Group Univer packages so they move together, and keep the `⬆️ Bump` title (process.md).
- Respect the Artifactory/npm curation policy: a blocked or too-new version waits, and is never fetched from the public registry to bypass it.
- Say how often to patch and what to watch afterwards (backup status, SPN-032 when it lands).

## Out of scope

- Unattended automatic upgrades on the droplet. Public HTTPS hardening (SPN-038).

## Verify

- The Dependabot config validates, and one bump PR passes the backlog PR check.
- A dry run of the runbook on a disposable droplet, or a reviewer walk-through if none is available, recorded in the PR.
