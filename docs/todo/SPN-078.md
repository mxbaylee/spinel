# 🪐 SPN-078 Keep a Space's contents under one set of permissions

## Story

As the [Owner](../product/personas.md#owner), I want related Docs and Sheets to belong to one Space with one owner and one set of permissions, so that organizing or recovering the collection never separates its contents from their access rules.

## Scenarios

### One file and one access boundary

Given a Space in an existing folder contains nested Docs, Sheets and folders,
When an account receives View or Edit access, including through the outer folder,
Then every existing and future child has that effective role, no child can have its own grant or guest link, and exactly one Owner owns the Space and all its contents.

### Structure and identity survive recovery

Given a Space has ordered, nested content and trashed subtrees,
When it reloads or the whole Space moves, is trashed/restored, or is recovered from persisted data,
Then content, internal IDs, order, formula bindings and recovery metadata remain intact, without cycles or changed ownership.

## Rules

- Implement the durable Space/child model and inherited-access foundation described in [Spaces and file roles](../design/spaces.md). A Space is one file in existing folders; internal Docs and Sheets may themselves contain children, and folders only group children. Owner, 2026-10-20; #116.
- View cannot mutate; Edit manages internal content/tree. Outer sharing, rename/move/trash remain owner-controlled until SPN-079. Exactly one Owner inherits all file Admin powers; the server Operator receives no content access. Owner, 2026-10-20; #118.
- Reuse current access, collaboration, image, Formula and trash services. Every supported HTTP/socket/MCP/export boundary rechecks Space scope, including after async work, revocation/downgrade, trash and disabled-owner checks. Unimplemented Space/child routes and capabilities refuse access; this foundation exposes no incomplete product navigation or guest links. Original SPN-078 scope, split 2026-10-21.
- Persist subtree boundaries, original parent/location and deletion/recovery information; reveal locations only when readable. SPN-091 supplies account navigation/recovery and SPN-092 supplies guests and integration acceptance. Owner, 2026-10-21; #126.
- Refuse cycles and unsupported standalone-file moves into/out of a Space without retaining or inventing child grants. Preserve stable bindings for backup/owner-transfer integration in SPN-092; retain bounded Operator resource use and account-only identity isolation. Owner, 2026-10-20; #116–118.

## Out of scope

- Account UI (SPN-091), guest links/formula and other cross-feature integration (SPN-092), delegated Admin (SPN-079), replacing folders, child grants, standalone-file conversion/extraction, bulk Space offline downloads or a new export format.

## Verify

- Unit/API: inherited View/Edit, future children, sole ownership, owner-only outer operations, viewer refusal, cycles, unsupported conversions and unauthorized child/cross-Space routes.
- Persistence: ordered/nested reload, whole-Space move/trash/restore, internal subtree recovery and serialization retain IDs/content/formula bindings; supported requests/sockets recheck async revocation, downgrade, trash and disabled owners, while incomplete capabilities remain unavailable.
