# 🔔 SPN-163 Show which files still need to sync without asking for action

## Story

As the [Owner](../product/personas.md#owner), I want files with unsynced offline edits listed near the top with a plain indicator, so that I know nothing is required of me while they sync. [Collaborators](../product/personas.md#collaborator) see the same state for their own edits.

## Scenarios

### Pending files are visible and ask for nothing

Given a downloaded Doc has saved offline edits that have not been acknowledged,
When I am on the file list,
Then that file appears near the top with an indicator such as "Needs to sync", and any banner is informational with no action button.

### The indicator clears when delivery is acknowledged

Given that file is syncing after reconnect,
When the edit is acknowledged and durably cleaned up,
Then the indicator and any banner disappear without my opening the file.

## Rules

- Follow [sustainable testing](../testing.md); keep the Verify plan and progress evidence current. [Policy](../implementation/SPN-115.md#guidance-for-every-open-ticket-and-progress-checkpoint), owner 2026-11-01.

- Observed in the SPN-156 own-phone run, 2026-11-16 (owner): Pixel 10, Chrome 157.0.8103.78, installed app, build `ccc201ef` of [PR 289](https://github.com/mxbaylee/spinel/pull/289). With a saved offline edit, the file list showed the **Offline changes on this device** banner (`web/OfflineRecoveryEntry.tsx`) with a **Recover my doc** button, and **no per-row "Not synced yet" badge**. The button seemed to do nothing for a while and then opened the Doc. After reconnect the banner went away and the edit synced. An earlier run saw a popup that cleared before it could be read.
- Owner preference, chat 2026-11-16: pull docs that need to sync to the top of the list with an indicator, with an info banner and no action, "Needs to sync" style. Owner called the current banner a weird design.
- Keep the recovery entry for genuine recovery (retained work whose original is inaccessible, `docs/offline.md`). This ticket changes how ordinary pending work is shown, not what recovery does.
- Investigate why the per-row badge (`web/OfflineStatus.tsx`, **Not synced yet**) did not show in this flow, and why **Recover my doc** lagged.
- Lead: before going offline, nothing told the owner a document was not yet downloaded; the first attempt hit the unsaved-changes prompt (`web/App.tsx`). Consider a cue, and record the decision.
- UI work follows [docs/design/](../design/README.md): playbook first if a pattern is missing, a Storybook story for every new component or state, and `visual-review` with light, dark and phone captures.

## Out of scope

- Closed-app OS background sync. Changing replay, authority or checkpoint behavior.

- Fixture readiness/cleanup: the existing offline fixtures with a controllable acknowledgement.
- Environment and source/shared dependencies: `web/OfflineStatus.tsx`, `web/OfflineRecoveryEntry.tsx`, `web/Dashboard.tsx`, `web/offline/useOfflineDownloads.ts`.
- Evidence: light, dark and phone captures of the states, and a repeat own-phone observation.
