# 🧯 SPN-063 Regularly prove Spinel can recover from its backups

## Story

As the [Operator](../product/personas.md#operator), I want Spinel to check regularly that its configured backups recover a usable workspace, so that recovery has been tried recently and still works if the database or hosting changes.

## Scenarios

### Recover locally before deployment

Given a private filesystem backup destination and local recovery keys/configuration, without cloud credentials,
When the real scheduler creates a backup and the verifier retrieves it,
Then a fresh isolated target recovers the workspace through the same encrypted format and semantic checks used for offsite backups,
And status distinguishes local publication, verified recovery and unverified offsite protection.

### A weekly restore check

Given the configured database, asset and recovery-configuration backups,
When the weekly verification runs,
Then it restores the newest complete recovery point into an isolated disposable target, checks storage integrity and application invariants against the recovery inventory, and deletes the target,
And the admin backup status shows the result and when it ran.

### A broken backup is noticed

Given the newest recovery point is incomplete, unreadable or fails integrity,
When the check runs,
Then backup status shows the failure and the last good restore check, and the backup is kept for inspection.

### Rotating the key

Given the configured recovery method's credential and key-rotation steps in docs/backups.md,
When recovery credentials or a self-managed encryption key change,
Then new backups and verification keep working, retained backups stay recoverable until they expire, and status identifies the applicable recovery method/key without revealing secrets.

## Rules

- Retain SQLite with one application instance and **no database-engine adapter pattern**, following the owner's conditional direction and the [accepted capacity decision](../implementation/SPN-063.md#accepted-decision-keep-sqlite-without-database-adapters), 2026-10-27. The [capacity writeup](../implementation/SPN-063-capacity.md) distinguishes engine limits, current application safeguards and measurements still needed. This preparation keeps the ticket open; implement its verifier directly for the selected SQLite recovery path.

- The owner's later [backup-options proposal](../implementation/SPN-063.md#proposed-backup-options-and-assisted-restore) (2026-10-27) permits narrow destination adapters: manual encrypted download, configured S3-compatible automatic backup, separate diagnostics retention, and staged UI restore/maintenance. These are proposed coherent increments; this writeup neither ships them nor marks the weekly verifier complete.

- Migrated decision records: [Single SQLite runtime and consistent copies](../implementation/SPN-025.md#legacy-decision-68-single-sqlite-runtime-and-consistent-copies).

- Implement before deployment with a supported filesystem destination, shared recovery configuration and real local scheduling/restore tests, following the [accepted pre-deployment decision](../implementation/SPN-063.md#accepted-decision-implement-recovery-before-deployment) (owner follow-up and agent design, 2026-10-27). This supersedes launch-only implementation timing. SPN-038 retains selected-provider and actual target-host acceptance before public exposure; missing cloud/host access does not block local implementation.

- Follow the [filesystem publication, mount, status and local acceptance contract](../implementation/SPN-063-backup-options.md#filesystem-destination-and-local-acceptance). No fake cloud credentials, partial published artifacts, unsafe path cleanup or fallback to the host disk when the configured mount is absent. A same-host archive never alone satisfies independent offsite protection.

- Reuse the landed encrypted native-Space recovery acceptance in docs/backups.md: verify outer/internal tree, prior deletion batches, per-child native images/history/generations, grants and ownership handover invariants in the isolated restore. SPN-092/SPN-064 already supplied a one-time proof; this ticket makes it repeatable. Grooming, 2026-10-22.

- SPN-047 handoff: Backups & health presents last successful verification and current failure together. Follow [the composed design](../design/admin.md) and decision [#126](../implementation/SPN-047.md#legacy-decision-126-approved-redesign-and-its-limits) (2026-10-20); preserve current behavior and require [independent theme/persona screenshot review](../implementation/grooming-2026-10-26.md#agent-decisions-and-visual-review) on the PR.

- SQLite plus one encrypted archive format is selected, with supported filesystem storage and the existing Spaces destination sharing the recovery path. Reopen the backend decision only for a measured operating/recovery failure or a concrete multi-host/availability requirement; alternatives remain documented, without a database adapter framework. This narrows the earlier open comparison (owner chat, 2026-10-21). Provider redundancy or a successful backup status alone does not prove Spinel recovers; see [backup scope](../backups.md#recovery-requirements-and-hosting-options).
- Reuse `scripts/deploy/backup.ts` and scheduler leases while SQLite is selected. Current restore checks archive authentication, SQLite integrity/foreign keys and recovery metadata, not table counts or application invariants; add snapshot-bound inventory and semantic checks. Any replacement checks equivalent native integrity and application invariants covering accounts/grants, snapshots/history, images and required configuration. Build for the chosen backend, not a generic multi-provider framework.
- Bound memory, disk and runtime. The current archive guard requires 2.1 times logical database bytes plus 256 MiB of free staging space (docs/backups.md); verification/activation declare their additional limits. Skip with a visible reason rather than exhausting resources. Any cloud verification target has a bounded cost and cleanup plan before use.
- Never restore over the live dataset or send notifications from the restored target. Protect scratch data and credentials, remove temporary resources even after failure, and retain the source recovery point for inspection.
- Document compromise recovery and safe credential/key rotation for the configured method. Preserve old-key access for retained encrypted backups until expiry.
- Counts and status only; no document content in logs (admins can't see documents).

## Out of scope

- External alerting (SPN-032). Actual provider/target-host launch acceptance (SPN-038); the fresh-host procedure remains in docs/backups.md. Manual workspace UI actions, diagnostics expiry, maintenance/supervised activation and notices need separately registered implementation scopes; this ticket delivers the destination and recurring isolated verifier, not all proposed controls.

## Verify

- Unit/integration: real scheduled encrypted filesystem publication, retrieval and successful application recovery; destination path/mount/collision failures, leases/retry/retention holds, missing/truncated data, wrong/retained keys, integrity failure, low resources, process termination, restart reconciliation and scoped cleanup. Preserve Spaces transport regression coverage; follow the linked matrix without claiming unrun provider tests.
- Playwright: the admin status shows the last restore check and a failed one.
