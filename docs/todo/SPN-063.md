# 🧯 SPN-063 Regularly prove Spinel can recover from its backups

## Story

As the [Operator](../product/personas.md#operator), I want Spinel to check regularly that its configured backups recover a usable workspace, so that recovery has been tried recently and still works if the database or hosting changes.

## Scenarios

### A weekly restore check

Given the configured database, asset and recovery-configuration backups,
When the weekly verification runs,
Then it restores the newest complete recovery point into an isolated disposable target, checks storage integrity and application invariants against the recovery inventory, and deletes the target,
And the admin backup status shows the result and when it ran.

### A broken backup is noticed

Given the newest recovery point is incomplete, unreadable or fails integrity,
When the check runs,
Then backup status shows the failure and the last good restore check, and the backup is kept for inspection.

### Rotating the key

Given the configured recovery method's credential and key-rotation steps in docs/backups.md,
When recovery credentials or a self-managed encryption key change,
Then new backups and verification keep working, retained backups stay recoverable until they expire, and status identifies the applicable recovery method/key without revealing secrets.

## Rules

- Schedule this work during launch, after the deployment and database choices are concrete. There is no current deployment; do not build a pre-production verifier around a database that may be replaced. Preserve the recovery acceptance and implement for the selected backend ([owner chat, 2026-10-23](../implementation/grooming-dependency-registration-2026-10-23.md#align-work-with-the-undeployed-product)).

- Reuse the landed encrypted native-Space recovery acceptance in docs/backups.md: verify outer/internal tree, prior deletion batches, per-child native images/history/generations, grants and ownership handover invariants in the isolated restore. SPN-092/SPN-064 already supplied a one-time proof; this ticket makes it repeatable. Grooming, 2026-10-22.

- SPN-047 handoff: Backups & health presents last successful verification and current failure together. Follow [the composed design](../design/admin.md) and decision #126 (2026-10-20); preserve current behavior and owner screenshot approval.

- SQLite plus encrypted Spaces backups is today's implementation, not a permanent constraint. Reassess the single configured recovery method if the pre-production database changes; managed database backups/PITR may supply it. Provider redundancy or a successful backup status alone does not prove Spinel recovers. Owner, chat 2026-10-21; see [backup scope](../backups.md#recovery-requirements-and-hosting-options).
- Reuse `scripts/deploy/backup.ts` and scheduler leases while SQLite is selected. Its verification checks integrity and manifest counts; any replacement checks equivalent native integrity and application invariants covering accounts/grants, snapshots/history, images and required configuration. Build for the chosen backend, not a generic multi-provider framework.
- Bound memory, disk and runtime. The current SQLite path needs twice the database size plus 256 MiB (docs/backups.md); a replacement defines its own safe limits. Skip with a visible reason rather than exhausting resources. Any cloud verification target has a bounded cost and cleanup plan before use.
- Never restore over the live dataset or send notifications from the restored target. Protect scratch data and credentials, remove temporary resources even after failure, and retain the source recovery point for inspection.
- Document compromise recovery and safe credential/key rotation for the configured method. Preserve old-key access for retained encrypted backups until expiry.
- Counts and status only; no document content in logs (admins can't see documents).

## Out of scope

- External alerting (SPN-032). Restoring onto a fresh host, which docs/backups.md already covers.

## Verify

- Unit/integration: successful application recovery, missing/truncated data, wrong key/credentials where applicable, integrity failure, low resources, interrupted verification and cleanup.
- Playwright: the admin status shows the last restore check and a failed one.
