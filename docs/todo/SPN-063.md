# 🧯 SPN-063 Prove the latest backup restores, on a schedule

## Story

As the [Operator](../product/personas.md#operator), I want Spinel to check regularly that its newest offsite backup actually restores, and to rotate the backup key safely, so that recovery has been tried recently, not just once with synthetic data.

## Scenarios

### A weekly restore check

Given offsite backups in the private Space,
When the weekly verification runs,
Then it downloads the newest backup, decrypts it, restores it into a scratch file, checks SQLite integrity and table counts against that backup's manifest, deletes the scratch copy,
And the admin backup status shows the result and when it ran.

### A broken backup is noticed

Given the newest backup is truncated, can't be decrypted or fails integrity,
When the check runs,
Then backup status shows the failure and the last good restore check, and the backup is kept for inspection.

### Rotating the key

Given I follow the key-rotation steps in docs/backups.md,
When I install a new recovery key,
Then new backups use it, older backups stay restorable with the old key until they expire, and the status says which key each uses.

## Rules

- Extend `scripts/deploy/backup.ts` and the existing scheduler leases. Bound its memory and disk: staging needs twice the database size plus 256 MiB (docs/backups.md). Skip with a clear status rather than filling the volume.
- Never restore over the live database. The scratch file lives on the encrypted volume and is always removed, even after a failure.
- Record a compromise procedure: revoke the Spaces key, rotate the recovery key, and decide which backups to delete.
- Counts and status only; no document content in logs (admins can't see documents).

## Out of scope

- External alerting (SPN-032). Restoring onto a fresh host, which docs/backups.md already covers.

## Verify

- Unit: success, truncated object, wrong key, integrity failure, low disk and cleanup after a crash.
- Playwright: the admin status shows the last restore check and a failed one.
