# 🪲 SPN-174 Fix the phone Doc offline replay flake

## Story

As the [Owner](../product/personas.md#owner), I want a phone Doc edited offline to sync back into the original Doc when I reconnect, so that I never find a duplicate "offline copy" and CI stops failing at random.

## Scenarios

### Reconnect replays into the original

Given a downloaded phone Doc with an offline edit that survived two offline reloads,
When the phone reconnects from the file list and opens the Doc,
Then the edit replays once into the original, the save status reads "Synced", and no recovery copy is created.

### A real conflict still keeps the copy

Given the original Doc was changed, trashed or revoked while offline,
When the phone reconnects,
Then one recovery copy is created and the original is left unchanged.

## Rules

- Evidence, 2026-11-24: `e2e/offline-editing.spec.ts:696` "phone doc: durable edits survive two offline reloads and reconnect exactly once" (project `sync-production`) failed on the first attempt and on retry 1, then passed on retry 2. `failOnFlakyTests` turns that red. Runs: [main, SPN-155 merge 45463717032](https://github.com/mxbaylee/spinel/actions/runs/45463717032) and [PR 313 head 1ce49aaa, run 45528695543](https://github.com/mxbaylee/spinel/actions/runs/45528695543). PR 313 changes nothing under `web/` or `e2e/`. Artifacts expire after 7 days.
- Both runs show the same trace: "Loading document…", then "Changes not saved yet — keep this tab open.", then "Your offline changes were saved as Offline doc (offline copy, …). The original was not changed." The failing assertion is `synced(page)` after the Doc is opened from the file list (`offline-editing.spec.ts:821`).
- First decide whether this is a product bug or a fixture race. A real replay that wrongly takes the recovery path is a product bug, because the Owner gets a duplicate Doc. Record the answer in `docs/implementation/SPN-174.md` before changing code.
- Unverified hypothesis: it is related to SPN-155's connection-opening change (merged as `d78973e2`). Nothing here proves SPN-155 caused it.
- Do not weaken the test: no longer timeout, no dropped assertion, no raised retries, no `failOnFlakyTests` change. Owner, chat 2026-11-24.
- Follow [sustainable testing](../testing.md); keep the Verify plan and progress evidence current. [Policy](../implementation/SPN-115.md#guidance-for-every-open-ticket-and-progress-checkpoint), owner 2026-11-01.
