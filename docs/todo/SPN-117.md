# 🔧 SPN-117 Keep the development server alive on the pinned Node runtime

## Story

As the [Operator](../product/personas.md#operator), I want the pinned runtime to serve development assets without aborting, so that browser validation produces trustworthy results.

## Scenarios

### Serving a large development response does not terminate Node

Given the supported pinned Node/Vite environment and the affected browser workload,
When the server sends development assets,
Then it completes the requests without the recorded fatal V8 abort,
And an unexpected server exit remains an immediate, diagnosable failure.

## Rules

- Follow the [runtime failure evidence](../implementation/ci-reliability-2026-10-28.md#runtime-and-destination-follow-ups), agent judgment 2026-10-28. Main still pins Node 26.12.1; the failed run's Buffer.byteLength/HTTP/Vite stack and later connection refusals do not establish a production crash or a Sheet defect.
- Isolate the trigger sufficiently to distinguish Node/V8 behavior from the Vite/application response path. Choose a supported runtime update or narrow mitigation using primary upstream evidence and a reproducible comparison.
- Keep repository, CI and container runtime expectations consistent. Preserve original fatal diagnostics, source/platform versions and every attempt; a green rerun alone does not establish a remedy.
- Do not delete the development journey, disable first-attempt failure detection, or retry navigation against a dead process. SPN-120 owns the remaining shared fixture diagnostics after SPN-116's [scope split](../implementation/SPN-116.md#scope-split), not the runtime repair.
- Operator gains reliable maintenance validation; the other personas retain existing behavior and content/access protections. Current evidence supports M impact rather than a claimed production availability incident.

## Out of scope

- Broad dependency upgrades, wholesale removal of development coverage, or an unverified production incident claim.

## Verify

- A focused reproducer/comparison and the affected development workload, with a predeclared bounded repetition budget and retained first attempts.
- Normal production/container behavior and all required final-SHA checks after any runtime change; actual fatal exits still fail clearly.
