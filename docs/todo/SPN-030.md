# 💾 SPN-030 Back up offsite and prove a restore works

## Story

As the [Operator](../product/personas.md#operator), I want encrypted backups sent offsite every day, and a restore I have actually tried, so that losing the droplet doesn't lose anyone's documents.

## Scenarios

### Daily backup

Given a running instance,
When the nightly job runs,
Then a consistent copy of the database and uploaded files is encrypted and sent to offsite storage (DigitalOcean Spaces or S3, PRD §9),
And old backups are kept on a schedule (7 daily, 4 weekly, 6 monthly).

### Restoring

Given only the backup and its key,
When I follow the restore guide on a new droplet,
Then Spinel comes up with every document and history intact.

### Failure is loud

Given a backup fails,
When I next open the admin panel,
Then I see the failure and when the last good backup was.

## Rules

- Restore accounts/passkeys, native snapshots, image blobs, history and required configuration into encrypted storage. The stopped local archive in docs/deployment.md was only listed, not restore-tested or sent offsite. Decided 2026-10-17 in #23.
- Marked must-ship in grooming, 2026-10-17, ahead of the PRD's post-production list: the Owner relies on Spinel daily and the droplet is a single point of failure.
- Use SQLite's online backup API, never a raw file copy of a live database.
- The backup and restore commands are TypeScript (`.ts`), never `.js` or `.mjs`. Owner, chat 2026-10-17.

## Verify

- An automated test that backs up and restores into a temporary directory and compares.
- The owner's restore drill, noted in the PR.
