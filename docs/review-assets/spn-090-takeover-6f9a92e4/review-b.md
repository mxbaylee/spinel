## 🐛 B1 — same-title late storage answer can update the wrong result (P2, blocking)

Locations: `web/offline/protection.ts:25`, `web/offline/useOfflineDownloads.ts:418–423`, and `src/ui/offlineProtection.test.ts:19`.

`answeredMessage` identifies the pending result using its text and the generic deciding detail. The caller checks `scope.isCurrent()`, but `offlinePreparation` (`web/offline/offlineStore.ts:859`) fences account epoch, cancellation token and mounted lifetime, not individual toggle operations. The download completes and `toggle` clears busy while `persist()` is still unresolved. A later same-account download can therefore create a distinct pending result with identical text.

Concrete sequence: download a document named “Trip journal” while its storage request A remains pending; dismiss the result; download another document with the same name (or remove and prepare the original again), yielding pending request B and the same result text. A then resolves denied/error. Its callback accepts B's text/detail and replaces B's deciding message. When B later resolves granted, its callback refuses to update because A already changed that detail. The newer result remains attributed to the wrong request. Neither dismissing the first result nor the account-lifetime guard prevents this sequence. This is incorrect storage-protection guidance; no document corruption is asserted.

The current newer-message test changes the title to “Field notes,” so it misses the collision. Fix by binding the late answer to the exact displayed result instance or a per-operation identity, preserving account/mount and dismissal fences. Add an identical-text newer-result negative, its own-result positive, and an out-of-order-answer check proving B's result is not consumed by A. The helper's documented “newer message stays exactly as it is” contract should hold independently of names.
